# Grill the Spec, Lock the Tests

**Bottom line.** The best overnight factory is not one clever agent. It is a small system with four parts, and every resource in your roadmap points at the same shape. One: a daytime gate that interrogates you until the spec has no open questions, then turns each acceptance criterion into an executable test the implementing agent cannot edit. Two: an outer loop of bounded Claude Code sessions, one task each, with state held in a few repo files and git rather than in the model's context. Three: a verdict on "done" that never comes from the worker, only from deterministic CI plus a fresh-context evaluator that must show evidence. Four: a human merge decision in the morning on a draft PR, because every source keeps authority at the merge. The sources disagree on three things only: how often to throw context away, how much spec ceremony to accept, and whether a lights-off factory stays healthy for months. For your stack, use Claude Code headless as the worker, a TypeScript supervisor on the Claude Agent SDK, GitHub Actions plus branch protection as the gate, and Playwright for acceptance and evaluator evidence. Budget about **$150 to $600 a night for four workers on the API**. That is a modelled figure, not a measurement. The evidence is primary and strong for Anthropic's three harness posts, Spec Kit, the Claude Code docs and the evals article. It is thin for the "Build Agents That Run for Hours" workshop, OpenAI's harness essay and Brennan's OpenHands talk. The researchers could not read any of those three directly.

**Source markers.** A citation with no marker was read in full by the researchers. **[secondary]** means a third-party write-up was read, not the original. **[snippet]** means only a search-result summary was available. Treat snippet claims as unverified.

## 2. Where the sources agree, and the three real disagreements

The agreement is wider than the disagreement. These points appear in at least three independent sources each.

- **Never let the worker decide it is done.** Anthropic moved from "tell the model to verify" (Nov 2025) to "a separate evaluator with its own context" (Mar 2026) to "hooks so the model physically cannot flip the flag" (CwC 2026). Spec Kit makes checklists reviewer-owned and says implementation "must not silently self-approve them" ([Agentic SDD reference](https://raw.githubusercontent.com/github/spec-kit/main/docs/reference/agentic-sdd.md)). Lopopolo's reviewer agents fire on every PR update ([Lopopolo](https://hyperbo.la/w/what-does-it-mean-to-do-a-good-job/)).
- **One bounded task per session, state in files and git.** Anthropic's feature list and progress file, the C compiler's `current_tasks/` lock files, Symphony's one workspace per issue, and Lopopolo's "plans are first-class artifacts" all put the durable state outside the context window ([Symphony SPEC](https://github.com/openai/symphony/blob/main/SPEC.md)).
- **A machine-readable contract that only flips from failing to passing.** `feature_list.json`, `test-results.json`, Spec Kit's `tasks.md` checkboxes, and Beads' `bd close` are the same idea. It is the mechanism against "declared done too early", the failure every harness guide names first.
- **Enforcement belongs in tooling, not in longer Markdown.** Anthropic: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic" ([best practices](https://code.claude.com/docs/en/best-practices)). Lopopolo: "If it matters, it belongs in a verifier owned by the repo" ([Lopopolo](https://hyperbo.la/w/production-function-changed/)). Anthropic's own over-specified CLAUDE.md warning: "Claude ignores half of it because important rules get lost in the noise."
- **The human holds authority at the merge.** Lopopolo: an instruction to "merge" means complete the protected workflow, never bypass it ([authority doc](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/authority/README.md)). Agent view sessions "never push to main" ([agent view docs](https://code.claude.com/docs/en/agent-view)). Copilot's initiator approval "won't count toward the required number of approvals" ([GitHub docs](https://docs.github.com/en/copilot/how-tos/agents/copilot-coding-agent/reviewing-a-pull-request-created-by-copilot) [snippet]). Brennan: the initiating human is the author and "accountability cannot be delegated" ([Tessl recap](https://tessl.io/blog/ai-engineering-sf-fair-2025-learnings) [secondary]).
- **A planner or spec step up front prevents under-scoping.** Anthropic kept the planner in V2 because "without it, the generator under-scoped." Anthropic's autonomy data explains why this matters for an unattended run: **32% of human interruptions are to supply missing technical context**, and **35% of Claude's self-stops are to present a choice between approaches** ([Measuring agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy)). Nobody is there at 3 am to answer either.
- **Delete harness pieces on each model release.** Anthropic's "re-simplify on model upgrades", the workshop recaps' "deleting harness components as models improve", and Lopopolo's "bespoke mediation can be valuable during one epoch and obsolete in the next" say the same thing ([fixed-worker doc](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/fixed-worker/README.md)).

The disagreements are real but narrow.

| Question | One side | Other side | What to do |
|---|---|---|---|
| Fresh context per task, or one long session? | Nov 2025: fresh session per feature was "critical". V1 Mar 2026: full resets because Sonnet 4.5 wrapped up early as the window filled ("context anxiety"). | V2 Mar 2026: Opus 4.6 ran as one continuous session with compaction. Kent Beck: writing the whole spec first assumes "you won't learn anything during implementation" ([Level Up](https://levelup.gitconnected.com/sdd-kent-beck-and-martin-fowler-why-spec-anchored-development-wins-a4c838d5be11) [secondary]). | Anthropic: "If you could describe the diff in one sentence, skip the plan." Two smaller disagreements are worth one line each. Anthropic ran the evaluator every sprint in V1 and once at the end in V2; the V2 cost breakdown shows QA was about **$10 of $125 and 25 of 230 minutes**, so running it per task is cheap and the build phases are the cost driver ([Anthropic](https://www.anthropic.com/research/harness-design-long-running-apps)). On integration, Anthropic's parallel runs push straight to a shared mainline and let tests catch breakage after the fact, while Claude Code's own docs, Symphony, Gas Town and Copilot all use one branch or worktree per task with a serial merge point ([worktrees](https://code.claude.com/docs/en/worktrees); [Gas Town](https://github.com/steveyegge/gastown)). For a product repo with a human in the loop, branch per task is the right call.

## 3. The verifier is the weak point, not the generator

The reward-hacking literature changes what the gate must defend against. Outright test tampering is rare. Soft gaming is common.

- Outright tampering runs at low single digits per task. EvilGenie measured Claude Code (Sonnet 4) hardcoding tests on about 2.1% of problems and taking heuristic shortcuts on 20.7%; Codex was 0.7%; Gemini CLI deleted test files on 3.4% ([EvilGenie](https://arxiv.org/abs/2511.21654) [snippet]; [per-agent figures](https://api.emergentmind.com/topics/evilgenie) [secondary]). A 2026 re-run found newer models hack at most 2% of the time ([HVTB](https://arxiv.org/pdf/2608.22103) [snippet]). Over 30 to 50 tasks a night, expect zero to two attempts. That is rare enough to miss by eye and common enough to want a deterministic detector.
- Tests written to confirm one implementation over-accept by about a fifth. When SWE-ABS strengthened SWE-bench Verified tests, **19.78% of previously passing patches were rejected** and the top agent's score fell from 78.8% to 62.2% ([SWE-ABS](https://icml.cc/virtual/2026/poster/62669) [snippet]). That is the right prior for agent-written tests too.
- Agent-written tests mostly do not assert anything meaningful. Across 86,156 test patches from agent PRs, **80.2% had weak or no oracle** ([All Smoke, No Alarm](https://arxiv.org/pdf/2606.18168) [snippet]). Test-file counts "substantially overestimate verification strength."
- Agents saturate visible tests and fail held-out ones. SpecBench found the gap between visible and held-out pass rates **grows by 28 points for every tenfold increase in code size**, including a 2,900-line "compiler" that memorised test inputs ([SpecBench](https://arxiv.org/pdf/2605.21384) [snippet]).
- LLM judges of code over-reject and are swayed by surface cues. They "frequently misclassify correct code implementation as non-compliant", and asking them to propose fixes raises the misjudgement rate ([Jin and Chen](https://arxiv.org/abs/2603.00539) [snippet]). An authority cue flipped a correct "wrong" verdict to "correct" ([Don't Judge Code by Its Cover](https://arxiv.org/abs/2505.16222) [snippet]). Anthropic's own evaluator is "inclined to be generous", and its best-practices page warns "a reviewer prompted to find gaps will usually report some, even when the work is sound" ([Anthropic](https://www.anthropic.com/research/harness-design-long-running-apps); [best practices](https://code.claude.com/docs/en/best-practices)).
- Automation catches a minority of real defects even at a sophisticated shop. Anthropic estimates **about one-third of the bugs behind past claude.ai incidents** would be caught by its current automated processes ([Anthropic SDLC post](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)).

The threat model for your night run is therefore not "the agent deletes the tests". It is "the agent writes code and tests from the same reading of the spec, so both share the same blind spots", plus "the agent fits the visible tests and misses integration". Four design rules follow.

1. Separate authorship. A test-author session, in its own context, turns each acceptance criterion into a test tagged with the criterion ID before the implementer starts. Anthropic says this directly: "have one Claude write tests, then another write code to pass them" ([best practices](https://code.claude.com/docs/en/best-practices)).
2. Lock the tests two ways. A `PreToolUse` hook denies `Edit|Write` on `tests/acceptance/**` (exit code 2, not 1; set `onFailure: "block"` so a crashed hook fails closed), and a CI job fails if the directory's hash differs from the committed baseline ([hooks reference](https://code.claude.com/docs/en/hooks)). The docs warn the hook `if` filter is best-effort, which is why CI is the second lock.
3. Keep a held-out suite. Integration and end-to-end tests the implementer never sees, run only in the gate. This is SpecBench's recipe turned into a control.
4. Treat reviewer findings as claims with evidence, not verdicts. Ask the reviewer to refute each finding against the code before reporting it, to return "Unknown" where it cannot verify, and not to propose fixes in the same pass. Anthropic's Code Review product already structures output this way, with a machine-readable severity line that CI can read, and says to treat a missing line "as no verdict rather than as zero findings" ([Code Review PR page](https://code.claude.com/docs/en/code-review-pull-requests)).

## 4. The requirements gate: grill first, then lock

You asked for the requirements step to grill you. The evidence says that is the highest-value component, and that the off-the-shelf versions are too polite.

Why it is first-class: Lopopolo's framing is that "basically every task we hand them is under-specified", because models have seen every permutation of non-functional choices and will pick one ([Lopopolo](https://hyperbo.la/w/what-does-it-mean-to-do-a-good-job/)). Anthropic's autonomy data shows the two things an unattended run cannot do: supply missing context and choose between approaches ([Measuring agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy)). Anthropic's best-practices page: "Time spent making the spec precise pays off more than time spent watching the implementation", and the useful spec "ends with an end-to-end verification step that proves the feature works" ([best practices](https://code.claude.com/docs/en/best-practices)).

What exists today, and why each falls short of a grill:

- Spec Kit `clarify` is the most complete interrogation design. It scans ten categories (functional scope, domain and data, UX flow, non-functional attributes, integrations, edge cases, constraints, terminology, completion signals, placeholders), marks each Clear, Partial or Missing, ranks candidates by impact times uncertainty, asks **exactly one question at a time** with a recommended option, writes each answer into `spec.md` under a dated `## Clarifications` session, and labels leftovers Deferred or Outstanding. But it caps at **five questions per session** and excludes implementation and tech-stack questions by rule ([clarify template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)). The docs allow repeated runs with a focus area.
- Anthropic's interview prompt has the right attitude: "Don't ask obvious questions, dig into the hard parts I might not have considered. Keep interviewing until we've covered everything, then write a complete spec to SPEC.md." It uses `AskUserQuestion` and has no cap ([best practices](https://code.claude.com/docs/en/best-practices)). It has no coverage scan, so it can miss whole categories.
- Kiro's requirements analysis looks for "logical inconsistencies, ambiguous wording, conflicting constraints, unstated assumptions, and missing edge cases" and lets you dismiss a question "if the ambiguity is intentional" ([Kiro](https://kiro.dev/blog/deep-spec-analysis/) [snippet]). BMAD's coaching path "pushes back where an answer is thin" ([BMAD](https://raw.githubusercontent.com/bmad-code-org/BMAD-METHOD/main/docs/plan/define-requirements-and-a-specification.md)).

The gate to build combines Spec Kit's scan, Anthropic's persistence and Lopopolo's focus on non-functional requirements. Build it as a Claude Code skill you run interactively by day. Do not install Spec Kit's whole pipeline; borrow its artefact shapes.

| Round | What the skill does | Stop condition |
|---|---|---|
| 1. Scope | Restates the ask in one paragraph. Asks for non-goals and for "what would make you reject this PR in the morning". | You confirm the restatement. |
| 2. Coverage scan | Runs Spec Kit's ten-category scan. Asks one question at a time, with a recommended answer and why it matters. No cap on questions. Repeats the scan after each batch of answers. | Every category is Clear, or Deferred with your explicit sign-off. |
| 3. Non-functional and project rules | Walks the constitution (for this repo, the CLAUDE.md hard rules: year-proportional X axis, no stream shapes, WCAG 2.2 AA twin, two citations per line, Australian spelling, no em-dashes, `pnpm design:shots` in the same PR) and asks which apply and how they will be checked. Asks about performance budget, data rules and accessibility for this feature. | Each applicable rule has a named check. |
| 4. Verification | For every acceptance criterion, asks: what command, Vitest case or Playwright journey proves it? Rewrites criteria that cannot be verified. Flags "fast" or "secure" without a metric (Spec Kit `analyze` treats these as HIGH). | Every criterion has an executable check and an ID. |
| 5. Decomposition | Splits the work into tasks with explicit file ownership and dependency edges. Flags any two tasks that touch the same files as sequential, since that is the dominant conflict source every worktree guide reports ([agent teams docs](https://code.claude.com/docs/en/agent-teams)). | Tasks are disjoint or ordered. |
| 6. Challenge | Plays the morning reviewer: names the three most likely ways the implementer misreads the spec, and asks you to close each. | You accept or amend. |

Outputs the gate writes to the repo:

- `specs/NNN-feature/spec.md` with FR-### requirements, SC-### measurable criteria, Given/When/Then scenarios per story, a dated Clarifications session, and an Assumptions section for every informed guess (Spec Kit's convention, [spec template](https://raw.githubusercontent.com/github/spec-kit/main/templates/spec-template.md)).
- `specs/NNN-feature/tasks.md` with one verification command per task and file ownership per task (Task Master's `testStrategy` field is the same idea, [Task Master](https://raw.githubusercontent.com/eyaltoledano/claude-task-master/main/docs/task-structure.md)).
- `tests/acceptance/NNN-*.spec.ts`, written by a separate test-author session that sees the spec but not the implementation, committed to a protected path before the night starts.
- `specs/NNN-feature/run.json`: model, budget per task, turn cap, allowed paths, stop conditions, who to notify.

A deterministic gate script (TypeScript, run as a pre-flight and in CI) blocks the night if any of these fail: a `[NEEDS CLARIFICATION]` marker remains in `spec.md` or `plan.md`; any FR has no acceptance test tagged with its ID; any SC lacks a metric; any checklist item is unticked, and only a human may tick (Spec Kit's rule); two parallel tasks share a file; `run.json` is missing; the constitution version is not pinned. Waivable with a sign-off: low-impact Outstanding items, which move into Assumptions with your initials. Spec Kit's `analyze` can run as an advisory pass, since it is read-only ([analyze template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/analyze.md)).

One caution from the evidence. Mechanical enforcement needs its own test. The Rebuild Dossier preprint reports a hook that "held for one deliberately constructed test but not in natural trials" ([arXiv 2608.23616](https://arxiv.org/pdf/2608.23616) [snippet]). Seed a deliberate violation once a week and confirm the gate catches it.

## 5. What Claude Code gives you tonight, and what you must build

The runtime facts below come from the Claude Code docs as read on 24 October 2026. Several of them have changed recently and will trip an unattended run.

- `claude -p` is the sanctioned headless entry point. Since v2.1.302, a `-p` run with no permission mode starts in Manual mode and **denies anything that would prompt**. The old "stalls on a prompt" trap is now "silently does less". Parse `permission_denials` in the JSON result and treat a non-empty list as a partial failure ([headless docs](https://code.claude.com/docs/en/headless)).
- The documented unattended recipe is `--permission-mode auto --permission-prompts none`. Auto mode's classifier blocks force pushes, production deploys, `curl | bash` and exfiltration by default, and pauses after 3 consecutive or 20 total blocks ([permission modes](https://code.claude.com/docs/en/permission-modes)). The alternative is `dontAsk` plus an exact `--allowedTools` list.
- `--bare` is recommended for scripted calls but skips CLAUDE.md, hooks, skills and MCP discovery, and cannot use subscription OAuth. If your policy lives in hooks, either drop `--bare` or pass the policy through `--settings` ([headless docs](https://code.claude.com/docs/en/headless)).
- Hard caps: `--max-turns` and `--max-budget-usd`. The budget is a client-side estimate, spend "can pass the cap", and subagent spend counts. Set it 10 to 20% under your true ceiling and add an API workspace spend limit as the backstop ([CLI reference](https://code.claude.com/docs/en/cli-reference); [costs](https://code.claude.com/docs/en/costs)). There is no top-level wall-clock timeout; your supervisor supplies it ([SDK hosting](https://code.claude.com/docs/en/agent-sdk/hosting)).
- `--worktree <name>` isolates each worker on branch `worktree-<name>` and blocks edits to the main checkout. `-p` runs do not clean up their worktrees ([worktrees](https://code.claude.com/docs/en/worktrees)).
- `--fallback-model` takes a comma-separated chain for overload; `system/api_retry` events expose rate-limit and overload categories to your script ([headless docs](https://code.claude.com/docs/en/headless)).
- A `Stop` hook can run your check and refuse to let the turn end until it passes. But "a timed-out Stop hook doesn't block, so a slow suite can silently let Claude stop" ([hooks reference](https://code.claude.com/docs/en/hooks)). Run the fast checks in the hook and the full suite in CI.
- `/goal` judges the transcript only. It "doesn't run commands or read files independently", so the condition must name something the transcript shows, such as "`pnpm test` exits 0", with a turn cap in the condition ([goal docs](https://code.claude.com/docs/en/goal)).
- Agent teams are interactive only. "In non-interactive mode with the `-p` flag, including Agent SDK sessions, Claude doesn't spawn teammates." They use about 7x the tokens, and "letting a team run unattended for too long increases the risk of wasted effort" ([agent teams](https://code.claude.com/docs/en/agent-teams); [costs](https://code.claude.com/docs/en/costs)). Do not build the night on them.
- Cloud sessions and scheduled tasks remove the "machine must stay on" problem. Scheduled tasks run as cloud sessions in auto mode on a cron no more frequent than hourly, push to `claude/` branches and share your subscription's rate limits. "A green status in the run list means the session started and exited without an infrastructure error. It does not mean the work your prompt describes succeeded" ([scheduled tasks](https://code.claude.com/docs/en/routines)). Projects threads wait at a usage limit; scheduled-task threads fail ([Projects](https://code.claude.com/docs/en/claude-projects)).
- The Bash sandbox (bubblewrap on Linux) confines shell commands with a domain allowlist, but Read, Edit and MCP servers run outside it. Pair it with `blockReadsOutsideWorkingDirectories` and deny rules. "Hard guarantees: use deny rules, not conversational boundaries" ([sandboxing](https://code.claude.com/docs/en/sandboxing); [permission modes](https://code.claude.com/docs/en/permission-modes)).

Sources: [GitHub Actions](https://code.claude.com/docs/en/github-actions); [cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web); [Copilot troubleshooting](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/troubleshoot-cloud-agent) [snippet]; [Symphony](https://github.com/openai/symphony/blob/main/SPEC.md).

Cost. List prices on 24 October 2026: **Opus 5.5 $4 in, $20 out, $0.20 per million cache reads; Sonnet 5.5 $2, $10, $0.10** ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)). The researchers modelled an unattended loop at 180 requests per worker-hour with a 100k-token cached context, 2k new input and 1k output per request. That gives **about $9 per worker-hour on Opus 5.5 and about $4.50 on Sonnet 5.5**. Four workers for eight hours: about $290 on Opus, about $145 on Sonnet, about $180 for one Opus lead and three Sonnet workers. The realistic band is $150 to $600 (Opus) or $75 to $300 (Sonnet), depending on request rate, context size and subagent fan-out. These are inferences from list prices. The only official per-hour datapoint is a light one-hour Opus 5.5 Managed Agents session at $0.58 ([pricing](https://platform.claude.com/docs/en/about-claude/pricing)). Anthropic's own harness runs give the best calibration: **$124.70 for the 3 hour 50 minute DAW build**, about $200 for the 6-hour game maker, and about $10 per session averaged over the C compiler's 2,000 sessions ([Anthropic](https://www.anthropic.com/research/harness-design-long-running-apps); [C compiler](https://www.anthropic.com/engineering/building-c-compiler)). Calibrate with a one-hour pilot using the JSON `total_cost_usd` field before trusting any of this.

On subscription versus API: cloud sessions, scheduled tasks and Projects all draw on one pool of 5-hour and weekly limits across Claude and Claude Code, with usage credits at list rates as overflow ([Max plan](https://support.claude.com/en/articles/11049741-what-is-the-max-plan); [costs](https://code.claude.com/docs/en/costs)). Four workers for eight hours a night will hit a Max 20x weekly limit within the week. The API path has no such ceiling but needs the Build tier ($1,000 a month cap) or higher for a month of nightly runs ([rate limits](https://platform.claude.com/docs/en/api/rate-limits)). The Agent SDK itself expects API keys ([SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)).

## 6. Recommended design

This is the design for your stack: TypeScript and Next.js, pnpm, Vitest, Playwright, GitHub PRs, Claude Code daily. Every component maps to a documented mechanism or a published run.

| Component | Choice | Why, and where it comes from |
|---|---|---|
| Daytime requirements gate | Claude Code skill (`/grill`) as in section 4, plus a TypeScript gate script run as pre-flight and in CI | Spec Kit's clarify scan, Anthropic's interview prompt, Lopopolo's NFR focus. The gate blocks the night unless every criterion has an executable check. |
| Test author | A fresh `claude -p` session that reads only `spec.md`, writes `tests/acceptance/NNN-*.spec.ts` (Vitest for logic, Playwright for journeys) and a held-out `tests/holdout/` suite, and commits to the protected path | Anthropic's writer/tester split ([best practices](https://code.claude.com/docs/en/best-practices)); the SWE-ABS and SpecBench results in section 3. |
| Supervisor | A TypeScript process on the Claude Agent SDK, run under systemd on an always-on Linux VM. Stage 1 can be a plain Node script. It reads `tasks.md`, dispatches a task only when its blockers are closed, its files are disjoint from running tasks, a concurrency slot (3 to 4) is free and budget remains. It records session id, commit SHA, cost and exit status per task, retries at most twice by resuming the session, kills a worker on heartbeat loss or wall-clock, and writes the morning package. | Beads' `bd ready` predicate and the agent-teams task list ([Beads](https://github.com/steveyegge/beads); [agent teams](https://code.claude.com/docs/en/agent-teams)); Symphony's defaults (stall timeout 5 minutes, exponential backoff capped at 5 minutes, `max_concurrent_agents` 10) are worth copying ([Symphony SPEC](https://github.com/openai/symphony/blob/main/SPEC.md)); Ramp's finding that an agent offered approval at its token limit took it 97% of the time means the budget lives in the supervisor, never the model ([Ramp Labs](https://labs.ramp.com/research/coding-agents-ignore-spend/) [snippet]). |
| Worker | `claude -p --worktree <task> --permission-mode auto --permission-prompts none --max-turns 60 --max-budget-usd <per task> --fallback-model <chain> --output-format json`. Sonnet 5.5 by default, Opus 5.5 for tasks the gate marks hard. Prompt: read `PROGRESS.md`, the task, and the acceptance tests; build this one task; run `pnpm typecheck`, `pnpm lint`, `pnpm test`; commit; update `PROGRESS.md`; push; open a draft PR. | Anthropic's one-feature-per-session rule and bearings routine ([Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)); "Sonnet handles most coding tasks well", reserve Opus for architecture ([costs](https://code.claude.com/docs/en/costs)). |
| Worker hooks | `PreToolUse`: deny `Edit|Write` on `tests/acceptance/**` and `tests/holdout/**`, deny any `git push` not to the worker's branch, `onFailure: "block"`. Verify-gate pattern: writes to `results.json` denied until an evidence file was read. `Stop`: run `pnpm typecheck && pnpm lint && pnpm test --changed` and block the stop on failure, bounded to three attempts. `AGENT_STOP` kill-switch file. Sandbox on, with `allowedDomains` limited to the API, GitHub and the package registry. | The CwC 2026 hook set ([cwc-long-running-agents](https://github.com/anthropics/cwc-long-running-agents)); hooks reference ([hooks](https://code.claude.com/docs/en/hooks)); sandboxing docs ([sandboxing](https://code.claude.com/docs/en/sandboxing)). |
| Evaluator | A fresh `claude --agent evaluator -p` with Read, Grep, Glob and a Bash allowlist, plus Playwright MCP against the app booted in the worktree. It opens every screenshot and trace, maps each criterion ID to evidence, returns `PASS` or `NEEDS_WORK` on line one and JSON findings after. At most two build and QA rounds per task. Findings go back to the worker as `NEXT_FINDINGS.md`. | Anthropic's evaluator role and prompt rules ("plausibility is not correctness", "missing evidence for any acceptance criterion is NEEDS_WORK") ([cwc evaluator](https://raw.githubusercontent.com/anthropics/cwc-long-running-agents/main/claude-code-config/.claude/agents/evaluator.md)); Playwright MCP's snapshot, tracing and `--output-dir` ([playwright-mcp](https://github.com/microsoft/playwright-mcp)). For this repo the accessibility tree covers the network-directory twin well and the canvas poorly, so the canvas needs screenshot comparison. |
| CI gate (GitHub Actions on each draft PR) | Build; `tsc`; ESLint with custom rules for the hard rules (year-proportional geometry, stream-shape ban, citation count, spelling, punctuation), each erroring with the rule name and the fix; Vitest; **acceptance directory hash check**; Playwright acceptance plus held-out; axe on the directory twin; `pnpm design:shots` diff present when UI changed; Semgrep or CodeQL with zero critical or high; secret scan; Code Review severity line read with `gh api`, fail if `normal` is above zero or the line is missing; optional incremental Stryker on changed files with a 50 to 70% break threshold. | Lopopolo's "errors should identify the violated invariant and the likely repair" ([Lopopolo corpus](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/domain-modeling/README.md)); Anthropic's SDLC gate placement ([SDLC post](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)); Code Review severity recipe ([Code Review PR page](https://code.claude.com/docs/en/code-review-pull-requests)); axe covers about 57% of issues by volume ([Deque](https://www.deque.com/blog/automated-testing-study-identifies-57-percent-of-digital-accessibility-issues)); Stryker thresholds ([Stryker](https://stryker-mutator.io/blog/stryker-0-8-0/)). |
| Integration | One task, one branch, one draft PR into `overnight/<date>`. A single serial merge step rebases the branch on the integration branch, re-runs the gate, merges. On conflict, the branch goes back to a fresh worker with the conflict as the task. Branch protection: the agent identity cannot merge to `main`; a human approval that the agent cannot supply is required. | Gas Town's Refinery is the clearest published shape ([Gas Town](https://github.com/steveyegge/gastown)); Copilot's "initiator approval does not count" rule ([GitHub docs](https://docs.github.com/en/copilot/how-tos/agents/copilot-coding-agent/reviewing-a-pull-request-created-by-copilot) [snippet]); cloud Auto-fix cannot react to conflicts, so this step must ([cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web)). |
| Morning package | One Slack message or issue comment, generated by the supervisor with `--output-format json --json-schema`: a table of tasks with gate status per check and a link to each raw log; a criterion-to-test matrix with empty rows highlighted; evidence (test output, commands and exit codes, Playwright traces and screenshots, refreshed `docs/design` shots, a deep-link URL for the state shown); reviewer findings with "why flagged, how verified"; out-of-scope changes; run telemetry (turns, tokens, cost, retries, hook blocks, tampering detections, permission denials); what was not attempted and why. | "Have Claude show evidence rather than asserting success ... it works for sessions you weren't watching" ([best practices](https://code.claude.com/docs/en/best-practices)); Anthropic logs every approval with its signals and reviews "a risk-weighted sample" ([SDLC post](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)). Your job in the morning is to sample, not re-run. |
| Telemetry and evals | Log per task: model, turns, tokens, cost, each gate's result, retries. Build a regression set of 20 to 50 tasks from your own past failures with reference solutions. Run it on a schedule and track pass^k per task type. Read a transcript whenever a score moves. | "Demystifying evals" sizing and pass^k ([Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)); Anthropic's statistics guidance on resampling and paired comparisons ([statistics post](https://www.anthropic.com/research/statistical-approach-to-model-evals)). |

Where a different choice changes the design:

- **Subscription instead of API.** Run two or three workers as cloud scheduled tasks or a Project, on Max 20x with usage credits on and a monthly cap. Prefer Projects, which wait at a usage limit, over scheduled-task threads, which fail. You lose the supervisor's control over dispatch and budget per task, and you keep the "green does not mean success" caveat ([scheduled tasks](https://code.claude.com/docs/en/routines); [Projects](https://code.claude.com/docs/en/claude-projects)).
- **Runs longer than one process lifetime, or approval waits inside the night.** Add a durable engine. DBOS is the lightest for a TypeScript shop (a library plus the Postgres you already run); Temporal if you already operate it. Make each `claude -p` invocation one activity with a heartbeat, a start-to-close timeout and a retry that resumes the session rather than restarting it ([DBOS](https://docs.dbos.dev/architecture); [Temporal long-running activity](https://docs.temporal.io/design-patterns/long-running-activity)). Nothing in the evidence says you need this before stage 4.
- **LangGraph.** Add it only if you need model-driven routing between roles inside a task with shared message state. When the worker is Claude Code, the inner loop is already owned; LangGraph adds a second state store and no crash recovery ([checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)). The vendor rule of thumb, "use LangGraph alone for prototypes, add Temporal when runs are long", is Temporal's and LangChain's own positioning ([LangChain](https://langchain.com/resources/langgraph-vs-temporal) [snippet]).
- **Copilot cloud agent instead.** Turnkey issue-to-draft-PR with a firewall, but a **59-minute hard cap per session** and one PR per task. Good for a queue of small issues; chaining the next issue when a PR lands is yours ([Copilot troubleshooting](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/troubleshoot-cloud-agent) [snippet]).
- **Codex instead.** Internet is off by default during the agent phase, so dependencies must be installed in setup. Symphony is the closest open specification for the supervisor and its defaults are worth copying even on Claude ([Symphony SPEC](https://github.com/openai/symphony/blob/main/SPEC.md)).
- **Greenfield instead of your existing repo.** Use Anthropic's initializer pattern: a 200-feature JSON list and `init.sh` replace `tasks.md`, and the Nov 2025 quickstart is a working starting point ([quickstart](https://github.com/anthropics/claude-quickstarts/tree/main/autonomous-coding)).

## 7. Staged build plan

Each stage has an exit test. Do not start the next stage until the current one passes it. The order follows Anthropic's own sequence: verifier before worker, one worker before many.

| Stage | Build | Exit test | Effort |
|---|---|---|---|
| 0. Pilot and calibrate | One task from your backlog, run as `claude -p --worktree` with auto mode, `--permission-prompts none`, `--max-turns`, `--max-budget-usd`, JSON output. Read the transcript. | One unattended draft PR. Cost per task and `permission_denials` known. | 2 to 3 days |
| 1. Gate and locks | The `/grill` skill and gate script (section 4). `tests/acceptance/` and `tests/holdout/` conventions. `PreToolUse` deny hook plus CI hash check. The CI gate with the hard-rule lint messages. Branch protection on `main`. | Gate script blocks a spec with a leftover marker. A seeded edit to `tests/acceptance/` is blocked by the hook and, with the hook disabled, by CI. All CI checks run on a PR. | 1 to 2 weeks |
| 2. One worker, one night | Supervisor as a plain Node script: sequential tasks, `PROGRESS.md`, Stop hook, draft PR per task, morning package. Run three nights on gated specs. | Three nights with no human needed to produce PRs. First-pass integration rate under the full gate measured. Cost within the pilot band. | 1 to 2 weeks |
| 3. Independent verification | Test-author session separate from the worker. Evaluator subagent with Playwright MCP, two rounds max. Code Review severity wired to the gate. Reviewer findings presented as claims with evidence. | Evaluator catches a deliberately seeded defect that passes the acceptance tests. Observed false-reject rate recorded. | 1 to 2 weeks |
| 4. Parallel workers | Three workers on worktrees. Supervisor on the Agent SDK with the ready-queue predicate, file-ownership check, per-task budgets, heartbeat and wall-clock kills. Serial merge step with rebase and re-gate. Staggered starts. | Three workers for one night with every conflict resolved by re-dispatch. No cross-worker file overwrite. Cost within band. | 2 weeks |
| 5. Keep it healthy | Regression eval set of 20 to 50 tasks with pass^k tracking. Scheduled maintenance agent that gardens docs, finishes migrations and opens narrow refactor PRs. Re-simplify on each model release: remove one component, measure, keep or restore. Add a durable engine only when a run exceeds a process lifetime or needs an in-night approval wait. | Escaped defects per accepted feature over 30 days known. Human minutes per accepted PR falling. | Ongoing |

Metrics to publish internally from stage 2 onward: first-pass integration rate under the full gate (not raw merge rate, which is confounded by review depth); escaped defects per accepted feature over 30 days; human minutes per accepted PR; cost per accepted task; tampering detections and hook blocks per night. Planning assumptions from the public data: **60 to 80% of well-scoped tasks reach a mergeable PR first pass**, configuration and CI tasks closer to 90%, multi-file UI features below 60%; of PRs that pass a tests-only gate, about 20% will carry a semantic defect the tests missed ([Montréal study](https://codex.danielvaughan.com/2026/08/04/what-220000-pull-requests-reveal-agentic-pr-task-routing-codex-cli-test-coverage-gaps/) [secondary]; [SWE-ABS](https://icml.cc/virtual/2026/poster/62669) [snippet]). No source publishes human rework minutes per agent PR. You will have to measure your own.

## Conclusion

The resources were written to answer "how do I keep an agent working for hours". Read together, they answer a different question: what is the product of a software factory? It is the verifier. Anthropic's C compiler run and OpenAI's million-line codebase both had humans who wrote almost no code and spent their effort on tests, lints, reviewer prompts and reading traces. The worker model changed three times during those projects; the verifiers stayed. That is why the build plan puts the gate and the locked tests before the first overnight run, and why the morning routine is sampling evidence rather than re-running work.

The second shift is in how to hold the architecture. Every harness component Anthropic added in November 2025 was a patch for a model weakness, and half of them were gone by March 2026. Build the fresh-context resets, the per-task evaluator rounds and the sprint contracts as toggles with a measurement behind each, not as fixed structure. The one component the evidence says will not become obsolete is the human who decides what "a good job" means before the lights go off, and who reads the proof when they come back on.
