## Key question 1: What exactly does Spec Kit generate at each stage, and in which files?

### Takeaway
Spec Kit (1.x) is a Python CLI (`specify`) plus a set of slash-command prompt templates that an AI coding agent runs in order: constitution, specify, clarify, plan, checklist, tasks, analyze, implement, converge. Each command writes a specific Markdown artefact under `.specify/` (project-wide) or `specs/NNN-feature/` (per feature), and the later commands read the earlier ones as their only source of intent.

Two paths through the commands
- Quickstart "Shorter" path: specify, plan, tasks, implement, converge. "Full" path: constitution (once per project), specify, clarify, plan, checklist, tasks, analyze, implement, converge | [quickstart](https://raw.githubusercontent.com/github/spec-kit/main/docs/quickstart.md)
- "Only `/speckit.specify` is strictly required before `/speckit.plan`. Clarify, checklist, and analyze are optional 'quality gates' for work with meaningful ambiguity" | [Agentic SDD reference](https://raw.githubusercontent.com/github/spec-kit/main/docs/reference/agentic-sdd.md)

### Inferences
- The artefact chain is strictly linear by design: `constitution.md` constrains `spec.md`, which feeds `plan.md` and its satellites, which feed `tasks.md`, which `implement` executes and `converge` audits. Any readiness gate therefore has natural insertion points: after specify/clarify (spec quality), after plan (constitution check), after tasks/analyze (coverage), and before implement (the checklist gate that already exists).
- Because `converge` is append-only and `analyze` is read-only, the only command that rewrites intent is `specify`/`clarify`. A process that wants a versioned spec can rely on git for versioning: Spec Kit itself only versions the constitution (semver), not the feature spec.
- The hyphenated (`/speckit-*`) and dotted (`/speckit.*`) names refer to the same commands; the difference is the agent's slash-command syntax (skills versus prompt files).

### Gaps
- The 1.0.0 release notes do not say when `converge` was added or when the `/speckit-*` skill syntax was introduced; the history page skips both.
- No transcript or write-up of the two "Open Source Friday" videos was reachable.
- The GitHub launch blog post itself could not be fetched; its content is reconstructed from snippets and the repository docs.

## Key question 2: How does Spec Kit separate "what" from "how", and how are constraints and non-functional requirements captured?

### Takeaway
"What and why" live in `spec.md` (written for business stakeholders, technology-agnostic success criteria, no stack); "how" lives in `plan.md` and its satellites; project-wide constraints and non-negotiables live in the constitution, which `plan` must check against and `analyze` treats as automatically CRITICAL when violated. Non-functional requirements enter through the clarify taxonomy, the plan's Technical Context fields (performance goals, constraints, scale) and the constitution.

### Cited Findings
- Specify guidelines: "Focus on **WHAT** users need and **WHY**"; "Written for business stakeholders, not developers"; avoid tech stack, APIs or code structure; remove inapplicable optional sections rather than marking them "N/A" | [specify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/specify.md)
- The quickstart tells users to focus on "the **what** and **why**, not the tech stack" at specify, and that plan "is where tech stack and architecture go" (the Taskify example passes ".NET Aspire, Postgres, Blazor Server, and REST APIs" to plan) | [quickstart](https://raw.githubusercontent.com/github/spec-kit/main/docs/quickstart.md)
- Spec template mandatory sections: User Scenarios & Testing (user stories prioritised P1/P2/P3, each with "Why this priority", "Independent Test" and Given/When/Then "Acceptance Scenarios"; Edge Cases), Requirements (FR-### each beginning "System MUST" or "Users MUST be able to"; Key Entities "without implementation"), Success Criteria (SC-### that "must be technology-agnostic and measurable"), and Assumptions | [spec template](https://raw.githubusercontent.com/github/spec-kit/main/templates/spec-template.md)
- Success criteria rules: measurable with specific metrics (time, percentage, count, rate); "No mention of frameworks, languages, databases, or tools"; "verifiable without implementation details" | [specify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/specify.md)
- The methodology document says the feature spec focuses on "WHAT users need and WHY" and avoids "HOW to implement"; implementation choices belong in the plan, which must stay "high-level and readable", with code samples and algorithms pushed to separate `implementation-details/` files | [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md)
- Plan template Technical Context fields, each with a "NEEDS CLARIFICATION" option: Language/Version, Primary Dependencies, Storage, Testing, Target Platform, Project Type, and "Performance Goals, Constraints, and Scale/Scope"; a Constitution Check gate "must pass before Phase 0 research and be re-checked after Phase 1 design"; a Complexity Tracking table records each constitution violation, why it is needed and why a simpler alternative was rejected | [plan template](https://raw.githubusercontent.com/github/spec-kit/main/templates/plan-template.md)
- Constitution principles must be "declarative, testable, and free of vague language", using MUST or SHOULD, with "explicit rationale if not obvious"; the Governance section "lists amendment procedure, versioning policy, and compliance review expectations"; semver: MAJOR for "Backward incompatible governance/principle removals or redefinitions", MINOR for "New principle/section added or materially expanded guidance", PATCH for "Clarifications, wording, typo fixes" | [constitution command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/constitution.md)
- The methodology's constitutional articles: I Library-First; II CLI Interface (text in, text out, JSON supported); III Test-First ("non-negotiable": tests written, approved and confirmed failing before implementation); IV to VI project-defined; VII Simplicity and VIII Anti-Abstraction (at most three projects initially unless justified; use framework features directly); IX Integration-First Testing (real databases and services over mocks; contract tests mandatory before implementation); amendments need documented rationale, maintainer approval and a backwards-compatibility assessment | [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md)
- The methodology treats non-functional needs as requirements: production bottlenecks become new non-functional requirements and security vulnerabilities become constraints on future generations; the constitution is the system's "architectural DNA" and plan deviations must be justified | [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md)
- Clarify's coverage taxonomy includes "Non-Functional Quality Attributes (performance, scalability, reliability, observability, security/privacy, compliance)", "Integration & External Dependencies" and "Constraints & Tradeoffs" | [clarify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)
- Analyze treats the constitution as non-negotiable: "Constitution conflicts are automatically CRITICAL and require adjustment of the spec, plan, or tasks"; its ambiguity pass flags vague terms like "fast" or "secure" without measurable criteria | [analyze command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/analyze.md)
- Microsoft's AVM guidance lists what a constitution typically includes: required engineering standards, guardrails and constraints, required or discouraged patterns, organisational coding standards, testing expectations, cloud/platform governance, naming and tagging rules, compliance/security requirements (example: "Infrastructure must be declarative and written in Bicep only"; "Mandatory tags: owner, costCenter, env, application") | [AVM Spec Kit guide, updated 14 Oct 2026](https://azure.github.io/Azure-Verified-Modules/usage/ai-assisted-sol-dev/spec-kit/)
- For existing codebases: "Do not invent standards merely to fill the constitution template"; derive principles from "the repository's README, architecture decisions, contribution guide, and CI configuration"; "unrealistic rules create noise instead of useful constraints"; compatibility boundaries go in the spec, for example "Preserve current filters and authorization behavior" | [existing projects guide](https://raw.githubusercontent.com/github/spec-kit/main/docs/guides/existing-projects.md)

### Inferences
- Non-functional requirements have three homes and no single owner: cross-cutting rules in the constitution, feature-specific targets in SC-### and the plan's Technical Context, and gap detection in clarify's taxonomy. A readiness gate should check all three rather than assume NFRs are in one place.
- Constitution semver plus the Sync Impact Report gives a ready-made audit trail for constraint changes, which a nightly factory could require to be at a specific version before any run.

### Gaps
- The templates do not define a dedicated non-functional requirements section in `spec.md`; NFRs appear only as success criteria or clarify findings. Whether teams add an NFR section via presets is not documented in the pages read.

## Key question 3: How does Spec Kit ask clarifying questions, how many, and what does it do with unresolved items?

### Takeaway
Spec Kit interrogates the human in three bounded rounds: `specify` leaves at most three `[NEEDS CLARIFICATION]` markers and asks them as Q1 to Q3 with options; `clarify` asks at most five questions, one at a time, chosen from a ten-category coverage scan ranked by impact times uncertainty, and writes each answer into the spec; `checklist` asks up to three (max five) framing questions before generating. Everything else is resolved by "informed guesses" recorded in the Assumptions section, or left as explicitly labelled Deferred or Outstanding items in a completion report.

### Cited Findings

At specify
- Default: "Make informed guesses" using "context, industry standards, and common patterns to fill gaps," and record them in the Assumptions section; markers are reserved for points where scope or UX is significantly affected, multiple interpretations exist, or no reasonable default exists; "Maximum 3 [NEEDS CLARIFICATION] markers total"; priority order "scope > security/privacy > user experience > technical details"; reasonable defaults such as data retention or standard authentication "should not be asked about" | [specify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/specify.md)
- Only after validation, if markers remain, it presents up to three numbered questions (Q1 to Q3) with options A, B, C and Custom and waits for all answers | [specify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/specify.md)
- Marker example in the template: "[NEEDS CLARIFICATION: auth method not specified - email/password, SSO, OAuth?]" | [spec template](https://raw.githubusercontent.com/github/spec-kit/main/templates/spec-template.md)
- The methodology requires the LLM to flag ambiguities with the marker "including the specific question, rather than guessing," and the spec checklist requires that no markers remain before the spec is complete | [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md)
- Specify runs a validation loop against `checklists/requirements.md` (content quality, requirement completeness, feature readiness): failing items trigger fixes and re-validation "up to 3 iterations"; persisting issues are recorded in checklist notes and the user is warned | [specify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/specify.md)

At clarify
- Coverage scan over ten categories, each marked Clear, Partial or Missing: Functional Scope & Behavior; Domain & Data Model; Interaction & UX Flow; Non-Functional Quality Attributes; Integration & External Dependencies; Edge Cases & Failure Handling; Constraints & Tradeoffs; Terminology & Consistency; Completion Signals; Misc / Placeholders | [clarify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)
- Partial or Missing categories become candidate questions, "except where clarification would not change implementation or validation, or the item concerns implementation method, tech-stack comparison, or task breakdown" | [clarify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)
- "Maximum of 5 total questions across the whole session"; if more remain, the top five are chosen by an "(Impact * Uncertainty)" heuristic | [clarify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)
- Question format: begins `**Question:**` and ends with `?`, plain language, optional requirement ID; a "Why it matters" sentence; multiple choice shows `**Recommended:** Option [X] - <reasoning>` and a table of 2 to 5 mutually exclusive options (optionally a "Short" free-form row); short-answer questions show `**Suggested:**` and must be answered in "<=5 words" | [clarify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)
- Loop rules: "Present EXACTLY ONE question at a time"; replies of "yes", "recommended" or "suggested" accept the proposal; ambiguous replies trigger disambiguation without advancing; "Never reveal future queued questions in advance"; stop when ambiguities are resolved, the user signals completion, or five questions have been asked | [clarify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)
- Integration: create `## Clarifications` with `### Session YYYY-MM-DD`, append `- Q: <question> → A: <final answer>` per accepted answer, then apply each answer to the relevant section (Functional Requirements, Data Model, Success Criteria, Edge Cases or terminology), "replacing contradictory text rather than duplicating it", saving after each integration | [clarify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)
- Unresolved items are classified as Deferred (exceeds quota, or concerns implementation method, tech-stack comparison or task breakdown) or Outstanding (still Partial or Missing but low impact); the completion report "recommends whether to proceed to the plan step or re-run clarify later" | [clarify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)
- Post-write validation: exactly one bullet per accepted answer, no more than five questions, no vague placeholders or contradictions remain, only allowed headings added, terminology consistent; if `checklists/requirements.md` exists its checkboxes are re-evaluated ("Only toggle the `[ ]`/`[x]` marker portion of checkbox lines whose state changed") | [clarify command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/clarify.md)
- Clarify can take a focus area (Taskify example: task card behaviour, status changes, comment permissions, assignment) and can be run "as many times as needed" | [quickstart](https://raw.githubusercontent.com/github/spec-kit/main/docs/quickstart.md); [Agentic SDD reference](https://raw.githubusercontent.com/github/spec-kit/main/docs/reference/agentic-sdd.md)

At checklist
- "Derive up to THREE initial contextual clarifying questions" (Q1 to Q3), follow-ups Q4 to Q5 allowed, total not exceeding five; archetypes: scope refinement, risk prioritisation, depth calibration, audience framing, boundary exclusion, scenario class gaps; "If interaction isn't possible, defaults are Depth: Standard, and Audience: Reviewer (PR)" | [checklist command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/checklist.md)

How other tools interrogate the human (for comparison)
- Kiro's optional requirements analysis runs on `requirements.md` before design, looking for "logical inconsistencies, ambiguous wording, conflicting constraints, unstated assumptions, and missing edge cases" (example: "large files" or "fast response times"); it "takes minutes, not seconds"; findings appear as questions in chat naming the affected requirements with suggested fixes; users can write their own answer "or dismiss a question if the ambiguity is intentional"; resolved questions update `requirements.md` (snippets; kiro.dev blocked) | [Kiro: analyze requirements](https://kiro.dev/docs/specs/analyze-requirements/); [Kiro blog: Requirements analysis](https://kiro.dev/blog/deep-spec-analysis/)
- Anthropic's Claude Code guidance: "For larger features, have Claude interview you first ... using the `AskUserQuestion` tool"; suggested prompt: "Ask about technical implementation, UI/UX, edge cases, concerns, and tradeoffs. Don't ask obvious questions, dig into the hard parts I might not have considered. Keep interviewing until we've covered everything, then write a complete spec to SPEC.md." Then "start a fresh session to execute it" | [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- BMAD (v6.12 stable, v7 alpha) brief/PRD/UX skills start with a brain dump, then offer a "Fast path" that drafts the whole document with `[ASSUMPTION]` tags, or a "Coaching path" that "pulls the thinking out of you section by section and pushes back where an answer is thin"; the PRFAQ skill challenges vague answers and sends users back to brainstorming if they cannot name a customer or problem; the Product Owner agent (Sofia) "does not interview you about what you want", gives rich input no questions, and for sparse input offers "a best-effort draft with open questions or a guided walk through the sections"; run reports list `Assumption:` and `Open question:` lines | [BMAD: define requirements](https://raw.githubusercontent.com/bmad-code-org/BMAD-METHOD/main/docs/plan/define-requirements-and-a-specification.md)

### Inferences
- Spec Kit's question budget is deliberately small (3 + 5 + up to 5) and front-loaded on scope and security. A "grill me until resolved" process needs either repeated clarify runs with focus areas (the docs permit this) or a custom preset that raises the cap. The ten-category coverage table is the natural artefact to persist as evidence that interrogation happened.
- The explicit Deferred/Outstanding/Assumptions vocabulary is the hook for "accepted as an assumption": anything an informed guess resolved is already listed in Assumptions; anything clarify could not fit is labelled, so a gate can require every Outstanding item to be either answered or moved into Assumptions with a sign-off.
- Spec Kit excludes implementation-method and tech-stack questions from clarify by rule, so "how" ambiguities surface only in plan's Technical Context NEEDS CLARIFICATION fields. A readiness gate should scan both `spec.md` and `plan.md` for leftover markers.

### Gaps
- None of the Spec Kit pages read say what happens to clarify questions when no human is present (for example in a workflow run); the Agentic SDD reference explicitly omits unattended handling.
- Kiro's exact approval mechanics and whether gates can be disabled in the standard flow could not be verified on kiro.dev.

## Key question 4: How could a "requirements readiness gate" be built on top of Spec Kit (what checks, what blocks, what can be waived as an approved assumption)?

### Takeaway
Spec Kit already ships the raw materials for a gate: the auto-generated `checklists/requirements.md` with a 3-iteration validation loop, custom reviewer-owned checklists that `implement` reads as a read-only PASS/FAIL gate, the read-only `analyze` report with CRITICAL/HIGH/MEDIUM/LOW severities and a requirement-to-task coverage map, the plan's Constitution Check and Complexity Tracking, and `before_implement` hooks. What it does not ship is a single deterministic script that fails CI; teams assemble that themselves (an "Autonomous Run Governance" preset and extensions such as "Architecture Guard" and "Closed Vocabulary Check" exist in the community catalogue).

### Cited Findings

Existing gate mechanics
- Checklists are "unit tests for English": they "validate the quality, clarity, and completeness of requirements in a given domain", not whether the implementation works; items must be questions about requirement quality tagged with a dimension ("[Clarity]", "[Consistency]", "[Edge Cases]", "[Measurability]") and a reference ("[Spec §X.Y]" or "[Gap]"); "At least 80% of items must include a traceability reference"; items must not begin with "Verify", "Test", "Confirm" or "Check" (wrong: "Verify landing page displays 3 episode cards"; right: "Are the number and layout of featured episodes explicitly specified?") | [checklist command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/checklist.md)
- Implement treats checklists as a read-only gate: it tabulates total/checked/unchecked per file; PASS means zero unchecked items; on FAIL it stops and asks "Some checklists have unchecked items. Do you want to proceed with implementation anyway? (yes/no)"; "no", "wait" or "stop" halts; for custom checklists a checked box means the requirements-quality criterion is met and "it does NOT mean implementation work is complete" | [implement command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/implement.md)
- Custom checklists are "reviewer-owned"; an agent "may help evaluate them when explicitly asked, but implementation must not silently self-approve them" | [Agentic SDD reference](https://raw.githubusercontent.com/github/spec-kit/main/docs/reference/agentic-sdd.md)
- Analyze passes: A duplication; B ambiguity (vague terms, leftover TODO placeholders); C underspecification (requirements missing an object or measurable outcome, stories without acceptance criteria, tasks referencing undefined files); D constitution alignment; E coverage gaps (requirements with no tasks, tasks with no requirement, buildable success criteria not reflected in tasks); F inconsistency (terminology drift, entity mismatches, task-ordering contradictions, conflicting technology choices) | [analyze command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/analyze.md)
- Analyze severities: CRITICAL "Violates constitution MUST, missing core spec artifact, or requirement with zero coverage that blocks baseline functionality"; HIGH duplicate or conflicting requirements, ambiguous security or performance attributes, untestable acceptance criteria; MEDIUM terminology drift, missing non-functional task coverage, underspecified edge cases; LOW wording and minor redundancy; findings capped at 50; output includes a coverage summary mapping each requirement key to task IDs and metrics (total requirements and tasks, coverage percentage, ambiguity count, duplication count, critical count); "If CRITICAL issues exist, the report recommends resolving them before implementation"; it offers "concrete remediation edits for the top N issues" only on approval | [analyze command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/analyze.md)
- The quickstart's instruction after analyze: "fix them at the source and re-run before implementing" | [quickstart](https://raw.githubusercontent.com/github/spec-kit/main/docs/quickstart.md); the reference says run analyze "before implementing, while the artifacts can still be adjusted cheaply" and re-run "until it comes back clean" | [Agentic SDD reference](https://raw.githubusercontent.com/github/spec-kit/main/docs/reference/agentic-sdd.md)
- The methodology frames checklists as "unit tests" for the spec covering "completeness, testability, and measurable success criteria", phase gates where "Simplicity and anti-abstraction checks must pass or be documented under 'Complexity Tracking'", and an anti-speculation rule: features must trace to a user story and checklists require "No speculative or 'might need' features" | [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md)
- Implement's completion validation: "Verify all required tasks are completed", check the implementation matches the specification, "Validate that tests pass and coverage meets requirements", confirm it follows the plan; "Done When" is all tasks `[X]`, validation complete, hooks dispatched, summary reported | [implement command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/implement.md)
- Converge's gap types: `missing`, `partial`, `contradicts` (code conflicts with intent or a constitution MUST), `unrequested` (flagged, not deleted); CRITICAL covers constitution MUST violations and blocking gaps on P1 stories; it re-checks every task "regardless of checkbox state" because "completion claims are not evidence"; it is "not a diff tool" and the template does not mention running tests | [converge command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/converge.md)

Unattended operation and automation hooks
- `specify init ... --non-interactive` is recommended "in CI or agent harnesses so the setup doesn't wait for input" | [quickstart](https://raw.githubusercontent.com/github/spec-kit/main/docs/quickstart.md)
- Checklist defaults when "interaction isn't possible" are Depth: Standard and Audience: Reviewer (PR) | [checklist command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/checklist.md)

- Microsoft's AVM guide summarises the gate intent: "Use the clarify step to challenge assumptions and refine requirements before committing to implementation" and "Use analyze and checklist steps to catch inconsistencies early" | [AVM Spec Kit guide](https://azure.github.io/Azure-Verified-Modules/usage/ai-assisted-sol-dev/spec-kit/)

### Inferences (design proposal grounded in the above)
- Blocking checks that map directly to existing artefacts: (1) zero `[NEEDS CLARIFICATION]` markers in `spec.md` and in `plan.md` Technical Context; (2) `checklists/requirements.md` all `[x]`; (3) every custom checklist all `[x]` (so `implement` does not pause); (4) `analyze` reports zero CRITICAL and, for a nightly unattended run, zero HIGH in the security/performance and "untestable acceptance criteria" classes; (5) coverage map shows every FR-### and every P1 acceptance scenario mapped to at least one task; (6) Constitution Check passed or every violation has a Complexity Tracking row; (7) every SC-### has a metric and no technology words; (8) the spec contains a `## Clarifications` session dated within the current cycle (evidence the interrogation ran).
- Waivable with sign-off: clarify items labelled Outstanding (low impact) or Deferred (implementation questions), analyze MEDIUM/LOW findings, and constitution violations justified in Complexity Tracking. The waiver record should be a bullet in the spec's Assumptions section (the place Spec Kit already designates for "informed guesses") plus the reviewer's `[x]` on a custom checklist item, since Spec Kit forbids agents from self-approving those boxes.
- Enforcement point: a `before_implement` mandatory hook in `.specify/extensions.yml` (or a CI job in a Spec Kit workflow) that runs these checks as a script and exits non-zero; Spec Kit's own repo uses deterministic test steps around agentic steps in exactly this way. The read-only nature of `analyze` and the write-restrictions on `implement` and `converge` mean the gate cannot be "fixed" by the implementing agent rewriting the checklist.
- Because `converge` inspects code rather than running tests, the overnight loop still needs an independent executable test gate (see question 5); converge covers spec-to-code traceability, not behaviour.

### Gaps
- No Spec Kit page read documents how a workflow answers clarify questions or the implement "proceed anyway?" prompt when unattended; whether `--no-model-invocation` or workflow inputs can pre-answer them is not described in the fetched pages.
- The community presets "Autonomous Run Governance" and "Closed Vocabulary Check" were seen only by name in release notes; their behaviour was not read.

## Key question 5: How do acceptance criteria become executable tests rather than prose?

### Takeaway
Spec Kit expresses acceptance as Given/When/Then scenarios per user story, an "Independent Test" per story, and measurable SC-### criteria; tests in `tasks.md` are optional unless the spec requests them, but when present they must be written first and fail before implementation, ordered contract, integration, e2e, unit. Kiro's EARS notation and OpenSpec's `#### Scenario:` WHEN/THEN blocks serve the same purpose. Practitioners and vendor guidance converge on the same point: the highest-value part of a spec is machine-checkable acceptance criteria plus a verification command the agent can run.

### Cited Findings
- Spec template: each user story carries an "Independent Test" and "Acceptance Scenarios" written as Given/When/Then; each story must be "INDEPENDENTLY TESTABLE" and deliver a viable MVP alone; SC-### "must be technology-agnostic and measurable" | [spec template](https://raw.githubusercontent.com/github/spec-kit/main/templates/spec-template.md)
- Tasks template: "Tests are OPTIONAL - only include them if explicitly requested in the feature specification"; if included, "Write these tests FIRST, ensure they FAIL before implementation"; each story phase has a Goal, an Independent Test, test tasks (if requested) then implementation tasks, and a checkpoint; tasks are `[ID] [P?] [Story] Description` with exact file paths | [tasks template](https://raw.githubusercontent.com/github/spec-kit/main/templates/tasks-template.md)
- Implement runs "Test tasks ... before their implementation tasks (TDD)", halts if a non-parallel task fails, and at completion must "Validate that tests pass and coverage meets requirements" | [implement command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/implement.md)
- The methodology: "Acceptance scenarios become tests. Tests are part of the spec that generates both implementation and tests, not written afterward"; plans add test scenarios and quickstart validation scenarios; file creation order is "contract, then integration, then e2e, then unit tests, then source files"; Article IX makes contract tests mandatory before implementation and prefers real services to mocks | [spec-driven.md](https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md)
- Converge verifies acceptance scenarios (e.g. `US1/AC2`) by inspecting code within the scope named by plan and tasks; "The source does not mention running tests, executing acceptance scenarios, or checking runtime behavior" | [converge command template](https://raw.githubusercontent.com/github/spec-kit/main/templates/commands/converge.md)
- Microsoft's AVM guidance says tasks "typically include ... Acceptance criteria per task" and that test artefacts include unit and integration tests, IaC lint results, What-If validation JSON, PSRule configs and "Regression tests (if in constitution)" | [AVM Spec Kit guide](https://azure.github.io/Azure-Verified-Modules/usage/ai-assisted-sol-dev/spec-kit/)
- Kiro writes `requirements.md` as user stories with EARS acceptance criteria in the form "WHEN [condition] THE SYSTEM SHALL [behavior]", which its docs say "makes requirements easier to test and trace"; tasks are "sequenced ... based on dependencies, and link[ed] ... to requirements" (snippets) | [Kiro feature specs](https://kiro.dev/docs/specs/feature-specs/); [Kiro launch post](https://kiro.dev/blog/introducing-kiro/)
- OpenSpec requirement format: `### Requirement: Theme selection` with a SHALL statement ("The app SHALL let users switch between light and dark themes"), then `#### Scenario: User toggles dark mode` with **WHEN** and **THEN** bullets; "Plain Markdown: requirements with concrete scenarios, no special syntax to learn" | [OpenSpec README](https://github.com/Fission-AI/OpenSpec)
- Task Master's task schema includes a `testStrategy` field ("Test login/logout flow with valid and invalid credentials"; "Deploy and call endpoint to confirm 'Hello World' response") alongside `details`, `dependencies`, `priority`, `status` | [Task Master task structure](https://raw.githubusercontent.com/eyaltoledano/claude-task-master/main/docs/task-structure.md)
- Anthropic: "Give Claude a check it can run: tests, a build, a screenshot to compare. It's the difference between a session you watch and one you walk away from"; example before/after: "implement a function that validates email addresses" versus "write a validateEmail function. example test cases: user@example.com is true, invalid is false, user@.com is false. run the tests after implementing"; "The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works"; "Have Claude show evidence rather than asserting success" | [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- A compiled field study concludes "the highest-ROI part of a spec is machine-checkable acceptance criteria", reports one practitioner writing acceptance criteria into the spec and using them as end-to-end tests, and cites a practitioner claim of roughly 20x ROI from comprehensive acceptance tests in the spec (secondary compilation) | [agentic-engineering-field-study](https://github.com/ianhxu/agentic-engineering-field-study/blob/main/04-spec-driven-development.md)
- The O'Reilly/Stack Overflow column argues that as implementation gets cheaper "more of the difficulty moves into deciding what correct means and checking it reliably", warns a spec "can describe behavior that sounds precise but cannot actually be verified", and recommends "enough structure, examples, and executable checks" (snippets) | [Stack Overflow blog, 21 Aug 2026](https://stackoverflow.blog/2026/08/21/dispatches-from-o-reilly-the-right-amount-of-spec-for-agentic-development/); [O'Reilly Radar original](https://oreilly.com/radar/the-right-amount-of-spec-for-agentic-development)
- A research preprint ("Rebuild Dossier") locks interface contracts before tests and enforces discipline through hooks rather than prompt instructions; the authors report the hook "held for one deliberately constructed test but not in natural trials" and that a single prompt beat the apparatus on a larger app (snippet; arXiv blocked) | [arXiv 2608.23616](https://arxiv.org/pdf/2608.23616)

### Inferences
- In Spec Kit, Given/When/Then is the bridge: the specify step produces it, tasks can be told (via the spec or constitution's Article III) to generate failing tests from it, implement runs them, and analyze flags "untestable acceptance criteria" as HIGH. Teams wanting tests to be mandatory must say so in the constitution or spec, because the tasks template defaults to optional.
- Because converge audits by reading code and implement's "tests pass" check is self-reported, the only deterministic evidence of acceptance is an externally run test suite (CI, Stop hook, or `/goal`). The overnight design should treat executable acceptance tests as the exit criterion and converge as a traceability sweep.
- EARS (Kiro) and WHEN/THEN scenarios (OpenSpec) are easier to transliterate into test names and parameterised cases than free prose; Spec Kit's Given/When/Then is equivalent in intent.

### Gaps
- No primary source read gives a worked example of Spec Kit's `tasks.md` generating a test file per acceptance scenario; the mapping is asserted in templates, not demonstrated.
- The O'Reilly article's full argument and examples were not readable (blocked).

## Key question 6: What do practitioners report as the weaknesses (over-specification, stale specs, agents ignoring the spec)?

### Takeaway
The recurring critiques are: ceremony disproportionate to task size (small fixes ballooning into many stories and thousands of lines of Markdown), spec drift because nothing in the core toolchain reconciles spec and code automatically, agents ignoring or partially following elaborate instructions, a doubled review burden (prose plus code), and a philosophical objection (Kent Beck, endorsed by Martin Fowler) that writing the whole spec first assumes nothing will be learned during implementation. Thoughtworks placed SDD in "Assess" in November 2025 and it has since dropped off the Radar; one 2026 empirical study reportedly found no support for defect-reduction claims.

### Cited Findings
- Thoughtworks Technology Radar listed spec-driven development in the Assess ring (blip published November 2025), naming Kiro (requirements, design, tasks), spec-kit ("a similar three-step process with added orchestration and a 'constitution' of immutable principles") and Tessl; it found "the workflows remain elaborate and opinionated", "some tools generate lengthy spec files that are hard to review", and suggested the field "may be relearning that hand-crafting detailed rules for AI doesn't scale"; the blip "has since dropped off the current edition" (snippets; thoughtworks.com blocked) | [Thoughtworks Radar: spec-driven development](https://www.thoughtworks.com/radar/techniques/spec-driven-development)

### Inferences
- The weaknesses cluster into two engineering problems the daytime process must solve explicitly: (a) right-sizing (Spec Kit's docs now say processes are "independent entry points, not mandatory phases" and offer a five-command short path, which is the project's own response to the ceremony critique), and (b) reconciliation (choose flow-back, flow-forward or living spec in the constitution, and schedule `analyze` after every implementation change, because core will not reconcile for you).
- "Agents ignore the spec" is mitigated in Spec Kit by making the gates read-only to the implementing agent and reviewer-owned, and in Claude Code by moving must-happen checks from advisory prose to deterministic hooks. Both point the same way: enforcement belongs in tooling, not in longer Markdown.
- Beck's objection is addressed structurally by converge (append new tasks as learning happens) and by the flow-back model, but neither updates `spec.md`; a living-spec policy with a mandatory `analyze` re-run is the closest Spec Kit comes to "spec as hypothesis".

### Gaps
- The Marmelab and Scott Logic posts, Böckeler's article, Fowler's Fragments post, the Thoughtworks blip and the ESEM paper were all unreachable; figures (1,300 lines, 2,500 lines, 10x, 88,052 PRs, five hypotheses) are second-hand and the ESEM hypotheses are unknown.
- No systematic, peer-reviewed study of stale-spec failure rates was found; the field study itself says the "consensus" is practitioner opinion.

- A third-party guide claims CLAUDE.md compliance is "~80%" and hooks "100%"; this is a community estimate, not an Anthropic figure (snippet) | [search summary via community posts](https://dev.to/nikiforovall/my-claude-code-usage-best-practices-and-recommendations-1mcl)

### Inferences
- GitHub (constitution plus `.instructions.md`/`.chatmode.md`/`.prompt.md`), Anthropic (CLAUDE.md plus skills, hooks, subagents) and Spec Kit (constitution plus templates and hooks) all separate three things: always-on constraints, on-demand workflow prompts, and deterministic enforcement. A daytime requirements process should produce artefacts for each tier, not one long instructions file.

### Gaps
- The GitHub blog post's specific claims about specification files (`.spec.md`), agent memory, context helpers, session splitting and any measured consistency improvements could not be read; the Microsoft Learn module and GitHub Docs pages on custom instructions and AGENTS.md were also blocked (docs.github.com).

## Key question 9: How do comparable approaches work (Kiro, BMAD, OpenSpec, Task Master, Anthropic guidance)?

### Takeaway
Kiro (AWS) is the closest analogue to Spec Kit: three gated files with EARS acceptance criteria and an optional requirements-analysis step. BMAD is the maximalist, role-based alternative with a Product Owner agent, tiered planning paths and an unattended build mode. OpenSpec is the lightweight brownfield counterpoint built on delta specs. Task Master is a PRD-to-tasks compiler with a `testStrategy` per task. Anthropic's guidance is procedural rather than a tool: interview, write SPEC.md, run in a fresh session with executable verification.

### Cited Findings

Kiro (AWS)
- Specs produce `requirements.md` (or `bugfix.md`), `design.md` and `tasks.md` in `.kiro/specs/`; requirements are user stories with EARS acceptance criteria ("WHEN ... THE SYSTEM SHALL ..."); the design step "analyzes the codebase and generates diagrams, TypeScript interfaces, database schemas, and API endpoints"; tasks are sequenced by dependency and linked to requirements; in the standard flow "Once you confirm the requirements, Kiro generates a design.md document", and the design is reviewed before tasks; Quick Spec / Quick Plan "produce the same three artifacts in one pass, with no approval gates between phases" after up-front clarifying questions; Kiro reached general availability in November 2025 and succeeds Amazon Q Developer (snippets and third-party; kiro.dev blocked) | [Kiro specs docs](https://kiro.dev/docs/specs/); [Kiro Quick Spec](https://kiro.dev/docs/specs/quick-spec/); [Introducing Kiro](https://kiro.dev/blog/introducing-kiro/); [horadecodar](https://horadecodar.com.br/kiro-spec-driven-development/); [nevercodealone](https://nevercodealone.de/de/glossare/ki-tools-2026/kiro)
- Kiro's requirements-analysis refinement (see question 3) produces ambiguity findings as questions and updates `requirements.md` (snippets) | [Kiro blog](https://kiro.dev/blog/deep-spec-analysis/)
- Kiro CLI is also a supported Spec Kit integration | [Spec Kit docs toc](https://raw.githubusercontent.com/github/spec-kit/main/docs/toc.yml)

BMAD (Breakthrough Method for Agile Ai Driven Development)
- Two lines: "Stable v6.12" (npm installer, bug fixes only) and "V7 Preview Alpha" ("Expect breaking changes"), with a v7 release ETA of 16 October 2026; installs as a Claude Code plugin (`/plugin marketplace add bmad-code-org/bmad-plugins`), a Codex plugin, or via `npx skills add bmad-code-org/BMAD-METHOD --skill '*'` | [BMAD README](https://github.com/bmad-code-org/BMAD-METHOD)
- Delivery loop: Clarify, Plan, Build and verify, Learn and adjust; "Bigger work enters it earlier and goes round it more often"; skills include `bmad-build` (write and review a change), `bmad-project-context` (existing codebases) and `bmad-agent-po` (Sofia, the Product Owner) | [BMAD docs index](https://raw.githubusercontent.com/bmad-code-org/BMAD-METHOD/main/docs/index.md)
- Planning paths: direct edit ("You don't need BMad for an obvious, low-risk edit"), single session (`bmad-build`), epic-sized (Sofia fills requirements then slices into stories), project-sized ("spans several epics, or likely needs roughly 20 or more sessions"); "Well-defined intent means it says what should be true, what must not change, and what is out of scope"; Sofia's input ceiling is "roughly a 40-page document"; a PRD is needed "when more than one person must agree on what the product is, or more than one epic must not diverge"; artefacts include `brief-<slug>.md`, `prd-<slug>.md` with `addendum.md` and `.memlog.md`, `architecture-<slug>.md`, and an ordered `tickets.toml`; `bmad-build-auto` "runs one session unattended, once per story, after key decisions are stable"; `bmad-retrospective` closes an epic | [BMAD: choose a planning path](https://raw.githubusercontent.com/bmad-code-org/BMAD-METHOD/main/docs/plan/choose-a-planning-path.md)

- The field study characterises BMAD as "Maximalist, with many agent personas and adversarial code review; reviewers find it too heavy for routine work" (secondary) | [agentic-engineering-field-study](https://github.com/ianhxu/agentic-engineering-field-study/blob/main/04-spec-driven-development.md)

### Inferences
- The tools differ mainly in how much ceremony they default to and how they handle brownfield change: Spec Kit (feature directories, converge), Kiro (gated three files, no delta model), OpenSpec (delta specs archived into a living spec), BMAD (tickets and epics with an unattended per-story build). - Task Master's `testStrategy` field and Spec Kit's per-story "Independent Test" are the two places where a machine-checkable acceptance criterion is stored per unit of work; either could be the schema for a readiness gate's "every task has a verification command" rule.

## Key question 10: What does an unattended, overnight implementation run need from the daytime process, according to these sources?

### Takeaway
The sources agree that an agent can be left alone only when three things exist before it starts: a spec with no open markers and reviewer-approved checklists, a deterministic check it can run to know it is done, and permissions and review scoped so that its output is a proposal (draft PR), not a merge. Spec Kit supplies the first and part of the second; Claude Code's hooks and `/goal`, CI test steps and GitHub's label-triggered workflows supply the rest.

### Cited Findings
- Spec Kit: "Review each skill's output before moving to the next step"; "Reviewers decide checklist items"; "Fix analyze findings in the source documents before implementing"; "Review converge's results and the final output before opening a PR" | [quickstart](https://raw.githubusercontent.com/github/spec-kit/main/docs/quickstart.md)
- Staged implementation for large features: scope each run and "Verify each stage works before moving to the next"; implement can be run once for everything "or one phase at a time" | [Agentic SDD reference](https://raw.githubusercontent.com/github/spec-kit/main/docs/reference/agentic-sdd.md); [quickstart](https://raw.githubusercontent.com/github/spec-kit/main/docs/quickstart.md)
- Converge loop: "Repeat implement and converge until convergence reports `Converged`"; "Each pass finds fewer items; repeat until it reports converged" | [Spec Kit README](https://github.com/github/spec-kit); [Agentic SDD reference](https://raw.githubusercontent.com/github/spec-kit/main/docs/reference/agentic-sdd.md)
- Spec Kit's repo runs agents only after a maintainer applies a label; bug fixes land as draft PRs; test commands run deterministically alongside agentic selection | [Agentic SDLC guide](https://raw.githubusercontent.com/github/spec-kit/main/docs/guides/agentic-sdlc.md)
- Claude Code: "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available"; the `/goal` and Stop hook versions "are what let an unattended run finish correctly without you"; "If you can't verify it, don't ship it"; `--permission-mode dontAsk` "denies anything else that would need approval, which matters when you're running unattended"; auto mode uses a classifier that blocks "scope escalation, unknown infrastructure, and hostile-content-driven actions" | [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- BMAD's `bmad-build-auto` runs "one session unattended, once per story, after key decisions are stable" | [BMAD: choose a planning path](https://raw.githubusercontent.com/bmad-code-org/BMAD-METHOD/main/docs/plan/choose-a-planning-path.md)
- Microsoft Agent Framework advises running Copilot SDK agents with shell or file permissions "in a containerized environment (Docker/Dev Container)" | [Agent Framework docs](https://learn.microsoft.com/agent-framework/integrations/by-component/agent-services/github-copilot)
- The Rebuild Dossier preprint reports that hook-based enforcement "held for one deliberately constructed test but not in natural trials", a caution that mechanical enforcement needs its own verification (snippet) | [arXiv 2608.23616](https://arxiv.org/pdf/2608.23616)

### Inferences
- The daytime output that lets a night run proceed without prompts is: constitution at a known version; `spec.md` with zero markers and a dated Clarifications session; `checklists/requirements.md` and any custom checklists fully ticked by a human; `plan.md` with Constitution Check passed; `tasks.md` with tests requested (so the template generates failing tests first) and an Independent Test per story; a clean `analyze` report; and a verification command recorded per story or task. The night run then is implement, external test gate, converge, repeat, then draft PR.
- Spec Kit's implement prompt ("proceed anyway?") is the one interactive point that would stall an unattended run; the gate must therefore guarantee all checklists are complete before the run starts, or the preset must be overridden.

### Gaps
- No source documents a complete end-to-end unattended Spec Kit run (workflow definition, how clarify and implement prompts are suppressed, exit codes); the Spec Kit `reference/workflows.md` and `install/air-gapped.md` pages were not read and may contain this.
