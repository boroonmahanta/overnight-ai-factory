## Key question 1: For each engine, what cost and token data is available per run, with which identifiers, at what lag, and what is missing for a per-agent, per-night, per-project ledger?

### Takeaway
Every engine exposes per-run token counts at the client, but only Claude Code (and the Claude Agent SDK) reports a per-run dollar figure out of the box, and even that is a client-side list-price estimate; Copilot SDK reports per-session AI credits as `totalNanoAiu` through an experimental RPC, the Copilot CLI only shows `/usage` interactively and has no documented JSON usage schema for `-p`, the Copilot cloud agent shows token usage only in the web session view, and Codex emits tokens but no cost. Authoritative billing (GitHub AI usage report, Anthropic Cost API, OpenAI Costs API, Azure Cost Management) is daily or hourly and keyed by user, API key, workspace, project or resource, never by run, task or PR. A per-run ledger therefore has to be built from the client side and reconciled down to the billing grain.

### Inferences
- Per-engine "measured at run" availability, ranked: Claude Code / Agent SDK (tokens by type, list or contracted USD, per model, per session, per subagent tree, streamed by OTel) > Copilot SDK (tokens, multiplier per call; AI credits per session via experimental `getMetrics`) > Codex CLI (tokens incl. cached per turn, no money) > Copilot CLI `-p` (no documented machine-readable usage; workaround is to drive it through the SDK, or parse `events.jsonl` in the session-state folder) > Copilot cloud agent and third-party agents on GitHub (web view only; must be estimated) > Copilot code review (Actions minutes per workflow row only; credits land on a human or the org).
- Identifiers you can rely on at run time: Claude `session_id` and `request_id`; Copilot SDK `sessionId` (and cloud session URL `github.com/copilot/tasks/{sessionId}`); Codex `thread_id`; GitHub agent task id and PR number; ACA job execution name. None of these appear on any invoice row, so the ledger's own `run_id` must be the bridge and the invoice reconciliation must happen at day x identity x model.
- Lags for reconciliation: Anthropic about 5 minutes (minute buckets); OpenAI usage near real time [unverified lag]; Azure Cost Management daily with tags up to 24 hours (8 to 24 hours for inherited tags); GitHub billing daily with no published lag; Copilot metrics API within two full UTC days. A morning-after ledger should post "provisional" rows from telemetry and "final" rows two to three days later.
- For Copilot-heavy factories the practical design is: run long workers through the Copilot SDK (not raw CLI `-p`) so `assistant.usage` and `getMetrics` can be captured, keep cloud-agent use for short PR hygiene, and estimate its cost from model prices times a token profile, flagged as estimated.

## Key question 2: What concrete ledger schema should the factory keep, which values are measured versus estimated, and how do per-run estimates reconcile with the monthly invoice?

### Takeaway
Model the ledger on FOCUS so it can sit beside the Azure FOCUS export: one fact table of cost lines (one row per run x engine x model x cost type) carrying four cost columns (list, contracted, effective, billed or cash), plus run, task, outcome and human-time tables, and a daily reconciliation table that compares the sum of run estimates with the provider's billing grain (GitHub day x user x model; Azure day x resource tag x meter; Anthropic day x workspace or key x model). FOCUS 1.2 added virtual-currency columns that fit AI credits, 1.3 added allocation columns and a contract commitment dataset that fit partner credits, and 1.4 added billing period and invoice detail datasets; none of these versions has native token columns, and neither GitHub nor Anthropic publishes a FOCUS export, so the factory has to map those sources itself.

### Cited Findings

FOCUS as the reference model
- Microsoft's FOCUS summary: each charge carries list unit price ("what you would pay per unit without any negotiated discounts"), contracted unit price ("after negotiated discounts"), effective unit price ("after prepurchase commitment discounts were applied") and billed unit price ("what was or what gets invoiced"), with matching list, contracted, effective and billed cost columns "which makes it easier to quantify cost savings from negotiated and commitment discounts"; FOCUS uses the billing currency for all prices and costs; `SkuPriceId` identifies the price point. Source: [Microsoft Learn, What is FOCUS](https://learn.microsoft.com/cloud-computing/finops/focus/what-is-focus#benefits)
- FOCUS changelog: v1.2 (announced June 2025) added `PricingCurrency`, `PricingCurrencyContractedUnitPrice`, `PricingCurrencyEffectiveCost`, `PricingCurrencyListUnitPrice`, `BillingAccountType`, `SubAccountType`, `InvoiceId`, and extended `CurrencyFormat` to cover virtual currencies; v1.3 (announced December 2025) added `ServiceProviderName` and `HostProviderName` (deprecating `ProviderName` and `PublisherName`), allocation columns `AllocatedMethodDetails`, `AllocatedMethodId`, `AllocatedResourceId`, `AllocatedResourceName`, `AllocatedTags`, `ContractApplied`, a `ContractCommitment` dataset (12 columns incl. `ContractCommitmentCost`, `ContractCommitmentQuantity`, `ContractId`) and recency metadata (`DatasetInstanceComplete`, `DatasetInstanceLastUpdated`, `RecencyLastUpdated`, `TimeSectorComplete`); v1.4 (announced June 2026) added `BillingPeriod` and `InvoiceDetail` datasets (incl. `InvoiceDetailId`, `PaymentCurrencyBilledCost`), 17 `ContractCommitment` columns (incl. `PricingCurrencyContractCommitmentCost`, `ContractCommitmentLifecycleStatus`), removed `ProviderName` and `PublisherName`, and made `CurrencyFormat` require ISO 4217 codes and drop the virtual-currency allowance (virtual currency moves to the `PricingCurrency*` columns). No AI or token columns in any version. Source: [FOCUS_Spec CHANGELOG on GitHub](https://raw.githubusercontent.com/FinOps-Open-Cost-and-Usage-Spec/FOCUS_Spec/working_draft/CHANGELOG.md)
- [snippet] FOCUS 1.2 was ratified 29 May 2025 and its four new columns "provide requirements for reporting the cost and usage of these credits or tokens that SaaS providers may use to bill"; 1.3 ratified 4 December 2025; 1.4 ratified 4 June 2026 with "two datasets and 47 columns"; secondary coverage says 1.5 is planned to add "provider list pricing and native AI token tracking". Source: [FOCUS specification page](https://focus.finops.org/focus-specification/) [snippet]; [Amnic FOCUS guide 2026](https://amnic.com/blogs/finops-open-cost-and-usage-specification-guide-2026) [secondary]
- Azure FOCUS export: "Cost and usage details (FOCUS)" "combines actual and amortized costs", reduces processing and storage, is not supported at management-group scope, and supports one-time, daily month-to-date and monthly exports; daily exports run twice a day for the first five days of a month because "latent usage and charges are included in the invoice up to 72 hours after the calendar month is closed"; current-period charges "might get rerated" until the invoice closes; Cost Management keeps data at least seven years (13 months in the portal). Source: [Microsoft Learn, Cost Management exports](https://learn.microsoft.com/azure/cost-management-billing/costs/tutorial-improved-exports); [Understand Cost Management data](https://learn.microsoft.com/azure/cost-management-billing/costs/understand-cost-mgt-data#cost-and-usage-data-updates-and-retention)
- No GitHub FOCUS export was found: GitHub offers CSV usage reports (one row per user per model per day, with columns such as `aic_quantity` and `aic_gross_amount` per a docs commit), the AI usage page and the billing REST API; FOCUS mapping has to be built from those. [snippet] Source: [GitHub Docs, prepare for usage-based billing](https://docs.github.com/en/copilot/how-tos/manage-and-track-spending/prepare-for-usage-based-billing); [DX GitHub Copilot billing connector](https://docs.getdx.com/connectors/github-copilot-billing.md)

Source: [Microsoft Learn, Invoicing and chargeback](https://learn.microsoft.com/cloud-computing/finops/framework/manage/invoicing-chargeback)

### Inferences (proposed ledger design)

Grain and keys
- Natural key for a cost line: `(project_id, night_id, run_id, attempt_no, agent_role, engine, model, cost_type)`. `night_id` is the factory's local business date of the night (for example `2026-10-23` for the night starting that evening, Australia/Sydney), stored with `night_start_utc` and `night_end_utc` because provider rows are UTC days and a Sydney night spans two UTC dates.
- `run_id` = one dispatch of one agent role against one task (for example `p042-n20261023-t017-worker-a2`); `task_id` = the backlog item (issue number or spec id); `feature_id` = the client-visible deliverable that may span several tasks.

Tables (all money in AUD with the source currency and FX rate kept; FOCUS-like column names where they exist)
1. `dim_project` (project_id, client, contract_type [fixed, T&M, subscription, outcome], price_basis, github_org, github_cost_centre_id, service_identity_login, azure_subscription_id, azure_resource_group, project_tag, anthropic_workspace_id, openai_project_id, start_date, end_date).
2. `dim_engine_model` (engine [copilot-sdk, copilot-cli, copilot-cloud-agent, copilot-code-review, claude-code, codex-cli], model, provider, list_input_per_mtok, list_cached_input_per_mtok, list_cache_write_per_mtok, list_output_per_mtok, ai_credits_per_mtok_in/out/cache where Copilot, price_effective_from, price_source_url). Snapshot Copilot prices from `models.list` nightly.

Measured versus estimated
- Measured at run (engine-reported): Claude Code tokens and list-price USD; Copilot SDK tokens and AI credits; Codex tokens; wall-clock, retries and exit status from the orchestrator; ACA job duration and allocated vCPU and GiB; GitHub Actions minutes per workflow run (via the Actions API) [inference].
- Measured at billing grain only: GitHub AI credits per identity per model per day; GitHub Actions per repo per workflow per day; Azure cost per tagged resource per day; Claude-in-Foundry CCU per resource per day.
- Estimated: Copilot cloud agent and third-party agents on GitHub (no per-session export), Copilot code review credits (land on a human or org), shared Azure services (split by runtime or tokens), telemetry ingestion (split by event volume), seat amortisation, partner credit shadow value.

Reconciliation method
- Nightly: post provisional cost lines from telemetry at list price; post Azure compute from job runtime x list rate.
- Day +2 or +3: pull GitHub AI usage for each service identity, Azure FOCUS export rows by project tag, Anthropic Cost API by workspace; compute `variance = provider_sum - ledger_sum` per grain key; allocate the variance back to that day's runs pro rata to their list cost (FOCUS-style `AllocatedMethodId = variance_pro_rata`), mark lines reconciled.
- Month close: compare reconciled totals with the GitHub invoice (net) and the Azure invoice including "Azure credits applied"; book the credit as a separate funding line, never as a reduction of list or effective cost.

## Key question 3: How do you give each agent run a stable identity so costs can be joined across GitHub, Azure, Anthropic and OpenAI?

### Takeaway
Use two layers of identity. The billing layer is coarse and must be expressed in each provider's own allocation unit: one seated GitHub machine account per project placed in a project cost centre (because AI credits follow the triggering user and a user sits in only one cost centre), one Azure resource group and tag set per project, one Anthropic workspace and one OpenAI project per client project, with an API key per agent role. The run layer is fine-grained and lives in your own metadata: a factory-minted `run_id` stamped into the engine session id where the engine allows it, OTel resource attributes, the branch name, a commit trailer, PR labels and the ACA job execution environment, so every billing row can be joined down to runs through (identity, day, model) and every run can be joined up to a PR and outcome.

### Inferences (identity design)
- Billing identity per project, role in metadata: one machine account per client project (for example `acme-factory-bot`), seated for Copilot, in cost centre `cc-acme`, with a budget; all SDK, CLI and cloud-agent work for that project authenticates as, or is assigned by, that account. Separate accounts per agent role would give role-level billing rows but multiply seat fees and cost centres; role is cheaper to carry in run metadata and in per-role API keys on Anthropic and OpenAI, where keys are free.
- Cloud agent attribution: assign issues to Copilot through the API using the project machine account's token so the machine account is "the user who triggered" the session and becomes the co-author; this keeps code review credits on that account too. GitHub does not state this explicitly, so verify with one test night against the AI usage report (Gap).
- Avoid GitHub Actions `GITHUB_TOKEN` metering for Copilot CLI when you need project-level rows, unless each project is its own organisation, because that path meters to the organisation and ignores user budgets.
- `run_id` format: `{project}-{yyyymmdd}-{task}-{role}-{attempt}` (for example `acme-20261023-t017-worker-2`), deterministic so retries are countable. Stamp it into: Copilot CLI `--session-id` or `-n` (and the SDK session config); Claude Code `OTEL_RESOURCE_ATTRIBUTES="project.id=acme,night.id=2026-10-23,run.id=...,agent.role=worker,task.id=t017,engine=claude-code"`; Codex `[otel]` resource attributes if supported, else a wrapper that tags the JSONL; branch `factory/acme/2026-10-23/t017-worker-2`; commit trailer `Factory-Run-Id: ...`; PR labels `night:2026-10-23`, `role:worker`, `engine:copilot-sdk`, `factory`; ACA job execution env vars and an execution tag; APIM headers `x-project-id` (metric dimension) and `x-run-id` (logged only).
- Join path: provider billing row (identity or key or resource tag, UTC day, model) -> `dim_project` -> runs of that project on that UTC day and model -> allocate by run list cost; run -> branch and commit trailer -> PR number -> `fact_outcome`. The PR is the hinge between cost and revenue because acceptance, review time and rework all hang off it.
- Human attribution: review and rework minutes need their own capture, for example PR review events from the GitHub API for elapsed time plus a short timesheet code per PR, because API timestamps measure waiting, not effort.

## Key question 4: What should fully loaded cost per accepted feature include?

### Takeaway
Fully loaded cost per accepted feature is the sum, at list or shadow price, of every agent run that touched the feature (including planner, test author, evaluator and reviewer runs, failed attempts and retries), Copilot code review and Actions minutes, Azure sandbox, storage and egress, telemetry ingestion, an amortised share of seats, programme fees and the factory platform, and human triage, review and rework minutes at a loaded hourly rate, plus a share of the cost of features that were attempted and not accepted (the yield adjustment) and a warranty reserve. The public evidence says the human and yield terms usually dominate the token term: review time rises sharply with AI-generated volume and AI-generated PRs merge at far lower rates than human ones.

### Cited Findings
- Unit economics should be "a derivative of activity-based costing" and include "manual processes and steps outside of the cloud"; shared infrastructure is split "with utilization data". Source: [Microsoft Learn, FinOps unit economics](https://learn.microsoft.com/cloud-computing/finops/framework/quantify/unit-economics)
- Role split in a real harness run (Anthropic DAW V2, Opus 4.6 implied): planner 4.7 min, USD 0.46; three build rounds 2 h 7 min (USD 71.08), 1 h 2 min (USD 36.89), 10.9 min (USD 5.88); three QA rounds USD 3.24, 3.09, 4.06; total 3 h 50 min, USD 124.70. Derived: build (worker) about 91% of token cost, QA (evaluator) about 8%, planner under 0.5%; later rounds cost far less than the first. Source: [Anthropic Engineering, Harness design for long-running application development, 24 Mar 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Same post: retro game maker solo run 20 min, USD 9 (broken result) versus full planner-generator-evaluator harness 6 h, USD 200 ("over 20x more expensive") with a playable result, so evaluator and planner runs are a quality cost, not overhead to cut blindly. Source: [Anthropic Engineering, 24 Mar 2026](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- Copilot code review cost bands per review (GitHub estimate): Lite USD 0.05 to 1, Balanced USD 0.25 to 5 (default), plus Actions minutes for agentic context gathering. Source: [GitHub Docs, use code review](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/use-code-review)
- Agent teams "use approximately 7x more tokens than standard sessions when teammates run in plan mode"; background summarisation typically under USD 0.04 per session. Source: [Claude Code docs, manage costs](https://code.claude.com/docs/en/costs)
- [secondary] Faros AI (July 2025, 10,000+ developers, 1,255 teams): high-adoption teams completed about 21% more tasks and merged about 98% more PRs, while PR review time rose about 91%, PR size about 154% and bugs per developer about 9%, with no company-level improvement; the 2026 follow-up (22,000 developers) is reported as median review time up about 5x and 31% more PRs merged with no review. Source: [Augment Code summary of Faros findings](https://www.augmentcode.com/guides/ai-productivity-paradox-engineering-delivery); [Rob Bowley, Aug 2025](https://blog.robbowley.net/2025/08/21/new-research-shows-ai-assisted-coding-isnt-moving-delivery/); [Faros research page](https://faros.ai/research)
- [snippet] LinearB 2026 benchmarks (8,109,244 PRs, 4,813 teams): AI PRs merge within 30 days 32.7% of the time versus 84.4% for unassisted PRs; AI agent PRs wait 17.6 hours before review versus 3.4 hours. Source: [LinearB engineering benchmarks 2026](https://linearb.io/library/engineering-benchmarks-and-research); [LinearB AI in software development](https://linearb.io/library/ai-in-software-development)
- Telemetry, compute and orchestration costs for a small factory are small relative to tokens (about USD 110 to 160 per month infrastructure excluding tokens in the Azure notes, with compute price unverified). Source: see azure_infrastructure_for_agents.md Key question 1 Inferences
- [snippet] SPI 2026 benchmark (2025 data, 509 firms): billable utilisation 66.4% (record low), EBITDA 9.9%, project margin 37.7%, revenue per consultant USD 210K. Source: [Certinia analysis of the 2026 SPI benchmark](https://certinia.com/blog/analyzing-the-2026-spi-research-professional-services-maturity-benchmark-report/); [Rocketlane PS maturity index 2026](https://rocketlane.com/blogs/professional-services-maturity-index-2026); [Diabsolut](https://diabsolut.com/spi-benchmark-2026/)

### Inferences (cost stack and formula)
Cost components per accepted feature F (each at list or shadow price, with cash cost kept alongside):
1. Agent tokens or credits: all runs with `feature_id = F`, every role and attempt (measured or estimated per Key question 1).
2. Review agents: Copilot code review credits (estimate from the Lite or Balanced band or from the human-co-author attribution) and its Actions minutes (`dynamic/agents/copilot-pull-request-reviewer` rows).
3. CI and runners: Actions minutes for CI on the feature's PRs, cloud-agent sessions and `copilot-setup-steps`.
4. Azure sandbox: ACA job vCPU-seconds and GiB-seconds from execution start and end x allocation, storage for artefacts and transcripts, egress, Key Vault and orchestration (DTS) share.
5. Telemetry: Log Analytics and Azure Monitor ingestion split by event count or GB per run.
6. Seats and fixed fees amortised per night: Copilot seats for machine accounts (and the included credit pool), GitHub Enterprise seats, any Claude or Codex subscriptions, the Solutions Partner fee and specialisation upkeep, FinOps hub if used; allocate by nights run or by share of list cost.
7. Platform engineering: hours spent maintaining harness, evals and orchestrator, amortised per accepted feature.
8. Human time: spec writing and triage, review minutes, rework minutes, merge and release, client acceptance, each at a loaded hourly rate = (salary + on-costs such as superannuation, payroll tax, leave, equipment) / productive hours; with SPI-like 66% utilisation the loaded cost per productive hour is roughly 1.5x the raw hourly cost.
9. Yield adjustment: cost of rejected and abandoned tasks in the same project and night, spread over that night's accepted features (cost per accepted feature = total night cost / accepted features, not cost of the successful run alone).
10. Warranty reserve: a percentage of revenue sized from the revert-within-30-days and post-acceptance defect rates, for fixed-price work.

- Formula: `fully_loaded_cost(F) = sum(direct_run_cost_list(F)) + review_agent_cost(F) + ci_cost(F) + azure_alloc(F) + telemetry_alloc(F) + fixed_alloc(night) / accepted(night) + human_minutes(F) x loaded_rate / 60 + yield_alloc(night) + warranty_reserve(F)`.
- Expect the human term to dominate early: at an assumed loaded rate of AUD 150 per hour [assumption], 30 minutes of review and 30 minutes of rework add AUD 150, against token costs in the public examples of USD 7 to 70 per merged feature (Key question 6).

### Gaps
- No public dataset links review minutes per agent PR to dollar cost; Faros and LinearB report elapsed time, not effort.
- GitHub does not expose code review credit consumption per PR, so that line stays estimated.
- No authoritative Australian loaded-rate benchmark for software consultants was researched.

## Key question 5: How should the profitability matrix be structured so a project can be compared across engines and nights, and so pricing stays sound when credits run out?

### Takeaway
Build the matrix on cost at list (shadow) price, not cash: every line carries list, effective and cash cost, and the difference is shown as an explicit "credit subsidy" funding line, so margins are quoted twice (at list and at cash) and prices are set to clear the target margin at list. Partner credits are temporary, expire, are bound to the partner's billing account, are described by Microsoft as "internal-use-rights credits", and may not be usable for client delivery at all (the partner Visual Studio licences explicitly are not), so treating them as free in a price would be both commercially and contractually unsafe. Compare engines on cost per accepted feature and human minutes per accepted feature from controlled replays of the same tasks, and match the commercial model (time and materials, fixed price per feature, capacity subscription, outcome-based) to how certain the scope is.

### Inferences (matrix design and pricing method)
- Fact grain: one row per project x night x engine x model x agent role, rolled up to project x feature and project x month. Measures: tasks attempted, PRs opened, merged first pass, merged after rework, rejected, reverted within 30 days; tokens by type; AI credits; list cost by component (Key question 4); effective cost; cash cost; credit subsidy (list minus cash); human minutes by activity and cost; revenue recognised; margin at list; margin at cash; and the leading indicators in Key question 6.
- Views: (a) project P&L by night (are we making money on this client at list prices?); (b) engine bake-off (same task set replayed on two engines or models with the same harness settings, compared on list cost per accepted feature and human minutes per accepted feature, with sample sizes shown); (c) role cube (planner, test author, worker, evaluator, reviewer cost shares; the one public example, the Anthropic DAW run, had planner under 0.5%, worker about 91% and evaluator about 8%, with no test-author or reviewer role); (d) credit runway (remaining partner and included Copilot credits divided by list burn per night, with expiry dates); (e) reconciliation status (provisional versus final lines).
- Shadow price rules: GitHub AI credits at USD 0.01 per credit regardless of whether they came from the included pool, partner credits or cash; seats at list; Azure at retail pay-as-you-go from the FOCUS `ListCost` (sponsorship-type credits are 100% discounts on retail rates, per the billing notes); Claude or OpenAI at list per million tokens via `dim_engine_model`. Credit drawdown is posted as a separate negative "vendor funding" line so the P&L shows both margins without hiding the subsidy.
- Price floor per feature (fixed price): `price >= (expected list cost per accepted feature incl. human time, yield and warranty) / (1 - target gross margin)`, with expected cost taken as a high percentile (for example P80) of the matrix, not the mean, because the Insight spread (USD 7 to 70 for one feature) and harness sensitivity (2.5x) make the distribution wide.
- Commercial model by scope certainty: well-specified backlog items with test oracles suit fixed price per feature or per accepted PR; open-ended discovery suits time and materials (repriced as a "pod" day rate that bundles factory capacity); steady maintenance and test backfill suit a monthly capacity subscription (N accepted changes per month, unused capacity not refunded); outcome-based fees only where the outcome is measurable by the client (for example a migration completed with tests green), with a variable-consideration clause.
- Credits run out: if the matrix shows margin at list below target on any project, that project is only profitable because of subsidy; do not renew its price on those terms. Because partner credits may be restricted to internal use, confirm in the Terms of Participation Guide whether client delivery may draw on them; if not, run client work on a cash-paid subscription and keep credits for internal R&D, demos and the factory's own tooling, and the shadow price becomes the real price.

## Key question 6: What unit cost and price bands exist in the public data, and which leading indicators predict margin?

### Takeaway
Public token-only costs range from under a dollar for a scoped change to USD 7 to 70 per merged feature, about USD 125 to 200 for a multi-hour planner-worker-evaluator application build, and USD 20,000 for a two-week, 16-agent, 100,000-line compiler; interactive developer use averages about USD 13 per active day. These are list-price token costs only, almost never include human review, CI or rework, and are computed from tokens x list price rather than invoices. The indicators that move margin most are first-pass merge rate (because cost per accepted feature is cost per attempt divided by yield), retries or rounds per task, human review and rework minutes per PR, PR size, harness and model settings (effort, team mode, caching) and budget-cap hit rate.

### Inferences
- Indicative bands for planning (token or credit cost at list, before human time): small scoped change USD 0.50 to 5; single feature merged USD 7 to 70; multi-hour multi-agent build of a small app USD 100 to 200; per agent-hour USD 8 to 35 depending on model and harness. Treat these as wide priors and replace them with the factory's own P50 and P80 after about four weeks of nights.
- Margin model: `cost_per_accepted = (cost_per_attempt x attempts_per_task + human_cost_per_task) / first_pass_or_eventual_yield`. Halving yield doubles cost per accepted feature; this is why LinearB-style merge rates matter more than token prices.
- Dashboard indicators to track nightly, with suggested alert thresholds to tune locally: first-pass integration rate (share of tasks merged without human-requested changes); eventual acceptance rate; retries or rounds per task; review minutes per PR and rework minutes per PR; PR size (lines changed); evaluator rejection rate; budget-cap hit rate (`error_max_budget_usd` results, Copilot `session_limits_exhausted`); cache read share; cost per accepted feature P50 and P80 by engine; revert-within-30-days rate; credit runway in nights.
- Pricing bands: no reliable public price per agent-built feature was found; the anchors available are T&M rates (USD 150 to 280 per hour senior in the US, marketing-grade), Devin's agent-hour price (about USD 8 to 9), GitHub's per-review estimates and consultancy shifts to fixed price (Infosys 54%) and outcome pricing (IDC 30% by 2029). A defensible fixed price per feature is therefore cost-plus from the factory's own matrix, cross-checked against the client's hand-coded alternative (value-based ceiling).

### Gaps
- No public figure ties token cost to accepted client features in a services context, and none includes human review cost.
- HumanLayer, Ramp Labs, GitHub Copilot ROI and Cursor per-PR figures were not found or could not be read; Faros 2026 numbers are second-hand and inconsistent across summaries.
- The Anthropic posts do not say whether reported costs are list-price estimates from Claude Code or invoiced amounts.
