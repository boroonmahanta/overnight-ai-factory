Scope: GitHub platform features only (Actions, rulesets, merge queue, environments, Issues, Projects, APIs, reporting, GitHub Models, Codespaces, enterprise policies and cost attribution). ## Key question 1: Can Actions alone orchestrate the night (schedule start, dispatch N agent tasks, wait, re-gate, serial merge via merge queue, morning summary), and where does it break?

### Takeaway
Yes, almost entirely, provided the night is built as **short event-driven workflows plus a stateless reconciler**, not as one long supervisor job: a scheduled (time-zone aware) kickoff reads a queue of labelled issues, a matrix job assigns each issue to Copilot via the REST or GraphQL assignment API, PR and `merge_group` events re-gate each result, a merge queue serialises integration, environments with required reviewers hold human approval points for up to 30 days without consuming minutes, and a scheduled morning workflow builds the report from the REST API, writes a job summary and posts to a Teams Workflows webhook. It breaks at: the 6 hour job cap on GitHub-hosted runners (5 days self-hosted), the **user-token requirement for starting Copilot tasks** (installation tokens and `GITHUB_TOKEN` are refused), `GITHUB_TOKEN` not triggering downstream workflows and not reaching Projects, Copilot PRs needing "Approve and run workflows" by default, best-effort `schedule` timing (delays and dropped runs at the top of the hour), one-running-run-per-concurrency-group semantics (queue of 100), three-level `workflow_run` chains, secondary rate limits on content creation (80 per minute, 500 per hour), and, since 1 Oct 2026, retention policies that now delete checks and workflow runs after the configured period, so evidence must be exported.

### Cited Findings

**Hard limits for a 6 to 10 hour run (docs as of 23 Oct 2026)**
- Workflow run time: 35 days per run, including waiting and approval time; cannot be raised. Gate approval time: a workflow may wait up to 30 days on environment approvals. Job matrix: 256 jobs per workflow run (GitHub-hosted and self-hosted). Re-runs: 50 per run (raisable by support). Workflow file: 500 KB. Check runs: 50,000 per check suite. Source: [Actions limits](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/limits)
- Job execution time: **6 hours on all GitHub-hosted runners** (not raisable); **5 days on self-hosted runners**; self-hosted job queue time 24 hours before automatic cancellation. Source: [Actions limits](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/limits)
- `jobs.<job_id>.timeout-minutes` defaults to 360; step `timeout-minutes` maximum 360 for both GitHub-hosted and self-hosted. `GITHUB_TOKEN` expires when the job finishes or after 24 hours, so on self-hosted runners the token can be the limiting factor beyond 24 hours. Source: [Workflow syntax](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/workflow-syntax)
- Queueing: 1,500 triggering events per 10 seconds per repository; 500 workflow runs queued per 10 seconds (a run with 30 reusable workflows counts as 1); concurrency group queue up to 100 runs with `queue: max`. Source: [Actions limits](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/limits)
- Concurrency on GitHub-hosted runners: Enterprise plan 500 concurrent standard jobs (50 macOS); larger runners 1,000 (50 macOS, 100 GPU); raisable by support. Self-hosted: 10,000 runners per runner group; 1,500 runner registrations per 5 minutes. Source: [Actions limits](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/limits)
- Cache: 200 uploads, 1,500 downloads and 400 deletes per minute per repository; 10 GB per repository included, entries unused for 7 days are evicted, limit configurable upward (billed). Source: [Actions limits](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/limits); [Dependency caching reference](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/dependency-caching)

**Starting the night: `schedule`, `workflow_dispatch`, `repository_dispatch`**
- `schedule` uses POSIX cron, runs on the latest commit of the default branch, shortest interval every 5 minutes, and now accepts an optional IANA `timezone` (for example `Australia/Sydney`); during DST spring-forward, runs in skipped hours advance to the next valid time. Flag `actions-schedule-timezone` is on for GHEC. Source: [Events that trigger workflows: schedule](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- "The `schedule` event can be delayed during periods of high loads ... High load times include the start of every hour. If the load is sufficiently high enough, some queued jobs may be dropped." Schedule at an odd minute. Source: [Events that trigger workflows: schedule](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- On EMU enterprises, a scheduled workflow only runs if its `actor` (the last user to change the cron line) is an active account; a deprovisioned actor stops the schedule. Notifications for schedule failures go to that user. Source: [Events that trigger workflows: schedule](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- `workflow_dispatch` accepts up to 25 inputs on GHEC (types include choice, boolean, environment); runnable via API or `gh workflow run`. Source: [Manually run a workflow](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/manage-workflow-runs/manually-run-a-workflow); [Events that trigger workflows](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- `repository_dispatch`: `event_type` up to 100 characters; `client_payload` at most 10 top-level properties and 65,535 characters; runs on the default branch. This is the hook for an external (Azure) scheduler or for agents signalling completion. Source: [Events that trigger workflows: repository_dispatch](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/events-that-trigger-workflows)

**Chaining and fan-out**
- `workflow_run` cannot chain more than three levels (A to B to C to D; E and F never run); it fires regardless of the upstream conclusion (filter on `github.event.workflow_run.conclusion`) and the downstream run gets secrets and a write token even if the upstream did not. Source: [Events that trigger workflows: workflow_run](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- Reusable workflows: up to ten levels of nesting and up to 50 unique reusable workflows per workflow file on GHEC; billing always goes to the caller, and runner assignment uses only the caller's context. Source: [Reuse workflows](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/reuse-automations/reuse-workflows); [Reusing workflow configurations](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/reusing-workflow-configurations); [Actions billing and usage](https://docs.github.com/en/enterprise-cloud@latest/actions/concepts/billing-and-usage)
- Events caused by `GITHUB_TOKEN` do not start new workflow runs, except `workflow_dispatch` and `repository_dispatch`; PRs created or updated with `GITHUB_TOKEN` now create `pull_request` runs in an approval-required state (rolling out on github.com, flag on for GHEC). Source: [GITHUB_TOKEN](https://docs.github.com/en/enterprise-cloud@latest/actions/concepts/security/github_token); [Trigger a workflow](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)

**Concurrency (serialising work inside Actions)**
- A concurrency group allows at most one running job or run. Default `queue: single` keeps at most one pending (newer pending cancels older); `queue: max` allows up to 100 pending, FIFO by the time each started waiting ("ordering is not guaranteed"); `queue: max` cannot be combined with `cancel-in-progress: true`. Group names are case-insensitive. Source: [Control workflow concurrency](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency); [Concurrency concepts](https://docs.github.com/en/enterprise-cloud@latest/actions/concepts/workflows-and-actions/concurrency)
- Changelog dated 7 May 2026 announced larger concurrency queues (`queue: max`, up to 100). [snippet] Source: [GitHub changelog 2026-05-07](https://github.blog/changelog/2026-05-07-github-actions-concurrency-groups-now-allow-larger-queues)
- A REST API now exposes concurrency group state: `GET /repos/{owner}/{repo}/actions/concurrency_groups` and `/actions/concurrency_groups/{concurrency_group_name}`. Source: [REST: Actions concurrency groups](https://docs.github.com/en/enterprise-cloud@latest/rest/actions/concurrency-groups) (schema read from the GHEC OpenAPI description, [github/rest-api-description](https://raw.githubusercontent.com/github/rest-api-description/main/descriptions/ghec/ghec.yaml))

**Merge queue (serial integration)**
- Requires `merge_group` trigger on every workflow that reports a required check (and on organisation ruleset workflows); otherwise the queue never gets the check and the merge fails. Third-party CI must build branches prefixed `gh-readonly-queue/{base_branch}`. Source: [Managing a merge queue](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue); [Events that trigger workflows: merge_group](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- Settings: merge method; build concurrency 1 to 100 (`0` pauses dispatching `merge_group.checks_requested`); minimum and maximum group size 1 to 100 with a wait time to reach the minimum; "Only merge non-failing pull requests" (or allow a failed entry if the group head passes); status check timeout after which unreported checks count as failed. Each queued PR is tested on a temporary branch containing the base plus every PR ahead of it; a failure removes that PR and rebuilds the ones behind it; jumping the queue forces a full rebuild of in-progress entries. Removal reasons: failing CI, timeout, API or UI removal, unresolvable branch protection failure. Source: [Managing a merge queue](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue); [Available rules for rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
- Merge queue on private repositories needs GHEC; "Require merge queue" is a repository-level ruleset rule only (not available in organisation rulesets); cannot be used with branch protection patterns containing `*`. Source: [Managing a merge queue](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue); [Available rules for rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
- Programmatic enqueue: `gh pr merge` adds to the queue if checks passed, otherwise enables auto-merge; GraphQL `enqueuePullRequest` adds only if possible right now and otherwise errors. "Merge when ready" enables auto-merge even if "Allow auto-merge" is off. Source: [Merging a pull request with a merge queue](https://docs.github.com/en/enterprise-cloud@latest/pull-requests/how-tos/merge-and-close-pull-requests/merging-a-pull-request-with-a-merge-queue)

- REST primary limits: `GITHUB_TOKEN` 1,000 requests per hour per repository, or **15,000 per hour per repository for resources belonging to a GHEC account**; GitHub App installation on GHEC 15,000 per hour; PAT or user token 5,000 per hour (15,000 when made through an app owned by a GHEC org, but sharing the user's budget). Source: [Rate limits for the REST API](https://docs.github.com/en/enterprise-cloud@latest/rest/using-the-rest-api/rate-limits-for-the-rest-api)
- GraphQL: `GITHUB_TOKEN` 1,000 points per hour per repository (15,000 for enterprise-owned resources); GitHub App installation on GHEC 10,000 points per hour; users 5,000 (10,000 via GHEC-owned apps). Source: [Rate limits and query limits for the GraphQL API](https://docs.github.com/en/enterprise-cloud@latest/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)

**Workflow execution protections (new Actions policies)**
- Enterprise, organisation and repository "Actions policies" (separate from General settings) currently contain workflow execution protections: actor rules (users, roles, GitHub Apps, Copilot, Dependabot) and event rules (`push`, `pull_request`, `pull_request_target`, `workflow_dispatch` and so on), targeting repositories by visibility, deployment status or custom property, and scoping to workflow paths; Evaluate mode on GHEC with "Policy insights"; optional "Require lockfile" for pinned action dependencies. Disallowed runs fail with an error such as "Event 'workflow_dispatch' is not allowed to trigger Actions workflows". Source: [About Actions policies](https://docs.github.com/en/enterprise-cloud@latest/actions/concepts/about-actions-policies); [Control workflow execution](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/administer/control-workflow-execution)

### Inferences
- **Recommended Actions-native shape of a night** (synthesis):
  1. `night-kickoff.yml`: `schedule: - cron: '47 21 * * 0-4'` with `timezone: Australia/Sydney` (odd minute, off the hour), plus `workflow_dispatch` as a manual or external backup trigger. One short job queries issues labelled `factory:ready` whose blockers are closed (issue dependencies) and orders them by a Project or issue field; it emits a JSON matrix.
  2. `dispatch` job: `strategy.matrix` from that JSON (at most 256 entries; use `max-parallel` to cap concurrent agent sessions), runs in an environment `factory-dispatch` whose secret is a service-account user token (needed because the Copilot APIs refuse installation tokens), and calls the assignee endpoint with `agent_assignment`. Each call is a content-creating write, so 40 tasks is far under the 80 per minute and 500 per hour secondary limits, but labelling and commenting from many jobs at once can approach them.
  3. Re-gating is event-driven, not polled: required CI on `pull_request` and `merge_group` (repository workflows plus organisation ruleset workflows); turn on "allow workflows to run automatically" for Copilot PRs or nothing will run before morning.
  4. A reconciler `night-tick.yml` every 15 to 30 minutes (odd minute) reads state (open Copilot PRs, check conclusions, `/agents/repos/{owner}/{repo}/tasks` states) and acts: re-label, retry, enqueue passing PRs. It is stateless, so a delayed or dropped tick costs only latency. A free "sleep" is available via an environment with a wait timer, which is not billed.
  5. Serial integration: because Copilot cannot approve or merge and approvals are required on `main`, the overnight merge queue should target an **integration branch** with no approval requirement but strict required checks, enqueued by a GitHub App; a single morning PR from integration to `main` carries the human approval. Alternatively, leave PRs approved-pending and let humans approve in the morning so the merge queue drains on `main` after 07:00.
  6. `night-report.yml` at about 06:41 local: GraphQL/REST queries (PRs by `copilot-swe-agent` since kickoff, check-run conclusions and annotations, merge queue entries, agent task states, workflow run durations from job `started_at`/`completed_at`), a Markdown job summary (under 1 MiB per step), an artifact with JSON evidence (retention set to 400 days), a short Copilot CLI summary step (since GitHub Models is retired), and a POST of an Adaptive Card to a Teams Workflows webhook URL stored as a secret.
- **Where Actions alone stops being enough**: a single supervising process that holds state for 10 hours (6 hour cap on hosted runners); anything that must call Copilot APIs as a person in a CAP-protected EMU tenant (needs a CAP-exempt service account); exact start-time guarantees (use an external timer such as an Azure Logic App calling `workflow_dispatch` if 06:00 must mean 06:00); and long-term evidence (export to Azure Blob via audit log streaming plus artifact copies, given the new retention behaviour).
- Polling cost is the main hidden minutes drain: a GitHub-hosted job that sleeps while polling is billed per minute and capped at 6 hours, whereas environment wait timers and approval waits are free and event triggers cost nothing until they fire.

### Gaps
- No official statement of typical `schedule` delay magnitude; practitioner figures are in KQ5 and are [snippet] quality.
- Not verified whether a job waiting on required environment reviewers can exceed its own `timeout-minutes` (docs give only the 30 day gate limit).
- Docs did not state whether the "Approve and run workflows" requirement for Copilot PRs can be set at organisation level or only per repository.
- Exact daily cap on Copilot task creation per user was not found in GitHub platform docs (sibling notes cover Copilot usage limits).


## Key question 2: Which rules guarantee the agent can never merge its own work to main, and that the acceptance test directory cannot be changed by the agent? Name the exact ruleset settings.

### Takeaway
No single switch does it; the guarantee is a stack of four layers, all native: (1) a **branch ruleset on `main`** with "Restrict deletions", "Block force pushes", "Require a pull request before merging" (required approvals >= 1, "Dismiss stale pull request approvals when new commits are pushed", "Require review from Code Owners", "Require approval of the most recent reviewable push", the default-on "Require an additional approval for unattributed Copilot pull requests", plus a path-scoped **Required reviewers** entry for `tests/acceptance/**`), "Require status checks to pass" with the expected source app pinned, and "Require merge queue"; (2) a **push ruleset** with "Restrict file paths" on `tests/acceptance/**` (and on `.github/workflows/**`, `.github/hooks/**`, `CODEOWNERS`) whose bypass list holds only the named test-owner team; (3) **organisation or enterprise ruleset workflows** ("Require workflows to pass before merging") so the gate workflow lives in a central repository the agent cannot edit; (4) a **bypass list that never contains** Copilot cloud agent, the write role, or the automation's GitHub App. Copilot's own built-in limits (cannot approve, merge, or mark ready for review; initiator cannot approve) sit on top but are product behaviour, not configuration.

### Cited Findings

**Rulesets basics (docs as of 23 Oct 2026)**
- Up to 75 rulesets per repository and 75 organisation-wide rulesets; Enterprise plan can set rulesets at enterprise or organisation level targeting many repositories; rulesets are visible to anyone with read access. Source: [About rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
- Rulesets have no priority: all rulesets targeting a branch plus any classic branch protection are aggregated and the most restrictive version of each rule applies. Source: [About rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
- Enforcement statuses: Active, Evaluate (not enforced; violations shown on "Rule Insights"; Enterprise), Disabled. Useful for dry-running factory rules. Source: [About rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
- Bypass-eligible actors: repository admins, organisation owners, enterprise owners; maintain or write role (or custom roles based on write); teams (not secret teams); enterprise teams, enterprise apps and enterprise roles (public preview); GitHub Apps; Dependabot; and, on GHEC, **Copilot cloud agent**. Each bypass actor can be set to "Always allow" or "For pull requests only" (actor must open a PR and may then bypass and merge it). Source: [Creating rulesets for a repository](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository)
- If a ruleset is incompatible with Copilot cloud agent (for example, a rule allowing only specific commit authors), access to the agent is blocked, and docs suggest adding Copilot as a bypass actor to restore access. For a factory this is the trap to avoid: a Copilot bypass entry on a `main` ruleset would let the agent's work skip the gate. Source: [GitHub Copilot on GitHub: repository compatibility](https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/copilot-surfaces/copilot-on-github)

**Branch ruleset rules relevant to "never merge its own work"**
- "Restrict updates": only users with bypass permission can push to matching branches. "Restrict creations" and "Restrict deletions" are analogous ("Restrict deletions" selected by default). "Block force pushes" is enabled by default. Source: [Available rules for rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
- "Require a pull request before merging" additional settings: required approvals count (reviewers with write permission); "dismiss stale pull request approvals when commits are pushed"; "require review from Code Owners"; restrict who can dismiss reviews; "require an approval from someone other than the last person to push" (most recent reviewable push); require conversation resolution; restrict allowed merge method. Source: [Available rules for rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
- "Require an additional approval for unattributed Copilot pull requests" (public preview) is on by default for new and existing rulesets: when Copilot opens a PR under its own app identity (for example from a Teams or Slack thread), the ruleset requires one more approval than configured; no effect if zero approvals are required; with "approval from someone other than the last person to push", at least one approval must cover the last push and come from someone other than Copilot. Always applies for classic branch protection. Source: [Available rules for rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets); [Risks and mitigations for Copilot cloud agent](https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations)
- **Required reviewers** (path-scoped team approvals in a ruleset): up to 15 teams, each with 0 to 10 required approvals and a `.gitignore`-style file pattern list (with `!` negation); team needs write permission. This gives "changes under `tests/acceptance/**` need 1 approval from @org/acceptance-owners" without relying on CODEOWNERS. Feature flag shows GHEC available (GHES from 3.24). Source: [Available rules for rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
- "Require status checks to pass": checks can be pinned to an expected source GitHub App (must have `statuses:write`, must have recently submitted a check run); if any other person or integration sets the status, merging is blocked. "Strict" mode (require branch up to date) is the default. "Any person or integration with write permissions to a repository can set the state of any status check", which is why pinning the source matters for agents. Source: [Available rules for rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
- Other merge gates available as ruleset rules: "Require deployments to succeed before merging" (repo-level only), "Require signed commits", "Require linear history", "Require secret scanning alerts are resolved" (public preview), "Require code scanning results", "Require code quality results", "Require license compliance results", "Restrict code coverage" (public preview; minimum line coverage percentage and maximum drop vs default branch). Source: [Available rules for rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
- Metadata restrictions (Enterprise): regex on commit message, author or committer email, branch and tag names; a non-conforming push does not update the ref. Could enforce, for example, that every commit on `main` references an issue number. Source: [Available rules for rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)

**Push rulesets (protect `tests/acceptance/**`)**
- Push rulesets block pushes to a private or internal repository and its entire fork network based on file paths, path length, extensions and size; they need no branch targeting because they apply to every push. Source: [About rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
- "Restrict file paths": prevents commits that include changes in specified paths from being pushed; up to 200 entries, each up to 200 characters, `fnmatch` syntax (example `test/demo/**/*`). Allowed exceptions supported (GHEC). Source: [Available rules for rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
- Bypass for push rulesets is inherited by the whole fork network; delegated bypass (GHEC) lets contributors request bypass, approved by a designated reviewer list. Source: [Creating rulesets for a repository](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository); [About rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets)
- Copilot cloud agent can push only to its own `copilot/` branch (or the PR branch it was asked to work on), cannot run `git push` directly, and "is also subject to any branch protections and required checks for the working repository". Source: [Risks and mitigations for Copilot cloud agent](https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations)

**Organisation and enterprise ruleset workflows (gate the agent cannot edit)**
- "Require workflows to pass before merging" can be set at organisation or enterprise level (enterprise flag on GHEC); the workflow file lives in a source repository chosen in org settings, visibility must match the targets; ruleset workflows run only on `pull_request`, `pull_request_target` and `merge_group` with default activity types, and all filters (`branches`, `paths`, `types`) are ignored. Most CodeQL actions cannot be used inside ruleset workflows (only `upload-sarif`). Applying the rule blocks direct pushes, so target only PR-only branches. Source: [Available rules for rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)
- For `pull_request` events the run uses the PR merge commit (`refs/pull/N/merge`), meaning the workflow definition comes from the PR's own content. Source: [Events that trigger workflows](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/events-that-trigger-workflows)

**CODEOWNERS**
- `CODEOWNERS` in `.github/`, root or `docs/` (searched in that order); must be under 3 MB; owners (users or teams) need explicit write access; "Require review from Code Owners" makes any owned path need an owner's approval, and any one owner suffices. Source: [About code owners](https://docs.github.com/en/enterprise-cloud@latest/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners); [Available rules for rulesets](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets)

**Copilot-specific built-in limits (product behaviour, cross-reference only)**
- Copilot cloud agent creates draft PRs that must be reviewed and merged by a human; it cannot mark PRs "Ready for review", cannot approve or merge; the user who asked Copilot to create a PR cannot approve it; for Copilot automations, work is attributed to the automation's creator who likewise cannot approve. By default Actions workflows do not run on Copilot's PRs until a user with write access clicks "Approve and run workflows" (configurable to run automatically). Copilot code review approvals do not count toward required approvals by default. Source: [Risks and mitigations for Copilot cloud agent](https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations); [About Copilot code review](https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/code-review)
- `GITHUB_TOKEN`-created or updated PRs now create `pull_request` runs in an "approval-required" state that a user with write access must approve (rolling out on github.com; flag shows GHEC). Source: [Triggering a workflow from a workflow (reusable)](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)

**Environments as human approval points (deployment gates)**
- Required reviewers: up to six users or teams; only one needs to approve; optional "Prevent self-review" so the user who initiated the deployment cannot approve it even if listed; "Allow administrators to bypass" can be turned off; environment secrets are released only after approval. Wait timer: 1 to 43,200 minutes (30 days), not billed. Up to 6 custom (GitHub App) deployment protection rules per environment (public preview). Source: [Deployments and environments](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/deployments-and-environments)

### Inferences
- Recommended concrete stack for the factory repository (my synthesis of the cited rules):
  1. Branch ruleset "main-gate", target `~DEFAULT_BRANCH`, Active, bypass list empty (or only an org-owner break-glass team set to "For pull requests only"): Restrict deletions; Block force pushes; Require linear history; Require a pull request before merging with Required approvals = 1, Dismiss stale approvals = on, Require review from Code Owners = on, Require approval of the most recent reviewable push = on, Require conversation resolution = on, Additional approval for unattributed Copilot PRs = on (default), Required reviewers = `@org/acceptance-owners` x1 on `tests/acceptance/**`; Require status checks to pass (strict) with each check pinned to the GitHub Actions app (or your own checks app); Require code scanning results; Require merge queue.
  2. Push ruleset "protected-paths": Restrict file paths = `tests/acceptance/**`, `.github/workflows/**`, `.github/hooks/**`, `.github/agents/**`, `.github/CODEOWNERS`, `.github/copilot-instructions.md`; bypass = `@org/acceptance-owners` (and a platform team for the workflow paths) only. This stops the agent even creating a commit on its own branch that touches those paths, so it cannot weaken tests or rewrite the gate workflow in its PR.
  3. Organisation ruleset "factory-required-workflows" targeting repositories by custom property (for example `factory=enabled`): Require workflows to pass before merging, pointing at `org/factory-gates/.github/workflows/acceptance.yml@<sha or tag>`. Because that file is not in the agent's repository, its PR cannot alter the gate.
  4. Never add "Copilot cloud agent", "Write role" or the dispatcher GitHub App to any bypass list. Audit this nightly with `GET /repos/{owner}/{repo}/rulesets` (see KQ4 notes on APIs).
- The merge itself is then performed by the merge queue after a human (or a human-owned approval) has approved; the agent has no path to `main` because it cannot approve, cannot satisfy the "someone other than last pusher" rule, and has no bypass.
- Caution: "Required approvals" can be satisfied by any human with write access, including someone approving quickly in the morning. A second human gate on risky changes is best expressed as a Required reviewers team rule, not as more approvals.

### Gaps
- Docs do not say explicitly whether a push ruleset evaluates the merge commit that the merge queue creates on `main` when an allowed team member's PR changes `tests/acceptance/**`; test in Evaluate mode before relying on it.
- No source found stating whether "Required reviewers" (path-scoped) is GA or preview on GHEC as of 24 Oct 2026; the docs page carries no preview banner for it, while the unattributed-Copilot approval rule and code coverage rule are marked public preview.
- Not verified whether a ruleset workflow pinned to a tag versus a SHA is configurable via UI only or also via REST; check `POST /orgs/{org}/rulesets` schema before automating.

## Key question 3: What is the cheapest way to run heavy steps (Playwright, builds) within included minutes, and when do self-hosted Azure runners become the better choice?

### Takeaway
Run heavy steps on **standard GitHub-hosted Linux runners** (2-core x64 at USD 0.006 per minute, 2-core arm64 at USD 0.005, 1-core slim at USD 0.002), because only standard runners draw on the GHEC allowance of 50,000 minutes per month and overage is cheap; larger runners are always billed, never use included minutes, and are the only GitHub-hosted runners that can join an Azure VNET. Self-hosted runners are free of GitHub charges (docs as of 23 Oct 2026; a USD 0.002 per minute platform fee announced for March 2026 was postponed) and become the better choice when a job needs more than 6 hours, private Azure network access without larger-runner prices, Docker or GPU, warm multi-GB caches, more than 500 concurrent jobs, or when the night's minutes would routinely exceed the included pool by a wide margin. Codespaces is a poor headless worker sandbox: no included quota for organisations, USD 0.18 per hour for 2 cores, 12 hour hard lifetime, idle timeout 5 to 240 minutes.

### Inferences
- Illustrative minutes budget (my arithmetic, not a GitHub figure): 30 tasks a night, each a Copilot session of about 35 minutes on a standard Linux runner (about 1,050 minutes), plus Playwright CI of about 15 minutes run twice per PR (PR event plus `merge_group`, about 900 minutes), plus small orchestration jobs, is roughly 2,000 standard minutes a night, or about 40,000 over 20 nights. That sits inside the 50,000 included minutes only if nothing else in the enterprise uses them; every 10,000 minutes of overage on Linux 2-core costs about USD 60, so overage, not self-hosting, is the cheap pressure valve.
- Sharding Playwright across a matrix does not reduce minutes (it adds per-job setup and per-job rounding) but cuts wall-clock time; use it to keep each PR's gate inside the merge queue's status check timeout, not to save money.
- Avoid billing traps: running the full suite on both `pull_request` and `merge_group` doubles cost; consider a fast PR check and the full suite only on `merge_group`, which is what actually guards `main`. Keep Playwright browsers in `actions/cache` (nightly use keeps entries inside the 7 day window).
- Self-hosted Azure runners (ACA jobs or AKS with ARC, costed in the sibling Azure notes) win when: a step needs more than 6 hours; jobs must reach private Azure resources and the alternative is larger runners at USD 0.012+ per minute plus VNET; Docker-in-Docker, GPUs or very large caches are needed; or monthly standard-runner overage would exceed the Azure compute cost. Use ephemeral JIT or ARC runners, restricted runner groups, and never attach them to public repositories.
- Codespaces is useful for the morning human review (prebuilt environment for the reviewer), not for overnight agents. Its compute price is not the obstacle (2-core USD 0.18 per hour, against USD 0.36 per hour for 60 overage minutes on a Linux 2-core Actions runner); the obstacles are no included quota for organisations (Actions has 50,000 included minutes), the 12 hour hard lifetime, idle shutdown, and the lack of an event-driven job model, check runs and per-job isolation that Actions provides.

### Gaps
- Docs do not state precisely how Windows or macOS minutes draw down the 50,000 included minutes now that the dashboard shows spend in dollars ("minute multipliers" page now redirects to per-minute prices); treat the included pool as safe only for Linux standard runners until confirmed.
- No GitHub-published guidance on runner queue time targets or SLAs for hosted runners; incident history is in KQ5.
- The status of the postponed self-hosted platform fee after mid-2026 could not be confirmed from an official GitHub source (github.blog blocked).

## Key question 4: How do you attribute Actions minutes, runner cost and Copilot usage to a project (repository, cost centre, custom properties), with API endpoints and field names?

### Takeaway
Make each project a **cost centre** that contains the project's **repositories** (Actions, Codespaces, Packages and LFS are charged to the repository or organisation where usage happens) and the project's **service-account user** (AI credits for Copilot are charged to the user who triggered them, with priority over the organisation), optionally linked to its own Azure subscription; then pull daily figures from `GET /enterprises/{enterprise}/settings/billing/usage` (filter `cost_center_id`) and `/usage/summary` (filters `organization`, `repository`, `product`, `sku`, `cost_center_id`), and generate per-workflow detail with `POST /enterprises/{enterprise}/settings/billing/reports` (`report_type: detailed`), whose rows add `username` and `workflow_path`. Repository **custom properties** (for example `project=metro-map`) are not a billing dimension, but they drive organisation rulesets, Actions policies and, new in 2026, `repo_property_*` claims in Actions OIDC tokens, which lets self-hosted runner and Azure-side costs be tagged and authorised by project.

### Cited Findings
- Cost centre allocation by product: Actions charged to the cost centre containing "the repository or organization where the workflow runs"; Codespaces "the repository or organization where the codespace is created"; Packages the owning repository or organisation; Git LFS the repository or organisation; AI credits "the user who triggered AI credit usage (priority), or the organization that granted the user's Copilot license"; Copilot and GHE licences the licensed user (priority) or billing organisation. Source: [Cost center allocation](https://docs.github.com/en/enterprise-cloud@latest/billing/reference/cost-center-allocation); [Cost centers](https://docs.github.com/en/enterprise-cloud@latest/billing/concepts/cost-centers)
- Cost centres contain users, repositories, organisations and enterprise teams (direct user assignment beats enterprise-team assignment; with multiple teams, the earliest-created team wins); an Azure subscription can be attached to bill a cost centre to a different Azure subscription than the enterprise default (UI only). Limits: 1,000 active cost centres per enterprise, 25,000 resources per cost centre, 50 resources added or removed per call. Cost centres apply only to metered usage. Deleting a cost centre sends future usage to the enterprise; membership changes apply to future usage only. Source: [Cost centers](https://docs.github.com/en/enterprise-cloud@latest/billing/concepts/cost-centers); [Cost center allocation](https://docs.github.com/en/enterprise-cloud@latest/billing/reference/cost-center-allocation)
- `POST /enterprises/{enterprise}/settings/billing/cost-centers/{cost_center_id}/resource` body fields: `users`, `organizations`, `repositories`, `enterprise_teams`; callable by a GitHub App installed on the enterprise with write access to enterprise billing. Other endpoints: `GET/POST /enterprises/{enterprise}/settings/billing/cost-centers`, `/cost-centers/{cost_center_id}`, `/budgets`, `/budgets/{budget_id}`, `/budgets/{budget_id}/user-states`. Source: [REST: Cost centers](https://docs.github.com/en/enterprise-cloud@latest/rest/billing/cost-centers) (from the GHEC OpenAPI description)
- `GET /enterprises/{enterprise}/settings/billing/usage` (params `year`, `month`, `day`, `cost_center_id`; default returns usage without a cost centre) returns `usageItems[]` with `date`, `product`, `sku`, `quantity`, `unitType`, `pricePerUnit`, `grossAmount`, `discountAmount`, `netAmount`, `organizationName`, `repositoryName`. `GET .../usage/summary` adds filters `organization`, `repository`, `product`, `sku`, `cost_center_id`. Both are enhanced billing platform only and callable by an enterprise-installed GitHub App with billing read. AI-credit endpoint: `GET .../settings/billing/ai_credit/usage` (and legacy `premium_request/usage`). Source: [REST: Billing usage](https://docs.github.com/en/enterprise-cloud@latest/rest/billing/usage) (from the GHEC OpenAPI description)
- Report exports: `POST /enterprises/{enterprise}/settings/billing/reports` with `report_type` in `detailed`, `summarized`, `premium_request`, `ai_credit`, plus `start_date`, optional `end_date`, `send_email`; `GET .../reports` and `.../reports/{report_id}` to fetch. Source: [REST: Usage reports](https://docs.github.com/en/enterprise-cloud@latest/rest/billing/usage-reports) (from the GHEC OpenAPI description)
- Report columns: summarised report sums by `date`, `sku`, `repository`, `cost_center_name` (and `organization`); the detailed report adds `username` and `workflow_path` ("the path of the GitHub Actions workflow that generated the usage"); the AI usage report sums by `date`, `model`, `username` and adds `input`, `output`, `cache_read`, `cache_write` tokens and `app_client_id` for app-attributed usage. `discount_amount` includes included-usage discounts and self-hosted runner discounts. All usage logged in UTC by day. Source: [Billing reports](https://docs.github.com/en/enterprise-cloud@latest/billing/reference/billing-reports)
- Cost centre budgets can be excluded from the enterprise budget so a project has its own cap. Source: [Budgets (Copilot billing docs)](https://docs.github.com/en/enterprise-cloud@latest/copilot/concepts/billing-and-usage/organizations-and-enterprises/budgets)
- Custom properties: defined at organisation or enterprise level, types string, single select, multi select, true/false; names up to 75 characters without spaces; searchable with `props.` filters; REST `GET/PATCH /orgs/{org}/properties/schema`, `/orgs/{org}/properties/values`, `/enterprises/{enterprise}/properties/schema`. Source: [Managing custom properties for repositories](https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-organization-settings/managing-custom-properties-for-repositories-in-your-organization); REST paths from the GHEC OpenAPI description
- OIDC custom property claims: organisation or enterprise admins choose properties to include; every workflow run in a repository with a value set gets claims named `repo_property_<name>` (for example `"repo_property_business_unit": "payments"`), configured via UI or `POST /orgs/{org}/actions/oidc/customization/properties/repo` (enterprise equivalent `/enterprises/{enterprise}/actions/oidc/customization/properties/repo`). Intended for attribute-based access control in cloud trust policies. Source: [OpenID Connect concepts](https://docs.github.com/en/enterprise-cloud@latest/actions/concepts/security/openid-connect); [OIDC reference](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/security/oidc)
- Custom properties can target organisation rulesets and workflow execution policies (repositories selected "by visibility, deployment status, or custom property"). Source: [Control workflow execution](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/administer/control-workflow-execution)
- Actions usage metrics (per workflow, job, repository, OS, runner type, including self-hosted) show minutes but not cost ("do not apply minute multipliers"). Source: [Viewing GitHub Actions metrics for your organisation](https://docs.github.com/en/enterprise-cloud@latest/organizations/collaborating-with-groups-in-organizations/viewing-github-actions-metrics-for-your-organization)
- Per-run timing endpoints (`/actions/runs/{run_id}/timing`, `/actions/workflows/{workflow_id}/timing`) are closing down. Source: [REST: Workflow runs](https://docs.github.com/en/enterprise-cloud@latest/rest/actions/workflow-runs) (from the GHEC OpenAPI description)
- GHAS licences count unique active committers (commit pushed in the last 90 days); GitHub App bots are ignored. Source: [GitHub Advanced Security billing](https://docs.github.com/en/enterprise-cloud@latest/billing/concepts/product-billing/github-advanced-security)

### Inferences
- Per-project ledger recipe: (1) one repository (or set) per project in a cost centre named after the project; (2) one service-account user per project that starts that project's Copilot tasks, assigned directly to the same cost centre so AI credits follow it; (3) custom property `project` on each repository, enabled as an OIDC claim, so self-hosted runners on Azure obtain project-scoped credentials and Azure resources are tagged with the same key; (4) nightly job calls `/usage/summary?cost_center_id=...&day=...` for headline numbers and a weekly `detailed` export for `workflow_path` splits (agent sessions versus CI versus report jobs).
- Daily granularity and UTC dates mean a night that spans midnight UTC splits across two days; for Australian time zones the whole night (roughly 10:00 to 20:00 UTC) usually falls on one UTC date, which conveniently makes "per night" equal to "per UTC day".
- Per-run cost is not available from GitHub; derive it from job durations multiplied by the runner rate, and reconcile monthly against the billing report.
- A shared factory service account across projects would collapse all AI credits into one cost centre; that is the main attribution mistake to avoid.

### Gaps
- No way found to assign cost centres by custom property automatically; membership is explicit (users, repositories, organisations, enterprise teams).
- Whether Copilot cloud agent's Actions minutes appear with a recognisable `workflow_path` (for example a dynamic Copilot workflow) in the detailed report was not confirmed.
- Whether Copilot cloud agent commits count toward GHAS active committers (the agent is a bot, the initiator is co-author) was not confirmed.

## Key question 5: What do practitioners report about running agent fleets on Actions (queue delays, scheduled workflow drift, rate limits)?

### Takeaway
Evidence is thin and mostly second-hand (vendor blogs, community threads, third-party status trackers; GitHub's own blog and status pages were unreachable from this session, so most items are [snippet]). The consistent picture: scheduled workflows are best-effort and commonly run 15 to 30 minutes late at busy times, occasionally hours late or dropped; hosted-runner assignment had several multi-hour degradations in 2026 (February, May, July, August, October) while self-hosted runners were often unaffected; Copilot cloud agent itself hit an internal rate limit on 2 April 2026 that suspended work for about an hour; secondary rate limits (not the hourly primary limits) are what automation fleets actually hit, especially parallel jobs writing comments or using search; and merge queues stall on flaky tests and missing `merge_group` triggers. Design the night to tolerate a late start, a lost hour, and retries.

### Cited Findings

**Scheduled workflow drift**
- Official: `schedule` "can be delayed during periods of high loads", worst at the start of every hour, and "some queued jobs may be dropped". Source: [Events that trigger workflows: schedule](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/events-that-trigger-workflows)
- A vendor blog claims typical delays of 15 to 30 minutes or more under load; a small scheduler bake-off reported GitHub's best result over 17 minutes late, median about 26 minutes late, one run more than ten hours late. Third-party and small-sample. [snippet] Source: [Crontap: GitHub Actions cron drift problem](https://crontap.com/blog/github-actions-cron-drift-problem); [Joseph Hall: small bake-off](https://josephhall.org/blog/small-bake-off/)
- A GitHub Community discussion describes a new repository whose daily scheduled job was delayed 8 to 14 hours and once skipped entirely (single report). [snippet] Source: [GitHub Community discussion 201738](https://github.com/orgs/community/discussions/201738)
- Common practitioner mitigation: pick an off-peak minute, or trigger `workflow_dispatch` from an external scheduler via the API. [snippet] Source: [DEV Community: scheduled workflow limitations](https://dev.to/ksivamuthu/github-actions-scheduled-workflows-understanding-the-limitations-and-possible-solutions-5hm5); [itime.day: why scheduled workflows run late](https://itime.day/articles/github-actions-cron-delays)

**Hosted runner queue delays and incidents in 2026** (all [snippet]; GitHub availability reports and githubstatus.com could not be fetched)

Source: [GitHub availability report: May 2026](https://github.blog/news-insights/company-news/github-availability-report-may-2026/)
- 6 to 7 Aug 2026: Actions degraded, workflows failed to start or failed mid-run, webhooks throttled, impact roughly 10 hours by a third-party account. Source: [IncidentHub write-up](https://blog.incidenthub.cloud/github-actions-pages-outage-aug-6-2026)
- 5 Oct 2026: delays assigning GitHub-hosted runners escalating to job failures, resolved 22:49 (UTC presumed). Source: [UptimeRobot GitHub history 2026-10-05](https://uptimerobot.com/is-it-down/github/2026-10-05/)

**Rate limits as experienced by automation**
- Official secondary limits: 100 concurrent requests; 900 points per minute per REST endpoint (writes 5 points); 80 content-generating requests per minute and 500 per hour; "subject to change without notice" and may trigger "for undisclosed reasons". Search API: 30 requests per minute (code search 10 per minute). Best practice: honour `retry-after`, and when `x-ratelimit-remaining` is 0 wait until `x-ratelimit-reset`. Source: [Rate limits for the REST API](https://docs.github.com/en/enterprise-cloud@latest/rest/using-the-rest-api/rate-limits-for-the-rest-api); [REST: Search](https://docs.github.com/en/enterprise-cloud@latest/rest/search/search); [Best practices for using the REST API](https://docs.github.com/en/enterprise-cloud@latest/rest/using-the-rest-api/best-practices-for-using-the-rest-api)
- Maintainers report secondary-limit failures when several jobs call the API at the same time, and when workflows use the search API to find an existing PR before creating one. [snippet] Source: [ponylang release-notes-bot-action PR 38](https://github.com/ponylang/release-notes-bot-action/pull/38); [changesets/action issue 192](https://github.com/changesets/action/issues/192)
- GitHub itself warns that Actions users commonly hit the REST limits listed for `GITHUB_TOKEN`, apps and users, and that secondary limits are not configurable on GHEC. Source: [Actions limits](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/limits)

**Merge queue in practice**
- Practitioner and vendor guides (vendors sell merge-queue tooling, so biased): a single flaky failure forces every PR behind it to retest; teams often enable the queue, discover workflows lack the `merge_group` trigger, and turn it off; "checks never start in queue context" is the usual symptom of a missing trigger. A March 2026 GitHub incident affected Merge Queue per Trunk's status history. [snippet] Source: [Trunk changelog: flaky test detection on merge branches](https://trunk.io/changelog/flaky-tests-flaky-test-detection-on-merge-branches); [Tenki: GitHub merge queue setup](https://tenki.cloud/blog/github-merge-queue-setup); [devtoolbox: merge queue flaky required checks](https://devtoolbox.dedyn.io/blog/github-merge-queue-flaky-required-checks-guide); [Trunk status history](https://status.trunk.io/history/2)
- Official knob for flakiness: disable "Only merge non-failing pull requests" so a failed entry can still merge if the group head passes; status check timeout bounds a hung check. Source: [Managing a merge queue](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue)

**Agent fleets on Actions specifically**
- No independent write-up of a 20+ task overnight Copilot fleet driven from Actions was found (consistent with the sibling Copilot notes). The nearest evidence is GitHub's own gh-aw repository reports, already summarised in `copilot_coding_agent_and_agent_hq.md`.

### Inferences
- Treat 06:00 report timing and 22:00 kickoff timing as "within about 30 minutes, usually"; if the morning report must land before stand-up, run it at about 05:41 and have it degrade gracefully if upstream work is still running.
- Budget one lost hour per night for platform hiccups (runner assignment or Copilot internal throttling); make the reconciler idempotent so a missed tick or a cancelled job is simply retried on the next tick.
- Spread write calls: a 40-task fan-out that labels, comments and assigns in parallel from 40 matrix jobs is exactly the "multiple requests at the same time from different jobs" pattern that trips secondary limits; serialise writes in one job or use `max-parallel` and backoff on `retry-after`.
- Avoid the search API in hot loops (30 per minute); list issues by label instead, or keep state in a Project.
- Self-hosted runners on Azure isolate the factory from hosted-runner assignment incidents (February 2026 explicitly left self-hosted unaffected), which is a reliability argument independent of cost.

- No quantitative data found on Copilot cloud agent queue time (time from assignment to session start) under load.
