## Key question 1: For a night of 20 to 40 tasks, how would you queue, start, monitor and chain them with the coding agent, and where does the 59 minute cap bite?

### Takeaway
The cloud agent is a per-task, single-repo, single-branch, single-PR worker with a hard 59 minute wall clock per session and no built-in queue, so a 20 to 40 task night needs an external dispatcher (REST agent tasks API, issue assignment API, `gh agent-task`, or Copilot automations) that submits well-scoped tasks, polls task `state`, and chains follow-ups by commenting `@copilot` on the PR or starting a new task with `head_ref`. The cap bites on anything that needs environment bootstrap plus a long test suite plus iteration in one shot, so the factory must decompose work before dispatch and treat `timed_out` as a normal outcome to re-dispatch.

### Cited Findings

Entry points and programmatic dispatch (official docs, read 24 Oct 2026)

- The cloud agent can be started from GitHub.com (issues, agents tab, dashboard, Copilot Chat, new repositories and failing Actions runs), GitHub Mobile, IDEs (VS Code, JetBrains, Eclipse, Visual Studio 2026), the REST API, the GitHub CLI, the GitHub MCP Server, Jira, Slack, Microsoft Teams, Azure Boards, Linear and Raycast, and automatically via Copilot automations. Some entry points open a PR automatically; in others you ask for a PR in the prompt or create one from the session log afterwards. [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/start-copilot-sessions)
- Agent tasks REST API (public preview): `POST /agents/repos/{owner}/{repo}/tasks` with `prompt` (required) plus optional `base_ref`, `model` (omit for Auto model selection) and `create_pull_request`. `GET /agents/repos/{owner}/{repo}/tasks`, `GET /agents/tasks` (all repos) and `GET .../tasks/{task_id}` return `state` in `queued`, `in_progress`, `completed`, `failed`, `idle`, `waiting_for_user`, `timed_out` or `cancelled`. Only user-to-server tokens (PAT, OAuth app token, GitHub App user-to-server token) are accepted; GitHub App installation tokens are not supported. [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-via-the-api)
- The OpenAPI description (24 Oct 2026) adds request fields `custom_agent` (filename of a `.github/agents/*.agent.md` without extension) and `head_ref` (existing branch; with `base_ref` the agent looks up the open PR for that branch and commits to it), and documents that `POST .../tasks` "is only available to users with a Copilot Business or Copilot Enterprise subscription". The task object carries `id`, `html_url`, `name`, `creator`, `state` (derived from the most recent session), `session_count`, `artifacts[]` (type `pull` or `branch`), `custom_agent`, `archived_at`, `created_at`, `updated_at`. List endpoints filter by comma-separated `state`, `since`, `is_archived`, `creator_id` and sort by `created_at` or `updated_at`. [Source](https://raw.githubusercontent.com/github/rest-api-description/main/descriptions/api.github.com/api.github.com.json)
- Issues can be assigned to Copilot via REST (`assignees: ["copilot-swe-agent[bot]"]` with an `agent_assignment` object: `target_repo`, `base_branch`, `custom_instructions`, `custom_agent`, `model`) or GraphQL (`createIssue`, `updateIssue`, `addAssigneesToAssignable`, `replaceActorsForAssignable` with `agentAssignment`, requiring the `GraphQL-Features: issues_copilot_assignment_api_support,coding_agent_model_selection` header). A fine-grained PAT needs read on metadata and read/write on actions, contents, issues and pull requests. The bot login is `copilot-swe-agent`. [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-via-the-api)
- When an issue is assigned, Copilot receives the title, description, existing comments and any extra instructions; it does not react to later comments on the issue. Follow-ups go on the PR. You can only pick a target repo where you have write access and the cloud agent is enabled. [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-on-github)
- GitHub CLI: `gh agent-task create "prompt" [--base BRANCH] [--repo OWNER/REPO] [--follow]`, `gh agent-task list`, `gh agent-task view [--repo] PR_NUMBER --log [--follow]`. Requires gh v2.80.0+; public preview. [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-from-cli)
- From Copilot CLI you can hand a task to the cloud agent with `/delegate <prompt>` or a `&` prefix; the CLI commits unstaged changes as a checkpoint to a new branch, the cloud agent opens a draft PR, and the CLI prints the PR and session links. [Source](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/delegate-tasks-to-cca)

Hard limits

- "Each Copilot cloud agent session has a maximum execution time of 59 minutes. This limit cannot be extended or bypassed. If a task exceeds the limit, the session times out and stops." The docs advise breaking work into smaller tasks and allow a shorter `timeout-minutes` in `copilot-setup-steps.yml`. Other limits: can only change one repository per run, works on one branch at a time, and "can open one pull request per task"; by default the GitHub MCP server only sees the working repo's issues and PRs. [Source](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-on-github)
- `copilot-setup-steps.yml` accepts `timeout-minutes` with a maximum value of 59. [Source](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment)
- Troubleshooting: "If the session remains stuck, it will time out after an hour." Retry by unassigning and reassigning the issue, or re-posting the comment. [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/troubleshoot-cloud-agent)
- Hooks reference: `sessionEnd` `reason` under the cloud agent is typically `complete`, `error` or `timeout`; an `agentStop` hook that returns `decision: "block"` forces another turn "which still counts against the job's timeout". [Source](https://docs.github.com/en/copilot/reference/hooks-reference)
- No documented concurrency cap on simultaneous cloud agent sessions was found in the docs read; the agents docs say "You can run multiple agent sessions concurrently". [Source](https://docs.github.com/en/copilot/concepts/agent-capabilities/choosing-and-delegating-agent-work/agent-management)

Monitoring

- The agents panel (any GitHub page) or `github.com/copilot/agents` lists sessions you started or that others asked Copilot to work on; opening a session shows the log, token usage and session length. Session logs show "internal reasoning and the tools it used". You can steer a running session from the prompt box (each steering message consumes AI credits; steering is not available for third-party agents), stop a session (Actions run ends, pushed commits are kept) and archive stopped sessions. [Source](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)
- A "Copilot started work" timeline event with a "View session" link appears on the PR; logs stream live. An eyes emoji reaction on the comment or issue confirms pickup. [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/troubleshoot-cloud-agent)
- Copilot Chat on GitHub.com can answer "what changed, what was validated, and why" by reading the agent session logs of a Copilot PR, and can start another session from the conversation. [Source](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-on-github)
- [snippet] Changelog 10 Jun 2026: "Copilot Chat now sees your agent sessions" (chat reflects in-progress session status). [Source](https://github.blog/changelog/2026-06-10-copilot-chat-now-sees-your-agent-sessions)

Iterating and chaining

- Mention `@copilot` in a PR comment (works on Copilot-created and human PRs); by default Copilot pushes commits to the PR branch, or you can ask for a separate PR. Review comments can be delegated one at a time ("Fix with Copilot") or as a batch ("Add to batch", then "Fix and commit" or "Fix and open pull request"), with a model picker. "Copilot remembers context from previous sessions on the same pull request"; if the PR was created by a custom agent, `@copilot` continues with that agent. Merge conflicts: "Fix with Copilot" in the merge box or an `@copilot` mention; Copilot resolves, verifies build, tests and linter, then requests review. Failing Actions runs: "Fix with Copilot" on the run page starts a session that pushes a fix to the branch. [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-on-github)
- Only users with write access can trigger Copilot via comments; comments from others are never shown to the agent. Copilot only responds to mentions on open PRs. Batch review comments with "Start a review" rather than single comments, because each submitted comment can start work. Copilot keeps the PR title and body in sync with its changes. [Source](https://docs.github.com/en/copilot/tutorials/cloud-agent/get-the-best-results)
- Research, plan, iterate: sessions "do not create pull requests automatically" unless asked; you can review the diff on the `copilot/BRANCH-NAME` branch, continue the conversation, then click "Create pull request". Only on GitHub.com (and in preview for Teams and Slack); Azure Boards, Jira and Linear integrations only create PRs directly. [Source](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/research-plan-iterate)
- Copilot automations (GA for Pro, Pro+, Max, Business, Enterprise; private and internal repos only): triggers are a schedule (hourly, daily or weekly), issue created, PR opened, PR synchronized, with search-query and changed-files filters; you select the tools the run may use (for example push changes, update labels, create a PR); any writer can create one; automations are private to their creator but sessions are visible to repo readers; stored outside Git; billed (Actions minutes and AI credits) to the creator; events from users without write access are ignored by default; PRs opened by an automation are attributed to the creator, who therefore cannot approve them; Actions workflows still need human approval. "Run now" tests an automation immediately. [Source](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-automations); [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/create-automations)
- Automations REST API (24 Oct 2026 OpenAPI): `POST /agents/repos/{owner}/{repo}/automations` with `name`, `prompt`, `triggers`, `model`, `reasoning_effort` (`none`, `low`, `medium`, ...), `tools[]`, `allowed_custom_agents[]`, `enabled`, `owner_type` (`user` or `repository`), `write_scope` (`trigger` or `repository`), `require_actor_write_permission`; `GET /agents/automations/available-triggers` and `/available-tools` return machine-readable schemas; `GET /agents/automations/{id}/tasks` lists runs. [Source](https://raw.githubusercontent.com/github/rest-api-description/main/descriptions/api.github.com/api.github.com.json)
- Automations triaging issues attach a rationale and confidence to each change; the repo "automation level" (Full control, Cautious default, Balanced, Full automation) decides what applies automatically versus waits in an approvals panel; `is:issue is:open has:suggestions` finds pending suggestions; the same rationale/confidence can be sent via the issues REST/GraphQL APIs by your own integration. [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/manage-rationale-confidence-approvals)
- Actions workflows do not run on Copilot pushes until a writer clicks "Approve and run workflows"; a repo admin can disable "Require approval for workflow runs" (warning: unreviewed Copilot code could then gain write access or reach Actions secrets). [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/configuring-agent-settings)
- GitHub Agentic Workflows (public preview) are a code-reviewable alternative for chaining: markdown plus frontmatter compiled to `.lock.yml` Actions workflows, read-only tokens by default, writes only via declared `safe-outputs` (for example `create-issue`, `add-labels`, `assign-to-agent`), threat detection on outputs, engines Copilot (default), Claude, Codex, Gemini; `max-ai-credits` default 1,000 AIC per run. [Source](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-github-agentic-workflows)
- gh-aw default guardrails: 20-minute timeout on the agentic step, 60-minute timeout on the agent job, 10-minute detection job timeout, 1,000 AIC per run and 5,000 AIC per workflow per day; `max-turns` defaults to 500; Copilot engine supports `max-continuations`; `fallback-models` for ordered model fallback. [Source](https://raw.githubusercontent.com/github/gh-aw/main/docs/src/content/docs/reference/cost-management.md); [Source](https://raw.githubusercontent.com/github/gh-aw/main/docs/src/content/docs/reference/engines.md)

### Inferences
- A practical night plan: (1) pre-decompose into tasks that fit a 20 to 40 minute budget including setup, because the 59 minutes include `copilot-setup-steps` and any test runs; (2) dispatch with `POST /agents/repos/{owner}/{repo}/tasks` (Business/Enterprise) or issue assignment (any paid plan) using a PAT held by a service account with write access, passing `custom_agent` and `model`; (3) poll `GET /agents/tasks?state=...&since=...` on a timer, and watch PR webhooks (`pull_request`, `issue_comment`, `check_run`); (4) when a task reaches `completed` with a `pull` artifact, approve and run workflows, request Copilot code review, then post `@copilot` with the review findings or start a follow-up task with `head_ref` to keep iterating; (5) treat `timed_out` and `failed` as re-dispatch with a narrower prompt.
- Because there is no server-side queue or rate card for concurrent sessions, the dispatcher should bound concurrency itself (Actions concurrency on the org, pooled AI credits, and review bandwidth are the real limits).
- Copilot automations are a ready-made nightly scheduler but only hourly/daily/weekly cadence, one repo each, private/internal repos only, and billed to the creating user, so they suit "every night at 02:00 fix failing tests" rather than a 40-task fan-out.
- Reported merge rates of roughly 75 to 80% on GitHub's own well-instrumented repo and 55 to 84% by task type in academic data imply a factory should expect one in four or five PRs to need rework or closure; fixes and docs merge best, performance and chore/version-bump tasks worst.

## Key question 2: What exactly is the sandbox (runner type, network, tools, time), and how are repo rules enforced on the agent?

### Takeaway
Each cloud agent job is an ephemeral GitHub Actions runner (default `ubuntu-latest`, Linux only unless you bring Windows or self-hosted runners) with a default-on egress firewall, Agents-scoped secrets only, pre-approved tools, no interactive user and a 59 minute ceiling; on the GitHub side the agent is a bot that can push only to its own `copilot/` branch or the PR branch, cannot mark PRs ready, approve or merge, is subject to rulesets like a human, and the person who started the task cannot count as the approver.

### Cited Findings

Runner and environment

- The agent works in "its own ephemeral development environment, powered by GitHub Actions"; by default a standard GitHub-hosted runner. Customise via `.github/workflows/copilot-setup-steps.yml`, which must be on the default branch and contain a single job named `copilot-setup-steps`; only `steps`, `permissions`, `runs-on`, `services`, `snapshot` and `timeout-minutes` (max 59) are honoured. If a setup step fails, remaining steps are skipped and the agent starts with the environment as is. `fetch-depth` on `actions/checkout` is overridden. Larger runners (more CPU, memory, disk, Azure private networking) and self-hosted runners are supported; "only compatible with Ubuntu x64 Linux and Windows 64-bit runners". For self-hosted runners GitHub recommends ephemeral single-use runners (ARC or Runner Scale Sets), you must disable the integrated firewall (it is incompatible with self-hosted runners and Windows), allow the required hosts, and can set proxy env vars via Agents variables. [Source](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment)
- Required outbound hosts for self-hosted or private-network runners: `uploads.github.com`, `user-images.githubusercontent.com`, `api.individual.githubcopilot.com`, `api.business.githubcopilot.com`, `api.enterprise.githubcopilot.com`, plus npm registry hosts if the Codex third-party agent is used. [Source](https://raw.githubusercontent.com/github/docs/main/data/reusables/copilot/cloud-agent-required-hosts.md)
- Organisation owners can set the default runner type (standard `ubuntu-latest` or a labelled runner/group) for all repos and block repos from overriding it via `runs-on`. [Source](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-organization/configure-runner-for-coding-agent)
- Hooks reference describes the cloud agent execution environment: Linux only (`bash` hooks honoured, `powershell` ignored); working directory `/workspace` when a repo is cloned, else `/root`; filesystem ephemeral (files written by hooks are discarded when the job ends); outbound network restricted by the firewall ("By default only GitHub and Copilot hostnames are reachable" for hook scripts; other hosts need an admin firewall allow rule); env vars `GITHUB_COPILOT_API_TOKEN`, `GITHUB_COPILOT_GIT_TOKEN` and `COPILOT_AGENT_PROMPT` are set, `GITHUB_TOKEN` is not; "Fully non-interactive. The agent runs with all tool permissions pre-granted"; only `.github/hooks/*.json` from the cloned repo is loaded (no user settings, plugins or `settings.json`). [Source](https://docs.github.com/en/copilot/reference/hooks-reference)
- The cloud agent is not available in personal repos owned by Enterprise Managed Users because it runs on GitHub-hosted runners, which are unavailable there. Max image attachment size is 3.00 MiB. [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/troubleshoot-cloud-agent)
- [snippet] Startup is over 20% faster since Apr 2026 thanks to Actions custom images. [Source](https://github.blog/changelog/month/04-2026/)

Network firewall

- The firewall is on by default with a recommended allowlist (OS package repos such as Debian, Ubuntu, Red Hat; container registries such as Docker Hub, ACR, ECR; language package registries for C#, Dart, Go, Haskell, Java, JavaScript, Perl, PHP, Python, Ruby, Rust, Swift; certificate authorities; Playwright browser download hosts). Blocked requests add a warning (blocked address and command) to the PR body or comment. Org owners set Enable firewall, Recommended allowlist and Allow repository custom rules to Enabled, Disabled or Let repositories decide, and maintain an org custom allowlist; repo admins can add custom rules when allowed. Limitations: it "only applies to processes started by the agent via its Bash tool", not to MCP server processes or `copilot-setup-steps` processes; only inside the Actions appliance; "Sophisticated attacks may bypass the firewall". Copilot code review has its own independent firewall section. [Source](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-the-firewall)

Secrets, variables and MCP

- Dedicated "Agents" secrets and variables exist at org and repo level and are exposed as environment variables to the agent and to `copilot-setup-steps.yml`; names prefixed `COPILOT_MCP_` are only passed to MCP servers; "Copilot cloud agent does not have access to Actions, Codespaces, or Dependabot secrets and variables"; values are masked in session logs; lowest level wins on name clashes. [Source](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/configure-secrets-and-variables)
- Guardrails tutorial: keep data the agent must not see in Actions secrets (it cannot read them in sessions or setup steps); the `GITHUB_TOKEN` default permission policy does not affect the agent's own token but does apply to `copilot-setup-steps.yml`; use GitHub-hosted runners so each run is a fresh VM; policies that do not apply to the cloud agent are custom models (BYOK) and private MCP registries. [Source](https://docs.github.com/en/copilot/tutorials/cloud-agent/build-guardrails)
- Out-of-the-box MCP servers: `github` (read-only tools by default, token scoped to the source repo) and `playwright` (localhost only). Repo-level MCP configuration can add servers; custom agents can further restrict tools. [Source](https://docs.github.com/en/copilot/reference/custom-agents-configuration)
- For Business and Enterprise, both the "Copilot cloud agent" policy and "MCP servers on GitHub.com" policy are disabled by default and must be enabled by an org owner; repo access can be limited to selected repos (also via a REST API for cloud agent management); "Allow automations" is a separate toggle. [Source](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-organization/add-copilot-cloud-agent)
- For Pro, Pro+ and Max the cloud agent is enabled by default; for Business and Enterprise it is disabled by default. [Source](https://docs.github.com/en/copilot/concepts/enterprise/cloud-agent-access)

Repository rules and review controls

- "If a ruleset or branch protection rule is incompatible with Copilot cloud agent, access to the agent is blocked. For example, a rule that only allows specific commit authors can prevent Copilot from creating or updating pull requests." For rulesets, admins can add Copilot as a bypass actor. [Source](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-on-github)
- Risks and mitigations: only writers can trigger the agent; it can push to a single branch (a new `copilot/` branch, or the PR branch when `@copilot` is mentioned on an existing PR) and "is also subject to any branch protections and required checks"; "It cannot directly run `git push` or other Git commands"; it opens draft PRs, "cannot mark its pull requests as 'Ready for review' and cannot approve or merge"; workflows do not run until a writer approves; "Prevents the user who asked Copilot cloud agent to create a pull request from approving it" (preserves Required approvals); "Requires an additional approval when a pull request isn't attributed to a person", enabled by default in rulesets (admins can turn off) and always for branch protection rules; hidden characters such as HTML comments are stripped from issues and comments before they reach the agent; commits are authored by Copilot with the initiator as co-author, signed ("Verified"), and each commit message links to the session logs. [Source](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations)
- Guardrails tutorial: "Copilot cloud agent is subject to rulesets just like human developers"; consider requiring code scanning or code quality results in rulesets; protect `.github` Copilot and MCP config files with CODEOWNERS and "Require review from Code Owners". [Source](https://docs.github.com/en/copilot/tutorials/cloud-agent/build-guardrails)
- Built-in validation: by default the agent checks its code with CodeQL, secret scanning, the GitHub Advisory Database (malware, CVSS High/Critical) and gets "a second opinion" from Copilot code review before completing the PR; no GHAS licence needed; a repo admin can toggle each tool off. [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/configuring-agent-settings); [Source](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations)

Cloud sandboxes (CLI and Copilot app, distinct from the cloud agent)

- Cloud sandboxing runs an interactive CLI or Copilot app session in an isolated ephemeral Linux environment built on Azure Container Apps Sandboxes; public preview; `copilot --cloud --experimental`; "You can't run the CLI programmatically in a cloud sandbox" (no `-p` or `-i`); sessions can be stopped (snapshot) and resumed; billed at USD 0.000024 per compute second, USD 0.000003 per GiB-second memory, USD 0.005 per GiB-month snapshot storage; org policy "Cloud Sandbox access" disabled by default; shares policy configuration with the cloud agent. Local sandboxing (Microsoft eXecution Container, bubblewrap on Linux, Seatbelt on macOS) is off by default and free. [Source](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/about-cloud-and-local-sandboxes)

### Inferences
- "Initiator approval not counting" is a hard property: the service account that dispatches tasks can never be the approver, and an unattributed Copilot PR needs an extra approval under default rulesets, so the factory needs a distinct reviewer identity (human or, if enabled, Copilot code review approvals) and should expect a two-approval path unless admins switch the extra-approval rule off.
- Because `copilot-setup-steps.yml` must live on the default branch and the firewall ignores processes started in setup steps and MCP servers, those two surfaces are the real exfiltration and supply-chain boundary; lock them behind CODEOWNERS.
- A Windows or self-hosted path trades away the integrated firewall, so for an unattended night the GitHub-hosted Ubuntu runner with the recommended allowlist is the safer default.

### Gaps
- The exact runner spec (vCPU, RAM, disk) of the default `ubuntu-latest` agent runner is not stated in Copilot docs (standard Actions runner sizes apply but were not fetched).
- The docs give two descriptions of default egress: the firewall page says a recommended allowlist of package registries is on by default, while the hooks reference says only GitHub and Copilot hostnames are reachable by default for hook scripts; which applies to hook processes versus agent Bash processes was not clarified.
- No document found describing what the agent's own token can do beyond "simple push operations" (for example whether it can call the GitHub API to edit issues), other than the GitHub MCP server's read-only default.

## Key question 3: How do custom agents and AGENTS.md shape behaviour, and are hooks or deterministic blockers available?

### Takeaway
Behaviour is shaped by layered Markdown (repo `.github/copilot-instructions.md`, path-scoped `.instructions.md`, any `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, org instructions) plus custom agent profiles in `.github/agents/*.agent.md` that fix the system prompt, model, tool allowlist and MCP servers; deterministic enforcement exists via repository hooks in `.github/hooks/*.json`, whose `preToolUse` hook can allow, deny or modify any tool call and runs as shell in the sandbox, which is the direct equivalent of Claude Code hooks (with `ask` mapped to `deny` because nobody is there).

### Cited Findings

Custom instructions

- The cloud agent supports `/.github/copilot-instructions.md`, `/.github/instructions/**/*.instructions.md` (with `applyTo` globs), `**/AGENTS.md`, `/CLAUDE.md` and `/GEMINI.md`, plus organisation-wide instructions; repository-wide instructions are prioritised first. Repo-wide instructions also apply to Copilot Chat and code review. On the first PR in a repo Copilot comments with a link to auto-generate a `copilot-instructions.md`. Instructions should state build, test and validation commands because the agent "is more likely to produce good pull requests" when it can validate in its environment. [Source](https://docs.github.com/en/copilot/tutorials/cloud-agent/get-the-best-results)
- Reference table: on GitHub.com the cloud agent honours repository, path-specific, all agent-instruction files and organisation instructions; Copilot code review honours repository, path-specific, a code-review-only set and organisation instructions; Copilot CLI additionally honours personal `~/.copilot/copilot-instructions.md` and `~/.copilot/instructions/**/*.instructions.md`. [Source](https://docs.github.com/en/copilot/reference/custom-instructions-support)

Custom agents

- Profiles live in `.github/agents/NAME.agent.md` (filename chars `. - _ a-z A-Z 0-9`); org-level agents live in the org's `.github` or `.github-private` repo under a root `agents` directory, enterprise-level in a designated org's `.github-private`; the agent appears in the agents tab dropdown once merged to the default branch. [Source](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/create-custom-agents)
- Frontmatter: `name` (optional), `description` (required), `target` (`vscode` or `github-copilot`), `tools` (list or comma string; unset = all tools, `[]` = none, MCP tools as `server/tool` or `server/*`), `model`, `disable-model-invocation` (prevents automatic selection; replaces retired `infer`), `user-invocable`, `mcp-servers` (YAML form of the repo MCP JSON; `stdio` maps to `local`; secrets via `${{ secrets.COPILOT_MCP_X }}` or `${{ vars.X }}`), `metadata`. Prompt body max 30,000 characters. `handoffs` and `argument-hint` from VS Code agents are ignored by the cloud agent. Tool aliases: `execute`/`shell`/`Bash`, `read`, `edit`, `search`, `agent` (invoke another custom agent), while `web` and `todo` are not applicable in the cloud agent. Lowest level (repo over org over enterprise) wins on name clashes; versioning is by commit SHA of the profile, and PR follow-ups use the same version as the task that created the PR. MCP processing order: out-of-the-box servers, then the agent profile, then repository settings. [Source](https://docs.github.com/en/copilot/reference/custom-agents-configuration)
- Custom agents are selectable when prompting in the agents panel or tab, when assigning an issue, via the REST `custom_agent` field, and in Copilot CLI via `/agent` or `--agent`; the PR description notes which custom agent did the work. [Source](https://raw.githubusercontent.com/github/docs/main/data/reusables/copilot/custom-agents-using.md); [Source](https://raw.githubusercontent.com/github/rest-api-description/main/descriptions/api.github.com/api.github.com.json)
- Agent skills in `.github/skills` are also loaded by the cloud agent and by code review (review-focused skill names such as `code-review`). [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/use-code-review)

Hooks (deterministic blockers)

- Hooks "run code rather than asking the model to follow a rule"; a `preToolUse` hook can "programmatically approve or deny tool executions". Repository hooks for CLI and cloud agent live in `.github/hooks/*.json` (CLI also `~/.copilot/hooks/*.json`); format: `{"version": 1, "hooks": {"preToolUse": [{"type": "command", "bash": "...", "powershell": "...", "cwd": "...", "env": {...}, "timeoutSec": 30}]}}`; hooks run synchronously and block the agent (keep under 5 seconds). [Source](https://docs.github.com/en/copilot/concepts/customizations/hooks)
- The hooks file "must be present on your repository's default branch to be used by Copilot cloud agent". [Source](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/use-hooks)
- Event support under the cloud agent (reference table): `sessionStart` fires once per job (never as a resume); `sessionEnd` fires once (reason `complete`, `error` or `timeout`); `userPromptSubmitted` fires at most once; `userPromptTransformed` fires (mutation only); `preToolUse` fires and can allow, deny or modify, with `"ask"` treated as `"deny"`; `postToolUse` fires and can modify the tool result or inject context; `postToolUseFailure` fires (exit code 2 gives recovery guidance); `agentStop` fires and `decision: "block"` forces another turn (counts against the timeout); `subagentStart`/`subagentStop` fire; `errorOccurred` fires; `preCompact` fires only for `auto`; `notification` does not fire; `permissionRequest` has no effect because tool calls are pre-approved ("Use `preToolUse` to make permission decisions in cloud agent"); policy hooks are CLI only; `prompt` hook entries may not fire; HTTP hooks must target an allow-listed host. Only `bash` (or `command`) entries run. `modifiedPrompt` from `userPromptSubmitted` is honoured only by SDK programmatic hooks. [Source](https://docs.github.com/en/copilot/reference/hooks-reference)
- Troubleshooting: default hook timeout 30 seconds; scripts must be executable with a shebang; output must be single-line JSON. [Source](https://raw.githubusercontent.com/github/docs/main/data/reusables/copilot/cloud-agent/troubleshoot-hooks.md)
- In the Copilot CLI (not the cloud agent) permission rules are also available as `--allow-tool`, `--deny-tool`, `--available-tools`, `--excluded-tools`, `--allow-url`, `--deny-url` with filters such as `shell(git:*)`, `write(README.md)`, `url(https://*.github.com)`, `github(create_issue)`; deny takes precedence over allow. [Source](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-programmatic-reference)
- Automations add a separate deterministic control: the selected `tools` list is "the main way you control the scope" and the automation "can only take action in the single repository it is scoped to". [Source](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-automations)
- GitHub Agentic Workflows enforce writes through declared `safe-outputs` and run agents with read-only tokens, with secrets kept in downstream jobs and threat detection on proposed outputs. [Source](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-github-agentic-workflows)

### Inferences
- A factory can encode "never touch `data/*.yaml` without a citation" or "block `rm -rf`, `git push --force`, network curls" as a `preToolUse` bash hook that inspects the JSON tool args and returns `permissionDecision: "deny"`; an `agentStop` hook can refuse to let the agent stop until a validation script passes, at the cost of consuming the 59 minutes.
- Because hooks and agent profiles are read from the default branch at job start, changes to guardrails need their own reviewed PR before the night run; the agent cannot weaken its own hooks mid-run.
- Custom agents are the right place to pin a model, trim tools (for example `tools: ["read", "edit", "search", "execute", "github/*"]`) and attach a repo-specific checklist, and the REST `custom_agent` field lets the dispatcher route tasks to different profiles (writer, tester, docs).

### Gaps
- The docs do not state whether hooks apply to third-party coding agents (Claude, Codex) running inside GitHub; they say those agents share the cloud agent's "security protections, mitigations, and limitations" but not its hook or custom-agent configuration.
- No documented size or count limits for hook files or for the number of custom agents.

## Key question 4: Can the Copilot SDK or CLI run a long-lived loop under our own orchestration, and what limits apply?

### Takeaway
Yes. Copilot CLI has a headless mode (`copilot -p ... --autopilot --allow-all --max-autopilot-continues N --max-ai-credits N --output-format json`) and a persistent server mode (`copilot --headless --port`), and the GA Copilot SDK (TypeScript, Python, Go, .NET, Java, Rust) drives that runtime over JSON-RPC with persistent, resumable sessions, typed event streams, programmatic hooks, per-session AI credit caps, fleet mode and even GitHub-hosted "cloud sessions". The limits are mostly yours to engineer (no built-in queue, locking, load balancing or idle timeout by default) plus the account's pooled AI credits, model rate limits and, for cloud sessions, the same cloud agent policies.

### Cited Findings

Copilot CLI programmatic mode

- `-p PROMPT` runs non-interactively and exits; `-s` suppresses stats; `--output-format json` emits JSONL; `--allow-all` (alias `--yolo`) equals `--allow-all-tools --allow-all-paths --allow-all-urls`; `--allow-tool`, `--deny-tool`, `--available-tools`, `--excluded-tools`, `--allow-url`, `--deny-url`; `--no-ask-user`; `--model` (for example `gpt-6-astra`, `claude-haiku-4.5`); `--agent`; `--fleet`; `--attachment`; `--secret-env-vars` (`GITHUB_TOKEN` and `COPILOT_GITHUB_TOKEN` redacted by default); `--trust-folder` (trust repo hooks, workspace MCP and plugin settings for one non-interactive session); `--share=PATH` writes the session transcript to Markdown, `--share-gist` to a secret gist; env vars `COPILOT_ALLOW_ALL`, `COPILOT_MODEL`, `COPILOT_HOME`, `COPILOT_AUTO_UPDATE=false` (pin version in CI), `COPILOT_GITHUB_TOKEN` > `GH_TOKEN` > `GITHUB_TOKEN`. Model precedence: custom agent model, `--model`, `COPILOT_MODEL`, settings `model`, default; `effortLevel` can be set in `~/.copilot/settings.json`. `copilot workflow run NAME --args @file.json --silent --output-format json` runs a dynamic workflow with a final `workflow.result` record and exit codes 0, 1, 2, 130. [Source](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-programmatic-reference)
- Command reference: `--autopilot` keeps working until `task_complete` is called; `--max-autopilot-continues=COUNT` (default unlimited); `--max-ai-credits=CREDITS` soft cap per response; `--mode autopilot`; `--plan --mode autopilot` (plan-then-autopilot without human approval; also `COPILOT_PLAN_THEN_AUTOPILOT`); `--resume[=ID|name]`, `--continue`, `--session-id`, `-n NAME`, `--worktree`; `-p` exit summary prints a `copilot --resume=SESSION-ID` hint; `COPILOT_TASK_WAIT_TIMEOUT_SECONDS` (default 600) bounds how long `-p` waits for background agents or shell commands; `/usage` shows per-model tokens and AI credit consumption; `/autopilot [OBJECTIVE] --max-ai-credits N` pauses when the cap is reached. [Source](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-command-reference)
- Programmatic autopilot example from the docs: `copilot --autopilot --yolo --max-autopilot-continues 10 -p "YOUR PROMPT HERE"`. In non-interactive mode any action not pre-approved is denied automatically. [Source](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/use-autopilot-mode); [Source](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli-in-actions)
- Autopilot stops when the task is complete, a problem occurs, Ctrl+C, or the continuation limit is reached; autopilot (continuation), `--allow-all` (approvals) and `--no-ask-user` (no clarifying questions) are separate controls; GitHub recommends local or cloud sandboxing before granting broad permissions. [Source](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/use-autopilot-mode); [Source](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/autopilot)
- AI credit session limits (public preview): `--max-ai-credits=N` (minimum 30), soft limits (an in-flight response completes), run ends when reached in non-interactive mode; `/limits set max-ai-credits N` interactively. [Source](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/set-session-limit)
- Scheduling inside a session: `/every [INTERVAL] PROMPT` (alias `/loop`, self-paced if no interval) and `/after DELAY PROMPT`, experimental, fixed intervals 10 seconds to 1 day, only while the interactive session is running; for unattended schedules use cron or Task Scheduler with `copilot -p`. [Source](https://docs.github.com/en/copilot/how-tos/copilot-cli/automate-copilot-cli/schedule-prompts)
- Fleet: `--fleet` with `-p`, `-i` or piped input runs parallel subagents (orchestrator decomposes the task); more subagents means more AI credits; not supported with `--acp`. `/tasks` lists background subagent tasks. [Source](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/speed-up-task-completion); [Source](https://docs.github.com/en/copilot/concepts/agent-capabilities/choosing-and-delegating-agent-work/delegating-and-parallelizing-work-with-agents)
- Dynamic workflows (public preview) are code-defined processes (in Copilot extensions) that can run deterministic steps and agents in sequence or parallel, pause at checkpoints and resume; available in Copilot app, CLI and SDK; not for Pro/Pro+ annual subscribers on legacy request billing. [Source](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/dynamic-workflows)
- Remote control (steer a CLI session from GitHub.com or Mobile) requires an interactive session and the machine to stay online; it is "not available when you use the CLI programmatically with the `--prompt` option". Policy "Store local sessions in the Cloud" must be "View and control". [Source](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/about-remote-control)
- CLI in GitHub Actions: with `permissions: copilot-requests: write` and the org policy "Allow use of Copilot CLI billed to the organization" (on by default when Copilot CLI is enabled), `GITHUB_TOKEN` authenticates and usage is metered to the organisation; user-level budgets are then not considered (use cost centres); GitHub recommends Agentic Workflows over raw `copilot` steps because of prompt-injection risk from fork PRs. [Source](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/copilot-cli-in-github-actions); [Source](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli-in-actions)

Copilot SDK

- [snippet] The SDK reached GA on 2 Jun 2026 (technical preview 22 Jan 2026, public preview 7 Apr 2026) with Node.js/TypeScript, Python, Go, .NET, Rust and Java. [Source](https://github.blog/changelog/2026-06-02-copilot-sdk-is-now-generally-available/)
- Architecture: "The SDK is a transport layer" that sends prompts to the Copilot CLI over JSON-RPC; the CLI runs the tool-use loop; each `assistant.turn_start`/`turn_end` pair is exactly one LLM call; `session.idle` is the reliable done signal (`sendAndWait()` waits for it), `session.task_complete` is optional and persisted; in autopilot the CLI injects a nudge message until the model calls `task_complete`; turn count can be read from `~/.copilot/session-state/<sessionId>/events.jsonl`. [Source](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/agent-loop)
- Setup paths: bundled CLI (Node, Python, .NET include the CLI; Go needs a separate CLI), local CLI, GitHub OAuth, BYOK (your own OpenAI or Azure keys, including Azure Managed Identity), backend services, multi-tenancy, scaling, experimental in-process runtime. [Source](https://docs.github.com/en/copilot/how-tos/copilot-sdk/setup/choosing-a-setup-path)
- Backend services: run `copilot --headless --port 4321` (bind `--host 0.0.0.0` for other hosts) as a persistent server, connect with `RuntimeConnection.forUri`, use `mode: "empty"` plus per-session `gitHubToken` for multi-user; no official Docker image (build from `github/copilot-cli` releases); "No built-in auth between SDK and CLI"; session state on local disk; "No idle timeout by default" (`--session-idle-timeout <seconds>`); single CLI server is a single point of failure; background-worker pattern creates a session per job, `sendAndWait`, then `disconnect`. [Source](https://docs.github.com/en/copilot/how-tos/copilot-sdk/setup/backend-services)
- Scaling: isolation patterns (CLI per user, shared CLI with session IDs, shared sessions with your own Redis locking); horizontal scaling needs shared storage for `~/.copilot/session-state/`; limitations: no built-in session locking, no load balancing, file-based state, single-process CLI; `infiniteSessions` with `backgroundCompactionThreshold` for long runs; sample Kubernetes and Azure Container Instances manifests. [Source](https://docs.github.com/en/copilot/how-tos/copilot-sdk/setup/scaling)
- Session limits: `sessionLimits: { maxAiCredits }` on create or resume; checked after model calls return so a response can overshoot; events `session.session_limits_changed`, `session.usage_checkpoint`, `session_limits_exhausted.requested` (needs a decision to continue) and `.completed`. [Source](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/session-limits)
- Usage: `assistant.usage` per model call (tokens, billing multiplier), `session.usage_info` (context window), `session.usage.getMetrics` (session totals in `totalNanoAiu`, per-model breakdown; experimental), `models.list` (per-model token prices and multiplier), `account.getQuota` (`premium_interactions`, `chat`, `completions` snapshots with `entitlementRequests`, `usedRequests`, `remainingPercentage`, `resetDate`); OpenTelemetry export is available. [Source](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/usage-and-billing)
- Hooks in the SDK: `onPreToolUse` returns `permissionDecision: "allow" | "deny"` with a reason; plus `onPostToolUse`, session lifecycle, `userPromptSubmitted` (can rewrite the prompt), subagent start/stop. [Source](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/hooks)
- Fleet mode via `session.rpc.fleet.start({ prompt })` (experimental; verified in TS, Python, Go, .NET, Rust; Java binding not found); coordination through SQL todos with `pending -> in_progress -> done | blocked`; sub-agents are stateless and need full context; `subagent.started/completed/failed` events. [Source](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/fleet-mode)
- Cloud sessions: `createSession({ cloud: { repository: { owner, name, branch } } })` runs on GitHub-hosted compute, is published at `https://github.com/copilot/tasks/{sessionId}` and routed to the `copilot-developer-sandbox` agent slug; requires cloud-agent entitlement and org policies allowing remote control and cloud viewing; `policy_blocked` is a non-retryable failure reason; the first `session.send` must wait for `session.start` with `producer === "copilot-agent"` or the prompt is silently dropped; set `streaming: true` for deltas. [Source](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/cloud-sessions)
- Remote sessions (`enableRemoteSessions: true` or `session.rpc.remote.enable()`) expose a locally running SDK session in "Mission Control" on GitHub web and mobile with a shareable URL; requires auth and a GitHub repo working directory. [Source](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/remote-sessions)

### Inferences
- For a self-hosted supervisor, the SDK is suitable: one headless CLI per worker container (or a CLI pool), a job queue in your own system, `sessionLimits.maxAiCredits` plus `onPreToolUse` policy per job, `session.idle` as completion, `getMetrics` for cost per task, and `--share`/`events.jsonl` for transcripts. You must supply concurrency control, retries, idle timeouts, persistent storage and locking.
- The cloud agent's 59 minute cap does not apply to CLI or SDK sessions you host; the binding constraints there are your runner's lifetime, `COPILOT_TASK_WAIT_TIMEOUT_SECONDS`, `--max-autopilot-continues`, AI credit caps and model rate limits.
- Mixing the two: use SDK or CLI workers for long multi-hour loops on your own Azure compute, and the cloud agent for GitHub-native PR hygiene (review-comment fixes, conflict resolution, failing-check fixes) where its branch and approval protections are valuable.

### Gaps
- No documented per-user or per-org request rate limits for the CLI/SDK beyond the generic "rate limits exist" page.

## Key question 5: How are third-party agents (Claude Code, Codex) inside Agent HQ billed and limited compared with the native agent?

### Takeaway
As of 24 Oct 2026 the Claude and Codex coding agents on GitHub are still public preview, run through the same entry points, sandbox protections and PR workflow as the cloud agent, are billed the same way (Actions minutes plus AI credits by model and tokens from your Copilot plan, no separate subscription), but offer fewer controls: you pick a model from a short provider-specific list (Auto does not use Copilot's auto model selection), cannot steer mid-session, and they are installed as hidden GitHub Apps; Cognition, xAI and Google agents announced for Agent HQ in Oct 2025 were not found in the docs as shipped third-party coding agents.

## Key question 6: What does each PR session leave behind as evidence (logs, session transcript, premium request count)?

### Takeaway
Every cloud agent task leaves a durable, repo-shared session log on GitHub.com (reasoning, tool calls, validation results, token usage, session length), signed commits that name the initiator as co-author and link back to the session, a draft PR whose body records the custom agent used and any firewall blocks, a REST task record with state and artifacts, enterprise-level session and audit log entries, and PR lifecycle metrics in the usage metrics API; what it does not leave is a per-session invoice line (AI credit usage cannot be traced to a specific session in the billing UI), and cloud agent sessions can be archived but never deleted.

### Cited Findings

- Cloud agent sessions "run in an ephemeral environment hosted by GitHub. The environment is destroyed when the session ends, but the session log remains available on GitHub.com. These sessions are shared by default and visible to people with access to the repository." Cloud agent sessions support Share and Archive but not Delete. Local CLI and Copilot app sessions are stored under `~/.copilot/session-state/` with a SQLite session store and are synced to the account by default (controlled by `remote` and `remoteExport` settings and the "Store local sessions in the Cloud" policy). [Source](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/session-data)
- The session view shows progress, "token usage, and session length"; logs show internal reasoning and tools used; commits are authored by Copilot with the initiator as co-author, signed ("Verified"), and "Each commit message includes a link to the session logs, so you can trace why a change was made during code review or an audit"; stopping a session preserves pushed commits; sessions appear in the repo's Agents tab "All sessions" view; you can query your own synced sessions in natural language (for example "Show me sessions where the agent struggled"). [Source](https://docs.github.com/en/copilot/how-tos/copilot-on-github/use-copilot-agents/manage-and-track-agents)
- "Details about the analysis performed and the actions taken by Copilot cloud agent can be reviewed in the session log" (CodeQL, advisory database, secret scanning); "Session logs and audit log events are available to administrators." [Source](https://docs.github.com/en/copilot/concepts/security-governance-and-network-settings/risks-and-mitigations)
- Firewall blocks are recorded as a warning (blocked address and command) in the PR body or comment. [Source](https://docs.github.com/en/copilot/how-tos/copilot-on-github/customize-copilot/customize-the-firewall)
- The PR description notes which custom agent completed the work. [Source](https://raw.githubusercontent.com/github/docs/main/data/reusables/copilot/custom-agents-using.md)
- Agent session logs include a link to matched public code when code references are detected. [Source](https://docs.github.com/en/copilot/concepts/copilot-surfaces/copilot-on-github)
- REST task records: `state`, `session_count`, `artifacts` (PR and branch), `custom_agent`, `creator`, timestamps, `html_url`; `GET /agents/tasks/{task_id}` "Returns a task by ID with its associated sessions". [Source](https://raw.githubusercontent.com/github/rest-api-description/main/descriptions/api.github.com/api.github.com.json)
- `gh agent-task view --log [--follow]` streams or dumps the session log from the terminal. [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/cloud-agent/use-cloud-agent-from-cli)
- Enterprise AI Controls show agent sessions from the last 24 hours with filters `agent:copilot-cloud-agent`, `organization`, `repository`, `status:in_progress`, `timeframe:7d`, `user`; the audit log records agentic activity and can stream Copilot agent session events (public preview, EMU and data-residency enterprises); Copilot usage records are available via REST; OpenTelemetry from Copilot clients can carry identity and, if enabled, prompt, response and tool content. [Source](https://docs.github.com/en/copilot/how-tos/administer-copilot/manage-for-enterprise/manage-agents/monitor-agentic-activity); [Source](https://docs.github.com/en/copilot/reference/enterprise-administrators/agent-session-filters)
- Actions taken by the hidden `anthropic code agent` and `openai code agent` GitHub Apps are visible in the audit log. [Source](https://docs.github.com/en/copilot/concepts/agent-capabilities/about-agents/about-third-party-coding-agents)
- Copilot usage metrics include "pull request lifecycle metrics" (PR creation and merge counts, median time to merge, review suggestion activity) and let you compare overall PR activity with "pull requests created by Copilot", at org or enterprise level, via the usage metrics API, dashboards and NDJSON export; data lands within two full UTC days. [Source](https://docs.github.com/en/copilot/concepts/billing-and-usage/copilot-usage-metrics/copilot-metrics)
- Billing visibility: the AI usage page shows credits and cost by model, but "you generally cannot trace consumed credits to specific prompts, sessions, or exact features at a per-request level"; Business/Enterprise users see their own cycle consumption on the Copilot settings page. [Source](https://docs.github.com/en/copilot/how-tos/manage-and-track-spending/monitor-ai-usage)
- Copilot code review cost is visible as Actions minutes under the `copilot-pull-request-reviewer` workflow and in billing reports with `workflow_path` `dynamic/agents/copilot-pull-request-reviewer`. [Source](https://docs.github.com/en/copilot/reference/copilot-billing/models-and-pricing)
- CLI and SDK evidence: `--share=PATH` writes a Markdown transcript (default `./copilot-session-<ID>.md`), `--share-gist` a secret gist; `/share html` exports interactive HTML; `events.jsonl` under `~/.copilot/session-state/<sessionId>/`; `session.usage.getMetrics` gives per-model token and nano-AI-unit totals; `assistant.usage` events give per-call tokens and multiplier. [Source](https://docs.github.com/en/copilot/reference/copilot-cli-reference/cli-programmatic-reference); [Source](https://docs.github.com/en/copilot/how-tos/copilot-cli/use-copilot-cli/chronicle); [Source](https://docs.github.com/en/copilot/how-tos/copilot-sdk/features/usage-and-billing)

Gate components: Copilot code review and autofix

- Copilot code review posts standard PR review comments labelled High, Medium or Low severity, with suggested changes; by default it leaves a "Comment" review that does not count toward required approvals, but every review includes an approval assessment and, when approvals are enabled (public preview; off by default; configurable at enterprise, org and repo level, with file-path controls), it "can submit an approving review that satisfies your repository's required-approval rule"; new pushes dismiss the approval. Reviews can be requested via REST by adding `copilot-pull-request-reviewer[bot]` as a reviewer, via `gh pr create --reviewer @copilot` or `gh pr edit --add-reviewer @copilot`, or automatically via rulesets ("Review new pushes", "Review draft pull requests"). Review effort levels: Lite (estimated USD 0.05 to 1 of credits per review) and Balanced (USD 0.25 to 5, default); reviews use Actions minutes for agentic context gathering and fall back to a limited review if hosted runners are disabled; environment configurable via `copilot-code-review.yml`; "Fix with Copilot" on a review comment hands the fix to the cloud agent. Comments replying to Copilot are not read by Copilot. [Source](https://docs.github.com/en/copilot/how-tos/use-copilot-agents/use-code-review); [Source](https://docs.github.com/en/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/code-review)
- Autofix: two experiences. Agentic autofix (assign one or more code scanning alerts to Copilot; it explores, fixes, validates by re-running CodeQL with the code scanning query suite, opens a draft PR; consumes Code Security AI credits and Actions minutes; needs org or enterprise enablement; no Copilot licence required; not for EMU repos; cannot confirm fixes for custom queries, `security-extended` or third-party tools) and Copilot Autofix (single suggested change per alert, on by default for CodeQL repos, free of AI credits, available on public repos and GHAS Code Security repos). [Source](https://docs.github.com/en/code-security/concepts/code-scanning/autofix-for-code-scanning)
- [snippet] Copilot Autofix REST endpoints (public preview since Dec 2024): `POST /repos/{owner}/{repo}/code-scanning/alerts/{number}/autofix` to generate, `GET` the same path for status and the fix, `POST .../autofix/commits` to commit it to a branch. [Source](https://github.blog/changelog/2024-12-16-copilot-autofix-can-now-be-generated-with-the-rest-api-public-preview)

### Inferences
- A per-task evidence bundle is achievable without extra tooling: task JSON from the agent tasks API, PR number and head SHA, commit list (each linking to the session), the session log URL (`github.com/copilot/tasks/<id>` style URLs are what the SDK docs show), code review comments via the pulls REST API, check runs, and audit log entries. Pull the session log text through the web UI or `gh agent-task view --log` and store it, since there is no documented REST endpoint returning the log body.
- Cost attribution per task is not available from GitHub billing; estimate it from model and the token usage shown in the session view, or move long loops to SDK sessions where `getMetrics` gives exact totals.
- Code review comments are machine-readable through the standard PR review APIs (severity is in the comment text, not a structured field), so a gate can count unresolved High findings; CodeQL results are available as code scanning alerts and SARIF via the code scanning API.

### Gaps
- No REST endpoint documented for downloading a cloud agent session transcript; only the web viewer and `gh agent-task view --log` were found.
- No documented retention period for cloud agent session logs.
- Severity on code review comments appears as a label in the comment body; no structured severity field in the API was found.
- Whether the session view's "token usage" is exposed via API or export was not found.
