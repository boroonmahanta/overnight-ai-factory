## Key question 1: What does OpenAI (Lopopolo) mean by "harness", and what are its parts?

### Takeaway
A "harness" is everything around a fixed model-plus-agent that lets it recover intent, operate the real system, respect authority, prove its outcome and leave the next run better equipped: AGENTS.md as a map, a docs tree as the knowledge base, custom linters and structural tests that explain the rule when they fail, reviewer agents with a convergence policy, skills and runbooks for repeatable work, observability and a bootable app the agent can drive, and background "garbage collection" agents that prune drift. The practice holds the model constant and improves only the two external levers, context and tools.

### Cited Findings

It improves the two external levers—context and tools—and curates the environment around them. The worker should be able to recover intent, operate the real system, respect authority, prove the outcome, and leave the next run better equipped." — [lopopolo/harness-engineering README](https://github.com/lopopolo/harness-engineering/blob/trunk/README.md)

### Inferences
- "Harness" is broader than "prompt plus tools": it includes the repository's architecture, its executable policy, its review loop and its maintenance loops. Lopopolo's framing makes the repository itself a prompt ("code is prompts for future prompts"), so repo hygiene is a harness concern.
- The parts that OpenAI, Anthropic and Böckeler all converge on are: a short routing instruction file, retrievable docs, deterministic checks that fail with actionable messages, an inferential review layer, and some mechanism to stop stale instructions and stale code from accumulating.

## Key question 2: Which concrete practices did they describe (file layout, keeping docs current, mechanical enforcement of architecture, preventing drift)?

### Takeaway
The practices are: a short AGENTS.md that only routes; a docs tree organised by task class (design docs, product specs, execution plans, references) with machine-checked links and freshness; plans as first-class checked-in artefacts; "one concept, one owner" and finished migrations so the code teaches a single pattern; custom linters and structural tests whose error text carries the remediation; reviewer agents told to bias toward merge; a bootable per-worktree app with browser control and a local observability stack; and scheduled background agents that scan for drift from "golden principles", grade quality, open narrow refactoring PRs and garden stale docs.

### Cited Findings
- Root guide contents (Lopopolo corpus): "A root guide should contain: what the repository is and which compatibility surfaces matter; the operating loop expected for all work; a small set of task classes or golden paths; and links to the domain documents, commands, and proof appropriate to each class. Architecture, dependency posture, generation contracts, runbooks, and domain decisions belong beside the work they govern. Nested guides narrow the route as the worker enters a package or domain." — [docs/just-in-time-context](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/just-in-time-context/README.md)
- How the OpenAI team's docs were kept trustworthy (paraphrase of the OpenAI post via Lopopolo): a monolithic agent manual "grew too large to be useful"; a short root table of contents backed by indexed design documents, product specifications, execution plans and references "made progressive disclosure an owned repository feature. Link and freshness checks kept those routes trustworthy." — [docs/just-in-time-context](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/just-in-time-context/README.md)
- Docs record when they were true: the maintained-document system "records the repository revision where guidance is current" ("They embed git repository revisions of when they are current as of") and "archives guidance when it becomes irrelevant" ("They're sunset and archived when they become irrelevant or features get removed"); gardening agents "garden the individual git repositories that are used to bootstrap all the tasks". — [Aakash Gupta interview with Lopopolo, 25 May 2026, quoted via corpus](https://www.aakashg.com/how-pms-ship-100k-lines-of-code/)
- Lopopolo's three phases of context delivery (AI Native DevCon, 1 Jun 2026, paraphrased in corpus): grounding (a terse map: task class, architecture and decisions, critical journeys, commands to establish current state); the messy middle (let code, tool output, test failures, browser state and logs reveal the next context; "Errors should identify the violated invariant and the likely repair"); review and landing (reapply role-specific reviewers, acceptance criteria and proof requirements once the artefact has a stable shape; "Compress the trajectory into a decision-ready packet that a person can review directly"). — [docs/just-in-time-context](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/just-in-time-context/README.md); [AI Native DevCon transcript](https://tessl.io/registry/ainativedev/aidevcon-2026-ldn/0.100.8/files/talk-lopopolo-harness-engineering/transcript.md)
- Lint-as-context: "I turned on `no-await-in-loop` from ESLint in a large TypeScript codebase, finding 600 violations ... with agents, it is a single PR to both do the lint fixes and exhaustively add test coverage." And: "surface a descriptive failure to the model every time it writes another `fetch` call. The agent does not need to remember the rule up front; the verifier gives it the missing context exactly when it needs it." And: "The higher the agent throughput, the more policy has to be executable. Repeating the same invariant in comments on every agent-authored PR does not scale. If it matters, it belongs in a verifier owned by the repo." — [hyperbo.la, The Production Function Changed, 13 Mar 2026](https://hyperbo.la/w/production-function-changed/)
- A worked example of executable policy in a small repo (Lopopolo's blog, 17 Feb 2026): a `hld/` directory "where local development tools and policy enforcement live. It exists because conventions rot unless they are executable." Custom ESLint rules include `hyperbola/no-fs-imports` and `hyperbola/require-eslint-disable-justification` ("require coding models to justify why they disable lints"); source-structure lints "Ban `.mjs` and `.mts` files", "Forbid coverage-ignore pragmas: prevent coding models from hacking around code that does not enable testability", enforce dependency hygiene via a pnpm workspace catalog, enforce content placement, and even lint smart punctuation in prose. Vitest configs "enforce 100% thresholds for lines, functions, branches, and statements" because "There is zero incremental effort to do 80% coverage vs. 100%." — [hyperbo.la, 17 Feb 2026](https://hyperbo.la/w/harness-engineering-the-blog-build/)
- Architecture as a hard contract document: `docs/FRONTEND_ARCHITECTURE.md` opens "This document is a hard architecture contract for frontend code in this repository. If implementation diverges, code must be updated to match this document. Do not add workaround layers." Its "Non-Negotiable Rules" begin "Fix architecture, do not work around architecture" and "If blocked, report the concrete error and propose a proper architectural solution"; it ends with a "Banned Patterns" list and a "Validation Checklist" (`pnpm run lint`, `pnpm run test`, `pnpm run build`, plus manual confirmations). — [hyperbo.la, 17 Feb 2026](https://hyperbo.la/w/harness-engineering-the-blog-build/)
- Structural tests and diagnostics (corpus): "Architecture documents name package ownership and dependency direction. Structural tests enforce those relationships. Custom diagnostics explain the governing model and point the agent toward the proper repair, so a failed check supplies the missing context at the moment it is useful." — [docs/domain-modeling](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/domain-modeling/README.md)
- Why consistency matters ("code is prompts"): Lopopolo in the Aakash interview: "the code in the repository is prompts"; uniform structure lets the agent "more effectively cargo cult". The corpus: "One observability pattern lets context from one part of the repository apply elsewhere; six stacks require the agent to research which one belongs at each call site." Warning signs of duplicated ownership: "a second parser for a language the repository already models; exact tool versions copied into policy code and fixtures; JSON or YAML assembled from string fragments; commands that reimplement domain behavior; untyped external data flowing into internal code; and several defensive checks protecting the same invariant." — [docs/domain-modeling](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/domain-modeling/README.md); [Aakash interview](https://www.aakashg.com/how-pms-ship-100k-lines-of-code/)
- Finish migrations: "Leaving old and new patterns side by side makes both available as prompt material. A finished migration removes that ambiguity, and a ratchet turns the new pattern into durable context." The OpenAI post "observes that Codex reproduces uneven or suboptimal local patterns. A half-finished migration therefore creates competing prompts, and a bad helper can spread through every package". — [docs/domain-modeling](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/domain-modeling/README.md)
- Garbage collection (OpenAI post via corpus and search): "On a regular cadence, we have a set of background Codex tasks" that "scan for deviations from golden principles, update quality grades, open focused refactoring pull requests, and garden stale documentation. Small repairs land before a bad pattern can become prompt material for future changes." The corpus says these "replace a weekly human cleanup session." — [docs/continuous-maintenance](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/continuous-maintenance/README.md); [OpenAI post](https://openai.com/index/harness-engineering/)
- Feedback encoded as infrastructure (OpenAI post fragment): "Review comments, refactoring pull requests, and user-facing bugs are captured as documentation updates" and tooling. Lopopolo's promotion ladder: prompt adjustment and reroll while framing is being discovered; routing doc, runbook or skill when "stable knowledge must appear at a particular decision point"; reviewer when judgment "is qualitative, cross-cutting, or still gaining nuance"; type, API or domain tool when "the system can make correct use natural and misuse difficult"; lint, test or policy check when "a deterministic invariant should block recurrence"; architecture or migration when "repeated defects expose the wrong owner or dependency direction". — [docs/feedback](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/feedback/README.md)
- Steering-to-validator progression, Lopopolo (Tessl podcast, 9 Jun 2026, fragment): "the cheapest thing I can do is literally produce a change to my prompt ... making deterministic tests that suss out this behavior". — [Tessl podcast 109](https://tessl.io/podcast/109/)
- A concrete "missing-decision" case (OpenAI Build Hour, 10 Mar 2026, paraphrased in corpus): a product team's security-approved cryptography choice lived in an old Slack thread; Codex added a different npm crypto dependency; the team "encoded a repository rule requiring the security-approved implementation and forbidding alternate npm cryptography packages, and reran the change under that constraint." — [docs/feedback](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/feedback/README.md); [Build Hour transcript](https://rewiz.app/channels/%40openai/build-hour-api-codex)
- Reviewer convergence: "Implementation agents must acknowledge review feedback, but they can accept and fix, accept and defer, or push back. Reviewer agents are told to bias toward merging and only surface P2s and above. Without that guidance, the reviewers endlessly bully the implementer and nothing converges." — [hyperbo.la, What Does It Mean to Do a Good Job?, 10 Apr 2026](https://hyperbo.la/w/what-does-it-mean-to-do-a-good-job/)
- Giving the agent the real system (OpenAI post via corpus): "per-worktree application instances and ephemeral observability stacks that let Codex reproduce bugs, query logs and metrics, drive the UI, and validate its own changes"; the team's "local browser shell" mounted the UI "with Chrome DevTools already connected"; an Electron "component workbench" let Codex compose screens from production design-system components and return screenshots to a designer; a teammate replaced an MCP connection with "a local TypeScript daemon and a small CLI because the worker needed only two or three operations". — [docs/proof](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/proof/README.md); [docs/tool-legibility](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/tool-legibility/README.md)
- Tool output as context: tests and formatters that "only output the failing parts of the tests" (Latent Space fragment); the corpus warns that agents preemptively pipe `cargo test` through `head` or `tail`, which can kill the process or hide exit status, so "A repository-owned wrapper or test reporter should run the complete job once, preserve its true status and full output, return a semantic failure summary, and make the underlying evidence queryable without rerunning the test." — [docs/tool-legibility](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/tool-legibility/README.md)
- Inner-loop latency as a harness property: when GPT-5.3 added background shells the worker became "less willing to wait for a blocking build", so "Over one week, the team moved from a bespoke Makefile through Bazel and Turbo to Nx, stopping once the build loop completed in under roughly one minute"; a slower build "triggered another decomposition of the build graph." — [docs/effectiveness](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/effectiveness/README.md); [Latent Space fragment](https://www.latent.space/p/harness-eng)
- Skills vs runbooks (corpus): "A skill teaches an approach to the job ... Long imperative skills can overfit one path and make the worker refuse sensible exceptions." A documented failure: a push-PR skill that required a green local build refused to open an early draft PR that collaborators needed in order to help fix the build. "A runbook is a versioned contract for repeatable work. It records intent, preconditions, steps, safety boundaries, evidence, escalation, and rollback." A large skill library can live outside the scanned path with "a gitignored linking area" exposing "a small task-relevant set" per trajectory. — [docs/just-in-time-context](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/just-in-time-context/README.md); [docs/whole-job](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/whole-job/README.md)
- Test the docs in a fresh session: "The presence of a document proves only that it was written." Lopopolo's ablation framing "removes context or tools and measures whether performance regresses." — [docs/just-in-time-context](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/just-in-time-context/README.md); [docs/lineage](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/lineage/README.md)
- Anthropic's CLAUDE.md guidance (Claude Code docs, accessed 24 Oct 2026) matches the "map, not manual" view: "CLAUDE.md is loaded every session, so only include things that apply broadly. For domain knowledge or workflows that are only relevant sometimes, use skills instead." "Keep it concise. For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it. Bloated CLAUDE.md files cause Claude to ignore your actual instructions!" Include: bash commands Claude can't guess, style rules that differ from defaults, testing instructions, repository etiquette, project-specific architectural decisions, env quirks, gotchas. Exclude: anything derivable from code, standard conventions, detailed API docs, frequently changing information, file-by-file descriptions. "Treat CLAUDE.md like code: review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts." — [Claude Code best practices](https://www.anthropic.com/engineering/claude-code-best-practices)
- Advisory vs deterministic: "Unlike CLAUDE.md instructions which are advisory, hooks are deterministic and guarantee the action happens." Example prompts: "Write a hook that runs eslint after every file edit" or "Write a hook that blocks writes to the migrations folder." — [Claude Code best practices](https://www.anthropic.com/engineering/claude-code-best-practices)
- Anthropic's context-engineering principle: "good context engineering means finding the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome"; "context rot" means recall degrades as tokens grow, so context "must be treated as a finite resource with diminishing marginal returns"; Claude Code uses a hybrid where "CLAUDE.md files are naively dropped into context up front, while primitives like glob and grep allow it to navigate its environment and retrieve files just-in-time". — [Anthropic, Effective context engineering for AI agents, 29 Sep 2025](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Anthropic's long-running harness post also found format matters: "we landed on using JSON for this, as the model is less likely to inappropriately change or overwrite JSON files compared to Markdown files." — [Anthropic, Effective harnesses for long-running agents, 26 Nov 2025](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Horthy's complementary practice (HumanLayer, Aug 2025): a research/plan/implement workflow that keeps context utilisation "in the 40%-60% range", with reusable prompt files checked into `.claude/commands/` (research_codebase.md, create_plan.md, implement_plan.md); "A bad line of code is… a bad line of code. But a bad line of a plan could lead to hundreds of bad lines of code. And a bad line of research ... could land you with thousands of bad lines of code." — [HumanLayer, Advanced Context Engineering for Coding Agents](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md)

### Inferences
- The recurring design pattern across OpenAI and Anthropic is "shift knowledge from advisory prose into something that fires at the moment of need": a lint error, a structural test, a hook, a failing browser journey. Prose is for routing and judgment; mechanics are for invariants.
- Drift prevention has two paths in Lopopolo's model: forward (put the invariant at its earliest owner, usually a type or lint) and backward (migrate the existing population in one PR so no counterexample remains as precedent). The background GC agents are the backward path running continuously.
- For a repo like this one (hand-curated YAML, build-time geometry, hard editorial rules), the direct analogue is: schema validation plus custom lint rules for the CLAUDE.md "hard rules" (year-proportional X axis, no stream shapes, citation count, spelling, punctuation), each with an error message that names the rule and the fix.

## Key question 3: What did Lopopolo say the human's job becomes, and what stays with humans?

### Takeaway
Humans move from implementation to choosing invariants, setting the acceptance bar, deciding what to build, holding authority at consequential boundaries, and judging proof. What stays human: zero-to-one product definition, difficult interface refactors where the interface shape is unknown, consequential or irreversible mutations (merges past protected branches, production cutovers, new credentials), and deciding whether evidence is sufficient.

### Cited Findings
- "In these workflows, human implementation is no longer the constraint. The scarce work is choosing the invariant and deciding whether the proof is sufficient." — [hyperbo.la, The Production Function Changed, 13 Mar 2026](https://hyperbo.la/w/production-function-changed/)

### Inferences

## Key question 4: What does Brennan (OpenHands) say about task scoping, definition of done, the execute-inspect-repair loop, and failure modes?

## Key question 6: Patterns for an unattended multi-hour run

### Takeaway
The documented patterns are: a repository-owned contract the run reads at start (WORKFLOW.md or an init.sh plus progress file plus feature list), one feature at a time with a commit and a progress note after each, a check the agent can run (tests, build, browser journey) that gates "done", a hard rule against editing the tests or feature list, bounded concurrency with stall timeouts and exponential-backoff retries, a sub-minute inner loop, authority that stops at a human handoff state (draft PR, "Human Review"), and a fresh-context adversarial reviewer before the run claims completion.

### Cited Findings
- Lopopolo's overnight workflow: "My laptop hums with its lid half closed at night ... running `caffeinate -sdi` so a PR or three can get authored, pushed, reviewed, and merged while I'm asleep. When I want an end-to-end run, I prompt Codex with `$task $launch-app $local-obs $commit $push $land $github-pr-media` and let it rip." — [hyperbo.la, 13 Mar 2026](https://hyperbo.la/w/production-function-changed/)
- Preconditions for a background task: "A background task needs enough context to identify the correct change, static guardrails to prevent obvious regressions, and an acceptance procedure that produces evidence for review. If those pieces exist, the work does not need to wait for a sprint slot. The agent can execute asynchronously, attach tests, logs, or screenshots to the PR, and ask a human for a merge decision rather than implementation time." — [hyperbo.la, Software Work Is No Longer Scheduled, 13 Mar 2026](https://hyperbo.la/w/software-work-not-scheduled/)
- What a maintenance runbook must tell the agent (corpus): "which external and repository state to inspect; how to decide whether work is needed; which changes fall inside the standing mandate; which checks establish a safe candidate; which mutations require human approval; how to prove the real outcome; what to record when the run changes nothing; how to recover after partial progress; and when the runbook or the loop itself should be retired." A loop "should finish in one of a small number of durable states: nothing needed, candidate proposed, change proved, approval requested, recovery required, or policy obsolete. Quiet no-op runs are healthy. Repeated rediscovery of the same facts signals missing state." Escalation "should carry a decision-ready packet: current state, attempted work, evidence, risk, and the smallest unresolved choice." — [docs/continuous-maintenance](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/continuous-maintenance/README.md)
- Task closure checklist for ordinary software work (corpus): retrieve context; reproduce or inspect current behaviour; implement the root correction; update generated artefacts and public contracts; run focused and system-level proof; adversarially review; respond to material review and CI failures; obtain required approval; merge or deploy through the normal protected path; verify the user-visible result. — [docs/whole-job](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/whole-job/README.md)
- Keep durable intent sparse: "Long Codex trajectories repeatedly compact their active history ... user intent remains a high-signal influence while older tool results are more likely to be summarized or pruned ... Keep that channel focused on the outcome, acceptance bar, and authority boundary." Narrow policy should instead arrive via repository reads, test failures and focused reviewers, with "a short repository route" so the worker can retrieve the rule again after compaction. — [docs/whole-job](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/whole-job/README.md)
- Planning for long runs: the OpenAI post treats plans as checked-in artefacts, "reviewed separately, updated as evidence changes, and carried across a long trajectory" (paraphrase of corpus; fragment "Plans are treated as first-class artifacts"). — [docs/whole-job](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/whole-job/README.md)
- Disposable probe before a hard cutover (Tessl podcast, 9 Jun 2026, fragment "50,000 line of diff PR and throw it away"): Lopopolo lets the agent produce an exploratory diff of up to roughly 50,000 lines, pushes it for inspection, discards it, and turns the failure map into "roughly fifteen preparation and staging pull requests before returning to the cutover." — [docs/effectiveness](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/effectiveness/README.md); [Tessl podcast 109](https://tessl.io/podcast/109/)
- Small harness tweaks change wall-clock: an instruction to sleep while long queries are pending "produced a reported threefold wall-clock reduction without changing the underlying query." — [docs/effectiveness](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/effectiveness/README.md)
- Symphony (OpenAI, open-source spec, announced about 27 Apr 2026): "a long-running automation service that continuously reads work from a configured issue tracker, creates an isolated workspace for each issue, and runs a coding agent session for that issue inside the workspace." It "keeps the workflow policy in-repo (`WORKFLOW.md`) so teams version the agent prompt and runtime settings with their code." Defaults: poll every 30 s; `max_concurrent_agents` 10; `max_turns` 20 per worker session; `turn_timeout_ms` 1 hour; `stall_timeout_ms` 5 minutes ("If `elapsed_ms > codex.stall_timeout_ms`, terminate the worker and queue a retry"); failure retries use `delay = min(10000 * 2^(attempt - 1), agent.max_retry_backoff_ms)` capped at 5 minutes; clean exits get a 1 s continuation retry to re-check whether the issue is still active; reconciliation stops runs whose tracker state became terminal or ineligible; restart recovery is tracker- and filesystem-driven with no database; `WORKFLOW.md` is hot-reloaded and "Invalid reloads MUST NOT crash the service; keep operating with the last known good effective configuration". Hooks (`after_create`, `before_run`, `after_run`, `before_remove`) run with a 60 s default timeout. "A successful run can end at a workflow-defined handoff state (for example `Human Review`), not necessarily `Done`." Host-side tracker secrets "SHOULD NOT be inherited by the coding-agent child process." — [openai/symphony SPEC.md (Draft v1), accessed 24 Oct 2026](https://github.com/openai/symphony/blob/main/SPEC.md)
- Symphony README: "Symphony works best in codebases that have adopted harness engineering. Symphony is the next step -- moving from managing coding agents to managing work that needs to get done." Agents "provide proof of work: CI status, PR review feedback, complexity analysis, and walkthrough videos. When accepted, the agents land the PR safely." It is "a low-key engineering preview for testing in trusted environments." Secondary reports of internal impact disagree (fivefold vs sixfold increase in landed PRs in the first three weeks). — [openai/symphony README](https://github.com/openai/symphony/blob/main/README.md); [OpenAI Symphony post](https://openai.com/index/open-source-codex-orchestration-symphony/); [Tessl blog](https://tessl.io/blog/openai-open-sources-symphony-a-spec-for-orchestrating-codex-agents)
- Codex `/goal` for persistent objectives (Lopopolo, 17 Jul 2026): "A goal is a process for doing and discovering work which itself spawns tasks (e.g. 'keep p95 CI latency under N minutes') ... The loop does not terminate when one patch lands; instead, it keeps observing the metric, generating interventions, testing them, and asking for human review when it needs authority." Footnote: Codex "continues planning, acting, testing, and iterating until the goal is achieved, paused, or constrained by budget." — [hyperbo.la, Code Reds Need Maintenance Loops](https://hyperbo.la/w/code-reds-need-maintenance-loops/); [OpenAI cookbook on goals](https://developers.openai.com/cookbook/examples/codex/using_goals_in_codex)
- Anthropic's long-running harness (26 Nov 2025): "even a frontier coding model like Opus 4.5 running on the Claude Agent SDK in a loop across multiple context windows will fall short of building a production-quality web app if it's only given a high-level prompt". Failure modes: "the agent tended to try to do too much at once—essentially to attempt to one-shot the app"; "a later agent instance would look around, see that progress had been made, and declare the job done"; marking features complete without end-to-end testing; time wasted figuring out how to run the app. Solutions: an initializer agent writes `init.sh`, `claude-progress.txt`, an initial git commit, and a `feature_list.json` of "over 200 features" all marked `"passes": false`; coding agents "work on only one feature at a time", commit with descriptive messages, update the progress file, and may change only the `passes` field ("It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality"); every session starts with `pwd`, reading progress and git log, running `init.sh` and a basic end-to-end smoke test via Puppeteer before new work. — [Anthropic, Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Anthropic's walk-away test: "Give Claude a check it can run: tests, a build, a screenshot to compare. It's the difference between a session you watch and one you walk away from." "Claude stops when the work looks done. Without a check it can run, 'looks done' is the only signal available". Gating options: in-prompt iterate; a `/goal` condition re-checked after every turn ("If Claude stalls, Claude Code eventually stops the run with the goal still set"); "a Stop hook runs your check as a script and blocks the turn from ending until it passes"; a verification subagent "so the agent doing the work isn't the one grading it." "The /goal and Stop hook versions are what let an unattended run finish correctly without you." "Have Claude show evidence rather than asserting success". — [Claude Code best practices](https://www.anthropic.com/engineering/claude-code-best-practices)
- Unattended fan-out (Anthropic): loop `claude -p` over a task list with `--allowedTools "Edit,Bash(git commit *)"` and `--permission-mode dontAsk` ("denies anything else that would need approval, which matters when you're running unattended"); "Test on a few files, then run on all of them"; auto mode uses a classifier that blocks "scope escalation, unknown infrastructure, and hostile-content-driven actions". Adversarial review: "The longer Claude works unattended, the more an independent check matters before you count the work as done." — [Claude Code best practices](https://www.anthropic.com/engineering/claude-code-best-practices)
- Context techniques for long horizons (Anthropic): compaction (Claude Code keeps the summary "plus the five most recently accessed files"); "tool result clearing" as the lightest-touch compaction; structured note-taking (a `NOTES.md`); sub-agents that each use tens of thousands of tokens but return "1,000-2,000 tokens". — [Anthropic, Effective context engineering, 29 Sep 2025](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Horthy's "ralph" loop reference: "running an agent in a while loop forever with a simple prompt" (`while :; do cat PROMPT.md | npx --yes @sourcegraph/amp; done`), which a hackathon team used to "(mostly) port BrowserUse to TypeScript overnight". — [ACE-FCA](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/ace-fca.md); [Geoffrey Huntley, Ralph](https://ghuntley.com/ralph/)
- Horthy's counter-pattern: ship "vertical slices" (API contract with mock data, then UI, then wiring, then DB) rather than the model's preferred "horizontal plans" (migrations, service, API, frontend), and "send off a model to do 1-3 slices at a time, and review the code as I go. It's a lot easier to resteer early on ... than to end up on the other side of 2k+ lines of code with no idea what's broken." — [Why Software Factories Fail](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)
- Authority during unattended runs (corpus): "Let the worker inspect, edit, build, test, simulate, and iterate where effects are isolated and recoverable. Most mistakes in that envelope are inexpensive feedback." Credentials should be brokered by a sidecar so the key "stays out of model context and the repository"; "Endpoint-bound access adds an independent revocation boundary ... A grant can expire or be withdrawn even when a trajectory is still running." — [docs/authority](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/authority/README.md)
- Agent self-report as telemetry, not policy: Lopopolo's MLD files (`MISTAKES.md`, `LEARNINGS.md`, `DESIRES.md`) are "agent-emitted telemetry for the harness builder"; "Corroborate those self-reports before publishing them as context." OpenAI's "confessions" research is cited as sharpening why such reflection "remains low-trust telemetry until traces, tests, review, and outcomes corroborate it." — [docs/just-in-time-context](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/just-in-time-context/README.md); [sources README](https://github.com/lopopolo/harness-engineering/blob/trunk/sources/README.md)
- Nightly distillation (AI Native DevCon, 1 Jun 2026, fragment "Every review comment, every night"): collect review comments, interrupted runs, agent interventions, failed builds and production exceptions, then have agents propose durable improvements; Lopopolo also describes collecting all Codex trajectories to "slurp them up and distill them" and "Running agent loops over them every day" (Latent Space fragments). — [docs/continuous-maintenance](https://github.com/lopopolo/harness-engineering/blob/trunk/docs/continuous-maintenance/README.md); [Latent Space](https://www.latent.space/p/harness-eng)

### Inferences
- Combining OpenAI and Anthropic, an overnight run for this repository would want: (1) a checked-in run contract (what to build, in what order, how to prove each step, where to stop); (2) a machine-readable feature or phase list the agent may only flip to "passes"; (3) `pnpm` scripts that fail fast with the rule name (schema validation, octilinear geometry checks, spelling and punctuation lints, citation-count checks); (4) a Stop hook or goal condition that refuses to end a turn until lint, tests and build pass; (5) one commit and progress note per completed phase; (6) a fresh-context reviewer before any PR is marked ready; (7) authority that ends at a draft PR for a human to merge.
- The strongest shared warning is "declare victory too early": every reachable harness guide adds a mechanical gate against it because instructions alone do not hold.

### Gaps
- No reachable source gives a tested recipe for a single-agent, single-repo overnight run on a Node/pnpm project with screenshots as acceptance evidence; the closest are Anthropic's web-app demo (Puppeteer MCP) and Lopopolo's `$github-pr-media` skill, whose contents are not public.
- Symphony's observed internal effect ("fivefold" vs "sixfold" PRs in three weeks) is inconsistent across secondary sources and OpenAI's post could not be read.
- The "~500 lines of rules" compliance threshold that one search summary attributed to a practitioner could not be pinned to a source (candidates: [O'Reilly Radar](https://www.oreilly.com/radar/agent-harness-engineering/), [Addy Osmani](https://addyosmani.com/blog/agent-harness-engineering/)); treat as unverified.
