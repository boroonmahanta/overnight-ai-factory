# AI coding agents building Power Platform and Copilot Studio work as code (as of 1 November 2026)

Conventions: every claim carries a source link and the date the source was read (1 Nov 2026) plus the source's own date where shown. [snippet] = only a search summary was available. [secondary] = third-party write-up. No em-dashes by house rule.

## Q1. Power Apps code apps: status, CLI, TypeScript and connectors, deploy, licensing, AI-agent positioning

### Takeaway
Code apps are a first-class, code-first SPA hosting option on Power Platform with a new npm-based `pa` CLI that has a documented service-principal, non-interactive `pa app push` for CI. Microsoft explicitly positions them for AI coding agents through the `code-apps-preview` plugin in the `microsoft/power-platform-skills` marketplace, which works in GitHub Copilot CLI and Claude Code.

### Cited Findings
- Code apps let developers build SPAs (React, Vue, others) in a code-first IDE and run them on Power Platform, with Entra auth, 1,500+ connectors callable from JavaScript, and Managed Platform policy enforcement (sharing limits, Conditional Access, DLP). The overview page carries no "preview" banner as read on 1 Nov 2026. ([Power Apps code apps overview](https://learn.microsoft.com/power-apps/developer/code-apps/overview), read 1 Nov 2026)
- Prerequisites: IDE, Node.js LTS, Git, Power Apps CLI. An admin must turn on "Enable code apps" per environment in PPAC (Settings > Product > Features), or at scale through environment groups and rules. ([overview](https://learn.microsoft.com/power-apps/developer/code-apps/overview), read 1 Nov 2026)
- Licensing: end users need Power Apps Premium, or pay-as-you-go, or an App Pass, or auto-claim of a premium licence. ([overview](https://learn.microsoft.com/power-apps/developer/code-apps/overview), read 1 Nov 2026)
- Limitations that matter for a factory: code apps do NOT support Power Platform Git integration; no SAS IP binding (assets served from a public endpoint, use Conditional Access by location instead); no Secure Implicit Connections yet; not in Power Apps for Windows; no PowerBIIntegration function; no SharePoint forms integration. ([overview](https://learn.microsoft.com/power-apps/developer/code-apps/overview), read 1 Nov 2026)
- CLI change: `pac code` is now marked "(Preview)" and will be deprecated. From Power Apps SDK (`@microsoft/power-apps`) v1.0.4 an npm-based CLI ships; Microsoft says to use it instead. `pac code` subcommands: `init`, `add-data-source`, `delete-data-source`, `list`, `list-connection-references`, `list-datasets`, `list-sql-stored-procedures`, `list-tables`, `push`, `run`. ([pac code reference](https://learn.microsoft.com/power-platform/developer/cli/reference/code), read 1 Nov 2026)
- New CLI is `pa` (`npm install --global @microsoft/power-apps-cli`). Command groups: `pa app`, `pa auth`, `pa connection`, `pa connector`, `pa solution`, `pa telemetry`. Key commands: `pa app init`, `pa app add data-source`, `pa app add dataverse-api`, `pa app add flow`, `pa app push [--solution-id] [--non-interactive]`, `pa app share --principal --access play|edit`, `pa connection create --connector ... --json`, `pa connector list --json`, `pa solution list --json`. Most parameters have `PA_CLI_*` environment variable equivalents. In non-interactive mode, `pa app add data-source` fails until `--as table|action` is given. ([Power Apps CLI command reference](https://learn.microsoft.com/power-apps/developer/code-apps/reference/cli), read 1 Nov 2026)
- Quickstart scaffold: `npx degit github:microsoft/PowerAppsCodeApps/templates/vite my-app`, then `pa app init --display-name ... --environment-id ...`, `pa app run`, `npm run build`, `pa app push`. ([Quickstart: create a code app using the Power Apps CLI](https://learn.microsoft.com/power-apps/developer/code-apps/how-to/create-an-app-from-scratch), read 1 Nov 2026)
- TypeScript and connectors: adding a data source generates typed model and service files (for example `Office365UsersModel.ts`, `Office365UsersService.ts` under `src/generated/`), with CRUD methods for tabular sources (`create`, `update`, `delete`, `get`, `getall`). The doc says the edits after adding data sources can be done "by using an agent in your IDE", naming GitHub Copilot agent mode. ([Connect your code app to data](https://learn.microsoft.com/power-apps/developer/code-apps/how-to/connect-to-data), read 1 Nov 2026)
- Flows: `pa app add flow --flow-id` downloads the flow's OpenAPI definition and generates typed TS models and services. Only instant flows with the Power Apps trigger, solution-aware only, and the person running it must have access to the flow and its connections. ([Add Power Automate flows to a code app](https://learn.microsoft.com/power-apps/developer/code-apps/how-to/add-flows), read 1 Nov 2026)
- Architecture: `power.config.json` holds metadata used by CLI and client library for connections and publishing; client library `@microsoft/power-apps` (reference page shows version 1.2.2) gives connector access plus app, user and host context. ([Code apps architecture](https://learn.microsoft.com/power-apps/developer/code-apps/architecture); [client library reference](https://learn.microsoft.com/javascript/api/powerapps-sdk-node/power-apps-client-lib-code-apps?view=powerapps-js-latest), read 1 Nov 2026)
- Headless deploy: set `PA_CLI_USE_SP_AUTH=true`, `PA_CLI_SP_CLIENT_ID`, `PA_CLI_SP_CLIENT_SECRET`, `PA_CLI_SP_TENANT_ID`, then `pa app push --non-interactive`. Exit code 0 means published. Catch: a maker must first share the app with the service principal with `edit` access (`pa app share --principal <Enterprise Application object ID> --access edit`), once, from an interactive session. "A service principal can't grant itself access." Only client secret is documented (no OIDC or federated credential option on this page). ([Publish code apps with a service principal](https://learn.microsoft.com/power-apps/developer/code-apps/how-to/use-service-principal), read 1 Nov 2026)
- AI-agent positioning: Microsoft's "Quickstart: Build a code app with GitHub Copilot" uses Copilot CLI with `/plugin marketplace add microsoft/power-platform-skills` then `/plugin install code-apps-preview@power-platform-skills`, then `/code-apps-preview:create-app`. The plugin "checks and installs dependencies", scaffolds, inits, adds connectors, implements UI and can deploy. The page says the same plugin works with Claude Code "through Open Plugins". ([Quickstart: Build a code app with GitHub Copilot](https://learn.microsoft.com/power-apps/developer/code-apps/how-to/quickstart-github-copilot), read 1 Nov 2026)
- Related: "vibe apps" in Power Apps can be converted into code apps, after which they are managed with code-app ALM tooling. ([Convert a vibe app to a code app](https://learn.microsoft.com/power-apps/vibe/convert-vibe-to-code), read 1 Nov 2026)

### Inferences
- For an unattended factory, `pa` + service principal + `--non-interactive` is the deploy path. The first share-to-SP step is a one-time human bootstrap per app, so the factory needs a "first publish" runbook step done by a maker.
- The plugin name `code-apps-preview` signals the agent skills are still preview even if the hosting feature itself reads as GA. Treat skills as useful but unstable.
- Because code apps are excluded from Power Platform Git integration, source control is the repo itself (the SPA source plus `power.config.json`), and solution membership is via `--solution-id` on push.

### Gaps
- I did not find an explicit GA date for code apps in this pass (only that the overview has no preview banner and `pac code` is labelled preview).
- No OIDC or workload identity federation option is documented for `pa` (client secret only on the SP page).

## Q2. Copilot Studio agents as code: file format, `pac copilot`, VS Code extension, source control, what is still portal-only

### Takeaway
Copilot Studio agents now have a real file-based loop: `pac copilot init | clone | pull | push | pack` gives a CLI-driven, Git-friendly workspace of YAML files (`agent.mcs.yaml`, `topics/*.mcs.yaml`, `actions/`, `knowledge/`, `workflows/*/workflow.json`, `settings.mcs.yml`, `connectionreferences.mcs.yml`), and `pack` builds a solution zip offline for CI. Microsoft's own docs name GitHub Copilot and Claude Code as supported editors of these files. Connections and consent, live testing, and harness choice still lean on the portal or interactive sign-in.

### Cited Findings
- `pac copilot` sync loop: `init` (scaffold, or with `--environment` scaffold + pack + import + connect in one step), `clone` (download existing agent with sync metadata), `pull` (three-way merge of server state into local files), `push` (upload only what changed, "including knowledge files, cloud flows, and connection references"; stops if the same item changed on the server), `pack` (workspace to solution `.zip` for `pac solution import`). ([pac copilot reference](https://learn.microsoft.com/power-platform/developer/cli/reference/copilot), read 1 Nov 2026)
- `pac copilot pack` "is a local operation ... needs no authentication and no environment, so it's safe to run in a build pipeline". `pack` works for both classic and CLI-authored (CliCopilot) workspaces. ([pac copilot reference](https://learn.microsoft.com/power-platform/developer/cli/reference/copilot), read 1 Nov 2026)
- `pac copilot init --authoring-mode cli-copilot` scaffolds a "CLI-authored CliCopilot agent"; default is `classic`. `init` local mode needs no sign-in. Schema name defaults to `{publisher-prefix}_{sanitized-name}`. A new environment can fail first import with "Async operations are currently disabled for this organization", retry after a minute or two. ([pac copilot reference](https://learn.microsoft.com/power-platform/developer/cli/reference/copilot), read 1 Nov 2026)
- `pull` and `push` take no `--environment`; they read target agent and environment from the workspace sync metadata and fail with "workspace not found" outside a `clone`/`init` folder. "A successful push mutates the live agent." ([pac copilot reference](https://learn.microsoft.com/power-platform/developer/cli/reference/copilot), read 1 Nov 2026)
- Other `pac copilot` commands: `create` (from template YAML), `extract-template`, `extract-translation` / `merge-translation` (resx or json localisation), `list`, `publish`, `delete`, `status`, `quarantine`, `model list|predict|prepare-fetch`, and `mcp --run` (local PAC CLI MCP server). ([pac copilot reference](https://learn.microsoft.com/power-platform/developer/cli/reference/copilot), read 1 Nov 2026)
- Cloned folder layout (standard harness): `actions/*.mcs.yml` (connectors), `knowledge/files/`, `topics/*.mcs.yaml`, `workflows/<name>/metadata.yaml` + `workflow.json`, `trigger/*.mcs.yaml`, `agent.mcs.yaml` (main definition), `icon.png`, `settings.mcs.yml`, `connectioreferences.mcs.yml` [sic in doc]. ([Clone your agent in VS Code](https://learn.microsoft.com/microsoft-copilot-studio/visual-studio-code-extension-clone-agent), read 1 Nov 2026)
- Editable as files via the extension: knowledge sources, knowledge files, tools, topics (AdaptiveDialog YAML with Power Fx conditions such as `condition: =Topic.Continue = true`), triggers (`kind: ExternalTriggerConfiguration`), and Azure Bot Service skills. Tools include prompts, Power Automate workflows, CUA tools, custom connectors, REST APIs and MCP connectors. New knowledge files dropped into `knowledge/files` upload on apply. ([VS Code extension overview](https://learn.microsoft.com/microsoft-copilot-studio/visual-studio-code-extension-overview); [Edit agent components](https://learn.microsoft.com/microsoft-copilot-studio/visual-studio-code-extension-edit-agent-components), read 1 Nov 2026)
- The VS Code extension is GA. Microsoft lists "Agent-driven development: use Visual Studio Code with GitHub Copilot, Claude Code, or your favorite agent to create and update Copilot Studio agent definition components" as a supported scenario. Issues tracked at github.com/microsoft/vscode-copilotstudio. ([VS Code extension overview](https://learn.microsoft.com/microsoft-copilot-studio/visual-studio-code-extension-overview), read 1 Nov 2026)
- Sync semantics in the extension: Preview, Get, Apply. Apply "modifies the live agent immediately" but "isn't the same as a publish operation" and does not publish. Apply is blocked if remote changes have not been fetched. Testing after apply is done in the Copilot Studio test pane in the browser. ([Synchronize your changes](https://learn.microsoft.com/microsoft-copilot-studio/visual-studio-code-extension-synchronization), read 1 Nov 2026)
- Multi-environment: Microsoft recommends solutions and pipelines for dev, test, prod; extension "Reattach Agent" can point a folder at another environment but Microsoft frames that as the non-solution path. ([Clone your agent in VS Code](https://learn.microsoft.com/microsoft-copilot-studio/visual-studio-code-extension-clone-agent), read 1 Nov 2026)
- The extension repo README shows two agent shapes: `classic` (`agent.mcs.yml`: topics, actions, knowledge files, AI prompts, workflow, custom connector, sub-agent, connection references) and `cli` (`agent.sync.yaml`: "behaviors (skills with `SKILL.md` and scripts), knowledge capabilities, a workflow, connection references under `infrastructure/`"), plus a standalone `workflow.sync.yaml` cloud flow shape. Its E2E tests also exercise compatibility with `pac` and a separate `msagent` CLI (`msagent auth login`, `msagent agent delete`). ([microsoft/vscode-copilotstudio README](https://github.com/microsoft/vscode-copilotstudio), read 1 Nov 2026 via raw.githubusercontent.com)
- Harness split: Copilot Studio now has a standard harness (topics, rule-based), a "GitHub Copilot harness" (goal-driven, skills, memory, Bash sandbox, hooks replace topics, prompts replaced by skills, usage-based Copilot Credits) and a Customer Conversation harness. Agents cannot move between standard and GitHub Copilot harness. The VS Code clone docs say they apply to the standard harness. Microsoft states the GitHub Copilot harness is a Copilot Studio framework, "not the GitHub Copilot service", and customer data is not sent to the GitHub Copilot service. ([Harnesses in Copilot Studio](https://learn.microsoft.com/microsoft-copilot-studio/harnesses-overview); [GitHub Copilot harness overview](https://learn.microsoft.com/microsoft-copilot-studio/agents-experience/overview), read 1 Nov 2026)
- GitHub Copilot harness agents cannot be called from a Power Automate cloud flow via the Copilot Studio connector; use the agent node in a Copilot Studio workflow instead. ([Call Copilot Studio agents from Power Automate](https://learn.microsoft.com/power-automate/call-copilot-studio-agent), read 1 Nov 2026)
- Still portal or interactive: connection creation and consent ("Complete any required sign-in or consent through the supported interactive experience"; "Otherwise, complete setup through the Copilot Studio web experience"). ([Connect to Copilot Studio with MCP](https://learn.microsoft.com/microsoft-copilot-studio/agents-experience/copilot-studio-mcp), read 1 Nov 2026). Agent identities (Entra Agent IDs) are auto-managed; you cannot bring your own. ([Agent identities and authentication](https://learn.microsoft.com/microsoft-copilot-studio/govern-agents-identities-overview), read 1 Nov 2026). Agent accounts (Frontier preview) are created in the Copilot Studio Preview portal before first publish. ([Give your agent an account](https://learn.microsoft.com/microsoft-copilot-studio/agents-experience/authoring-agent-account), read 1 Nov 2026)
- `pac auth create` supports `--githubFederated` (GitHub OIDC, needs `--tenant` and `--applicationId`), `--azureDevOpsFederated`, `--managedIdentity` (DefaultAzureCredential), client secret, certificate, and `--deviceCode`. ([pac auth reference](https://learn.microsoft.com/power-platform/developer/cli/reference/auth), read 1 Nov 2026)

### Inferences
- Factory rule candidate: agents are authored in the repo as a `pac copilot` workspace; CI runs `pac copilot pack` (offline, deterministic) and `pac solution import` with an OIDC-federated SP. `push` is reserved for the dev environment loop because it mutates the live agent.
- Because `pull`/`push` depend on hidden sync metadata, the factory must commit or regenerate that metadata deliberately, or prefer `pack` + `solution import` for any environment the agent did not clone from.
- The `cli` shape (`agent.sync.yaml` with `SKILL.md` behaviors) looks like the code-native shape for GitHub Copilot harness agents. It is only evidenced in the extension repo README and the `--authoring-mode cli-copilot` flag, so treat it as early.

### Gaps
- No Learn page found listing exactly which agent settings cannot round-trip through files (for example authentication settings, channels, Entra SSO config). The docs only say connections and consent need the interactive experience.
- Whether `pac copilot clone/pull/push` work under a service principal or federated profile is not stated (they "require an authenticated profile"). Needs a test.
- `msagent` CLI: no Learn reference page found in this pass.

## Q3. MCP servers for the platform: Dataverse, PAC CLI, Copilot Studio, flows, canvas; auth and headless use

### Takeaway
There are now five Microsoft MCP surfaces: the Dataverse MCP server (remote `/api/mcp` plus a local `@microsoft/dataverse` proxy), the PAC CLI built-in MCP server (`pac copilot mcp --run`), Copilot Studio MCP (`@microsoft/copilot-studio-mcp`), the FlowAgent MCP server for cloud flows, and the Canvas Authoring MCP server. All are designed around a signed-in developer. The GitHub Copilot cloud agent cannot use remote MCP servers that need OAuth, so the only headless-friendly routes are local stdio servers that can pick up a pre-authenticated profile (PAC or Dataverse CLI profile, `az login`) created by setup steps. That is plausible but not documented end to end by Microsoft.

### Cited Findings
- Dataverse MCP remote URL: `https://{org}.crm.dynamics.com/api/mcp` (preview tools at `/api/mcp_preview`). Microsoft lists Copilot Studio, VS Code GitHub Copilot, GitHub Copilot CLI, Claude desktop and Claude Code as clients. ([Connect to Dataverse with MCP](https://learn.microsoft.com/power-apps/maker/data-platform/data-platform-mcp), read 1 Nov 2026)
- Governance: only Copilot Studio is enabled by default. Each other client must be allowed per environment in PPAC (Settings > Product > Features > Dataverse Model Context Protocol > Advanced Settings), for example "Microsoft GitHub Copilot". Allow-listing applies only to `/api/mcp`. ([Configure the Dataverse MCP server](https://learn.microsoft.com/power-apps/maker/data-platform/data-platform-mcp-disable), read 1 Nov 2026)
- Billing: Dataverse MCP server GA 15 Dec 2025, and "usage of the Dataverse MCP Server will be subject to billing" from 15 Dec 2025. Tools: `search_data`, `search`, `create_record`, `update_record`, `delete_record` (only after explicit user approval), `create_table`, `update_table`, `delete_table`, `read_query` (Dataverse SQL SELECT), `describe`, `upsert_skill`, `delete_skill`, file upload and download via SAS URLs. ([Release plan 2025 wave 2: Dataverse MCP Server](https://learn.microsoft.com/power-platform/release-plan/2025wave2/data-platform/dataverse-mcp-server), archived as of October 2026, read 1 Nov 2026)
- Copilot CLI config: `~/.copilot/mcp-config.json` or project `.mcp/copilot/mcp.json` with `{"type":"http","url":"<org URL>/api/mcp"}`; or `copilot plugin marketplace add github/awesome-copilot` then `copilot plugin install dataverse@awesome-copilot` and `/dataverse:mcp-configure`. ([Connect Dataverse MCP with GitHub Copilot](https://learn.microsoft.com/power-apps/maker/data-platform/data-platform-mcp-vscode), read 1 Nov 2026)
- Non-Microsoft clients: (a) local proxy `npx -y @microsoft/dataverse mcp https://yourorg.crm.dynamics.com` (Claude Code: `claude mcp add dataverse -t stdio -- npx -y @microsoft/dataverse mcp <url>`), needs one-time tenant admin consent for app `0c412cc3-0dd6-449b-987f-05b053db9457` and enabling the "Dataverse CLI" client in PPAC; or (b) remote endpoint with your own Entra app registration that has the Dynamics CRM `mcp.tools` permission, added to the allowed clients list. "The authentication flow used by the Entra app depends on the MCP client you're using." ([Dataverse MCP in non-Microsoft clients](https://learn.microsoft.com/power-apps/maker/data-platform/data-platform-mcp-other-clients), read 1 Nov 2026)
- `@microsoft/dataverse` is the "Dataverse CLI (Preview)": latest 1.0.88, first published 6 Mar 2026, last modified 29 Oct 2026. It has "profile-based authentication compatible with PAC CLI auth profiles" and `auth create` supports service principal (`--applicationId` + `--clientSecret`), `--managedIdentity`, `--githubFederated`, `--azureDevOpsFederated`, and `--deviceCode` for "SSH, container, CI". `dataverse mcp <orgUrl> --validate` checks auth, MCP enablement and allow-listing. ([npm registry: @microsoft/dataverse](https://registry.npmjs.org/@microsoft%2Fdataverse), read 1 Nov 2026)
- PAC CLI built-in MCP server: `pac copilot mcp --run`, or without installing PAC: `dnx Microsoft.PowerApps.CLI.Tool --yes copilot mcp --run` (needs .NET 10+). Microsoft shows registration for Visual Studio, VS Code and Claude Code (`claude mcp add-json pac-cli '{"type":"stdio","command":"dnx","args":["Microsoft.PowerApps.CLI.Tool","--yes","copilot","mcp","--run"]}'`). Framed as "designed for local development and testing purposes". ([Use Power Platform CLI with built-in MCP server](https://learn.microsoft.com/power-platform/developer/howto/use-mcp), read 1 Nov 2026)
- Copilot Studio MCP: client launches `npx -y @microsoft/copilot-studio-mcp@latest` (stdio, Node 22.18+). Sign-in is "Microsoft work-account sign-in in the browser", then pick an environment. Tools: `discover_resources`, `get_consumption`, `manage_agents` (draft authoring, lifecycle, sharing, evaluation runs), `manage_workflows`, `get_copilot_studio_skills` (skills `agent-authoring`, `workflow-authoring`, `workflow-troubleshooting`, `testing-and-credits`). Saving a draft is separate from publishing. npm package first published 16 Oct 2026, latest 1.0.2. ([Connect to Copilot Studio with MCP](https://learn.microsoft.com/microsoft-copilot-studio/agents-experience/copilot-studio-mcp); [Configure access](https://learn.microsoft.com/microsoft-copilot-studio/agents-experience/copilot-studio-mcp-configure); [npm: @microsoft/copilot-studio-mcp](https://registry.npmjs.org/@microsoft%2Fcopilot-studio-mcp), read 1 Nov 2026)
- FlowAgent MCP (Power Automate plugin): self-contained stdio bundle `server/mcp.mjs`, 50+ tools for flows (create, surgical edit, copy, publish, delete), runs (resubmit, cancel, diagnose), connections. Auth is Azure CLI `az login` plus MSAL. Saves local backups before every update or delete. ([power-platform-skills: Power Automate plugin README](https://github.com/microsoft/power-platform-skills/tree/main/plugins/power-automate), read 1 Nov 2026 via raw.githubusercontent.com)
- Canvas Authoring MCP server (`CanvasAuthoringMcpServer`, .NET 10): generates, validates and compiles `.pa.yaml` "in conjunction with a running coauthoring studio session. The Power Apps Studio browser tab must remain open for the duration of the session." ([power-platform-skills: canvas-apps AGENTS.md](https://github.com/microsoft/power-platform-skills/blob/main/plugins/canvas-apps/AGENTS.md), read 1 Nov 2026)
- GitHub Copilot cloud agent MCP limits: "only support MCP tools" (no resources or prompts), and "For MCP servers configured in repository settings or custom agent profiles, [cloud agent] ... do not currently support remote servers that use OAuth for authentication and authorization." The agent calls MCP tools "autonomously and does not ask for approval". Secrets for MCP must be Agents secrets prefixed `COPILOT_MCP_`. ([GitHub Docs source: repo-mcp-limitations](https://raw.githubusercontent.com/github/docs/main/data/reusables/copilot/mcp/repo-mcp-limitations.md); [About MCP](https://github.com/github/docs/blob/main/content/copilot/concepts/customizations/mcp.md); [Configure MCP servers](https://github.com/github/docs/blob/main/content/copilot/how-tos/copilot-on-github/customize-copilot/configure-mcp-servers.md), read 1 Nov 2026)
- GitHub's own pattern for Azure-authenticated MCP in the cloud agent: `copilot-setup-steps.yml` with `permissions: id-token: write`, `environment: copilot`, and `azure/login` using `AZURE_CLIENT_ID` and `AZURE_TENANT_ID` Agents secrets (OIDC, no secret), then a local stdio MCP server that uses `azcli` auth. ([Configure MCP servers, Azure DevOps example](https://github.com/github/docs/blob/main/content/copilot/how-tos/copilot-on-github/customize-copilot/configure-mcp-servers.md), read 1 Nov 2026)
- Copilot CLI supports both local and remote MCP servers. ([About MCP](https://github.com/github/docs/blob/main/content/copilot/concepts/customizations/mcp.md), read 1 Nov 2026)

### Inferences
- Cloud agent: the remote Dataverse endpoint (`/api/mcp`, Entra OAuth) is out. The workable pattern is setup steps that OIDC-login (`azure/login` or `pac auth create --githubFederated`), then a local stdio server (`@microsoft/dataverse mcp`, PAC MCP, FlowAgent) that reuses that profile. This is inferred from the documented pieces; Microsoft does not document Dataverse MCP with app-only tokens.
- If the SP's own app ID (not `0c412cc3-...`) calls `/api/mcp`, it must be added to the PPAC allowed client list. Plan this in environment provisioning.
- Copilot Studio MCP and Canvas Authoring MCP are interactive by design (browser sign-in, open Studio tab). Treat them as human-in-the-loop tools, not factory tools. Use `pac copilot` for Copilot Studio in CI instead.
- Dataverse MCP is billed since 15 Dec 2025. A chatty agent loop against it has a run cost in the customer's tenant, separate from Copilot credits.

### Gaps
- No Microsoft doc confirms the Dataverse MCP server accepts application (client credentials) tokens. Needs a test with an SP on a dev environment.
- Exact Dataverse MCP billing rate (credits per call) not captured in this pass.

## Q4. Microsoft guidance, skills, plugins and samples for AI-assisted Power Platform development and ALM

### Takeaway
Microsoft now ships an official, MIT-licensed plugin marketplace, `microsoft/power-platform-skills`, with 11 plugins for GitHub Copilot CLI and Claude Code (code apps, model-driven apps, canvas apps, Power Automate, PCF, Power Pages, MCP apps, mobile, process intelligence, Dataverse). Learn pages tell makers to use them. Plus a separate `microsoft/Dataverse-skills` plugin that is listed in GitHub's `awesome-copilot` and Anthropic's `claude-plugins-official` marketplaces. Most skills assume an interactive maker with `pac auth` and `az login`; several have plan-approval steps.

### Cited Findings
- `microsoft/power-platform-skills`: "Official agent skills/plugins for Power Platform development by Microsoft", a plugin marketplace "containing GitHub Copilot/Claude Code plugins". Plugins: `power-pages`, `model-apps`, `pcf` (preview), `mcp-apps`, `code-apps-preview`, `mobile-app`, `power-apps-mobile-extension`, `canvas-apps`, `power-automate`, `process-intelligence`, and `dataverse` (sourced from `microsoft/Dataverse-skills`). Installer also installs `pac` if missing and enables auto-update. Copilot CLI reads `marketplace.json`, Claude Code reads `.claude-plugin/marketplace.json`. ([power-platform-skills README](https://github.com/microsoft/power-platform-skills), read 1 Nov 2026 via raw.githubusercontent.com)
- The same README documents headless permission settings: Copilot CLI `--allow-tool 'shell(pac *)'` or `--allow-all-tools --deny-tool ...`; Claude Code `defaultMode: acceptEdits` with `Bash(pac *)` allows, or `--dangerously-skip-permissions`. Telemetry is default-on for Power Pages, Mobile Apps, Model Apps and Power Automate plugins; CI opt-out via `POWER_PLATFORM_SKILLS_TELEMETRY_<PLUGIN>_OPTOUT`. ([power-platform-skills README](https://github.com/microsoft/power-platform-skills), read 1 Nov 2026)
- Model-driven apps: Learn page "Build and edit model-driven apps with AI code generation tools" tells makers to run `/app-builder` from the `model-apps` plugin in GitHub Copilot CLI or Claude Code. It produces an App Spec (personas, tables, relationships, forms, views, charts, business rules, BPFs, security roles, sitemap, JS validation, generative pages), shows a dry-run build plan, builds only after approval, and can verify the deployed app against the spec. ([Learn: model-driven apps with AI code generation tools](https://learn.microsoft.com/power-apps/maker/model-driven-apps/model-driven-app-external-tools), read 1 Nov 2026)

## Q5. Running the GitHub Copilot cloud agent against Dataverse, versus Copilot CLI or SDK, or Claude Code, on a self-hosted runner

### Takeaway
The cloud agent can be made to work against an Australian Dataverse environment: `copilot-setup-steps.yml` may request `id-token: write` and run OIDC logins (`azure/login`, and by extension `pac auth create --githubFederated`), Agents secrets are injected as env vars, and a custom allowlist rule for `dynamics.com` covers `*.crm6.dynamics.com`. The hard limits are the 59-minute session cap, no OAuth remote MCP, one repo and one PR per Actions-based task, and a firewall that only covers the agent's Bash tool. Copilot CLI (or SDK) on a self-hosted or GitHub-hosted runner with `pac` pre-installed removes the 59-minute cap (6 h hosted, 5 days self-hosted job limit), bills to the org via `GITHUB_TOKEN` + `copilot-requests: write`, and is the better fit for long Power Platform jobs.

### Cited Findings
- Setup steps: the job must be named `copilot-setup-steps`; only `steps`, `permissions`, `runs-on`, `services`, `snapshot` and `timeout-minutes` (max 59) are honoured. If a setup step fails, Copilot skips the remaining setup steps and starts anyway. ([Customize the agent environment](https://github.com/github/docs/blob/main/content/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment.md), live source read 1 Nov 2026)
- OIDC in setup steps is a documented GitHub pattern: `permissions: id-token: write`, `environment: copilot`, `azure/login` with `client-id` and `tenant-id` from Agents secrets, `allow-no-subscriptions: true`. ([Configure MCP servers](https://github.com/github/docs/blob/main/content/copilot/how-tos/copilot-on-github/customize-copilot/configure-mcp-servers.md), live source read 1 Nov 2026)
- PAC supports GitHub OIDC directly: `pac auth create --githubFederated` with `--tenant` and `--applicationId`; Microsoft has a tutorial for OIDC/FIC with GitHub Actions for Power Platform and grants the app access in PPAC as an application user. ([pac auth](https://learn.microsoft.com/power-platform/developer/cli/reference/auth); [OIDC/FIC tutorial](https://learn.microsoft.com/power-platform/alm/tutorials/github-actions-oidc-fic), read 1 Nov 2026)
- FIC subject pitfall: GitHub `sub` claims for repositories "created, renamed, or transferred on or after July 15, 2026 include numeric organization and repository IDs, such as `repo:octo-org@123456/octo-repo@456789:environment:prod`". Subjects must match exactly. ([Learn: Databricks workload identity federation for GitHub Actions](https://learn.microsoft.com/azure/databricks/dev-tools/auth/provider-github), read 1 Nov 2026) [secondary for GitHub behaviour, but a Microsoft page]
- Agents secrets: dedicated Agents secrets and variables at repo or org level; exposed as env vars to the agent and to `copilot-setup-steps.yml`; names prefixed `COPILOT_MCP_` go only to MCP servers. The cloud agent does not get Actions, Codespaces or Dependabot secrets. In a cloud sandbox session only secrets (not variables) are available. ([Configure secrets and variables](https://github.com/github/docs/blob/main/content/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/configure-secrets-and-variables.md), live source read 1 Nov 2026)
- Firewall: a recommended allowlist is on by default (package registries, container registries and so on). The live allowlist reference has zero entries for `dynamics` and none for `login.microsoftonline.com`, so Dataverse and Entra endpoints are not allowed by default. Custom rules accept a domain (covers subdomains, so `dynamics.com` allows `org.crm6.dynamics.com`) or a URL prefix. Org owners can block repo-level custom rules. ([Customize the firewall](https://github.com/github/docs/blob/main/content/copilot/how-tos/copilot-on-github/customize-copilot/customize-the-firewall.md); [allowlist reference](https://github.com/github/docs/blob/main/content/copilot/reference/copilot-allowlist-reference.md); [custom-allowlist-add-entries reusable](https://github.com/github/docs/blob/main/data/reusables/copilot/cloud-agent/custom-allowlist-add-entries.md), live source read 1 Nov 2026)
- Firewall scope: "only applies to processes started by the agent via its Bash tool. It does not apply directly to MCP server processes or processes started in configured Copilot setup steps." ([Customize the firewall](https://github.com/github/docs/blob/main/content/copilot/how-tos/copilot-on-github/customize-copilot/customize-the-firewall.md), live source read 1 Nov 2026)
- Australian Dataverse host: OCE region URL is `crm6.dynamics.com`. ([Datacenter regions](https://learn.microsoft.com/power-platform/admin/new-datacenter-regions), read 1 Nov 2026)
- Session cap: "Each Copilot session that runs on GitHub Actions has a maximum execution time of 59 minutes. This limit cannot be extended or bypassed." Actions-based sessions can change only the one repository and open one PR per task; cloud sandbox sessions can work across multiple repositories. ([About Copilot on GitHub](https://github.com/github/docs/blob/main/content/copilot/concepts/copilot-surfaces/copilot-on-github.md), live source read 1 Nov 2026)
- Self-hosted runners for the cloud agent: supported on Ubuntu x64 and Windows 64-bit, ephemeral single-use (ARC) recommended, and the integrated firewall must be disabled (it is not compatible with self-hosted runners or Windows). Larger GitHub-hosted runners with Azure private networking are the other option. ([Customize the agent environment](https://github.com/github/docs/blob/main/content/copilot/how-tos/copilot-on-github/customize-copilot/customize-cloud-agent/customize-the-agent-environment.md), live source read 1 Nov 2026)
- Copilot CLI in Actions: `npm install -g @github/copilot`, `copilot -p "<prompt>" -s --allow-tool='shell(...)'`, `GITHUB_TOKEN: ${{ github.token }}`, `permissions: copilot-requests: write`. Non-interactive runs deny any tool not pre-approved. GitHub recommends GitHub Agentic Workflows (`gh-aw`) for most automation. ([Use Copilot CLI in Actions](https://github.com/github/docs/blob/main/content/copilot/how-tos/copilot-cli/use-copilot-cli-in-actions.md), live source read 1 Nov 2026)
- Billing for CLI in Actions: with `GITHUB_TOKEN` in an org-owned repo, usage "is metered directly to the organization" if "Allow use of Copilot CLI billed to the organization" is on; user budgets do not apply, use cost centres. With a PAT it draws on that user's seat. ([Copilot CLI in GitHub Actions concept](https://github.com/github/docs/blob/main/content/copilot/concepts/agent-capabilities/agent-powered-workflows-and-operations/copilot-cli-in-github-actions.md), local clone dated 23 Oct 2026)
- Copilot SDK headless auth: server-to-server tokens (GitHub App installation token `ghs_` with the Copilot permission, or `GITHUB_TOKEN` in Actions) for "organization-attributed automation and direct organization billing"; BYOK to Microsoft Foundry/Azure OpenAI, Anthropic, or Foundry Local. Plugin directories exist for "CI, in headless server deployments". ([Copilot SDK auth docs](https://github.com/github/docs/tree/main/content/copilot/how-tos/copilot-sdk/auth), local clone dated 23 Oct 2026)
- Actions job limits: 6 hours per job on GitHub-hosted runners, 5 days on self-hosted. ([Actions limits](https://github.com/github/docs/blob/main/content/actions/reference/limits.md), local clone dated 23 Oct 2026)
- The `power-platform-skills` README gives the permission flags for both engines in unattended mode (see Q4). Claude Code headless MCP registration for PAC and Dataverse is documented by Microsoft (see Q3).

### Inferences
- Cloud agent recipe for a Power Platform repo: setup steps install `pac` (dotnet tool or `dnx`), Node, `@microsoft/power-apps-cli`, `@microsoft/dataverse`; run `azure/login` (OIDC) and `pac auth create --githubFederated`; add custom allowlist rules for `dynamics.com`, `login.microsoftonline.com`, `api.bap.microsoft.com`, `api.powerapps.com` and `*.powerplatform.com` style endpoints (the exact host set is not documented by GitHub or Microsoft for this case and needs a test). OIDC tokens obtained in setup steps expire (Entra access tokens are typically about 1 hour), which roughly lines up with the 59-minute cap.
- Use the cloud agent for bounded edits (builders, YAML, TypeScript, tests) that only need `pac solution pack`/`check` and maybe a dev import. Use Copilot CLI on a runner for long jobs: environment provisioning, import plus publish waits, Copilot Studio `push` loops, solution checker runs.
- Claude Code on the same self-hosted runner is a like-for-like fallback: same skills marketplace, same `pac` and `dataverse` profiles, MCP via `claude mcp add`. Cost moves from Copilot credits to cash.

### Gaps
- Whether `copilot-setup-steps.yml` runs in the new "cloud sandbox" session type (as opposed to Actions-based sessions) is not stated in the docs read.
- No GitHub or Microsoft doc lists the exact Power Platform hostnames the agent must allowlist.

## Q6. Builder pattern (Python builders generate solution XML/JSON, CI fails on drift): precedent and pitfalls

### Takeaway
There is no Microsoft doc that prescribes "generate unpacked solution files from code and fail CI on `git diff`", but Microsoft's own agent tooling has moved the same way: the model-apps plugin keeps an App Spec, lints it, dry-runs, applies idempotently through an SDK, and can download a deployed app back into the spec. On the file side, Microsoft supports hand edits to only a small part of `customizations.xml`, has a new YAML source-control format that diffs far better, and warns that `pack` can silently drop a component whose files are missing. Those facts favour builders that emit the YAML format (or per-component files) plus a pack-and-diff gate, over agents editing unpacked XML directly.

### Cited Findings
- Microsoft: defining solution components by editing exported `customizations.xml` is not supported for tables, columns, relationships, choices, web resources, processes, plug-in assemblies, SDK steps, security roles, field security profiles and more; "Invalid XML or incorrect definition of solution components can cause errors that will prevent importing a manually edited unmanaged solution." Use XSD schema validation (CustomizationsSolution.xsd, FormXml.xsd, SiteMap.xsd, RibbonCore.xsd and others). ([When to edit the customizations file](https://learn.microsoft.com/power-platform/alm/when-edit-customization-file); [Edit with schema validation](https://learn.microsoft.com/power-apps/developer/model-driven-apps/edit-customizations-xml-file-schema-validation), read 1 Nov 2026)
- SolutionPackager is "no longer the recommended way"; use `pac solution unpack | pack | clone | sync`. ([SolutionPackager tool](https://learn.microsoft.com/power-platform/alm/solution-packager-tool), read 1 Nov 2026)
- Two source formats. XML (legacy): `Other/Solution.xml` + `Other/Customizations.xml`. YAML source-control format: `solutions/<Name>/solution.yml`, `solutioncomponents.yml`, `rootcomponents.yml`, `missingdependencies.yml`, `publishers/<Name>/publisher.yml`, plus `entities/`, `workflows/`, `modernflows/`, `canvasapps/`. YAML gives "cleaner, more readable per-component diffs", multi-solution repos, and is the only format that supports canvas `.msapp` and modern flows. Native Git integration always writes YAML. Microsoft says use YAML "for all new projects". ([SolutionPackager tool](https://learn.microsoft.com/power-platform/alm/solution-packager-tool); [Source control with solution files](https://learn.microsoft.com/power-platform/alm/use-source-control-solution-files), read 1 Nov 2026)
- Silent-drop pitfall: if a component is listed in `rootcomponents.yml` but its source files are missing, "The tool still succeeds (exit code 0) and produces a valid .zip file, but the declared component is omitted from the packaged solution." ([SolutionPackager troubleshooting](https://learn.microsoft.com/power-platform/alm/solution-packager-tool#troubleshooting), read 1 Nov 2026)
- Layout pitfall: YAML manifests placed at the folder root instead of `solutions/<Name>/` make the tool fall back to XML and report a misleading "Cannot find required file ...\Other\Customizations.xml" error. ([SolutionPackager troubleshooting](https://learn.microsoft.com/power-platform/alm/solution-packager-tool#troubleshooting), read 1 Nov 2026)
- `/map` lets pack read build outputs (plug-in DLLs, web resources, `.nupkg`) from build folders instead of committing them. ([SolutionPackager /map](https://learn.microsoft.com/power-platform/alm/solution-packager-tool#use-the-map-command-argument), read 1 Nov 2026)
- Microsoft precedent for spec-driven builders: model-apps `/app-builder` uses an App Spec, `spec-lint` + `validateAppSpec` before live calls, a phase-grouped dry-run plan, idempotent apply via the headless `cds-maker-sdk`, optional `--verify`, and "downloads a deployed app back into an editable App Spec". Microsoft warns "Changes made outside the skill can affect later AI-assisted edits." ([model-apps README](https://github.com/microsoft/power-platform-skills/blob/main/plugins/model-apps/README.md); [Learn page](https://learn.microsoft.com/power-apps/maker/model-driven-apps/model-driven-app-external-tools), read 1 Nov 2026)
- Copilot Studio precedent: `pac copilot pack` builds a solution zip from a YAML workspace offline; `extract-template` / `create` round-trip an agent through a template YAML. (See Q2.) ([pac copilot](https://learn.microsoft.com/power-platform/developer/cli/reference/copilot), read 1 Nov 2026)
- Code apps precedent: `pa app add data-source|flow` generate typed TS models and services from connector and flow OpenAPI; `pa app refresh data-source` regenerates them. That is a generator whose output should be committed and drift-checked. ([Power Apps CLI reference](https://learn.microsoft.com/power-apps/developer/code-apps/reference/cli), read 1 Nov 2026)
- Community [secondary][snippet]: a drift tool notes "Dataverse re-serializes solution XML on every export, drowning real changes in thousands of lines of noise" and canonicalises snapshots before compare ([DataverseDrift on NuGet](https://www.nuget.org/packages/DataverseDrift)); Flowline notes the solution version lives in several files at once (Solution.xml, the assembly, control manifests, the .dll.data.xml sidecars) ([Flowline wiki: Philosophy](https://github.com/RemyDuijkeren/Flowline/wiki/11-Philosophy)); a Git integration write-up describes `customizations.xml` as the index needed to rebuild the solution ([dev.to: Dataverse Git integration](https://dev.to/_neronotte/dataverse-git-integration-preview-how-solution-components-are-saved-12p7)); an import guide recommends "Block unmanaged customizations" over force-overwrite for unmanaged drift in non-dev environments ([Making Dataverse solution imports fast](https://blog-8ru.pages.dev/making-solution-imports-fast/)). All read via search summary only on 1 Nov 2026.

### Inferences
- Factory rules that follow from the above: (1) builders emit the YAML source-control format, never hand-edited `customizations.xml`; (2) agents edit builder inputs (spec files, Python), not generated output; (3) CI runs builders, then `git diff --exit-code`, then `pac solution pack`, then a manifest check that every `rootcomponents.yml` entry has files (because pack exits 0 on a silent drop), then `pac solution check`; (4) builders must be deterministic (stable ordering, no timestamps or fresh GUIDs on re-run, fixed line endings), else the drift gate flaps; (5) round-trip test: export from dev, unpack, and diff against generated output to catch server-side normalisation, using canonicalisation where Dataverse re-serialises.
- Where Microsoft already has a generator (pa codegen, `pac copilot pack`, model-apps App Spec), wrap it instead of writing a Python one, and drift-check its output the same way.
- Version stamps that live in several files are a classic drift source; have one builder own them.

### Gaps
- No Microsoft guidance found on generating cloud flow `workflow.json` or form XML from code; only schema docs and the FlowAgent tool (API-based).
- No published community write-up found that covers AI agents editing unpacked solution files specifically.
