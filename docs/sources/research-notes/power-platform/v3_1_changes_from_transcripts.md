## The 15 items, with where each lands

1. In-loop verification skill and CLI ("hands and eyes"). T1 16:14 to 22:54: verification is "the single most important skill"; the agent must run the code and interact like a user, take traces and snapshots; a CLI inside the skill holds the deterministic parts so agents stop rebuilding verification each time; every app has its own verification skill, kept up to date ("automaintained"), treated as critical infrastructure. Gap in V3: verification only in the gate. Add an `lcp-verify` skill plus CLI for the Power Platform lane: open apps through Microsoft's Playwright toolkit with the lane test user, query Dataverse through the Web API, trigger a flow and check FlowRun, run Copilot Studio test sets, capture screenshots and traces, and emit an evidence JSON. The executor uses its lane copy in its own loop (not a verdict); the evaluator and gate run a trusted copy from the gate repo. A per-solution verify profile describes the app's routes and key flows. Changes only by reviewed PR. Lands in: section 5 (new subsection near the evaluator), Appendix C (skill definition), the component register (IP), the build plan (stage 1 or 2 exit test), risks.
2. Outer loop and triage. T1 34:50 to 45:40: external context (Slack, email, Linear, X) feeds the inner loop through connectors and routines; agents triage, reproduce on main with the verification skills, and get their own context ("context not control"). Gap: V3 starts work at the day gate only. Add an outer loop for AI Managed Services clients: inputs from the client's service desk or ITSM, Teams channels, Application Insights and Dataverse error alerts, and ADO bugs; a triage agent reproduces each report in `factory-test` with `lcp-verify`, checks it still exists on main, groups related reports so work is not duplicated, and writes repro steps and evidence to a draft ADO bug; Spec Kit's bug workflow assess step applies; a human sets Factory Eligible. Lands in: operating model (section 2), a new subsection under lanes or section 5, ADO fields (Appendix D), stages, ledger (triage cost rows).
3. Grouping related work (the coordinator function, not a custom orchestrator). T1 39:10 to 45:40 and 47:35 to 49:04: coordinator or "chief of staff" agents see the forest, group related bug reports and avoid duplicate work. V3 rightly dropped the custom Foundry "Chief of Staff" infrastructure; keep that decision but restore the function as a triage or night-plan step using shipped primitives (a Copilot CLI session, Copilot dynamic workflows or fleet mode), not a custom orchestrator. Lands in: the triage subsection and the night plan build at 17:00.
4. Trust ladder replacing phase-and-date framing. T1 1:36 to 2:00, 16:14 to 17:30, 49:34 to 51:19, 56:30 to 59:26: trust is climbed through verification and environment; review by sampling instead of blocking; how far you go depends on how verifiable the domain is. Add explicit rungs per project and per change class with evidence to climb and drop back, for example: L0 humans run agents by day with the safety net; L1 night shift, humans merge every PR; L2 auto-merge into `integration` for eligible low-danger classes with humans sampling the merged PRs (risk-weighted sample, all with evaluator unknowns); L3 wider change classes as verification coverage grows. `main` is always human for client work. Power Platform is less verifiable than pure code (UI, consent, connectors, conversations), so investment in verification tooling is how a project climbs. Keep the 45-day timeline as a calendar for building the factory, but make auto-merge eligibility a rung earned per project and change class, not a phase. Lands in: section 2 rules, section 5.10 (Merge Danger and auto-merge), section 11 (stages), Appendix B (thresholds by rung), metrics (sampled defect rate).
5. Facts versus decisions in the grill and at night. T2 2:35 to 4:07: grilling asks one question at a time and says why ("asking multiple questions at once is bewildering"); a confirmation gate ("do not enact the plan until I confirm we've reached a shared understanding"); the agent finds facts itself by exploring and asks the user only for decisions. T1 38:01 to 38:44: get the agent to answer its own questions with real data, not guesses. Add to the Get AI preset and the day gate; and at night: look up facts (codebase, Dataverse metadata via MCP or Web API, ADO history, glossary, decision records), PARK only on decisions. Lands in: section 6, section 2 rules, Appendix C executor instructions, PARK protocol.
6. Two-axis code review with coding standards outside AGENTS.md and named smells. T2 5:56 to 7:53: review on two axes as parallel sub-agents: standards (does it conform to the repo's documented coding standards, kept in a separate coding-standards.md, not in agents.md) and spec (does it faithfully implement the originating ticket or spec); naming Martin Fowler's smells (mysterious name, duplicated code, feature envy, data clumps, primitive obsession, repeated switches, divergent change, speculative generality, message chains, middle man) makes agents find and fix them. Add: the uploaded plan's "Factory Manifestos" become per-practice `coding-standards.md` files (protected path); the read-only reviewer runs two parallel passes; add a named smell list plus a few Power Platform smells labelled as our suggestions (for example hard-coded GUIDs or environment URLs, flows outside solutions, missing connection references or environment variables, unbounded or non-delegable queries, copy-pasted flow branches). The reviewer still only raises Merge Danger. Lands in: section 5 (review agent), Appendix B.4, Appendix C (reviewer definition), section 7 retro.
7. TDD rules for the worker. T2 5:02 to 5:28 and 12:13 to 13:17: implement uses TDD at pre-agreed seams, runs type checks and single test files regularly, the full test sweep once at the end, then code review, then commit; TDD is red before green, one slice at a time; refactoring moves to code review, not the implement loop. Add to the executor agent: red before green at the seams named in the spec's testability contract; builders and lints often; one scenario at a time while building; the full lane suite once at the end; no refactoring outside the ticket (raise it in review). Locked acceptance tests stay authored by someone else. Lands in: section 5 executor, Appendix C.
8. Discovery map for foggy work (Pocock's Wayfinder) and research tickets run overnight. T2 7:53 to 11:51: Wayfinder is for work "too big for one agent session and wrapped in fog"; it charts a shared map on the issue tracker; decisions are sub-issues with blocking relationships, each sized to one agent session, typed research (away-from-keyboard), grilling (needs a human), prototype, or task (config, provisioning, access); when all close, the map becomes the spec; a research skill runs a background agent against primary sources and writes Markdown notes. Name clash: the uploaded plan's "Wayfinder" is a planning agent that writes ADO Epics and stories. Resolve it: rename the uploaded plan's agent (suggest "Story Planner") and use "Wayfinder" for the discovery map, or the other way round; pick one and record it in the decision log. Add the discovery map as an ADO pattern for client discovery phases (parent item with typed child items and predecessor links), and let the factory run research tickets overnight as a new night workload type with its own ledger rows. Lands in: section 6 (before the day gate), section 4 or 5 (night workload types), ADO fields (Appendix D), decision log.

Lands in: section 6, design-first rule in section 2.
10. Gardening routines with a findings buffer. T1 45:54 to 49:04: much of the PR volume is gardening; a routine agent looks for banned patterns and appends to a document instead of fixing; a human reviews every few days, sees they are the same thing, and fixes the root cause; buffers help see the big picture. Lands in: section 7 or a new routines subsection, ADO fields, ledger.
