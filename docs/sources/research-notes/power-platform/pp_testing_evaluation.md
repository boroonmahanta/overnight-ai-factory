## 1. Power Apps Test Engine: status, authoring, auth, app types, CI, outputs

### Takeaway
Test Engine is deprecated (effective April 2026) and Microsoft no longer maintains its docs or GitHub repo; it never reached GA (public preview only, from 28 May 2025). Do not build the factory on `pac test run`. The official replacement is the open-source Power Platform Playwright samples (TypeScript, standard Playwright runner), which Microsoft says works headlessly in GitHub Actions.

### Cited Findings
- "Effective April 2026, Test Engine is deprecated. The documentation and GitHub repository are no longer maintained by Microsoft and will be removed in a future release." Reason given: "near-zero usage and failed to meet customer needs in an evolving AI landscape. The Power Fx implementation created unnecessary limitations that are avoided if using Playwright directly (Test Engine is built on Playwright)." Replacement: Power Platform Playwright samples, which "resemble how Microsoft tests first-party applications internally". (read 1 Nov 2026) [Important changes (deprecations) coming in Power Platform](https://learn.microsoft.com/power-platform/important-changes-coming#deprecation-of-test-engine)
- The `pac test` CLI reference now heads the group "(Deprecated) Execution of automated tests for a Power App" and `pac test run` itself is still labelled "(Preview)". (read 1 Nov 2026) [pac test](https://learn.microsoft.com/power-platform/developer/cli/reference/test)
- `pac test run` parameters, for the record: required `--environment-id`, `--tenant`, `--test-plan-file`; optional `--provider` (`Canvas`, `Mda`, `Portal`, `Powerfx`), `--user-auth` (`Storagestate`, `Dataverse`), `--auth` certificate provider (`None`, `Certenv`, `Certstore`), `--output-directory`, `--log-level`, `--domain`, `--queryparams`, `--use-static-context`. So it covered canvas, model-driven (Mda), Power Pages (Portal) and Power Fx/Dataverse (Powerfx) providers. (read 1 Nov 2026) [pac test](https://learn.microsoft.com/power-platform/developer/cli/reference/test)
- 2025 release wave 1 plan item "Test Power Apps with the test engine": public preview 28 May 2025, GA column blank; page banner says "As of October 2026, this content is archived and no longer maintained." The item described tests as "Power Fx in YAML files", canvas and model-driven support, open source, "updated authentication", and Playwright integration for C# tests. (read 1 Nov 2026) [Release plan 2025 wave 1: Test Power Apps with the test engine](https://learn.microsoft.com/power-platform/release-plan/2025wave1/data-platform/test-power-apps-test-engine)
- Microsoft's migration guide maps Test Engine concepts to Playwright: YAML test file to `*.test.ts`; `testSuite.testCases` to `test.describe()`; `testStep` to `test()`; `appLogicalName` to `directUrl` in `AppProvider.launch()`; `onTestCaseStart` to `test.beforeEach()`; `Assert` to `expect()`; `Select` to `canvasFrame.locator('[data-control-name="..."]').click()`; `Screenshot` to `page.screenshot()` or `toHaveScreenshot()`; `environmentVariables` to `.env`. (read 1 Nov 2026) [Migrate from Power Apps Test Engine](https://learn.microsoft.com/power-platform/developer/playwright-samples/migration-guide)
- Comparison table on the samples overview: Test Engine = Power Fx YAML, .NET runtime, config-file auth, no Page Object Model, no AI authoring, limited custom assertions, canvas + model-driven. Playwright samples = TypeScript, Node.js, reusable storage state, POM, AI authoring via Playwright MCP, any Playwright/Jest matcher, canvas + model-driven + custom pages + Gen UX. (read 1 Nov 2026) [Power Platform Playwright samples overview](https://learn.microsoft.com/power-platform/developer/playwright-samples/overview)

### Inferences
- Any factory design that names `pac test run` or Test Engine YAML as the acceptance-test format should be changed to Playwright TypeScript. Test Engine may still run, but it is unsupported, preview-only, and slated for removal, so it is a poor base for locked acceptance tests that must keep working for months.
- The TRX, screenshot and video outputs Test Engine produced are moot. The equivalent evidence now comes from Playwright's own reporters (HTML report, JUnit XML, trace.zip, screenshots, video), which are standard and well understood.

### Gaps
- I did not verify the current state of github.com/microsoft/PowerApps-TestEngine (archived flag, last commit date). Learn says it is "no longer maintained".
- No official statement on when `pac test` will be removed from the CLI.

## 2. Playwright directly against Power Apps (the supported path): auth, selectors, CI, Playwright MCP

### Takeaway
Microsoft now publishes and recommends a Playwright toolkit for canvas apps, model-driven apps, custom pages and Gen UX apps. It runs headlessly in GitHub Actions with a test user who signs in by certificate (local `.pfx` or Azure Key Vault), producing storage state in `globalSetup`. Canvas selectors use `data-control-name` inside the `fullscreen-app-host` iframe. Microsoft explicitly supports Playwright MCP as an AI aid for authoring tests against a live app.

### Cited Findings
- Repo: github.com/microsoft/power-platform-playwright-samples, a Rush monorepo with `power-platform-playwright-toolkit` (page objects, components, locators, auth helpers) and `e2e-tests` (reference tests against a Northwind Traders solution). Supported: canvas (`CanvasAppPage`), model-driven (`ModelDrivenAppPage`), custom pages (via `ModelDrivenAppPage`), AI-generated Gen UX apps (`GenUxPage`). Claims: "CI/CD ready: Works headlessly in GitHub Actions, Azure Pipelines, and any Playwright-compatible environment"; cross-browser (Chromium, Firefox, WebKit). Microsoft says to clone or fork and reference the toolkit locally (it is not described as a published npm package). (read 1 Nov 2026) [Power Platform Playwright samples overview](https://learn.microsoft.com/power-platform/developer/playwright-samples/overview)
- Authentication options: (1) password, for local dev (`MS_AUTH_CREDENTIAL_TYPE=password`, run `npm run auth:headful`); (2) certificate from local `.pfx` (`MS_AUTH_CREDENTIAL_PROVIDER=local-file`), "more secure than passwords and works well for both local development and CI/CD"; (3) certificate from Azure Key Vault (`MS_AUTH_CREDENTIAL_PROVIDER=azure-keyvault`), pipeline service principal needs "Key Vault Certificate User". In CI "authentication runs in `globalSetup` before the test suite starts. The script acquires fresh storage state headlessly using the configured credential provider." Two storage-state files: one for make.powerapps.com, one for the CRM/Dynamics domain (`npm run auth` then `npm run auth:mda`). A GitHub Actions YAML example is given. `ConfigHelper.checkStorageStateExpiration()` checks token expiry. (read 1 Nov 2026) [Authentication guide](https://learn.microsoft.com/power-platform/developer/playwright-samples/authentication-guide)
- Troubleshooting table on the same page: "Authentication tokens have expired" means re-run auth; `ERR_ABORTED` during model-driven auth means the Power Apps state expired and you must run the Power Apps auth before the MDA auth. (read 1 Nov 2026) [Authentication guide](https://learn.microsoft.com/power-platform/developer/playwright-samples/authentication-guide)
- Canvas apps run inside `iframe[name="fullscreen-app-host"]`. "All controls inside the app have a `data-control-name` attribute that matches the control name you set in Power Apps Studio. Gallery items have `data-control-part="gallery-item"`." Text inputs can be targeted by `aria-label`. "Canvas apps backed by Dataverse can take 30-60 seconds to load data into a gallery. Use a 60-second timeout." `skipMakerPortal: true` plus `directUrl` "saves 10-20 seconds per test". (read 1 Nov 2026) [Test canvas apps](https://learn.microsoft.com/power-platform/developer/playwright-samples/canvas-application)
- Migration troubleshooting: "Control not found: Verify `data-control-name` in DevTools - it might differ from Power Fx name". (read 1 Nov 2026) [Migrate from Power Apps Test Engine](https://learn.microsoft.com/power-platform/developer/playwright-samples/migration-guide)
- Model-driven apps: `GridComponent` wraps the AG Grid list view and uses `[row-index]` attributes; `FormComponent` wraps the Xrm FormContext (`getAttribute`, `setAttribute`, `save`, `isDirty`, `isValid`, `navigateToTab`, and `execute(formContext => ...)` for arbitrary Xrm code). Field inputs follow `input[data-id="<schema>.fieldControl-text-box-text"]`. The sample CRUD test uses `waitForTimeout(3000)` after save. (read 1 Nov 2026) [Test model-driven apps](https://learn.microsoft.com/power-platform/developer/playwright-samples/model-driven-application)
- AI-assisted testing: the Playwright MCP server "gives AI assistants live access to your running browser" for "generating selectors, writing tests with live inspection". Named supported assistants include GitHub Copilot and "Claude (Anthropic, Claude Code)". Recommended workflow ends with "Review and commit the generated test." (read 1 Nov 2026) [AI-assisted testing overview](https://learn.microsoft.com/power-platform/developer/playwright-samples/ai-overview)

### Inferences
- Selector stability for locked tests: `data-control-name` is the maker-set control name, so a locked acceptance test that selects by control name will break (correctly) if the implementing agent renames controls. Put the required control names in the spec so the implementer must use them. Prefer `aria-label` and accessible-name selectors where the spec defines user-visible labels, because they double as an accessibility check.
- MFA and conditional access: Microsoft's documented CI path is certificate-based sign-in for a dedicated test user, which implies that user must be allowed to sign in non-interactively with a certificate (Entra certificate-based authentication) and must be excluded from, or satisfy, any conditional access policy that demands interactive MFA or a compliant device. A password-only test user will fail wherever security defaults or CA policies force MFA. This is inference: the guide does not discuss conditional access directly.
- Playwright MCP as a click-through evaluator: technically practical, because the same storage state can be loaded into an MCP-driven browser against the Dev environment. Microsoft positions it for authoring, not for grading. For the factory, an MCP evaluator should be a separate agent with its own credentials and a held-out scenario list, producing a Playwright trace and screenshots, and its verdict should be advisory next to the deterministic locked suite.
- Timing: allow 30-60 s per canvas app launch with Dataverse data. A suite of 10-20 UI scenarios is likely 5-15 minutes on one worker, before parallelism. This is an estimate from the timeouts above, not a measured figure.

### Gaps
- No official guidance found on conditional access exclusions, MFA, or the licence a CI test user needs. The adjacent identity researcher may cover this.
- No first-party statement on flakiness rates or the official recommended worker count against a single environment (service protection limits may apply).

## 3. Copilot Studio agents: built-in evaluation, Copilot Agent Kit, Direct Line and Agents SDK, the new harnesses, and whether the 5-minute human test-pane check is still needed

### Takeaway
A large part of the "5 minutes in the test pane" check can now be automated and graded. Standard-harness agents have built-in agent evaluation (single-response sets up to 100 cases, conversation sets up to 20 cases) with deterministic methods (exact match, keyword match, tool use) and AI graders (general quality, compare meaning, custom labels), and a run can be started and read from code through the Power Platform REST API or `pac copilot-studio run-maker-evaluation-test-set`. The Copilot Agent Kit (renamed from Copilot Studio Kit) adds Direct Line-driven multi-turn tests, a deterministic "plan validation" check on which tools the generative orchestrator picked, and rubric-based AI grading. The weak spots: evaluation runs as a signed-in user (not a service principal), test sets are visible to every maker on the agent, and agents on the new GitHub Copilot harness only have a preview Evaluate tab with "General quality" as the only method and no documented API. Keep a short human look for tool or instruction changes on new-harness agents, and for anything that needs connector consent or manual auth.

### Cited Findings
**Harnesses (context for "the new harness")**
- Copilot Studio now has three harnesses: the GitHub Copilot harness ("reasoning-heavy, multi-step work"), the Customer Conversation harness (voice and chat for customers), and the standard harness ("rule-based agents and agent flows"). The GitHub Copilot harness is "a Microsoft Copilot Studio authoring and orchestration framework, not the GitHub Copilot service". (read 1 Nov 2026) [Harnesses in Copilot Studio](https://learn.microsoft.com/microsoft-copilot-studio/harnesses-overview)
- Many evaluation articles carry the note "This article describes features used in agents or agent flows powered by the standard harness", including the REST API automation page. (read 1 Nov 2026) [Automate agent evaluations with Power Platform API](https://learn.microsoft.com/microsoft-copilot-studio/analytics-agent-evaluation-rest-api)

**Standard harness: built-in agent evaluation**
- Single-response test sets hold up to 100 test cases; questions up to 1,000 characters; CSV import with columns Question, Expected response. Results are kept for 89 days, export to CSV to keep longer. (read 1 Nov 2026) [Create a single response test set](https://learn.microsoft.com/microsoft-copilot-studio/analytics-agent-evaluation-create)
- Test methods: General quality (AI, scored out of 100%), Content safety (pass/fail), Compare meaning (AI, 100%, needs expected answer), Tool use (pass/fail, expected capabilities), Keyword match (pass/fail), Text similarity (100%), Exact match (pass/fail), Custom (pass/fail against maker-written evaluation instructions and labels). (read 1 Nov 2026) [Create a single response test set](https://learn.microsoft.com/microsoft-copilot-studio/analytics-agent-evaluation-create)
- Conversation (multi-turn) test sets: "up to 20 test cases. Each test case supports up to 12 total messages, which is 6 pairs of questions and answers." Methods allowed: General quality, Keyword match, Tools use, Custom. (read 1 Nov 2026) [Create a conversational test set](https://learn.microsoft.com/microsoft-copilot-studio/analytics-agent-evaluation-multi-turn)
- Evaluation "runs as the currently signed-in user. To test as a different user, sign out, sign in with that user's account". Also: "Any maker with access to the agent can also view the test sets linked to that agent." Generated test cases "can include sensitive data that the connected account can access." (read 1 Nov 2026) [About agent evaluation](https://learn.microsoft.com/microsoft-copilot-studio/analytics-agent-evaluation-intro); [Create a single response test set](https://learn.microsoft.com/microsoft-copilot-studio/analytics-agent-evaluation-create)
- Four safety evaluators exist: hatefulness and unfairness, sexual content, violence, self-harm; Microsoft says they "don't guarantee that an agent is safe". (read 1 Nov 2026) [About agent evaluation](https://learn.microsoft.com/microsoft-copilot-studio/analytics-agent-evaluation-intro)
- REST API (api-version 2024-10-01) on `https://api.powerplatform.com/copilotstudio/environments/{EnvironmentId}/bots/{BotId}/api/makerevaluation/...`: list test sets, get test set, `POST .../testsets/{TestSetId}/run`, list test runs, get test run. Run result per test case includes `metricsResults[].type`, `result.data` (for general quality: `abstention`, `relevance`, `completeness`), `status`, `errorReason`, `aiResultReason`. Prerequisite: "A user access token issued by Microsoft Entra ID (OAuth 2.0)" from an app registration with Power Platform API scope. Optional `mcsConnectionId` sets the user profile for authenticated connections; without it "the evaluation runs without authentication". The run is asynchronous. (read 1 Nov 2026) [Automate agent evaluations with Power Platform API](https://learn.microsoft.com/microsoft-copilot-studio/analytics-agent-evaluation-rest-api)
- `pac copilot-studio` (preview) has `list-maker-evaluation-test-sets`, `get-maker-evaluation-test-set`, `run-maker-evaluation-test-set` (options `--evaluation-run-name`, `--mcs-connection-id`, `--run-on-published-bot` true or false for draft, `--tools-connections` JSON array), `list-maker-evaluation-test-runs`, `get-maker-evaluation-test-run`. No create or import command for test sets is listed. (read 1 Nov 2026) [pac copilot-studio](https://learn.microsoft.com/power-platform/developer/cli/reference/copilot-studio)
- The same evaluation actions exist in the Microsoft Copilot Studio connector (Evaluate Agent, Get Agent Test Run Details, Get Agent Test Runs, Get Agent Test Set Details, Get Agent Test Sets) for use in Power Automate. (read 1 Nov 2026) [Trigger agent evaluations with connectors](https://learn.microsoft.com/microsoft-copilot-studio/analytics-agent-evaluation-automate-tools)
- Microsoft's model-migration guidance: "Keep the set with the agent in source control, and rerun it unchanged for every model change"; "Split the set by risk area"; latency and credit cost are "Not reported by evaluation". (read 1 Nov 2026) [Run and validate an AI model migration for Copilot Studio agents](https://learn.microsoft.com/microsoft-copilot-studio/guidance/manage-agent-model-migration)

**New GitHub Copilot harness agents**
- The Evaluate tab is "a production-ready preview feature". "Currently, the only available test method is General quality, an AI-based assessment... The General quality test method doesn't compare responses to expected answers." Evaluations "only support agents set to use No authentication or Authenticate with Microsoft. Agents set to Authenticate manually aren't supported." Evaluations run as the signed-in user. Credit usage is shown per run and per test case. (read 1 Nov 2026) [Evaluate an agent (preview)](https://learn.microsoft.com/microsoft-copilot-studio/agents-experience/analytics-agent-evaluation-intro)
- Conversations can be uploaded by CSV (max 5 MB), generated with AI (10, then 25 or 50), or written by hand. A run session can be downloaded with metadata (evaluation name, run ID, agent version, test method) plus each turn's input, response and score; CSV export is also available. (read 1 Nov 2026) [Create a test set for an agent (preview)](https://learn.microsoft.com/microsoft-copilot-studio/agents-experience/analytics-agent-evaluation-create); [Run an evaluation for an agent (preview)](https://learn.microsoft.com/microsoft-copilot-studio/agents-experience/analytics-agent-evaluation-results) [snippet]
- The Preview tab gives an activity trace with "chain-of-thought (CoT) trace" showing knowledge sources consulted and tools invoked. Using, testing and evaluating these agents "might consume Copilot Credits". (read 1 Nov 2026) [Preview and test an agent (GitHub Copilot)](https://learn.microsoft.com/microsoft-copilot-studio/agents-experience/preview-overview) [snippet]
- Agent nodes inside workflows (GitHub Copilot harness) have their own graders: Pass or Fail plus "Evidence or reasoning"; limits: up to five AI-generated test methods per node, "up to 20 evaluations per agent node per day", evaluations run against the most recent test output. (read 1 Nov 2026) [Add an agent node to a workflow (GitHub Copilot)](https://learn.microsoft.com/microsoft-copilot-studio/workflows-experience/agent-node-workflow) [snippet]
- A Customer Conversation harness Evaluate tab also exists (preview) with Single response and Conversation (preview) data types. (read 1 Nov 2026) [Evaluate an agent (Customer Conversation) (preview)](https://learn.microsoft.com/microsoft-copilot-studio/agents-experience/analytics-agent-evaluation-customer-conversation) [snippet]

**Copilot Agent Kit (formerly Power CAT Copilot Studio Kit)**
- Learn now calls it the "Copilot Agent Kit". It runs tests "against the Copilot Studio APIs (Direct Line API)" and can enrich results from Application Insights and Dataverse conversation transcripts. (read 1 Nov 2026) [Enhance agent testing with Copilot Agent Kit](https://learn.microsoft.com/microsoft-copilot-studio/guidance/kit-test-capabilities) [snippet]
- Test types: Response Match (equals, contains, begins with, and so on), Attachments (Adaptive Card JSON, plus "AI Validation"), Topic Match (needs Dataverse transcript enrichment; multi-topic match for generative orchestration), Generative Answers (LLM judge against sample answer or validation instructions, needs AI Builder), Multi-turn (ordered child tests in one conversation, each child marked critical or not), and Plan Validation (expected tools, actions and connected agents must appear in the dynamic plan to a pass threshold %). "Plan validation is a deterministic test." Connector consent cards can be automated as a two-step multi-turn test with an `Invoke Actions` payload `{"action": "Allow", "id": "submit", "shouldAwaitUserInput": true}`. Tests can be bulk edited through Excel. (read 1 Nov 2026) [Configure tests in Copilot Agent Kit](https://learn.microsoft.com/microsoft-copilot-studio/guidance/kit-configure-tests)
- Rubrics: an LLM judge grades 1-5 against a rubric. Testing mode (rubric on the test case) gives grade only and pass or fail by passing grade; refinement mode (rubric on the test run) gives grade plus rationale and compares with human grades. Microsoft suggests iterating "until alignment is 80-90% or higher". (read 1 Nov 2026) [Use rubrics in tests](https://learn.microsoft.com/microsoft-copilot-studio/guidance/kit-rubrics-tests); [Rubrics reference guide](https://learn.microsoft.com/microsoft-copilot-studio/guidance/kit-rubrics-reference) [snippet]
- Agent config for test automation needs region, a token endpoint or a Direct Line secret (stored in Dataverse or Azure Key Vault), and optional Entra ID v2 user auth via two app registrations. (read 1 Nov 2026) [Configure agents in Copilot Agent Kit](https://learn.microsoft.com/microsoft-copilot-studio/guidance/kit-configure-agents) [snippet]
- Microsoft documents a quality gate where Power Platform Pipelines pause a deployment, run Kit tests from a cloud flow, and continue only if they pass (three environments: pipeline host, dev with the Kit installed, target). (read 1 Nov 2026) [Automate testing and deployment of agents using pipelines in Power Platform](https://learn.microsoft.com/microsoft-copilot-studio/guidance/kit-automate-test-deploy) [snippet]

**Scripted conversation clients (for a custom grader in GitHub Actions)**
- Direct Line: with web channel security on, exchange the secret for a single-conversation token at `POST https://directline.botframework.com/v3/directline/tokens/generate` (`expires_in` 1800 in the sample); "For a service-to-service app, specify the secret in the authorization header". - Microsoft's performance-testing guidance describes the Direct Line flow: get token, start conversation, POST activities, receive over the WebSocket stream. (read 1 Nov 2026) [Test conversational agents using Direct Line](https://learn.microsoft.com/microsoft-copilot-studio/guidance/conversational-agents-performance-testing-direct-line) [snippet]

The sample gets the token through MSAL (a user token). (read 1 Nov 2026) [Custom Copilot agent for Dynamics 365 and Power Apps reference architecture](https://learn.microsoft.com/dynamics365/guidance/reference-architectures/custom-copilot-agent-dynamics-365-power-apps#implement-the-pcf-control-integration) [snippet]

(read 1 Nov 2026) [Connect your code app to Copilot Studio agents](https://learn.microsoft.com/power-apps/developer/code-apps/how-to/connect-to-copilot-studio) [snippet]
- Related but different: the Microsoft 365 Copilot Agent Evaluations CLI (`@microsoft/m365-copilot-eval`, `runevals`) scores declarative agents in M365 Copilot with Foundry evaluators (Relevance, Coherence, Groundedness, Similarity, Citations, ExactMatch, PartialMatch) and JSON datasets with multi-turn `turns`; outputs HTML, JSON or CSV; exit codes for CI. Authentication support for other operating systems is coming soon." (read 1 Nov 2026) [Agent Evaluations CLI overview](https://learn.microsoft.com/microsoft-365/copilot/extensibility/evaluations-cli-overview); [Quickstart](https://learn.microsoft.com/microsoft-365/copilot/extensibility/evaluations-cli-quickstart); [Dataset schema and test design](https://learn.microsoft.com/microsoft-365/copilot/extensibility/evaluations-cli-create-tests)

### Inferences
- Answer to "is the 5-minute human test-pane check still needed?": for standard-harness agents, mostly no. A locked evaluation can cover tool selection (Tool use method or Kit Plan Validation, both deterministic), exact or keyword assertions, multi-turn slot filling, and AI-graded quality, and CI can trigger and read it. Keep the human step for (a) GitHub Copilot harness agents, where only General quality exists and no API is documented, (b) agents with "Authenticate manually", (c) first-time connector consent, and (d) a spot check of the AI grader's reasoning on failures. A realistic target is a 1-2 minute human review of a graded transcript bundle, not a 5-minute free-form session.
- Holding test sets out of the implementer's reach: built-in test sets live on the agent and any maker with access can see them, so the implementer (if it has maker rights in the Dev environment) can read them. Options: keep the held-out set only in a separate repo and run it through a custom Direct Line or Agents SDK harness owned by the evaluator identity; or create built-in test sets under a separate evaluator account in a separate environment the implementer cannot access, importing the agent solution there before evaluation. This is design inference.
- The most robust grader for the factory is a custom Node or .NET runner in GitHub Actions (Direct Line or `CopilotStudioClient`) that sends locked scripted turns, asserts deterministically on text, attachments and the tools seen in the transcript, and then calls an LLM judge with a locked rubric. That keeps tests, rubric and judge prompt in a locked path, produces a JSON transcript with grades as evidence, and runs on ubuntu. Verifying which tools ran may need Dataverse conversation transcripts or Application Insights, as the Kit does.
- Expect AI-graded results to vary between runs. Use pass thresholds over several runs (for example, 3 runs, pass if 2 of 3) for generative answers, and keep deterministic checks as the hard gate.

### Gaps
- No documented REST API or CLI for evaluation on GitHub Copilot harness agents was found as of 1 Nov 2026; the REST page is scoped to the standard harness.
- No documented API to create or import a built-in test set from a file (only list, get, run). Test sets may be stored in Dataverse, but I found no supported way to write them.
- Whether the evaluation REST API accepts an app-only (service principal) token is not stated; docs say "user access token".
- Run time for a 100-case evaluation is not documented ("might take several minutes" for the new harness).
- I did not read the github.com/microsoft/Power-CAT-Copilot-Studio-Kit README directly; findings come from Learn guidance pages.

## 4. Power Automate cloud flows: triggering and asserting from code, deterministic scenario tests

### Takeaway
There is no headless unit-test runner for cloud flows. Testing is black-box against a real Dev or Test environment: trigger the flow from code (HTTP trigger with Entra auth, or write a Dataverse row that fires a Dataverse trigger), then assert on (a) the side effects in Dataverse and (b) the run record in the Dataverse `FlowRun` table for solution-aware flows. Static results ("beaker" mocks) can stub slow or external actions, but they are set in the flow definition, so they must not ship. The designer "Test" pane is interactive only. Everything except the designer pane can run from an ubuntu GitHub Actions runner.

### Cited Findings
- HTTP trigger "Who can trigger the flow?": "Any user in my tenant", "Specific users in my tenant" (accepts email addresses or "object IDs of service principal users if you intend to use this flow to be triggered only by SPN"), or "Anyone" (legacy, URL is the credential). Token claims required: `aud` (public cloud `https://service.flow.microsoft.com/`, exact including trailing slash), `iss`, `tid`, and `oid` when restricted to specific users. (read 1 Nov 2026) [Add OAuth authentication for HTTP request triggers](https://learn.microsoft.com/power-automate/oauth-authentication)
- From 30 November 2025, HTTP and Teams Webhook trigger URLs containing `logic.azure.com` moved to new URLs as environments move to the new architecture; old URLs stopped working. (read 1 Nov 2026) [Troubleshoot Power Automate trigger problems](https://learn.microsoft.com/troubleshoot/power-platform/power-automate/flow-run-issues/triggers-troubleshoot) [snippet]
- Flows in solutions are stored in the Dataverse `workflow` table (`category` 5 = modern flow, `statecode` 0 off, 1 on, 2 suspended, `clientdata` = JSON definition plus connection references) and can be managed through the Dataverse SDK or Web API; "managing flows under My Flows aren't supported with code." (read 1 Nov 2026) [Work with cloud flows using code](https://learn.microsoft.com/power-automate/manage-flows-with-code)
- Run history in Dataverse: each run of a solution-aware flow writes a `FlowRun` elastic-table row with start and end time, duration, status (Success, Failed, Cancelled), trigger type, error code and message, workflow ID, parent run ID; default retention 28 days (`FlowRunTimeToLiveInSeconds`). Queryable through the Web API. Caveats: the ingest "isn't transactional, and hence isn't 100 percent lossless"; records can be throttled or skipped (signalled in `FlowEvent`); flow owners need read access to `FlowRun` or rows are not stored; "Flow execution history within flow details in the Power Automate portal is transactional, and therefore provides a lossless view of runs." Application Insights data is described as "more complete" and "deeper" (triggers and actions). (read 1 Nov 2026) [Manage cloud flow run history in Dataverse](https://learn.microsoft.com/power-automate/dataverse/cloud-flow-run-metadata)
- Built-in testing tools: Flow Checker (static analysis before run); Test Flow pane (manual, or automatic using "a recently used trigger or repeat a previous test run", and you must test manually once first); static results ("Static result on" in the Testing tab, beaker icon) to mock an action's status and outputs without running it, for example to avoid sending a real approval. (read 1 Nov 2026) [Test cloud flows](https://learn.microsoft.com/power-automate/guidance/coding-guidelines/test-cloud-flows)
- Application Insights can be linked at environment level for flow run, trigger and action telemetry. (read 1 Nov 2026) [Monitor your flows](https://learn.microsoft.com/power-automate/guidance/coding-guidelines/monitoring-and-alerting) [snippet]

### Inferences
- Deterministic scenario pattern for the factory: (1) seed test data with a unique run tag (for example a GUID in a name or a dedicated "test run" column) through the Dataverse Web API as an app user; (2) trigger: POST to the HTTP trigger with an Entra token for a named service principal, or create the Dataverse row that the trigger watches; (3) poll Dataverse for the expected side effect with a timeout (Dataverse-triggered flows usually start within seconds to a couple of minutes, but this is not guaranteed); (4) also check the `FlowRun` row for Status = Success and no error, treating a missing row as "unknown" not "fail" because ingest is lossy; (5) delete all rows carrying the run tag in an `afterAll` step, and run a nightly sweeper for leftovers.
- Keep side-effect connectors (email, Teams, approvals) pointed at test mailboxes or channels through environment variables and connection references in the Test environment. Do not let the implementing agent add static results to production flows; a solution-checker or custom lint step can scan `clientdata` for `staticResults` and fail the build. That lint is inference: I did not confirm the exact JSON key.
- Use the lossless portal run history (or Application Insights) only for investigation. For automated grading, side effects in Dataverse are the most reliable assertion.

### Gaps
- No supported public REST API for the Power Automate portal run history (the "lossless" view) was found in this pass; the Power Automate Management connector exists but I did not verify its current actions.
- No first-party unit-test framework for flow expressions or definitions was found.
- Typical latency from Dataverse row change to flow start is not documented here.

## 5. Dataverse server logic: plug-ins, low-code plug-ins (Power Fx), business rules

### Takeaway
Microsoft provides no unit-test framework for Dataverse. For C# plug-ins the standard answer is still the community FakeXrmEasy (in-memory fake of `IOrganizationService` and the execution context), which Microsoft names but does not support. Low-code (Power Fx) plug-ins are still preview and can only be tested by calling them: instant ones as custom APIs through the Web API, automated ones by creating, updating or deleting the row and checking the result. Business rules have no test hook: test them through the form (Playwright) for client-side behaviour, or through the Web API when scoped to Entity (server-side). Plug-in trace logs (`plugintracelogs`) give queryable evidence.

### Cited Findings
- "Microsoft Dataverse doesn't provide testing framework tools... A popular framework for server-side development is Fake Xrm Easy. This framework can be combined with your choice of .NET framework testing frameworks." "Microsoft does not provide support for tools created by the community." (read 1 Nov 2026) [Testing tools for server-side development](https://learn.microsoft.com/power-apps/developer/data-platform/testing-tools-server)
- Microsoft's own plug-in test path is integration testing in a test environment: register the assembly, add to an unmanaged solution, test behaviour, verify trace logs; "You might want to write a program that automates performing the operations that cause your plug-in to fire and includes many possible variations." Trace logs are queryable: `GET <org>/api/data/v9.0/plugintracelogs?$select=messageblock&$filter=startswith(typename,'BasicPlugin.FollowUpPlugin')`. Trace log rows survive a transaction rollback. The plug-in profiler can capture execution context for replay. (read 1 Nov 2026) [Debug plug-ins](https://learn.microsoft.com/power-apps/developer/data-platform/debug-plug-in)
- Plug-in projects "must target .NET Framework" (SDK-style project, `net462`); assembly limit 16 MB; `pac plugin init` scaffolds a project and `pac plugin push` imports it. (read 1 Nov 2026) [Build and package plug-in code](https://learn.microsoft.com/power-apps/developer/data-platform/build-and-package); [pac plugin](https://learn.microsoft.com/power-platform/developer/cli/reference/plugin)
- FakeXrmEasy v3 packages on NuGet point to a licensing agreement; the vendor docs describe a commercial licence with an organisation-wide licence key, usage tracked per test run through a storage connection, and an environment variable to exclude build and release pipeline users. [snippet] [NuGet: FakeXrmEasy.v365 3.3.0 licence](https://www.nuget.org/packages/FakeXrmEasy.v365/3.3.0/License); [FakeXrmEasy commercial licence overview](https://dynamicsvalue.github.io/fake-xrm-easy-docs/licensing/commercial-license/overview) (fetch blocked by the session network; search summary only)
- Low-code plug-ins (Dataverse Accelerator) are "(preview)". Two types: instant (manually run, input and output parameters, global or table scope, registered as a custom API) and automated (Create, Update or Delete event, pre- or post-operation). Test instant ones with the Test command or "Invoke an instant plug-in from the Dataverse Web API" as an unbound action or bound function; "Use output parameters to help validate expected behavior... Otherwise, you only see a success or failure". Test automated ones "by invoking the data event". (read 1 Nov 2026) [Use low-code plug-ins in Dataverse (preview)](https://learn.microsoft.com/power-apps/maker/data-platform/low-code-plug-ins)
- `pac power-fx run --file <file>` (preview) runs a file of Power Fx against the Dataverse environment of the active auth profile (for example `Collect(Contacts, {...})`, `FirstN(Contacts, 5)`), useful for seeding data or quick formula checks. (read 1 Nov 2026) [pac power-fx](https://learn.microsoft.com/power-platform/developer/cli/reference/power-fx#pac-power-fx-run)
- Business rules are stored in the `workflow` table with `category` 2. (read 1 Nov 2026) [Work with cloud flows using code](https://learn.microsoft.com/power-automate/manage-flows-with-code)

### Inferences
- Plug-in unit tests: because plug-ins target .NET Framework 4.6.2 to 4.8, run FakeXrmEasy tests on a `windows-latest` runner (or test the business logic in a separate `netstandard`/`net8` class library that the plug-in calls, which runs on ubuntu). Budget for the FakeXrmEasy commercial licence, or write thin hand-rolled fakes of `IOrganizationService` with Moq or FakeItEasy.
- Locked acceptance tests for all server logic should be integration tests against the Dev or Test environment through the Web API as an application user: create the row, read it back, assert the computed fields, query `plugintracelogs` for expected messages, then clean up. These run on ubuntu, take seconds per case, and work identically for C# plug-ins, low-code plug-ins and server-scoped business rules.
- Business rules scoped to a form only fire in the UI, so they need a Playwright form test (`FormComponent.setAttribute` then check field visibility, required level or value).

### Gaps
- I could not open the FakeXrmEasy licensing docs (host blocked) to confirm the current licence model and price; from prior knowledge v1.x was MIT and v2 and later are dual-licensed (RPL-1.5 or commercial), but this is unverified for 2026.
- Whether "Dataverse functions" (Power Fx) have moved to GA or been renamed in 2026 was not confirmed; Learn still says "(preview)" for low-code plug-ins.
- No first-party testing guidance for business rules was found.

## 6. Accessibility checks for canvas and model-driven apps

### Takeaway
The Power Apps Studio Accessibility checker is interactive only, but solution checker (`pac solution check`, the `check-solution` GitHub Action, or the Power Apps checker Web API) includes canvas-app accessibility rules and returns SARIF, so a subset of the same checks runs headlessly in CI. For the running app, axe-core through Playwright (`@axe-core/playwright`) is the practical automated layer; it is not documented by Microsoft for Power Apps, so treat it as inference and expect some noise from platform chrome.

### Cited Findings
- The Accessibility checker is opened from the App checker icon in Power Apps Studio; issues are Errors (for example "Missing accessible label", "Focus isn't showing" when `FocusBorderThickness` is 0), Warnings ("Missing captions", "HTML won't be accessible", "Turn off autostart"), and Tips ("Revise screen name", "Check the order of the screen items" when `TabIndex` > 0). Colour contrast is not automatically checked; Microsoft points to accessible colour guidance. (read 1 Nov 2026) [Review a canvas app for accessibility](https://learn.microsoft.com/power-apps/maker/canvas-apps/accessibility-checker)
- Guidance: text contrast 4.5:1 or greater, `AccessibleLabel` on inputs, never set `TabIndex` above 0, enable "Simplified tab index", test keyboard-only. (read 1 Nov 2026) [Create accessible canvas apps](https://learn.microsoft.com/power-apps/maker/canvas-apps/accessible-apps)
- Solution checker rule list includes canvas accessibility rules such as `app-include-alternative-input` and `app-avoid-autostart` (category Accessibility). (read 1 Nov 2026) [Use solution checker: best practice rules](https://learn.microsoft.com/power-apps/maker/data-platform/use-powerapps-checker#best-practice-rules-used-by-solution-checker) [snippet]
- `pac solution check` uploads a solution to the Power Apps Checker service, default ruleset "Solution Checker"; results are SARIF v2. The GitHub Action `check-solution` takes service principal credentials, `path`, `geo`, `rule-level-override`, and uploads logs as an artefact. In Managed Environments, solution checker enforcement can block import on critical violations. (read 1 Nov 2026) [pac solution](https://learn.microsoft.com/power-platform/developer/cli/reference/solution#pac-solution-check); [Power Apps checker web API report format](https://learn.microsoft.com/power-platform/alm/checker-api/overview#report-format); [GitHub Actions for Power Platform](https://learn.microsoft.com/power-platform/alm/devops-github-available-actions#solution-tasks); [Solution checker enforcement](https://learn.microsoft.com/troubleshoot/power-platform/dataverse/working-with-solutions/solution-checker-enforcement-import-issues)
- Model-driven deprecations that matter for a11y: Editable Grid and Power Apps Read-Only Grid controls deprecated from March 2026 because the Editable Grid "does not align with current Microsoft accessibility standards"; use the Power Apps grid control. (read 1 Nov 2026) [Important changes coming](https://learn.microsoft.com/power-platform/important-changes-coming)

### Inferences
- Layered a11y gate: (1) `pac solution check` in CI, fail on any Accessibility-category issue at Medium or above; (2) a locked Playwright pass that loads each screen and runs axe-core scoped to `iframe[name="fullscreen-app-host"]` for canvas apps and to the main form region for model-driven apps, with a baseline file of known platform violations so only new ones fail; (3) a keyboard-only Playwright script for the key journey (Tab order, visible focus). (2) and (3) are not Microsoft-documented for Power Apps.
- Spec-level rule for the factory: every interactive canvas control must have an `AccessibleLabel`; the locked tests can select by accessible name, which enforces this for free.

### Gaps
- No Microsoft doc found on running axe-core against Power Apps or on known false positives from the player chrome.
- The full list of solution checker canvas accessibility rule IDs was only seen partially.

## 7. Evidence a morning reviewer can trust

### Takeaway
Use standard, tamper-evident artefacts produced by the evaluator, not by the implementing agent: Playwright HTML report, JUnit XML, `trace.zip`, screenshots and video; SARIF from solution checker; Copilot Studio evaluation run JSON (per-case method results plus `aiResultReason`) or CSV export; a scripted-conversation transcript JSON with deterministic assertion results and rubric grades; `FlowRun` and `plugintracelogs` query results for back-end checks.

### Cited Findings
- Playwright migration mapping offers `page.screenshot()` and `toHaveScreenshot()` for visual evidence. (read 1 Nov 2026) [Migrate from Power Apps Test Engine](https://learn.microsoft.com/power-platform/developer/playwright-samples/migration-guide)
- Copilot Studio evaluation run details carry per-test-case `metricsResults` with `status`, `errorReason`, `aiResultReason`, plus `ownerId`, `startTime`, `endTime`; results kept 89 days in the product, export to CSV for longer. (read 1 Nov 2026) [Automate agent evaluations with Power Platform API](https://learn.microsoft.com/microsoft-copilot-studio/analytics-agent-evaluation-rest-api); [Create a single response test set](https://learn.microsoft.com/microsoft-copilot-studio/analytics-agent-evaluation-create)
- New-harness evaluations can be downloaded as a session package with run metadata and each turn's input, response and score. (read 1 Nov 2026) [Run an evaluation for an agent (preview)](https://learn.microsoft.com/microsoft-copilot-studio/agents-experience/analytics-agent-evaluation-results) [snippet]
- Solution checker output is SARIF v2. (read 1 Nov 2026) [Power Apps checker web API](https://learn.microsoft.com/power-platform/alm/checker-api/overview#report-format)
- `FlowRun` gives status, error code and message per run; `plugintracelogs` gives plug-in trace text. (read 1 Nov 2026) [Manage cloud flow run history in Dataverse](https://learn.microsoft.com/power-automate/dataverse/cloud-flow-run-metadata); [Debug plug-ins](https://learn.microsoft.com/power-apps/developer/data-platform/debug-plug-in)

### Inferences
- A one-page morning summary per PR could list: deterministic suite pass or fail counts; held-out suite pass rate (numbers only, not case text); a11y SARIF counts; Copilot eval scores against the last green baseline; links to the trace and transcript artefacts. Store artefacts with GitHub Actions `upload-artifact` and record their SHA-256 in the job summary so a reviewer can see they came from the evaluator job.
- Prefer graded transcripts with the rationale turned on only for failures, to keep LLM cost down.

### Gaps

## 8. Practical design: locked acceptance tests, held-out scenarios, headless matrix, run times

### Takeaway
Keep all acceptance and held-out assets outside anything the implementing agent can read or write: a separate repo or a CODEOWNERS-protected path, run by a separate workflow under a separate identity, against a Test environment the implementer has no maker rights in. Almost everything can run headlessly on ubuntu in GitHub Actions; the exceptions are FakeXrmEasy plug-in unit tests (.NET Framework, so Windows runner or a split library), the Copilot Studio evaluation API (needs a user token), and new-harness Copilot Studio evaluation (UI only). Rough suite times: minutes, not hours.

### Cited Findings
- Playwright toolkit "Works headlessly in GitHub Actions"; CI auth runs in `globalSetup` with a certificate. (read 1 Nov 2026) [Overview](https://learn.microsoft.com/power-platform/developer/playwright-samples/overview); [Authentication guide](https://learn.microsoft.com/power-platform/developer/playwright-samples/authentication-guide)
- Canvas load with Dataverse data 30-60 s; direct URL saves 10-20 s per test. (read 1 Nov 2026) [Test canvas apps](https://learn.microsoft.com/power-platform/developer/playwright-samples/canvas-application)
- Copilot Studio test sets are visible to "Any maker with access to the agent"; evaluation runs as the signed-in user; the REST API needs a user access token. (read 1 Nov 2026) [Create a single response test set](https://learn.microsoft.com/microsoft-copilot-studio/analytics-agent-evaluation-create); [REST API](https://learn.microsoft.com/microsoft-copilot-studio/analytics-agent-evaluation-rest-api)
- HTTP-triggered flows can be restricted to specific service principal object IDs. (read 1 Nov 2026) [OAuth for HTTP request triggers](https://learn.microsoft.com/power-automate/oauth-authentication)
- Kit Plan Validation is deterministic and checks the tools in the dynamic plan. (read 1 Nov 2026) [Configure tests in Copilot Agent Kit](https://learn.microsoft.com/microsoft-copilot-studio/guidance/kit-configure-tests)
- Microsoft says to keep agent test sets "in source control, and rerun it unchanged". (read 1 Nov 2026) [Model migration guidance](https://learn.microsoft.com/microsoft-copilot-studio/guidance/manage-agent-model-migration)

### Headless matrix (what runs in GitHub Actions on ubuntu today, as of 1 Nov 2026)
| Check | Headless on ubuntu? | Notes |
| --- | --- | --- |
| Canvas, model-driven, custom page UI tests (Playwright toolkit) | Yes | Certificate-auth test user; storage state for two domains. Documented by Microsoft. |
| Test Engine `pac test run` | Not recommended | Deprecated April 2026, preview only, repo unmaintained. |
| Solution checker (`pac solution check`, `check-solution` action) | Yes (cloud service) | Service principal; SARIF output. Runner OS support for the action not re-verified in this pass. |
| Dataverse integration tests (Web API) for plug-ins, low-code plug-ins, server business rules | Yes | Application user; any language. |
| FakeXrmEasy plug-in unit tests | Windows runner (inference) | Plug-ins target .NET Framework; commercial licence for v2+ (unverified). |
| Cloud flow scenario tests (HTTP or Dataverse trigger, assert side effects, `FlowRun`) | Yes | Real environment; `FlowRun` lossy, use as secondary signal. |
| Copilot Studio built-in evaluation via REST or `pac copilot-studio` (standard harness) | Partly | Needs a user token; test sets created in UI only; visible to all makers. |
| Copilot Studio scripted conversations via Direct Line or `CopilotStudioClient` plus own LLM judge | Yes | Most controllable; you build the grader. |
| Copilot Agent Kit test runs | Runs inside Dataverse, not in the runner | Triggerable from CI by creating a test run record (inference) or via Power Platform Pipelines gate (documented). |
| GitHub Copilot harness agent evaluation | No | Preview UI only, General quality only, no API documented. |
| Studio Accessibility checker | No | Studio UI only; use solution checker rules plus axe-core. |
| Agent Evaluations CLI (`runevals`) | No for Copilot Studio agents | Built for M365 Copilot declarative agents; Windows auth only per quickstart. |

### Inferences
- Structure (inference, design proposal):
  - `acceptance/` (locked): written by the spec author or a separate test-writer agent before implementation, from the spec. Contains Playwright specs, Web API integration tests, flow scenario tests, Copilot conversation scripts with deterministic assertions, and the rubric file. Protected by CODEOWNERS plus a branch ruleset; the implementer workflow's token has no write permission to it and a CI check fails any PR that touches it.
  - `heldout/` (secret): lives in a separate private repo the implementer cannot read. The evaluator workflow checks it out with its own deploy key, runs it, and posts only aggregate scores and failing-case IDs back to the PR, never the case text, so the implementer cannot overfit to it. Rotate a share of cases each month.
  - Identities: implementer service principal has maker rights in Dev only. Evaluator has its own certificate-auth test user (UI and Copilot), its own application user (Web API), and its own Test environment into which the PR's managed solution is imported before testing. This also keeps built-in Copilot Studio test sets out of the implementer's view.
  - Click-through evaluator (Playwright MCP agent): give it the held-out user stories in plain language, the evaluator's storage state, and a time box; require it to save a Playwright trace and screenshots for every claim it makes. Treat its verdict as advisory unless a deterministic test agrees.
- Rough run-time budget per PR (estimates, not measured): solution import into Test 3-10 min; solution checker 2-5 min; Web API integration tests 1-3 min; 10-20 Playwright UI scenarios 5-15 min on 2-4 workers; flow scenario tests 2-10 min (polling); Copilot scripted conversations, 20-50 turns 3-10 min plus judge calls; built-in evaluation of 100 cases "several minutes" or more. Total roughly 20-45 minutes, which fits an overnight window easily.
- Flakiness controls: retries 1 for UI tests with trace on first retry; unique run tags for all data; serial execution for tests that share a record type; three-run majority for generative-answer grades.

### Gaps
- No measured run times from Microsoft for any of these suites.
- Service protection API limits for many parallel Playwright sessions against one environment were not researched here.
- Licensing for test users (Power Apps, Copilot Studio credits for evaluation) was not covered; new-harness evaluation consumes Copilot Credits.
