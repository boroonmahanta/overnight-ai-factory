# Power Platform ALM, identity and environment management for an unattended overnight AI agent pipeline (as of 1 November 2026)

Research date: 1 November 2026. Primary sources are Microsoft Learn pages fetched via the Microsoft Learn MCP server on 1 November 2026 unless marked otherwise. [snippet] = only a search summary was available. [secondary] = third-party write-up.

## Q1. How does pac authenticate from GitHub Actions with OIDC workload identity federation, and does it work on GHE.com?

### Takeaway
pac has a documented switch, `pac auth create --githubFederated` (`-ghf`), that needs `--tenant` and `--applicationId` and no secret. Microsoft also publishes an OIDC/FIC tutorial for microsoft/powerplatform-actions (Learn page live on 1 Nov 2026). GHE.com changes only the token issuer (`https://token.actions.SUBDOMAIN.ghe.com`), so the Entra federated credential must use that issuer with the "Other issuer" scenario. I found no Microsoft statement that confirms or denies GHE.com support for pac federation, so treat it as "should work, must be proven in a spike".

### Cited Findings
- `pac auth create` flags (pac CLI reference, accessed 1 Nov 2026): `--githubFederated` / `-ghf`: "Use GitHub Federation for Service Principal Auth; requires --tenant and --applicationId arguments". It is a switch (no value). Sibling switches: `--azureDevOpsFederated` / `-adof` (same requirements), `--managedIdentity` / `-mi` (uses DefaultAzureCredential, honours `AZURE_CLIENT_ID`), `--clientSecret` / `-cs`, `--certificateDiskPath` / `-cdp`, `--certificatePassword` / `-cp`, `--deviceCode` / `-dc`, `--environment` / `-env` (ID, URL, unique name or partial name), `--name` / `-n` (1 to 30 characters), `--cloud` / `-ci` (Public, UsGov, UsGovHigh, UsGovDod, China, UsNat, UsSec). `--url` is deprecated in favour of `--environment`. Other auth verbs: `pac auth list`, `select --index|--name`, `update --index --environment`, `who`, `token` ("Display a Power Platform API access token for the currently selected authentication profile"), `clear`, `delete`. [pac auth reference](https://learn.microsoft.com/en-us/power-platform/developer/cli/reference/auth)
- Command shape for an unattended job (built from the documented flags above): `pac auth create --name lane1-exec --githubFederated --tenant <tenantId> --applicationId <clientId> --environment https://<org>.crm6.dynamics.com`. The job needs `permissions: id-token: write`. [pac auth reference](https://learn.microsoft.com/en-us/power-platform/developer/cli/reference/auth); [GitHub OIDC reference](https://raw.githubusercontent.com/github/docs/main/content/actions/reference/security/oidc.md)
- Microsoft Learn tutorial "Use OIDC/FIC authentication with GitHub Actions for Microsoft Power Platform" (accessed 1 Nov 2026) steps: set the repo OIDC subject template to `repository, workflow` (resolves to `repo:MyOrg/MyRepo:workflow:MyWorkflow`); create an Entra app registration; add API permission **Dynamics CRM**; add a federated credential with scenario **Other** and that exact subject; add the app as an application user with roles in each environment. The sample job uses `runs-on: ubuntu-latest`, `permissions: id-token: write, contents: read`, `microsoft/powerplatform-actions/actions-install@v1` with `pac-version-override: 2.4.1`, then `microsoft/powerplatform-actions/who-am-i@v1` with only `environment-url`, `app-id` and `tenant-id` (no `client-secret`). "The subject claim in GitHub and the subject identifier in your federated credential must match exactly." [Learn OIDC/FIC tutorial](https://learn.microsoft.com/en-us/power-platform/alm/tutorials/github-actions-oidc-fic)
- Conflict to note: the `export-solution/action.yml` on `main` (fetched 1 Nov 2026) still lists only `user-name`/`password-secret` or `app-id`/`client-secret`/`tenant-id`, and says `client-secret` is "Required if authenticating with app-id". It runs on `node24`, has `cloud` (default `Public`), `run-asynchronously`, `max-async-wait-time` (default 60 minutes). So federation support may differ per action; the safe pattern is to call `pac` directly in a `run:` step after `actions-install`. [export-solution action.yml](https://raw.githubusercontent.com/microsoft/powerplatform-actions/main/export-solution/action.yml); [Learn OIDC/FIC tutorial](https://learn.microsoft.com/en-us/power-platform/alm/tutorials/github-actions-oidc-fic)
- The powerplatform-actions repo (README, fetched 1 Nov 2026) lists these actions: actions-install, add-solution-component, assign-group, assign-user, backup-environment, branch-solution, build, catalog-status, check-solution, clone-solution, copy-environment, create-environment, delete-environment, delete-solution, deploy-package, download-paportal, export-data, export-solution, import-data, import-solution, install-application, install-catalog, pack-solution, publish-solution, reset-environment, restore-environment, set-online-solution-version, submit-catalog, unpack-solution, update-solution-version, upgrade-solution, upload-paportal, who-am-i. Examples use `@v1`; the README example uses `windows-latest` with "alternate runner OS is: ubuntu-latest". [powerplatform-actions README](https://github.com/microsoft/powerplatform-actions)
- Learn states the actions "can run on both Windows agents and Linux agents". [GitHub Actions for Power Platform](https://learn.microsoft.com/power-platform/alm/devops-github-actions)
- GitHub subject formats (GitHub docs source, fetched 1 Nov 2026): environment job `repo:ORG-NAME/REPO-NAME:environment:ENVIRONMENT-NAME`; pull request (no environment) `repo:ORG-NAME/REPO-NAME:pull_request`; branch (no environment, not PR) `repo:ORG-NAME/REPO-NAME:ref:refs/heads/BRANCH-NAME`. Default audience is the URL of the repository owner; Azure/Entra uses `api://AzureADTokenExchange`. [GitHub OIDC reference](https://raw.githubusercontent.com/github/docs/main/content/actions/reference/security/oidc.md); [Entra workload identity federation](https://learn.microsoft.com/entra/workload-id/workload-identity-federation-create-trust)
- Immutable subject change: "repositories created after July 15, 2026 now use an immutable default subject format": `repo:OWNER@OWNER-ID/REPO@REPO-ID:ref:refs/heads/BRANCH`, example `repo:octo-org@123456/octo-repo@456789:ref:refs/heads/main`. Older repos keep the old format unless they opt in; renames or transfers after 15 July 2026 switch to the new format. Not available on GitHub Enterprise Server. Microsoft's Databricks docs repeat this for environments: `repo:octo-org@123456/octo-repo@456789:environment:prod`. [GitHub OIDC reference](https://raw.githubusercontent.com/github/docs/main/content/actions/reference/security/oidc.md); [Azure Databricks GitHub federation](https://learn.microsoft.com/azure/databricks/dev-tools/auth/provider-github)
- GHE.com data residency: the expected claim "must substitute `githubusercontent.com`" with the data residency domain. For subdomain `octocorp` the issuer is `https://token.actions.octocorp.ghe.com` and discovery is `https://token.actions.octocorp.ghe.com/.well-known/openid-configuration`. Issuer customisation endpoint: `/enterprises/SUBDOMAIN/actions/oidc/customization/issuer`. [GitHub OIDC reference](https://raw.githubusercontent.com/github/docs/main/content/actions/reference/security/oidc.md) [snippet for the endpoint path]
- Subject customisation uses `include_claim_keys`; for example `["repo", "context", "job_workflow_ref"]` gives `repo:ORG/REPO:environment:ENV:job_workflow_ref:REUSABLE-WORKFLOW-PATH`. [GitHub OIDC reference](https://raw.githubusercontent.com/github/docs/main/content/actions/reference/security/oidc.md)
- Entra limits (fetched 1 Nov 2026): "A maximum of 20 federated identity credentials can be added to an application or user-assigned managed identity." The issuer plus subject pair must be unique per app; issuer, subject and audience fields each have a 600 character limit; a wrong subject is accepted at creation and "the exchange fails without error" later. Creating a credential needs app ownership or Application Administrator, Cloud Application Administrator, Global Administrator or Hybrid Identity Administrator. Flexible federated identity credentials (preview) allow a restricted expression language for subject matching. [Entra FIC considerations](https://learn.microsoft.com/entra/workload-id/workload-identity-federation-considerations); [Flexible FIC (preview)](https://learn.microsoft.com/entra/workload-id/workload-identities-flexible-federated-identity-credentials)
- Second conflict: `who-am-i/action.yml` on `main` (fetched 1 Nov 2026) also defines only `user-name`/`password-secret` and `app-id`/`client-secret`/`tenant-id` (plus `cloud`), with no federation input, even though the Learn tutorial calls it with no secret. Either federation is detected implicitly when `client-secret` is absent and `id-token: write` is granted, or the tutorial is ahead of the published action. [who-am-i action.yml](https://raw.githubusercontent.com/microsoft/powerplatform-actions/main/who-am-i/action.yml)
- Entra federated credential via PowerShell: `New-AzADAppFederatedCredential -ApplicationObjectId $appObjectId -Audience api://AzureADTokenExchange -Issuer 'https://token.actions.githubusercontent.com/' -Name 'GitHub-Actions-Test' -Subject 'repo:octo-org/octo-repo:environment:Production'`. The Entra portal GitHub scenario autopopulates the issuer for github.com, and "Pattern matching isn't supported for branches and tags". [Entra workload identity federation](https://learn.microsoft.com/entra/workload-id/workload-identity-federation-create-trust)

### Inferences
- For GHE.com, create each federated credential with the **Other issuer** scenario: issuer `https://token.actions.<subdomain>.ghe.com`, subject `repo:<org>/<repo>:environment:<env>` (or the `@ID` immutable form if the repo was created after 15 July 2026), audience `api://AzureADTokenExchange`. Read the real `sub` from a debug job before you create the credential.
- Use one GitHub environment per identity per lane (for example `lane1-exec`, `lane1-verify`, `lane1-review`, `merge`, `uat`, `prod`). Each maps to one federated credential on one Entra app. Exact-match subjects mean a lane job cannot borrow another lane's identity. Entra allows at most 20 federated credentials per app (see Cited Findings), so one app per identity keeps you well under it.
- pac reads the GitHub token itself when `-ghf` is set, so the issuer comes from the runner's `ACTIONS_ID_TOKEN_REQUEST_URL`. On GHE.com that URL points at the ghe.com issuer, so no pac change should be needed. This is inference, not documented.
- The Learn sample pins `pac-version-override: 2.4.1`; pin a pac version in the factory too, so a nightly run does not pick up a breaking change.

### Gaps
- No Microsoft or GitHub page found that says pac `--githubFederated` is tested on GHE.com data residency. Prove it with a one-job spike (`pac auth create -ghf ...` then `pac org who`).
- I did not confirm which pac version first shipped `--githubFederated`, or whether every powerplatform-actions action (not just who-am-i) accepts federation without `client-secret`.

## Q2. Service principals in Dataverse: application users, roles, least privilege, and what a service principal cannot do

### Takeaway
An application user is an unlicensed, non-interactive Dataverse user tied to an Entra app. Microsoft's tooling defaults it to System Administrator, and the docs say lower roles "can't deploy plug-ins and other code components". A tenant-level Power Platform "management application" registration (needed for environment creation and admin APIs) gives the SP Power Platform Administrator-equivalent rights with no granular scoping, and "a service principal can't register itself": an admin with a username and password must do it. OAuth-based connections (Teams, Outlook and most Microsoft 365 connectors) cannot be created by an SP, which is why the human bootstrap step exists.

### Cited Findings
- `pac admin create-service-principal --environment <id>` creates the Entra app plus SPN and adds it as an application user; optional `--name` and `--role` (default "System Administrator"). Output shows tenant ID, application ID, client secret in clear text, and expiry. "Solution Checker requires a role with prvAppendmsdyn_analysisjob privilege to append to the msdyn_analysisjob table. The System Administrator role has this privilege by default." [Build Tools service principal](https://learn.microsoft.com/power-platform/alm/devops-build-tools#configure-service-connections-using-a-service-principal); [pac admin reference](https://learn.microsoft.com/power-platform/developer/cli/reference/admin)
- Classic GitHub Actions tutorial API permissions for the app: Dynamics CRM `user_impersonation` (delegated), PowerApps Runtime Service `user_impersonation`, and PowerApps-Advisor `Analysis.All` (for solution checker). Application user is created in admin centre > Environment > Settings > Users + permissions > Application users > New app user, with a business unit and security role. [GitHub Actions get started tutorial](https://learn.microsoft.com/power-platform/alm/tutorials/github-actions-start)
- Power Platform API `addAppUser` (preview): `POST https://api.bap.microsoft.com/providers/Microsoft.BusinessAppPlatform/scopes/admin/environments/{environmentIdGuid}/addAppUser?api-version=2020-10-01` with body `{"servicePrincipalAppId": "<clientId>"}`. Caller must be a Power Platform admin or a Power Platform service principal application. "This always adds the application user as a System Administrator." [Create a Dataverse application user](https://learn.microsoft.com/power-platform/admin/create-dataverseapplicationuser)
- Tenant management app registration: "A service principal can't register itself. By design, an administrator using username and password context must register the application." API: `PUT https://api.bap.microsoft.com/providers/Microsoft.BusinessAppPlatform/adminApplications/{CLIENT_ID}?api-version=2020-10-01`; PowerShell `New-PowerAppManagementApp -ApplicationId $appId`; pac `pac admin application register`. [Create SP via API](https://learn.microsoft.com/power-platform/admin/powerplatform-api-create-service-principal); [Create SP via PowerShell](https://learn.microsoft.com/power-platform/admin/powershell-create-service-principal); [pac admin reference](https://learn.microsoft.com/power-platform/developer/cli/reference/admin)
- Limits of management SPs: "service principal authentication works for environment management, tenant settings, and Power Apps management. APIs related to Flow are supported ... in situations where a license isn't required, as it isn't possible to assign licenses to service principal identities". "Service principal applications are treated within Power Platform like how normal users are with the Power Platform Administrator role assigned. Granular roles and permissions can't be assigned to limit their capabilities." [Create SP via API](https://learn.microsoft.com/power-platform/admin/powerplatform-api-create-service-principal)
- Service-principal-owned flows: an application user "can have connections shared with them and own resources such as flows". For non-solution flows, connections must be shared with the SP; for solution flows that is not required. "You can't make a service principal application user a co-owner of a flow." Premium SP-owned flows need a Process or Per-flow licence, a flow group with a Process licence, or a designated licensed user (who must be a co-owner and hold, for example, Power Automate Premium; a Microsoft 365 seeded licence is not enough). Unlicensed premium SP flows can be suspended: "This flow was suspended because flows owned by service principals are not compliant." [Service principal owned flows](https://learn.microsoft.com/power-automate/service-principal-support); [Assign a user licence to SP flow](https://learn.microsoft.com/power-automate/assign-user-license-service-principal-flow); [Change flow owner](https://learn.microsoft.com/power-automate/change-cloud-flow-owner)
- Pipelines delegated deployment as service principal: the pipeline stage "deploys as the delegate (service principal or pipeline stage owner) instead of the requesting maker". Stage-owner delegation (a regular user) "can't deploy solutions containing connection references for OAuth connections". The SP approval flow needs "a Dataverse connection for the service principal. You need a client ID and secret." [Delegated deployments](https://learn.microsoft.com/en-us/power-platform/alm/delegated-deployments-setup)
- CoE guidance (older, still live): "Not all connectors yet support Service Principles." [CoE limitations](https://learn.microsoft.com/power-platform/guidance/coe/limitations) [note: page wording may be stale; Dataverse connector now does support SP connections per the pipelines page above]

### Inferences
- Least privilege for the execution SP in a Dev environment: in practice it needs System Administrator (or System Customizer plus extra privileges) because it creates tables, flows, apps and imports solutions with plug-ins. Restrict blast radius by scope, not role: add the execution app user only to its own lane's Dev environment, never to UAT or Prod, and do not register it as a tenant management app.
- Verification SP: same Dev environment, a custom role with read on business data plus create/delete on test data tables; it should not have customisation privileges, so it cannot "fix" what it is checking.
- Review SP (read only): a custom role with organisation-level Read on solution, solutioncomponent, workflow, canvasapp and customisation tables. No Write, Create, Delete, or Customization privileges. Solution checker needs `prvAppendmsdyn_analysisjob`, so either run the checker under the verification identity or add that one privilege.
- Merge/deploy SP: the only identity added to UAT and Prod, as the pipelines delegated-deployment SP (Deployment Pipeline Administrator in the host, System Administrator in targets).
- Why per-run environment creation needs a human (reasons from the sources above): (1) the tenant management-app registration must be done once by an admin with username and password; (2) once registered, the SP is effectively a full Power Platform Administrator with no granular scoping, which is too much power for an overnight agent; (3) OAuth connections (Teams, Outlook, other Microsoft 365 connectors) need an interactive sign-in that an SP cannot do, so every new environment would need a human to create and bind connections; (4) developer environments cannot be created for or by SPs (see Q4). Hierarchy security exclusions are a one-time setting per environment; I did not find a doc that says an SP cannot set them, so treat this as a bootstrap convenience, not a hard block.

### Gaps
- No single Microsoft list of "connectors that support service principal auth" was fetched. The connector reference pages each state supported auth types; check Teams and Office 365 Outlook pages before the bootstrap design is final.
- Whether `hierarchysecurityconfiguration` changes are blocked for application users is not documented in the pages read.

## Q3a. Dataverse Git integration (native source control) status in 2026

### Takeaway
Native Git integration works with Azure DevOps and GitHub. GitHub support entered public preview on 31 August 2026 (release plan) and is still labelled preview on Learn on 1 Nov 2026. It requires Managed Environments for both dev and target environments, is for developer environments only, and is unmanaged-only. It uses a new file format that is not the same as `pac solution unpack` output, so the factory should pick one format per repo.

### Cited Findings
- "Use Git integration with developer environments, not in your test or production environments. Use builds to create solution artifacts and pipelines in Power Platform to deploy." Solution objects are no longer duplicated per solution in the new format; they are stored once and shared across solutions in the same folder. [Git integration overview](https://learn.microsoft.com/en-us/power-platform/alm/git-integration/overview)
- Release plan "GitHub support for source code integration in Power Platform": public preview Aug 31, 2026; GA blank. Includes "improved performance, reliability, and new public APIs to streamline automation". The release plan page says "As of October 2026, this content is archived and no longer maintained" and points to the roadmap at aka.ms/AIatWorkRoadmap. [2026 wave 1 release plan entry](https://learn.microsoft.com/power-platform/release-plan/2026wave1/power-platform-governance-administration/github-support-source-code-integration-power-platform)
- GitHub connection (preview) setup: create a GitHub App with Repository permissions > Contents = Read and write; generate a private key and store it in Azure Key Vault in the same Entra tenant; grant **Key Vault Crypto User** to the Dataverse managed identity named `PPMI-githubappconfigmanagedidentity-{GUID}`; needs System Administrator in Dataverse and GitHub org admin; preview makers sites (make.preview.powerapps.com). It can be connected by code via `ConnectToGit` / `DisconnectFromGit` Web API. [Connect to GitHub (preview)](https://learn.microsoft.com/power-platform/alm/git-integration/connecting-to-github); [Git API](https://learn.microsoft.com/power-platform/alm/git-integration/git-api)
- FAQ: requires Managed Environments ("Managed environments are required regardless of environment type"); all users must meet Managed Environment licence requirements; Azure DevOps users need Basic access; "Does Git integration support cross-tenant workloads? Not currently."; sovereign clouds supported; for Azure DevOps, consent is needed if the environment is in a different geography from the repo; "Dataverse API's can also be used to commit changes automatically." [Git integration FAQ](https://learn.microsoft.com/power-platform/alm/git-integration/faqs)
- Only unmanaged changes are tracked; "Objects that are part of the managed layer aren't included in the commit." Conflicts are resolved per object (keep existing or accept incoming). [Source control operations](https://learn.microsoft.com/power-platform/alm/git-integration/source-control-operations)

### Inferences
- For an agent factory on GHE.com, the native GitHub integration is a poor fit today: it is preview, it uses a GitHub App and Key Vault per tenant, and I found no statement that it supports GHE.com hosts (examples use github.com/settings/apps). Keep the classic `pac solution export` + `unpack` (or `pac solution clone`/`sync`) flow in GitHub Actions as the source of truth.
- If the partner later adopts native Git, use it only in Dev lanes, and keep build plus pipelines for UAT/Prod as Microsoft recommends.

### Gaps
- No statement found on GHE.com (data residency) support for the native GitHub integration. Treat as unsupported until Microsoft says otherwise.

## Q3b. Solution ALM: pac solution commands, managed vs unmanaged, connection references and environment variables, pipelines and Managed Environments

### Takeaway
The factory's command set is `pac solution export` (unmanaged from Dev) then `unpack` to Git, then `pack --packagetype Managed` (or export `--managed`) for a build artifact, then `import --settings-file` into UAT/Prod. Power Platform pipelines can carry the Dev to UAT to Prod promotion with human approval through three gated extensions and a service principal delegated deployment. Pipelines now enforce that every target is a Managed Environment: from October 2026, deployments to unmanaged targets get 30 days (plus one 30 day extension) and are then blocked.

### Cited Findings
- `pac solution export --name <n> --path <zip> [--managed] [--include general,autonumbering,...] [--async] [--max-async-wait-time 60] [--overwrite] [--environment]`. `--targetversion` is deprecated and ignored. [pac solution reference](https://learn.microsoft.com/en-us/power-platform/developer/cli/reference/solution)
- `pac solution unpack --zipfile <zip> --folder <dir> [--packagetype Unmanaged|Managed|Both] [--allowWrite] [--allowDelete] [--clobber] [--map] [--localize] [--errorlevel Info]`; default packagetype Unmanaged; default output is the XML format (`Other\Solution.xml`). `pac solution pack --zipfile <zip> --folder <dir> [--packagetype ...]` auto-detects format: a `solutions/` folder with `*solution.yml` means the YAML source control format (the native Git integration format), which needs **Microsoft.PowerApps.CLI 2.4.1 or later**. Warning: if a component is in `rootcomponents.yml` but its files are missing (for example a canvas `.msapp`), "the pack operation still succeeds but omits that component". Multi-solution repos need `SolutionPackager.exe /action:Pack ... /SolutionName:<n>`. [pac solution reference](https://learn.microsoft.com/en-us/power-platform/developer/cli/reference/solution)
- `pac solution clone --name <n> [--outputDirectory] [--packagetype Both (default)] [--include ...]` creates a `.cdsproj` project (build with `dotnet build`); use clone when adding new components (for example plug-ins via `pac solution add-reference`), export when only changing existing content. `pac solution sync` refreshes a cloned project from the environment. [pac solution reference](https://learn.microsoft.com/en-us/power-platform/developer/cli/reference/solution)
- `pac solution import --path <zip> [--settings-file <json>] [--activate-plugins] [--force-overwrite] [--publish-changes] [--stage-and-upgrade] [--import-as-holding] [--skip-lower-version] [--skip-dependency-check] [--async] [--max-async-wait-time 60]`. If `--path` is omitted it assumes a cdsproj folder, and uses managed when `SolutionPackageType` is `Both`. [pac solution reference](https://learn.microsoft.com/en-us/power-platform/developer/cli/reference/solution)
- Connection references and environment variables: `pac solution create-settings --solution-zip <zip> --settings-file <json>` (or `--solution-folder`) generates "the deployment settings for connection references and environment variables", consumed by `pac solution import --settings-file`. Also: `pac solution version --strategy None|GitTags|FileTracking|Solution` (`--buildversion`, `--revisionversion`; GitTags uses env var `PacCli.PAT`), `pac solution online-version`, `pac solution delete`, `pac solution upgrade`, `pac solution publish`, `pac solution add-solution-component --solutionUniqueName --component --componentType [--AddRequiredComponents]`. [pac solution reference](https://learn.microsoft.com/en-us/power-platform/developer/cli/reference/solution)
- Managed vs unmanaged: "solutions stored in source control come from unmanaged solutions in a maker's environment ... Managed solutions are built from source control and deployed into downstream environments, such as test or production, and aren't editable in those environments." [Git integration overview](https://learn.microsoft.com/en-us/power-platform/alm/git-integration/overview)
- Pipelines basics: deploy solutions plus "connections, connection references, and environment variables"; no Dataverse table data. Managed and unmanaged artifacts are exported and stored in the host on every deployment; the same managed artifact per version moves through stages in order and "prohibits any tampering", so "customization can't bypass QA". Default import behaviour is Upgrade without overwrite customisations; advanced behaviours (update vs upgrade) "Not currently" configurable. Cross-tenant deploys: "No. We recommend using Azure DevOps or GitHub". Rollback: redeploy previous versions if the setting is on. Service principal connections can be used "for connectors that support service principal authentication, including custom connectors". Connection references with no value in solution or target "can't be updated during deployment". [Pipelines overview](https://learn.microsoft.com/power-platform/alm/pipelines)
- Licensing for pipelines: host should be production but need not be managed; developer environments need not be managed; "All other environments used in pipelines must be enabled as managed environments"; premium licences required for all managed environments. Example: Host = Production (no standalone licence), Development = Developer (no), QA = Developer (no), Production = Production (yes). [Pipelines overview](https://learn.microsoft.com/power-platform/alm/pipelines)
- Managed Environment enforcement for pipelines: "Starting in October 2026, the admin deployment page notifies admins when pipelines deploy to an unmanaged target environment. Admins must approve enabling managed environments for the target within 30 days ... one additional 30-day extension for each environment. After the grace period or extension expires, the system blocks pipelines deployments". Automatic conversion: admin centre > Deployment > Settings per pipelines host. [Admin deployment page FAQ](https://learn.microsoft.com/power-platform/alm/admin-deployment-hub)
- Custom host: as few as three environments (four recommended); all need Dataverse; Power Platform admin or System Administrator to install the Deployment Pipeline package; configure in the "Deployment Pipeline Configuration" app (environment records with type Development or Target and environment ID, then pipelines and stages). One environment can be linked to only one host. [Custom host pipelines](https://learn.microsoft.com/power-platform/alm/custom-host-pipelines)
- Gated extensions: **Pre-export Step Required** (trigger `OnDeploymentRequested`, action `UpdatePreExportStepStatus`, first stage only); **Is Delegated Deployment** (trigger `OnApprovalStarted`, completes `OnDeploymentCompleted`, action `UpdateApprovalStatus` which must be called by the delegate SP's connection); **Pre-deployment Step Required** (trigger `OnPreDeploymentStarted`, action `UpdatePreDeploymentStepStatus`). Status codes: 10 pending (system), 20 complete, 30 reject. Fields: `ApprovalComments` (maker-visible), `PreExportProperties` / `ApprovalProperties` (admin only). Triggers come from Dataverse "When an action is performed", Catalog Microsoft Dataverse Common, Category Power Platform Pipelines; full list `OnDeploymentRequested`, `OnApprovalStarted`, `OnApprovalCompleted`, `OnPreDeploymentStarted`, `OnPreDeploymentCompleted`, `OnDeploymentStarted`, `OnDeploymentCompleted`. Filter with trigger conditions on `DeploymentPipelineName` / `DeploymentStageName`. "You can't extend personal pipelines created within Power Apps". Extensions are "gradually rolling out across regions". [Extend pipelines](https://learn.microsoft.com/en-us/power-platform/alm/extend-pipelines)
- Delegated deployment with SP: needs Entra Cloud Application Administrator or Application Administrator, and the configuring user must own the **Enterprise application** (not just the app registration). Add SP as S2S user in host (Deployment Pipeline Administrator) and each target (System Administrator; "Lower permission security roles can't deploy plug-ins and other code components"). "All delegated deployments are pending until approved." Deployed objects are owned by the deploying identity. Different SPs per pipeline and stage are allowed. Sharing during deployment supports security roles, canvas apps, cloud flows, only on first deployment, security groups only. [Delegated deployments](https://learn.microsoft.com/en-us/power-platform/alm/delegated-deployments-setup)
- CLI for pipelines: `pac pipeline list [--pipeline <name|id>] [--environment]` and `pac pipeline deploy --solutionName <n> --stageId <id> --currentVersion <v> --newVersion <v> [--environment] [--wait]`. [pac pipeline reference](https://learn.microsoft.com/power-platform/developer/cli/reference/pipeline)

### Inferences
- Two workable promotion designs. (A) GitHub Actions does everything: build managed zip from main, `pac solution check`, then GitHub environment protection rules (required reviewers) gate `pac solution import` into UAT and Prod, using the merge SP via OIDC. (B) GitHub Actions calls `pac pipeline deploy --wait` and Power Platform pipelines own the approval (delegated SP plus an `OnApprovalStarted` flow, or a human approving in the admin deployment page). Design A keeps one audit trail in GitHub; design B gives Power Platform-native artifact immutability and the admin deployment hub view.

- Because pipelines block unmanaged targets, UAT and Prod must be Managed Environments, which brings the Managed Environment licence rules (Q8).

### Gaps

## Q5. Limits: Dataverse service protection, Power Platform requests per 24 hours, and three lanes sharing one tenant

### Takeaway
Service protection limits are per user per web server, so a separate application user per lane gives each lane its own 6,000 requests / 1,200 s execution / 52 concurrent budget. Daily Power Platform request limits are different: all application users in a tenant share one non-licensed pool (25,000 per 24 hours base for Power Apps or Power Automate tenants), so splitting identities does not help there.

### Cited Findings
- Default service protection limits **per web server**, per user, over a 5 minute (300 second) sliding window: 6,000 requests; 20 minutes (1,200 seconds) combined execution time; 52 or more concurrent requests. "These limits can change and might vary between different environments." Trial environments get one web server; most environments have more than one, and the count depends partly on purchased user licences. [Dataverse service protection API limits](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/api-limits)
- Error codes: requests `-2147015902` / `0x80072322` "Number of requests exceeded the limit of 6000 over time window of 300 seconds."; execution time `-2147015903` / `0x80072321` "Combined execution time of incoming requests exceeded limit of 1,200,000 milliseconds over time window of 300 seconds"; concurrency `-2147015898` / `0x80072326` "Number of concurrent requests exceeded the limit of 52." [Dataverse service protection API limits](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/api-limits)
- Retry-After: Web API returns HTTP 429 with a `Retry-After` header in seconds; the SDK returns a TimeSpan in `OrganizationServiceFault.ErrorDetails["Retry-After"]`. Request count and execution time are evaluated so you can overshoot within the window before enforcement; concurrency errors are immediate. Continued heavy sending extends the duration. ServiceClient / CrmServiceClient (after 9.0.2.16, May 2019) retry automatically. PowerShell `Invoke-RestMethod -MaximumRetryCount` retries 429. Debug headers: `x-ms-ratelimit-burst-remaining-xrm-requests`, `x-ms-ratelimit-time-remaining-xrm-requests` ("Don't depend on these values"). [Dataverse service protection API limits](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/api-limits)
- "Batch operations, importing solutions, and highly complex queries can be very demanding." Batch max 1,000 operations; start with batch size 10. Plug-in and custom workflow activity calls do not count toward service protection request counts, but their compute time is added to the triggering request. "Are limits applied differently for application users? No." Dataverse search has a separate 1 request per second per user limit. [Dataverse service protection API limits](https://learn.microsoft.com/en-us/power-apps/developer/data-platform/api-limits)
- Daily licensed limits per 24 hours: 40,000 per paid Power Platform licence (Power Apps Premium, Power Automate Premium, most Dynamics 365); 6,000 for Power Apps per app, pay-as-you-go, Microsoft 365 seeded; 250,000 per Power Automate per flow (legacy) or Process licence. Multiple paid licences on one user add up. [Requests limits and allocations](https://learn.microsoft.com/en-us/power-platform/admin/api-request-limits-allocations)
- Non-licensed pool (application users, non-interactive users, administrative users, SYSTEM): pooled per tenant per 24 hours. Dynamics 365 Enterprise/Professional tenants get 500,000 base + 5,000 per USL up to 10,000,000; Power Apps tenants get 25,000 base with no accrual; Power Automate tenants get 25,000 base with no accrual. "Does each application user ... get their own tenant-level limit? No, they don't. All application users ... share tenant-level limits." [Requests limits and allocations](https://learn.microsoft.com/en-us/power-platform/admin/api-request-limits-allocations)
- A cloud flow owned by a service principal does not use the non-licensed pool if it has a Process or Per-flow licence, is in a flow group with a Process licence, or has a designated licensed user. Process licence = 250,000 requests per 24 hours per flow, stack up to 10 on one flow, flow must be in a solution; a flow group shares one Process licence across up to 25 solution-aware flows (no stacking). Per-flow plan is legacy, replaced by Process. Power Platform requests add-on = +50,000 per 24 hours, but "You can't currently assign Power Platform requests add-on packs to users or flows." [Requests limits and allocations](https://learn.microsoft.com/en-us/power-platform/admin/api-request-limits-allocations)
- Power Automate is still in a "transition period" (page accessed 1 Nov 2026): Premium and seeded limits apply per cloud flow, not per user (Premium 200k per flow per 24 hours, Process 500k per licence, Free/Office 365 10k per flow). The 5 minute limit is 100,000 requests regardless of licence. "Enforcement of the official limits won't start until at least six months after Power Automate usage reporting is generally available." Background (automated, scheduled) flows use the limits of the flow owner; instant flows use the invoker. [Requests limits and allocations](https://learn.microsoft.com/en-us/power-platform/admin/api-request-limits-allocations)
- Usage reporting: Licensing > Power Automate > Usage in the admin centre has superseded the downloadable request reports; the reports show Caller Type values System, Non-Interactive, Application. [Requests limits and allocations](https://learn.microsoft.com/en-us/power-platform/admin/api-request-limits-allocations)

### Inferences
- Recommendation: give each lane its own execution and verification application user (and separate review and merge apps). This splits the per-user service protection budget, so one lane's solution import (heavy on execution time) cannot 429 the other two lanes. It also makes audit attribution clean.
- Each lane is in its own Dev environment, and limits are per user per web server per environment, so cross-lane contention in Dev is low even with one shared SP. The real shared-SP risk is UAT and Prod, where all lanes' deployments land.
- Daily request limits: splitting identities gives no extra headroom because the non-licensed pool is per tenant. A Power Apps/Power Automate-only tenant has only 25,000 non-licensed requests per 24 hours across all SPs. Overnight agent runs that seed and delete test data through Dataverse could get near this. Enforcement is still soft (transition period), but plan to monitor it, and give service-principal-owned flows a Process licence or a designated licensed user in UAT/Prod.
- Retry policy for the agent harness: honour `Retry-After` seconds, cap concurrency per SP well below 52 (for example 8 to 16), and serialise solution imports per environment.

### Gaps
- Microsoft does not publish how many web servers a given environment has, so the real per-environment ceiling is unknown.
- Whether developer environments (single user, free) get one web server like trials is not documented in the pages read.

## Q8. Licensing and cost for three Dev lanes plus UAT and Prod

### Takeaway
Application users need no licence and cannot be given one. The costs come from (1) Managed Environments, which require every active user in UAT, Prod and any managed Dev lane to hold a premium licence (Power Apps Premium or Power Automate Premium), with stricter checks from February 2027; (2) Dataverse database capacity, since each sandbox or production environment needs at least 1 GB free to create, copy or restore; and (3) premium cloud flows owned by a service principal, which need a Process licence (or Per-flow, or a flow group, or a designated licensed user) or they can be suspended.

- Application users, non-interactive users, administrative users and SYSTEM are "non-licensed" identities and draw from the tenant non-licensed request pool; "it isn't possible to assign licenses to service principal identities". [Requests limits and allocations](https://learn.microsoft.com/en-us/power-platform/admin/api-request-limits-allocations); [Create SP via API](https://learn.microsoft.com/power-platform/admin/powerplatform-api-create-service-principal)
- Managed Environment entitlement comes with Power Apps Premium, Power Automate Premium, Copilot Studio, Power Pages, Dynamics 365 Premium/Enterprise/Team Members, Dynamics 365 Customer Insights, and pay-as-you-go meters (Power Apps per app, Power Pages, Copilot Studio). "When you activate managed environments in an environment, all active usage requires one of these standalone licenses or pay-as-you-go meters." Either Power Apps Premium or Power Automate Premium satisfies the requirement for a user who runs both apps and flows. The Developer Plan does not include Managed Environment use rights. [Managed Environment licensing](https://learn.microsoft.com/power-platform/admin/managed-environment-licensing)
- Stricter enforcement: "Starting February 2027, areas where the licensing requirement was applied leniently, including ... apps used in managed environments, use of model-driven apps, and use of custom apps used outside a Dynamics 365 environment context, require users to have an appropriate premium license. Users who don't have one can't open and use the app". [Power Apps licensing FAQ](https://learn.microsoft.com/power-platform/admin/powerapps-licensing-faq)
- Pipelines: host can be a non-managed production environment; developer environments need not be managed; every other pipeline environment must be managed; premium licences required for all managed environments. [Pipelines overview](https://learn.microsoft.com/power-platform/alm/pipelines)
- Dataverse capacity: the first Power Apps, Power Automate, Copilot Studio or Dynamics 365 subscription adds "a one-time default capacity limit of 10 GB for the tenant". Accrual per licence: Power Apps per user (Premium) +250 MB database, +2 GB file; Power Apps per app +50 MB database, +400 MB file; Power Automate per user +250 MB database, +2 GB file; per flow +50 MB database, +200 MB file; log +0. Extra capacity is bought in 1 GB increments. [Power Platform licensing FAQs](https://learn.microsoft.com/power-platform/admin/powerapps-flow-licensing-faq#dataverse); [Power Automate licensing FAQ](https://learn.microsoft.com/power-platform/admin/power-automate-licensing/faqs); [Storage overview](https://learn.microsoft.com/power-platform/admin/whats-new-storage) [conflict: the Power Automate FAQ example says 10 Premium licences give "10.5 GB (10 GB plus 10 times 50 MB)", which uses 50 MB per licence, while the capacity table says +250 MB per user; treat the table as authoritative and confirm in the admin centre]
- Capacity tables: AuditBase, PlugInTraceLogBase and elastic tables use **Log** capacity; attachments, annotations, file/image columns, WebResourceBase, RibbonClientMetadataBase use File; everything else uses Database. Database deficits cannot borrow from Log or File. [Dataverse capacity details](https://learn.microsoft.com/power-platform/admin/capacity-storage)
- Each new sandbox or production environment, copy, or restore needs at least 1 GB of available database capacity; over-capacity tenants are blocked from these operations. Developer environments do not count against tenant capacity. [Create environment](https://learn.microsoft.com/power-platform/admin/create-environment); [Back up and restore FAQ](https://learn.microsoft.com/power-platform/admin/backup-restore-environments#faq); [Environment strategy](https://learn.microsoft.com/power-platform/guidance/adoption/environment-strategy)
- SP-owned premium flows need a Process or Per-flow licence on the flow, a flow group with a Process licence, or a designated licensed user (co-owner with Power Automate Premium; Microsoft 365 seeded is not enough), otherwise "This flow was suspended because flows owned by service principals are not compliant." Non-premium SP flows or flows used only in Dynamics 365 context are exempt. "Process licenses are environment-specific"; user licences are tenant-wide. [Service principal owned flows](https://learn.microsoft.com/power-automate/service-principal-support); [Assign a user licence to SP flow](https://learn.microsoft.com/power-automate/assign-user-license-service-principal-flow); [Power Automate licensing FAQ](https://learn.microsoft.com/power-platform/admin/power-automate-licensing/faqs)
- Solution-flow connections: for solution flows, sharing connections with the SP owner "isn't required". [Service principal owned flows](https://learn.microsoft.com/power-automate/service-principal-support)

### Inferences
- Minimum licence shape (counts only, prices not researched): every human tester or approver who opens apps in UAT or Prod needs Power Apps Premium (or Power Automate Premium). Human reviewers who only look at GitHub need nothing. The pipelines host can be a plain production environment.
- Capacity plan for five environments (3 Dev sandboxes + UAT + Prod) plus a pipelines host: at least 6 GB of database capacity just for environment existence (1 GB minimum free each at creation, real use grows), against a 10 GB tenant default plus per-licence accrual. Turning on auditing in all lanes will consume Log capacity, which defaults low; budget Log add-ons or set short audit retention in Dev.
- Agent-built flows in Dev that use premium connectors will be owned by the execution SP. Make a licensed human developer the designated licensed user (co-owner) in each Dev lane rather than buying Process licences for throwaway flows. In Prod, give long-lived premium SP-owned flows a Process licence or a flow group.

- The 50 MB vs 250 MB per-licence accrual conflict above needs checking against the tenant's admin centre view.
