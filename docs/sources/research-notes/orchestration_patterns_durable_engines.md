## Key question 0: What is the difference between a multi-agent orchestration framework and a durable workflow engine, and what does each actually guarantee?

### Takeaway
A multi-agent orchestration framework (LangGraph, AgentKit, the OpenAI Agents SDK) decides *what the model-driven work does next*: roles, hand-offs, shared state, routing. A durable workflow engine (Temporal, Inngest, Restate, DBOS, Azure Durable Task, Step Functions) decides *what happens to a long-running process when the world fails*: it journals completed steps, detects dead workers, re-dispatches work, retries with policy, and can sleep for hours without compute. LangGraph's checkpointer preserves *state* so a run can be resumed, but nothing in LangGraph detects a crash or restarts the process; a durable engine does both.

### Cited Findings

LangGraph (the orchestration framework side)
- LangGraph's checkpointer "saves a snapshot of graph state at each super-step, organized into threads" and provides "fault-tolerance and error recovery: if one or more nodes fail at a given superstep, you can restart your graph from the last successful step." Pending writes from nodes that completed in the same super-step are stored so "you don't re-run the successful nodes." [LangGraph checkpointers doc, langchain-ai/docs src/oss/langgraph/checkpointers.mdx](https://docs.langchain.com/oss/python/langgraph/checkpointers)
- Three durability modes. `"exit"`: persists "only when graph execution exits ... intermediate state is not saved, so you cannot recover from system failures (like process crashes) mid-execution." `"async"`: "persists changes asynchronously while the next step executes ... there is a small risk that LangGraph does not write checkpoints if the process crashes during execution." `"sync"`: "persists changes synchronously before the next step starts ... high durability at the cost of some performance overhead." [LangGraph checkpointers doc, Durability modes](https://docs.langchain.com/oss/python/langgraph/checkpointers)
- Storage: "By default, LangGraph checkpoints write the full value of every state channel at each super-step. For long-running threads with large accumulations ... this can produce significant storage growth over time." `DeltaChannel` stores only deltas. [LangGraph checkpointers doc](https://docs.langchain.com/oss/python/langgraph/checkpointers)
- `MemorySaver` and `InMemorySaver` "store checkpoints in RAM. When the process restarts, all checkpoints are lost." Production: `PostgresSaver`; keep `thread_id` under 255 characters; prune old checkpoints with a cron job. [LangGraph persistence doc](https://docs.langchain.com/oss/python/langgraph/persistence)
- Resume granularity is the node: "LangGraph's persistence layer creates checkpoints at node boundaries. When a workflow resumes after an interruption or failure, it starts from the beginning of the node where execution stopped. Smaller nodes mean more frequent checkpoints, which means less work to repeat." [Thinking in LangGraph](https://docs.langchain.com/oss/python/langgraph/thinking-in-langgraph)
- LangGraph's durable-execution page (search summary of the official page) says that "to get the most from durable execution, your workflow should be deterministic and idempotent, with side effects or non-deterministic operations wrapped inside tasks", and that LangGraph with a checkpointer "already has durable execution enabled." [LangGraph durable execution doc](https://docs.langchain.com/oss/python/langgraph/durable-execution)
- What LangGraph does not do: Temporal's blog argues LangGraph "checkpoints preserve data but not execution. If the process dies, something else must detect the failure and restart the run", and that pausing for approval is left to the developer (search summary, vendor claim). [Temporal, LangGraph in production: Temporal's LangGraph plugin adds Durable Execution, July 2026](https://temporal.io/blog/temporal-langgraph-plugin-durable-execution)
- LangChain's own comparison page says Temporal "has no built-in concept of prompts or LLM state" and "leaves context management, such as tracking message history and retrieval, for teams to build themselves", while LangGraph "models an agent as a graph of nodes and edges and understands message history and human-in-the-loop steps out of the box"; it states "many teams run both" (search summary, vendor page). [LangChain, LangGraph vs Temporal](https://langchain.com/resources/langgraph-vs-temporal)
- Diagrid's FAQ notes that running LangGraph inside Temporal activities "doesn't make the agent's internal state natively durable" (search summary, competing vendor). [Diagrid FAQ](https://www.diagrid.io/faq/temporal-comparison/can-i-use-langgraph-agents-with-temporal-for-durable-execution)

- Temporal's Vercel AI SDK plugin: model and tool calls "execute as Activities so Temporal can record results, retry failures and replay". [Temporal Vercel AI SDK README](https://github.com/temporalio/ai-integrations/tree/main/typescript/vercel-ai-sdk); the January 2026 blog says the plugin "wraps each LLM call in a Temporal Activity automatically" and "if a worker crashes after the model picks a tool, execution resumes at that point" (search summary). [Temporal ai-integrations LangGraph README](https://github.com/temporalio/ai-integrations/tree/main/python/langgraph); [Temporal samples-python langgraph_plugin README](https://github.com/temporalio/samples-python/tree/main/langgraph_plugin); [Temporal LangGraph integration docs](https://docs.temporal.io/develop/python/integrations/langgraph)

Inngest (durable functions plus AgentKit)

"Always cap iterations ... a coding agent that reads, edits, and tests might need 15 to 20." [Inngest, Sub-agent delegation](https://www.inngest.com/docs/durable-execution/durable-agents/sub-agent-delegation)

- AgentKit: "Networks can be thought of as while loops with memory (State) that call Agents and Tools until the Router determines that there is no more work to be done." `maxIter` "is useful when using a Default Routing Agent or a Hybrid Router to avoid infinite loops. [AgentKit Networks](https://agentkit.inngest.com/concepts/networks). [AgentKit Routers](https://agentkit.inngest.com/concepts/routers)

DBOS
- "DBOS checkpoints those workflows and steps to a Postgres database. When failures occur ... DBOS uses those checkpoints to recover each of your workflows from the last completed step." "There's no separate orchestration server and no infrastructure required besides Postgres." Overhead: "one database write per step ... plus two additional database writes per workflow." Recovery: "In single-node deployments, this happens automatically at startup when DBOS scans for incomplete (PENDING) workflows. In a distributed deployment, some coordination is required, either automatically through services like DBOS Conductor or manually." [DBOS Architecture](https://docs.dbos.dev/architecture)
- Guarantees: "Steps are tried at least once but are never re-executed after they complete"; "Transactions commit exactly once"; "An assigned workflow ID acts as an idempotency key"; "If an exception is thrown from a workflow, the workflow terminates ... and does not recover the workflow. [DBOS Python workflow tutorial](https://docs.dbos.dev/python/tutorials/workflow-tutorial)
- Steps: `@DBOS.step(retries_allowed=True, max_attempts=10)`, `interval_seconds`, `backoff_rate`, optional `should_retry` predicate; "A step with timeout_seconds=30, max_attempts=3 therefore allows up to three 30-second attempts, not 30 seconds total." [DBOS step tutorial](https://docs.dbos.dev/python/tutorials/step-tutorial)
- Workflow timeouts "are start-to-completion ... timeouts are durable: they are stored in the database and persist across restarts, so workflows can have very long timeouts"; on expiry "the workflow and all its children are cancelled." [DBOS workflow tutorial](https://docs.dbos.dev/python/tutorials/workflow-tutorial)

### Inferences
- The clean mental model: the orchestration framework is the *program*; the durable engine is the *operating system* that keeps the program's progress on disk and reschedules it onto a healthy worker. LangGraph with `durability="sync"` and Postgres gives you a resumable program, not a self-healing one.
- Every durable engine converges on the same contract: a deterministic coordinator (workflow/orchestration/function body) plus non-deterministic leaves (activity/step/ctx.run) that are at-least-once and must be idempotent. The engines differ mainly in topology (Temporal and Restate: separate server; DBOS: library plus Postgres; Inngest: hosted event platform; Durable Task: Azure-managed scheduler; Step Functions: managed state machine) and in how long and how cheaply they can sleep.
- For an overnight coding run, "exactly-once" in any engine applies to recording a step's result, never to the step's external side effects (an LLM call, a `git push`, a PR comment). Design every side-effecting step with an idempotency key or a pre-check.

## Key question 1: For an overnight run, what should be a durable workflow step and what should be inside an agent's own loop?

### Takeaway
Make every unit whose loss would cost money or time a durable step: each model call, each tool call with side effects, each test or build run, each git operation, each approval wait. Keep inside the agent's own loop only the cheap, deterministic glue (parsing a response, deciding the next tool) and anything the framework already journals for you. Across Temporal, Inngest, DBOS, Restate and Durable Task the published reference loops are identical in shape: workflow holds the message list and iteration counter, each LLM call is an activity/step, each tool call is an activity/step, and the loop rolls over (continue-as-new) or exits at a max-iteration cap.

### Cited Findings
- Microsoft's reference agent loop: "Each iteration of the loop: 1. Sends the current conversation context to the LLM via an activity or stateful entity. 2. Receives the LLM's response, which may include tool calls. 3. Executes any tool calls as activities (distributed across available compute). 4. Optionally waits for human input using external events. 5. Continues the loop with updated state, or completes when the agent signals it's done." The code uses `maxIterations = 100` and `if (state.Iteration % 10 == 0) context.ContinueAsNew(state)` "to keep the history bounded." [Agentic application patterns, Microsoft Learn](https://learn.microsoft.com/azure/durable-task/sdks/durable-agents-patterns)
- Microsoft's choice table: deterministic workflows (your code controls the sequence; LLM works inside steps) for "known ahead of time" sequences, "explicit guardrails" and auditability; agent loops when "steps can't be predicted." The evaluator-optimizer sample caps at `max_iterations = 5` and returns "best effort after max iterations." [Agentic application patterns](https://learn.microsoft.com/azure/durable-task/sdks/durable-agents-patterns)
- Temporal: "Tools that perform I/O or other non-deterministic work should run as Temporal activities, while deterministic, workflow-safe tools can run directly in the workflow." Model activities take `ModelActivityParameters(start_to_close_timeout=timedelta(seconds=30))`. [Temporal OpenAI Agents README](https://github.com/temporalio/ai-integrations/tree/main/python/openai_agents)
- Temporal's LangGraph plugin forces the decision per node: `metadata={"execute_in": "activity", "start_to_close_timeout": timedelta(seconds=30), "retry_policy": RetryPolicy(maximum_attempts=3)}` versus `"execute_in": "workflow"` for deterministic nodes; it "cannot be set in default_activity_options." [Temporal ai-integrations LangGraph README](https://github.com/temporalio/ai-integrations/tree/main/python/langgraph)
- Temporal's continue-as-new sample for LangGraph: "Capturing node results with cache() before continuing" and "Restoring cached results with temporal_graph(name, cache=...) so completed nodes are skipped"; "Each node executes exactly once despite multiple workflow invocations." [Temporal samples-python, continue_as_new](https://github.com/temporalio/samples-python/tree/main/langgraph_plugin/graph_api/continue_as_new)
- Inngest: LLM call in `step.run("think")`, each tool in `step.run("tool-<name>-<idx>")`, `MAX_ITERATIONS` guard, token-budget guard, and message pruning ("keep the original user message and recent messages, and drop the middle") to stay within context. [Inngest, Agent tool loops](https://www.inngest.com/docs/durable-execution/durable-agents/agent-tool-loops)
- DBOS: "If you need to perform any non-deterministic operation like accessing the database, calling a third-party API, generating a random number, or getting the local time, you should do it in a step instead of directly in the workflow function." Steps "should be idempotent". Large outputs should go to blob storage with steps returning pointers, because checkpoint write size equals output size. [DBOS Architecture](https://docs.dbos.dev/architecture)
- DBOS Vercel AI integration: "completed model calls are replayed from their Postgres checkpoints without contacting the provider"; "Your own tools' side effects are durable when you wrap their execute in DBOS.runStep" (search summary). [DBOS Vercel AI integration](https://docs.dbos.dev/integrations/vercel-ai)
- LangGraph: because resume restarts the node, "Smaller nodes mean more frequent checkpoints ... If you combine multiple operations into one large node, a failure near the end means re-executing everything from the start of that node." [Thinking in LangGraph](https://docs.langchain.com/oss/python/langgraph/thinking-in-langgraph)
- LangGraph Functional API: `@task` and `@entrypoint` decorators; parallel tasks are launched by creating futures before awaiting; the orchestrator-worker pattern is "often used when subtasks cannot be predefined ... common with workflows that write code or need to update content across multiple files." [LangGraph workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)
- Ronacher's "The Coming Loop" (23 June 2026) separates the inner agent loop (the model calling tools and editing files) from the outer harness loop, where "work goes into a queue, a machine attempts it, and a harness determines whether to continue. If not, the harness continues the same session, injects another message, starts a fresh session with modified context, or sends the task to another machine" (search summary). [Armin Ronacher, The Coming Loop](https://lucumr.pocoo.org/2026/6/23/the-coming-loop/)
- Claude Code as the inner loop: `claude -p` exits 0 on success and non-zero on failure; `--output-format json` returns `total_cost_usd` and `session_id`; `--resume <session_id>` continues a specific conversation from any directory; `--bare` "is the recommended mode for scripted and SDK calls". A SIGTERM "exits with code 143 ... leaves the turn that was in progress unfinished"; set `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1` to continue it on resume. A `-p` run waits up to 10 minutes for background work by default (`CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS`). [Claude Code, Run Claude Code programmatically](https://code.claude.com/docs/en/headless)

### Inferences
- A practical split for a coding factory: the durable engine owns the task graph, one workflow per task (plan, implement, verify, integrate), with each "implement" step being a single bounded `claude -p` or Codex invocation run as an activity with a start-to-close timeout, heartbeats, and a retry policy. Inside that activity the agent's own tool loop runs un-journaled; the engine records only the invocation's result (branch, commit SHA, cost, exit status, session id). Re-running a crashed activity should resume the agent's own session via `--resume <session_id>` rather than starting from scratch, because the engine only guarantees the step boundary.
- Where the agent framework already journals its inner loop (Temporal's OpenAI/Vercel plugins, Inngest's step.run per LLM call, Restate), journal at the model-call level too; the cost is history growth, which is why every vendor's long-loop sample rolls over after N iterations.
- Verification (tests, lint, type checks) belongs to the durable layer as its own step so that a crash between "implement" and "verify" does not lose the implementation, and so a verifier can gate the merge independently of the implementing agent (see Gas Town's Refinery in Q3).

### Gaps
- No source gave empirical data on the right activity granularity for coding agents (one whole task per activity versus one model turn per activity); the recommendations above are inferred from the vendors' sample code.

## Key question 2: How do you make a run survive a container restart, a model outage, a rate limit, or a stuck agent?

### Takeaway
Container restart: only a durable engine (or an engine-backed LangGraph plugin) re-dispatches work; a plain LangGraph checkpointer needs an external supervisor to re-invoke the thread. Model outage and rate limit: classify 429/5xx as transient, honour Retry-After, use the engine's per-step retry policy with backoff, and keep a fallback model chain. Stuck agent: heartbeat timeouts plus a hard start-to-close timeout, an iteration cap, a token/dollar cap enforced by the harness (not the model), and a watchdog that kills and reassigns.

### Cited Findings

Restart and recovery
- DBOS: "if one of your workers crashes or fails, Conductor detects the failure and automatically recovers its workflows to a compatible live worker"; without Conductor, single-node recovery scans for PENDING workflows at startup. Operators can `cancel_workflow` (preempts "at the beginning of its next step"), `resume_workflow` ("resume workflows that are cancelled or that have exceeded their maximum recovery attempts"), and `fork_workflow` from a specific step, "useful for recovering from outages in downstream services (by forking from the step that failed after the outage is resolved)". [DBOS Architecture](https://docs.dbos.dev/architecture); [DBOS workflow management](https://docs.dbos.dev/python/tutorials/workflow-management)
- Temporal: "If the Worker crashes, the heartbeat timeout expires and Temporal retries the Activity on a new Worker. The new attempt retrieves the last heartbeat details and resumes from the checkpoint." [Temporal, Long-running Activity pattern](https://docs.temporal.io/design-patterns/long-running-activity)
- Restate research agent: "Kill the process mid-run and restart it: Restate replays the journal, so completed steps aren't repeated and the run resumes exactly where it left off, no lost work, no duplicate LLM spend." [gvdongen/resilient-research-agent README](https://github.com/gvdongen/resilient-research-agent)
- LangGraph: interrupts "wait indefinitely until you resume execution"; `thread_id` "is effectively your persistent cursor. Reusing it resumes the same checkpoint." [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts). A LangChain forum thread titled "Auto resuming challenges in langgraph" discusses the double-execution pitfall when auto-resuming (search summary). [LangChain forum](https://forum.langchain.com/t/auto-resuming-challenges-in-langgraph/1657)
- LangGraph Server (LangGraph Platform, renamed LangSmith Deployment in October 2025 per changelog) runs background runs: create a run with `client.runs.create(thread_id, assistant_id, input=...)`, poll `runs.get` (status `pending` then `success`), `runs.join` to block, with `webhook` and `multitask_strategy` fields on the run. [LangSmith, Kick off background runs](https://docs.langchain.com/langsmith/background-run); the platform GA post describes "regular heartbeat signals", task queues, cron and webhooks (search summary). [LangGraph Platform GA blog](https://blog.langchain.com/langgraph-platform-ga); [LangChain changelog rename](https://changelog.langchain.com/announcements/ann_aXX99kriWrGO9)
- Claude Code agent teams do not survive a restart: "No session resumption with in-process teammates: /resume and /rewind do not restore in-process teammates. After resuming a session, the lead may attempt to message teammates that no longer exist." Also "a teammate's background work can't outlive the lead's process." Teams require an interactive session; "In non-interactive mode with the -p flag, including Agent SDK sessions, Claude doesn't spawn teammates." ### Inferences
- Layer the kill switches: (1) per model call: activity/step timeout plus retry policy; (2) per agent invocation: `--max-turns`, `--max-budget-usd` (with headroom) and a heartbeat-backed activity timeout; (3) per task: a durable workflow timeout (DBOS `SetWorkflowTimeout` cancels children too; Temporal workflow run timeout); (4) per run: a global spend counter in workflow state or a gateway-enforced concurrency and spend scope (Restate scope, LiteLLM-style gateway, Claude workspace limits), with a pause signal the operator can send.
- Retries multiply spend. For an LLM-heavy activity, cap `maximum_attempts` low (2 or 3), make the retry resume the agent session rather than restart it, and treat `max_output_tokens`, `invalid_request` and auth errors as non-retryable (DBOS `should_retry`, Temporal non-retryable error types).
- Rate limits are a shared resource, so throttle at dispatch (DBOS queue limiter, Gas Town scheduler, Restate scope, Temporal task-queue worker slots) rather than letting N parallel agents each discover the 429 independently.

### Gaps
- No source quantified typical heartbeat intervals or start-to-close timeouts for coding-agent activities; values must be tuned per repo (a full test suite can legitimately take 20 to 40 minutes).
- No official Anthropic guidance exists on resuming a `claude -p` session from a different container after a crash (the docs say `--resume` finds sessions "in any project on this machine", which implies transcript storage must be on shared or persisted disk for cross-container resume).

## Key question 3: How are dependencies between tasks scheduled so independent work runs in parallel without indiscriminate parallelism?

### Takeaway
Every working system reviewed uses the same three ingredients: an explicit dependency graph with "ready" semantics (a task is claimable only when its blockers are closed), one branch or worktree per task so parallel agents never share a working tree, and a serial integration point (merge queue or lead) that verifies before merging. Parallelism is bounded by a concurrency limit at the scheduler, not by how many tasks happen to be ready.

### Cited Findings

Dependency graphs and ready-queues
- Claude Code agent teams: "Tasks can also depend on other tasks: a pending task with unresolved dependencies cannot be claimed until those dependencies are completed." "Task claiming uses file locking to prevent race conditions." "When a teammate completes a task that other tasks depend on, it unblocks the dependent tasks without any action from you." Self-claim: "after finishing a task, a teammate picks up the next unassigned, unblocked task on its own." [Claude Code agent teams](https://code.claude.com/docs/en/agent-teams)
- Beads (the issue graph under Gas Town): "a dependency-aware graph, allowing agents to handle long-horizon tasks without losing context"; `bd ready` lists "tasks with no open blockers", `bd update --claim` takes one, `bd close` releases blockers; `bd dep add <child> <parent>` links tasks "(blocks, related, parent-child)"; "Hash-based IDs (bd-a1b2) prevent merge collisions in multi-agent/multi-branch workflows." Storage is Dolt, "Version-controlled SQL database with cell-level merge". [steveyegge/beads README](https://github.com/steveyegge/beads)
- Gas Town: Convoys "Bundle multiple beads that get assigned to agents"; Molecules are "Workflow templates that coordinate multi-step work. - Copilot CLI `/fleet`: "an internal orchestrator breaks the work into pieces, then dispatches independent chunks to multiple subagents in parallel", with an explicit "Analyze dependencies" step; "the orchestrator builds a dependency graph, the more explicit you are, the more accurate it is" (search summaries, third-party blogs). [LangGraph workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents); [Temporal samples README](https://github.com/temporalio/samples-python/tree/main/langgraph_plugin)
- langgraph-supervisor: `create_supervisor` builds `transfer_to_<agent>` hand-off tools; by default the hand-off "passes full message history"; `output_mode="full_history"` or `"last_message"`; supervisors can manage supervisors ("research_supervisor", "writing_supervisor" under a "top_level_supervisor"). - Gas Town hooks are "Git worktree-based persistent storage for agent work. Survives crashes and restarts." [steveyegge/gastown README](https://github.com/steveyegge/gastown)

- Gas Town's Refinery: "Per-rig merge queue processor. - Augment Code's Intent "creates a branch and worktree per Space, with a Coordinator that manages merge sequencing after the Verifier validates output" (search summary). [Augment Code guide](https://augmentcode.com/guides/git-worktrees-parallel-ai-agent-execution)
- SwarmGit "gives each agent its own branch and workspace, then merges changes back into main automatically when agents finish"; the search summary flags its "zero conflicts" framing as marketing. [swarmgit on PyPI](https://pypi.org/project/swarmgit/)
- Copilot: Actions on agent PRs are gated: "draft PRs from the agent require approval by a user with write permission before Actions run" (search summary). [Microsoft Learn, Security, risks and limitations of Copilot coding agent](https://learn.microsoft.com/en-us/training/modules/github-copilot-code-agent/2-security-risks-limitations-copilot-code-agent)
- Cost of parallelism: "Agent teams add coordination overhead and use significantly more tokens than a single session"; "Token costs scale linearly"; "Three focused teammates often outperform five scattered ones." [Claude Code agent teams](https://code.claude.com/docs/en/agent-teams)

### Inferences
- The scheduler should be a durable queue whose dequeue predicate is "all blockers closed AND concurrency slot available AND budget remaining", not a planner that fans out everything the LLM lists. Beads' `bd ready` and the agent-teams task list implement exactly this predicate; DBOS partitioned queues or Temporal child workflows with a semaphore give the same thing inside a durable engine.
- Integration should be serialised through one merge-queue worker (Gas Town's Refinery is the clearest published design): rebase the task branch on current main, run the verification gate, merge, and on conflict hand the branch back to a (fresh) agent with the conflict as the task. A bisecting queue lets several green branches batch while isolating the one that breaks the build.
- Dependency edges should be derived from file ownership as well as logical order: two tasks that touch the same files should be serialised even if the planner marked them independent, since that is the dominant conflict source reported by every worktree guide.

### Gaps
- I found no published, quantified comparison of merge strategies (rebase-and-retest versus bisecting batch queue) for agent-generated branches.
- The official GitHub Docs concept page for the Copilot cloud agent could not be fetched (both direct and raw paths failed); its dependency handling across multiple assigned issues is undocumented in what I could read.
- The Codex parallel-orchestration write-up (codex.danielvaughan.com, 18 April 2026) and Superset's guide were unreachable; their details are from search summaries only.

## Key question 4: Where do human approval points sit, and how does the workflow wait for them without burning budget?

### Takeaway
Approval gates belong at the durable layer, between the "propose" step and the irreversible step (merge, deploy, delete, spend above a threshold), and every durable engine suspends the workflow without compute while waiting: Temporal signals, Inngest `step.waitForEvent`, Restate awakeables, DBOS `recv`/`get_event`, Durable Task external events, Step Functions task tokens. LangGraph's `interrupt()` is a state-level pause that also waits indefinitely, but the node re-runs from its top on resume, so side effects before the interrupt must be idempotent. For an overnight run, every gate also needs a timeout policy (auto-reject, escalate, or auto-approve low-risk) so the run does not stall until morning.

### Cited Findings
- LangGraph `interrupt()`: "When an interrupt is triggered, LangGraph saves the graph state using its persistence layer and waits indefinitely until you resume execution." Requirements: a checkpointer ("use a durable checkpointer in production") and a `thread_id`. "The node restarts from the beginning of the node where the interrupt was called when resumed, so any code before the interrupt runs again." Rules: "Side effects called before interrupt must be idempotent"; "Place side effects after interrupt calls"; "Do not reorder interrupt calls within a node" because matching "is strictly index-based"; "Avoid while True + interrupt() loops inside a single node" (exponential re-execution). Static breakpoints via `interrupt_before` / `interrupt_after` at compile time also need a checkpointer. Parallel branches that each interrupt are resumed by mapping "each interrupt ID to its resume value." [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts); [interrupt reference](https://reference.langchain.com/python/langgraph/types/interrupt)
- Temporal LangGraph samples: "Chatbot that uses interrupt() to pause for human approval, Temporal signals to receive feedback, and queries to expose the pending draft." [Temporal samples-python langgraph_plugin](https://github.com/temporalio/samples-python/tree/main/langgraph_plugin)
- Inngest: `step.waitForEvent("wait-for-approval", { event: "agent/approval.response", match: "data.approvalId", timeout: "24h" })`; "The function is suspended while waiting, so there's no compute cost while a human reviews." Three outcomes to handle: approved, rejected, timed out (`null`). Timeout strategies table: Auto-reject for "High-risk actions (delete, deploy, send to external)", Auto-approve for "Low-risk, time-sensitive actions", Escalate ("Notify a different reviewer, then waitForEvent again"), Retry notification. Gates inside a tool loop: `APPROVAL_REQUIRED_TOOLS = ["send_email", "delete_record", "run_sql", "deploy"]`, a unique `approvalId` per iteration and tool, and on rejection a tool message "Tool call rejected by human reviewer ... Choose a different approach." Chained gates (editorial 48h, legal 72h) each durable and independent. [Inngest, Human-in-the-loop](https://www.inngest.com/docs/ai-patterns/human-in-the-loop)
- Inngest gotcha: "waitForEvent only catches events sent after the step executes" (search summary). [Inngest waitForEvent reference](https://www.inngest.com/docs/reference/functions/step-wait-for-event)
- Restate: "An awakeable is a promise that can be resolved externally via an API call by providing its ID"; "You can also use awakeables outside of tools, for example, to implement human approval steps in between agent iterations" (search summary). The research agent "parks on the human approval gate" after planning and is resolved by `curl http://localhost:8080/restate/awakeables/<awk_id>/resolve --json '{"approved": true}'` or a Slack Approve button; a follow-up message can instead "steer" the live run or "cancel" it "and its whole fan-out of researchers". [Restate tour, AI agents](https://docs.restate.dev/tour/ai-agents); [gvdongen/resilient-research-agent](https://github.com/gvdongen/resilient-research-agent)
- DBOS: `DBOS.recv(topic, timeout_seconds=60)` "waits for and consumes the next message ... returning None if the wait times out"; `DBOS.send` from a workflow has "exactly-once delivery", from plain code use an `idempotency_key`; "All messages are persisted to the database, so if send completes successfully, the destination workflow is guaranteed to be able to recv it." `set_event`/`get_event` publish status to callers and are persisted so recovery sees the same value. [DBOS workflow communication](https://docs.dbos.dev/python/tutorials/workflow-communication)
- Durable Task: "Deterministic agent orchestrations can pause for human input, approval, or review without consuming compute resources. Durable execution enables orchestrations to wait for days or even weeks ... When combined with serverless hosting, all compute resources are spun down during the wait period." Code: `human_input = yield context.wait_for_external_event("HumanInput")`. The Agent Framework integration "auto-generates three HTTP endpoints for HITL interaction": run, status, respond. [Durable Extension, Microsoft Learn](https://learn.microsoft.com/agent-framework/hosting/durable-extension); [Agentic application patterns](https://learn.microsoft.com/azure/durable-task/sdks/durable-agents-patterns); [Durable Task extension for MAF](https://learn.microsoft.com/azure/durable-task/sdks/durable-agents-microsoft-agent-framework)
- Step Functions: three patterns for long agent waits, "Step Functions task-token callbacks, direct Step Functions integration, and Lambda durable functions", the last letting "code-based workflows wait for the agent's callback without continuously consuming compute" (search summary). [CloudThat article](https://www.cloudthat.com/resources/?p=79102)
- Claude Code gates for unattended runs: `--permission-prompts none` means "Anything that would prompt is denied unless a PermissionRequest hook allows it, Claude is told that nobody can approve the request and not to retry it, and the run continues"; denials appear as `permission_denied` in stream-json. `--permission-mode dontAsk` "denies every call that would otherwise prompt, which is useful for locked-down CI runs." In agent teams, "A teammate can't approve a permission prompt or supply consent on your behalf", and "Teammate permission prompts appear in the lead session." Plan-mode teammates send a plan approval request that Claude Code auto-approves unless the permission mode was changed. [Claude Code headless](https://code.claude.com/docs/en/headless); [Agent teams](https://code.claude.com/docs/en/agent-teams)
- Where gates sit in coding pipelines: LangGraph interrupts let a pipeline "pause before automatically submitting a pull request and let a human engineer validate the change" (search summary). [GetWidget, Claude agents with LangGraph](https://www.getwidget.dev/blog/claude-agents-langgraph/)
- Risk framing: unsupervised multi-hour sessions "risk shipping unrequested features or unexpected code changes to production without human review" (search summary). [Adaline Labs, Claude Code vs OpenAI Codex](https://labs.adaline.ai/p/claude-code-vs-openai-codex)

### Inferences
- For a 6 to 10 hour overnight run the practical design is: no synchronous human gate inside the implement loop; gates only at merge-to-main (or at "integration branch to main") and at any action outside the repo. Each gate gets a timeout equal to the remaining night plus a morning window, with the default outcome being "hold the branch and open a PR" rather than auto-approve, so the run keeps producing reviewable artefacts without blocking downstream independent tasks.
- Approval requests should carry a durable correlation id (Inngest `match`, Restate awakeable id, Temporal signal on a known workflow id, DBOS topic) and the UI (Slack button, PR comment, dashboard) should post to the engine, not to the agent; this keeps the agent process stateless between gates.
- With LangGraph alone, put `interrupt()` in a dedicated node with no prior side effects, and have an external poller or webhook call `Command(resume=...)`; with LangGraph under Temporal, keep `InMemorySaver` and let signals drive the resume.

### Gaps
- None of the sources quantified what fraction of overnight coding tasks end up blocked on approval; the timeout strategies are design guidance, not measured outcomes.

## Key question 5: What do practitioners recommend starting with (LangGraph alone, a durable engine alone, both), and when to move from one to the other?

### Takeaway
The pattern across vendors and practitioners: start with the simplest harness that gives you a bounded loop and verifiable stop conditions; add a durable engine as soon as runs exceed one process lifetime, must survive restarts, or need to wait hours for people. LangGraph alone is adequate for short-lived graphs where a restart is acceptable; a durable engine alone is adequate when your "agent" is a CLI like Claude Code or Codex that already owns its inner loop; both together (via Temporal's LangGraph plugin, Durable Task plus LangChain, Restate plus LangChain) is what the vendors now ship for long-running multi-agent graphs. Critics of bare loops (Ralph) and of harness loops (Ronacher) agree the weak point is not durability but code quality and human judgement about "done".

### Cited Findings
- Rule of thumb from the LangGraph versus Temporal comparisons (search summary, vendor-authored): "Use LangGraph alone for prototypes and short-lived agents where a simple restart is acceptable. Add a durable engine like Temporal when runs are long, must survive failures, or wait on human approvals across days. Many teams run both." The claim "if you use LangGraph, you should also use Temporal" is Temporal's own. [LangChain, LangGraph vs Temporal](https://langchain.com/resources/langgraph-vs-temporal); [Temporal LangGraph plugin blog](https://temporal.io/blog/temporal-langgraph-plugin-durable-execution)
- Under the Temporal plugin, "Temporal's workflow history becomes the single source of execution progress, so teams should avoid duplicating it with a separate database checkpointer" (search summary), consistent with the plugin README's "use InMemorySaver." [Temporal LangGraph plugin blog](https://temporal.io/blog/temporal-langgraph-plugin-durable-execution); [Temporal ai-integrations LangGraph README](https://github.com/temporalio/ai-integrations/tree/main/python/langgraph)

- Ralph (Huntley's loop) as implemented by Anthropic's plugin: "Ralph is a Bash loop", a Stop hook "feeds the SAME prompt back" each iteration; "Claude's previous work persists in files; Each iteration sees modified files and git history." Good for "Well-defined tasks with clear success criteria ... Greenfield projects where you can walk away ... Tasks with automatic verification (tests, linters)"; not good for "Tasks requiring human judgment or design decisions ... Tasks with unclear success criteria." Claimed results: "Successfully generated 6 repositories overnight in Y Combinator hackathon testing; One $50k contract completed for $297 in API costs." [anthropics/claude-code ralph-wiggum plugin README](https://github.com/anthropics/claude-code/tree/main/plugins/ralph-wiggum)
- Ralph critiques (search summaries of blogs): an agent told to "make the tests pass" with write access "may delete the tests instead" (reward hacking seen across frontier models); loops "burn tokens, drift toward defensive complexity, and still need a senior engineer to decide when the output is actually done"; API costs of "$20 to 200+ for complex projects"; Claude Code's native `/goal` "productized the wrong part". [itnext, Ralph loop is innovative, I wouldn't use it for anything that matters](https://itnext.io/ralph-loop-is-innovative-i-wouldnt-use-it-for-anything-that-matters-cd92f2f0df2e); [Shipyard, Ralph loops in Claude Code](https://shipyard.build/blog/claude-code-ralph-loop/); [howaiworks, The Ralph technique](https://howaiworks.ai/blog/geoffrey-huntley-ralph-agentic-coding-loop)
- Ronacher (23 June 2026) sees harness loops as useful for "code porting, performance exploration, and security scanning" but warns models "tend to produce code that is too defensive, too complex, too local in its reasoning. They avoid strong invariants", and says he has "not had much success with this way of working for code I deeply care about" (search summaries). [Armin Ronacher, The Coming Loop](https://lucumr.pocoo.org/2026/6/23/the-coming-loop/); [Developers Digest summary](https://www.developersdigest.tech/blog/armin-ronacher-coming-loop-agent-comprehension)
- Claude Agent SDK versus LangGraph (TrueFoundry, September 2026, search summary): the Agent SDK "runs a fixed loop that the model steers, while LangGraph has you author an explicit graph"; graphs "suit multi-stage pipelines with validation gates." [TrueFoundry, Claude Agent SDK vs LangGraph](https://www.truefoundry.com/blog/claude-agent-sdk-vs-langgraph)
- Qodo moved "from predefined coding flows to a more dynamic agent after newer Claude models arrived" and chose LangGraph (search summary). [Qodo blog](https://www.qodo.ai/?p=12616)
- Limits of terminal-based multi-agent sessions for unattended work: "lack of persistence, missing audit logs, unmanaged API secrets, and no bridge to CI/CD pipelines"; "A dedicated framework gives you persistence, determinism and cost control" (search summaries). [kestra.io, Claude Code agents](https://kestra.io/resources/ai/claude-code-agents); [kanbots, Claude Code team orchestration](https://kanbots.dev/learn/claude-code-team-orchestration)
- DBOS positioning: a library that "checkpoints into the Postgres you already run" versus Restate as "a separate service" (search summary). [toolradar, DBOS vs Restate](https://toolradar.com/compare/dbos-vs-restate)

### Inferences
- Decision rule for this project: if the inner workers are CLI agents (Claude Code or Codex) and the outer control flow is a task DAG with merge gates, a durable engine alone is the better first step; LangGraph adds value only if you need model-driven routing between specialised roles inside a task (planner, implementer, reviewer) with shared message state. Adopt LangGraph-under-Temporal (or Durable Task) only when both are true.
- Move from "LangGraph alone" to "LangGraph plus engine" at the first of: a run longer than one container lifetime, a human gate that may wait more than a few minutes, fan-out to more than a handful of parallel sub-agents, or a need to audit and replay what ran (both Temporal and DBOS treat history as the audit trail; Microsoft cites "Compliance or auditability requires reviewable control flow" as a reason to prefer deterministic orchestrations).
- Whatever the orchestration layer, the practitioners' critiques imply the factory's real quality gate is external and deterministic: tests the agent cannot edit, lint and type checks, size and complexity budgets, and a reviewer role separate from the implementer.

### Gaps
- I found no neutral, measured study comparing LangGraph-only, engine-only and hybrid stacks on overnight coding workloads; all guidance is vendor positioning or practitioner opinion.
- Huntley's original Ralph post and Ronacher's essay were both blocked; quotes are from secondary summaries and the Anthropic plugin README.

## Key question 6: Concrete reference architectures with diagrams or code

### Takeaway
Six architectures are documented well enough to copy from: Microsoft's orchestration-based agent loop (code in four languages), Temporal's OpenAI Agents and LangGraph plugins (worker and activity diagram, samples), Inngest's tool loop with approval gates (TypeScript), Restate's steerable deep-research agent (Virtual Objects plus LLM gateway with concurrency scope), Gas Town (Mayor, Polecats, Refinery, Witness over Beads and git worktrees), and Claude Code agent teams plus worktrees (shared task list with dependencies, file-locked claiming, hooks as quality gates). AWS's Step Functions outer loop is the managed-cloud equivalent.

### Inferences
- A composite reference design for a 6 to 10 hour run, assembled from the above: (1) a durable engine workflow per night-run holding the Beads-style task graph and a global budget; (2) a durable queue with concurrency 3 to 5 dispatching ready tasks to child workflows; (3) each child workflow: create worktree (activity), run bounded `claude -p` (activity with heartbeat, `--max-turns`, `--max-budget-usd`, resume-on-retry), verify (activity), request merge (signal to a single Refinery-style merge-queue workflow), handle conflict by re-dispatch; (4) approval gates only at merge and external actions, each with a timeout and a PR as the fallback artefact; (5) a watchdog that cancels a child on heartbeat loss or budget overrun and re-queues the bead; (6) morning report built from the engine's history.
- Gas Town is the most complete open-source instance of this shape but is Claude-Code-centric, tmux-dependent and operationally heavy; Restate's research agent is the cleanest small example of fan-out, approval, steer and cancel; Microsoft's samples are the best language-neutral code to copy for the inner loop.
