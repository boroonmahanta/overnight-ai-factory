# Runtime options and costs for unattended overnight coding-agent runs (as of 24 October 2026)

Scope note for the writer: all Claude Code, Agent SDK, Managed Agents and Anthropic pricing claims below come from official docs fetched on 24 Oct 2026 (code.claude.com, platform.claude.com, support.claude.com). The official docs.github.com and developers.openai.com hosts were unreachable through this session's proxy, so GitHub Copilot and OpenAI Codex claims rely on search-engine snippets of those official pages (URLs given) plus github.com-hosted READMEs; treat exact Copilot and Codex numbers as "official but second-hand". ## KQ1. Claude Code headless and non-interactive runtime: what the flags do and what stalls a run

### Takeaway
`claude -p` is the sanctioned unattended entry point. Since v2.1.302 a `-p` run with no permission mode starts in Manual mode and *denies* anything that would prompt, so the historic "permission prompt stalls the run" trap has become "silent denial unless you pre-approve". The documented unattended recipe is `--permission-mode auto` (classifier reviews actions) or `dontAsk` plus an exact `--allowedTools` allowlist, with `--permission-prompts none` (v2.1.259+) so nothing waits for a human, `--bare` for reproducibility, and `--max-turns` / `--max-budget-usd` as hard caps.

### Cited Findings
- `-p` / `--print` runs non-interactively; exit code 0 on success, non-zero on failure; `--output-format json` returns `result`, `session_id`, `total_cost_usd` and a per-model cost breakdown; `stream-json` emits newline-delimited events ending in a `result` message — [Claude Code: Run Claude Code programmatically](https://code.claude.com/docs/en/headless)
- "With Claude Code v2.1.302 or later, `claude -p` runs start in Manual mode when nothing sets a permission mode" and "a call that needs approval is denied unless something approves it, such as a `PermissionRequest` hook or a `--permission-prompt-tool`" — [Headless docs](https://code.claude.com/docs/en/headless)
- `--permission-prompts none` (v2.1.259+): "Pass `--permission-prompts none` when nobody is available to answer permission prompts, for example in a scheduled job"; anything that would prompt is denied unless a `PermissionRequest` hook allows it, Claude is told not to retry, `AskUserQuestion` is removed, and denials appear as `permission_denied` system messages and in the result's `permission_denials` — [Headless docs](https://code.claude.com/docs/en/headless)
- Documented unattended example: `claude -p "Update the dependency pins and run the tests" --permission-mode auto --permission-prompts none` — [Headless docs](https://code.claude.com/docs/en/headless)
- `--bare`: skips auto-discovery of hooks, skills, commands, subagents, plugins, MCP servers, auto memory and CLAUDE.md; "recommended mode for scripted and SDK calls, and will become the default for `-p` in a future release"; bare mode never reads OAuth credentials, so you must set `ANTHROPIC_API_KEY` (it does not read `CLAUDE_CODE_OAUTH_TOKEN`); background tasks are disabled in bare mode — [Headless docs](https://code.claude.com/docs/en/headless)
- Without `--bare`, "a `-p` session runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json`, even in a folder you've never trusted" with no trust dialog — [Headless docs](https://code.claude.com/docs/en/headless)
- `--max-turns`: "Limit the number of agentic turns (print mode only). Exits with an error when the limit is reached. No limit by default." — [CLI reference](https://code.claude.com/docs/en/cli-reference)
- `--max-budget-usd`: when reached, "Claude Code stops the remaining background work instead of waiting"; the 1.1x data-residency multiplier also counts toward it — [Headless docs](https://code.claude.com/docs/en/headless); [Manage costs](https://code.claude.com/docs/en/costs)
- Background work at exit: a `-p` run stays open waiting for background commands, subagents, workflows and Monitor watches; default idle ceiling 10 minutes, tunable with `CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS` (0 = no cap) — [Headless docs](https://code.claude.com/docs/en/headless)
- SIGTERM exits with code 143, kills the Bash process tree, runs only `SessionEnd` hooks and records no result for the in-progress turn; set `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1` to continue the interrupted turn on resume; send SIGINT (or SDK `interrupt()`) first to end the turn cleanly — [Headless docs](https://code.claude.com/docs/en/headless)
- Resume: `--continue` (most recent conversation), `--resume <session_id>` or `--resume <path to .jsonl transcript>`; sessions are found by ID across projects on the machine; `--fork-session` creates a new ID on resume; `--session-id` sets a UUID up front; resumed runs report the conversation's whole cumulative cost — [Headless docs](https://code.claude.com/docs/en/headless); [CLI reference](https://code.claude.com/docs/en/cli-reference)
- `system/api_retry` events expose `attempt`, `max_retries`, `retry_delay_ms`, `error_status` and an `error` category (`rate_limit`, `overloaded`, `billing_error`, `authentication_failed`, etc.) for scripts to react to — [Headless docs](https://code.claude.com/docs/en/headless)
- Piped stdin is capped at 10 MB — [Headless docs](https://code.claude.com/docs/en/headless)
- Skills can be invoked in `-p` by putting `/skill-name` in the prompt; `/model`, `/effort`, `/config key=value` work as arguments — [Headless docs](https://code.claude.com/docs/en/headless)
- Long-lived subscription token for CI: `claude setup-token` mints a one-year OAuth token for `CLAUDE_CODE_OAUTH_TOKEN`; "requires a Pro, Max, Team, or Enterprise plan"; it cannot establish Remote Control or fetch claude.ai connectors — [Authentication](https://code.claude.com/docs/en/iam)
- Credential precedence in `-p`: `ANTHROPIC_API_KEY` is always used when present; cloud sessions always use subscription credentials and ignore `ANTHROPIC_API_KEY` — [Authentication](https://code.claude.com/docs/en/iam)
- Expiring login warning: "Renewing early matters most for sessions that run unattended. A background session... that outlives the login stops making progress once the credential expires" — [Authentication](https://code.claude.com/docs/en/iam)
- Permission modes table: `default` (Manual), `acceptEdits`, `plan`, `auto`, `dontAsk` (denies instead of asking), `bypassPermissions` (allow rules have no effect, deny rules still block) — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Auto mode: classifier (default model Claude Sonnet 5, overridable via `CLAUDE_CODE_AUTO_MODE_MODEL` v2.1.302+) reviews actions; blocked by default: `curl | bash`, force push, production deploys and migrations, `terraform destroy`, IAM grants, exfiltration; allowed by default: local file ops, installing deps from lockfiles, pushing to branches of the working repo except deploy-like names; broad allow rules such as `Bash(*)` are dropped on entering auto mode; "if the classifier blocks an action 3 times in a row or 20 times total, auto mode pauses and Claude Code resumes prompting" (not configurable); in a `-p` auto run with no prompt tool, a blocked action simply does not run and the session continues; auto is the built-in starting mode for interactive sessions from v2.1.283 — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Auto mode model requirements: Opus 4.6+, Sonnet 4.6+, Haiku 5.5 or Fable on the Anthropic API; Sonnet 5+, Opus 4.7+ on Bedrock, Vertex, Foundry — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- `bypassPermissions`: "Claude Code refuses bypass mode as root or under `sudo` on Linux and macOS, unless it detects a recognized sandbox"; admins can block it with `permissions.disableBypassPermissionsMode: "disable"`; "Cloud sessions ignore `bypassPermissions` and `dontAsk` from settings files"; `--restricted` (v2.1.248+) refuses bypass — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Doc recommendation: "Hard guarantees: use deny rules, not conversational boundaries. The classifier re-reads boundaries from the transcript, and context compaction can remove them." — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- Actions no mode auto-approves: explicit ask rules, connector tools set to `ask`, `AskUserQuestion`, MCP tools marked `requiresUserInteraction`, recognised `rm`/`rmdir` critical-path removals, reads outside working directories when `blockReadsOutsideWorkingDirectories` is on — [Permission modes](https://code.claude.com/docs/en/permission-modes)
- `--worktree` with `-p`: "Non-interactive runs with `-p` skip the trust check, so `claude -p --worktree` proceeds without it", but `-p` runs do not clean up their worktrees on exit — [Worktrees](https://code.claude.com/docs/en/worktrees)

### Inferences
- The stall mode has flipped: on current versions an unattended `-p` run will not hang on a prompt; it will quietly deny the action and the agent may "complete" with less done. Scripts should parse `permission_denials` in the JSON result and treat a non-empty list as a partial failure signal.
- A robust worker invocation today looks like: `claude --bare -p "<task>" --permission-mode auto --permission-prompts none --max-turns N --max-budget-usd X --output-format json --worktree <name> --mcp-config ... --append-system-prompt-file ...`, with `ANTHROPIC_API_KEY` set (bare mode cannot use subscription OAuth).
- Because `--bare` skips CLAUDE.md and project hooks, teams that rely on CLAUDE.md rules and hooks for policy must either drop `--bare` (and accept loading untrusted project config) or pass equivalent policy via `--settings` and `--append-system-prompt-file`.

### Gaps
- The CLI reference's exact one-line definition of `--max-budget-usd` was truncated in the fetched copy; its semantics are confirmed from the headless, costs and SDK agent-loop pages instead.
- No official statement found on a maximum wall-clock duration for a local `-p` session; the SDK hosting page states there is "No top-level session timeout" (see KQ4).

## KQ2. Running several Claude Code workers in parallel: worktrees, subagents, agent teams, agent view, dynamic workflows, projects, cloud sessions

### Takeaway
Anthropic documents five parallelism surfaces (subagents, agent view, agent teams, dynamic workflows, projects) plus worktrees and cross-session messaging as supporting tools. For unattended multi-worker overnight runs the realistic candidates are: (a) N independent `claude -p --worktree` processes driven by your own scheduler; (b) agent view background sessions (`claude --bg`) supervised by a local daemon with automatic worktree isolation and draft PRs; (c) cloud sessions or Projects on Anthropic infrastructure; (d) dynamic workflows for fan-out inside one session. Agent teams do not work in `-p`/SDK mode and are explicitly warned against for unattended use.

### Cited Findings
- Comparison table of the five approaches (subagents, agent view, agent teams, projects, dynamic workflows); "Running several sessions or subagents at once multiplies token usage" — [Run agents in parallel](https://code.claude.com/docs/en/agents)
- Worktrees: `claude --worktree <name>` (or `-w`) creates `.claude/worktrees/<name>/` on branch `worktree-<name>`; subagents can be isolated with `isolation: worktree` frontmatter; `.worktreeinclude` copies gitignored files such as `.env`; `worktree.baseRef` is `"fresh"` (default branch) or `"head"` — [Worktrees](https://code.claude.com/docs/en/worktrees)
- Worktree isolation enforcement: Claude Code blocks `Edit`/`Write`/`NotebookEdit` targeting the main checkout, blocks Bash whose cwd resolves to the main checkout, blocks git redirects (`git -C`, `GIT_DIR`, `cd` into main) and blocks commands whose shape it cannot verify; "None of them tracks which files a shell command writes, so a command that writes into the main checkout without running git there, such as `cp` or a shell redirect, isn't refused" — [Worktrees](https://code.claude.com/docs/en/worktrees)
- Worktree cleanup for `-p`: no exit prompt, worktrees not cleaned up, lock stays until a later sweep; a periodic sweep removes subagent and background-session worktrees older than `cleanupPeriodDays` only when they hold no uncommitted or unpushed work — [Worktrees](https://code.claude.com/docs/en/worktrees)
- Agent teams: experimental, enabled with `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`; "Spawning teammates also requires an interactive session. In non-interactive mode with the `-p` flag, including Agent SDK sessions, Claude doesn't spawn teammates"; "No session resumption with in-process teammates"; "Letting a team run unattended for too long increases the risk of wasted effort"; teammates inherit the lead's permission mode (and `--dangerously-skip-permissions`); teammates are not worktree-isolated so you must partition files; "Start with 3-5 teammates" — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- Agent team cost: "approximately 7x more tokens than standard sessions when teammates run in plan mode" — [Manage costs](https://code.claude.com/docs/en/costs)
- Hooks for teams: `TeammateIdle`, `TaskCreated`, `TaskCompleted` (exit 2 blocks or sends feedback) — [Agent teams](https://code.claude.com/docs/en/agent-teams)
- Agent view (research preview): `claude agents` dispatches and monitors background sessions; `claude --bg "prompt"` from the shell (`--name`, `--agent`, `--model`, `--resume <id> --bg`); a separate supervisor process keeps sessions running after the terminal closes; sessions survive sleep but "stop if the machine shuts down"; a finished session unattached for about an hour has its process stopped (pin with Ctrl+T); each dispatched session "moves into its own git worktree under `.claude/worktrees/`" before editing; on completion it commits, pushes, "may open a draft pull request, and never pushes to `main` or `master`, force-pushes, or merges"; scripting via `claude agents --json`, `claude attach`, `claude logs`, `claude stop`, `claude respawn`, `claude rm`, `claude daemon status`; `Notification` hook fires `agent_needs_input` / `agent_completed`; "running ten agents in parallel uses quota roughly ten times as fast as running one" — [Agent view](https://code.claude.com/docs/en/agent-view)
- `claude --bg` combined with `-p` is rejected — [Agent view version history v2.1.198](https://code.claude.com/docs/en/agent-view)
- `--dangerously-skip-permissions` on a `--bg` session "persists when the supervisor restarts the session" — [CLI reference](https://code.claude.com/docs/en/cli-reference)
- Dynamic workflows: a JavaScript script Claude writes that orchestrates "Dozens to hundreds of agents per run"; limits: up to 16 concurrent agents by default (`CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` 1 to 256, v2.1.269+), 4,096 items per `parallel()`/`pipeline()`, 1,000 agents per run; "Resumable in the same session"; "No mid-run user input"; available in `claude -p` and the SDK but the `ultracode` keyword does not trigger from a `-p` prompt or scheduled task prompt; in `-p`/SDK the Workflow tool goes through normal permission evaluation so add `Workflow` to allow rules or run in auto mode; `Large workflow` warning when more than 25 agents or projected tokens exceed 1.5 million; usage-limit pause/resume does NOT apply in `-p`, SDK, background or teammate sessions (affected agent fails instead) — [Dynamic workflows](https://code.claude.com/docs/en/workflows)
- `/batch` skill "has Claude split one large change into 5 to 30 worktree-isolated subagents" — [Run agents in parallel](https://code.claude.com/docs/en/agents)
- SDK subagent caps: `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` (default 3), `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` (default 20), `maxBudgetUsd`/`max_budget_usd` (no default) — [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents)
- Cloud sessions: "each `--cloud` command creates its own cloud session that runs independently"; "Rate limits: cloud sessions share rate limits with all other Claude and Claude Code usage within your account. Running multiple tasks in parallel consumes more rate limits proportionately"; "there's no separate charge for the cloud VM"; follow-ups can be queued from CI with `claude -p "msg" --cloud <session-id>`; `claude --teleport` pulls a cloud session to a terminal — [Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)
- Cloud VM resources: 4 vCPUs, 16 GB RAM, 30 GB disk; idle VM pauses "after a few minutes without activity" and can later be reclaimed; conversation history is restored on reopen but running shell commands, subagents and session-scoped scheduled tasks are not; setup scripts cached only when they finish in roughly five minutes; Bash default timeout 2 minutes, up to 10 minutes, raise with `BASH_DEFAULT_TIMEOUT_MS`/`BASH_MAX_TIMEOUT_MS` — [Cloud environments](https://code.claude.com/docs/en/cloud-environments); [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web)
- Projects (public beta, Pro and Max only, gradual rollout): one coordinator conversation starts cloud "threads" in parallel; "There's no fixed number; Claude starts as many as the work calls for... The enforced limit is 200 new threads per day across your projects"; new projects default to Opus at high effort for threads; threads run in auto mode; "A thread that reaches your plan's limit waits and continues on its own when the limit resets" (except threads started by a scheduled task); project instructions up to 16,000 characters; desktop notifications when a thread needs input or errors — [Projects](https://code.claude.com/docs/en/claude-projects)
- Cross-session messaging lets sessions on the same machine, other machines or the cloud exchange findings; a teammate or other session "can't approve a permission prompt or supply consent on your behalf" — [Agent teams](https://code.claude.com/docs/en/agent-teams); [Run agents in parallel](https://code.claude.com/docs/en/agents)

### Inferences
- For a fully headless overnight factory the lowest-friction local design is N `claude -p --worktree` processes under your own supervisor (systemd, a cron-started script, or an Agent SDK orchestrator), because agent view's draft-PR convenience is tied to interactive dispatch (`--bg` cannot be combined with `-p`) and agent teams are interactive-only.
- Agent view is attractive if a human will be around at the start (dispatch from a terminal then close it): it gives worktree isolation, commit/push/draft-PR and a supervisor for free, but the machine must stay awake and idle sessions are stopped after about an hour.
- Cloud sessions and Projects remove the "machine must stay on" problem and give PR creation and auto-fix, but all workers draw from one subscription's 5-hour and weekly limits, so 4 parallel cloud workers for 8 hours is likely to hit a Max plan limit and either wait (Projects) or fail (scheduled-task threads).

### Gaps
- No documented hard cap on the number of concurrent cloud sessions per account, only the shared rate-limit warning and the Projects "200 new threads per day" cap.
- No official per-session memory or CPU figures for local agent view sessions; the SDK hosting page's "1 GiB RAM, 5 GiB disk, 1 CPU per agent" starting point is the closest official sizing.

## KQ3. Starting on a schedule and getting a morning summary

### Takeaway
There are three official Anthropic schedulers: cloud scheduled tasks (formerly Routines; cron, API `/fire` endpoint, or GitHub events; Pro, Max, Team, Enterprise; run as cloud sessions in auto mode), the Claude Code GitHub Action on a `schedule:` cron (API key or subscription token; 6-hour job cap), and Managed Agents scheduled deployments (API-billed, cron with timezone, per-run budget). Morning summaries are not automatic anywhere; you get them by having the prompt post to Slack or a connector, open a PR, or by reading the run session, and by wiring the `Notification`/`Stop` hooks or the SDK result message to your own channel.

### Cited Findings
- Cloud scheduled tasks are "in research preview"; triggers: Schedule (recurring or one-off), API (HTTP POST with bearer token to the task's `/fire` endpoint), GitHub (`pull_request.*`, `release.*` with filters); available on Pro, Max, Team, Enterprise; created at claude.ai/code/routines or with `/schedule` (alias `/routines`); "Expressions that run more often than once per hour are rejected"; "if you schedule a run exactly on the hour, such as 9:00, it can start several minutes late" — [Automate work with scheduled tasks](https://code.claude.com/docs/en/routines)
- Scheduled tasks "run autonomously as full Claude Code cloud sessions"; each run starts "in auto mode unless auto mode is unavailable"; repeated classifier blocks produce a prompt that waits until someone answers it; Claude pushes to `claude/`-prefixed branches; each run opens as a full session you can review and create a PR from; "A green status in the run list means the session started and exited without an infrastructure error. It does not mean the work your prompt describes succeeded" — [Scheduled tasks](https://code.claude.com/docs/en/routines)
- Limits: scheduled runs 100 per hour per account; Run now, API fires and one-off re-arm 30 per hour per task; API fires 100 per hour per account; GitHub events have per-task and per-account hourly caps; runs "draw down subscription usage the same way interactive sessions do"; with usage credits on, runs continue on metered overage, otherwise "additional runs are rejected until your usage window resets"; if GitHub connection expires the task skips runs for up to 72 hours then turns off — [Scheduled tasks](https://code.claude.com/docs/en/routines)
- API fire endpoint: `POST https://api.anthropic.com/v1/claude_code/routines/<trig_id>/fire` with `anthropic-beta: experimental-cc-routine-2026-04-01`; body `{"text": ...}` is wrapped in `<routine-fire-payload>` and treated as untrusted unless the prompt opts in; "available to claude.ai users only and is not part of the Claude Platform API surface" — [Scheduled tasks](https://code.claude.com/docs/en/routines)
- Connectors (Slack, Linear, etc.) are all included by default in a scheduled task and should be pruned; example use cases include "posts a summary to Slack so the team starts the day with a groomed queue" — [Scheduled tasks](https://code.claude.com/docs/en/routines)
- `/schedule` requires a claude.ai subscription login (not an API key, profile or Bedrock) and is unavailable inside a cloud session — [Scheduled tasks](https://code.claude.com/docs/en/routines)
- Two other local schedulers exist: Desktop scheduled tasks (run only while the Desktop app is open) and session-scoped `/loop` (lives in one conversation; a `-p` run with a self-paced `/loop` keeps waiting for wakeups) — [Scheduled tasks](https://code.claude.com/docs/en/routines); [Headless docs](https://code.claude.com/docs/en/headless)
- GitHub Action on a schedule: with a `prompt` input the action runs in automation mode on any event including `schedule:`; the `Daily Report` example runs `cron: "0 9 * * *"` with `claude_args: --model claude-opus-5-5 --allowedTools "mcp__github__list_commits,mcp__github__list_issues"`; "GitHub runs scheduled workflows only from the default branch and, in public repositories, disables the schedule after 60 days without repository activity"; scheduled runs are attributed to the user who last changed the cron and must not be a bot unless listed in `allowed_bots` — [Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions)
- GitHub-hosted runner job limit: "Each job in a workflow can run for up to 6 hours of execution time. If a job reaches this limit, the job is terminated and fails"; self-hosted runners 5 days per job; workflow run 35 days; `timeout-minutes` max 360 — [GitHub Docs: Actions limits](https://docs.github.com/en/actions/reference/limits) (via search snippet)
- Managed Agents scheduled deployments: `schedule: {type: "cron", expression, timezone}` with minute granularity; jitter "up to 15 percent of the interval between runs, with a minimum of 5 seconds and a maximum of 9 minutes"; max 1,000 deployments per organisation; optional per-run `budget` copied onto each session; failed runs recorded as deployment runs with `error.type` (e.g. `session_rate_limited_error`); webhooks for deployment and run events; manual `run` endpoint — [Managed Agents: Scheduled deployments](https://platform.claude.com/docs/en/managed-agents/scheduled-deployments)
- Agent SDK result message: `ResultMessage` carries `subtype` (`success`, `error_max_turns`, `error_max_budget_usd`, `error_during_execution`, `error_max_structured_output_retries`), `total_cost_usd`, `usage`, `num_turns`, `session_id`, `stop_reason`; hooks `Stop`, `SubagentStop`, `SessionEnd` fire at completion — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Structured output for summaries: `--output-format json --json-schema '{...}'` returns `structured_output` validated against the schema (check for its presence; absent if Claude declined) — [Headless docs](https://code.claude.com/docs/en/headless)
- Agent view fires a terminal notification and the `Notification` hook with `agent_needs_input` or `agent_completed`; Projects send desktop notifications when a thread needs input or errors — [Agent view](https://code.claude.com/docs/en/agent-view); [Projects](https://code.claude.com/docs/en/claude-projects)
- Anthropic's long-running-agent harness guidance (26 Nov 2025): keep a progress file and a JSON feature list, commit as checkpoints, start each fresh session by reading git log and progress notes, run a basic end-to-end check first, leave code mergeable at session end — [Anthropic Engineering: Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- The `ralph-wiggum` plugin: `/ralph-loop "<prompt>" --max-iterations <n> --completion-promise "<text>"` uses a Stop hook to re-feed the same prompt until the promise string appears; "Always set `--max-iterations`" is "your primary safety mechanism"; `/cancel-ralph` stops it; README reports "one $50k contract was completed for $297 in API costs" — [anthropics/claude-code plugins/ralph-wiggum](https://github.com/anthropics/claude-code/tree/main/plugins/ralph-wiggum)

### Inferences
- A practical "kick off at 22:00, summary at 07:00" design: a cron (local, GitHub Actions, or a cloud scheduled task) launches the workers; each worker ends by writing a short status to a known file or PR description; a final scheduled task (or the last step of the launcher script) runs `claude -p` with `--json-schema` to aggregate statuses and post to Slack via a connector, or the launcher simply emails the JSON results.
- Cloud scheduled tasks are the only Anthropic scheduler that runs with zero local infrastructure and includes GitHub clone/push and connector delivery, but their hourly-minimum cadence and subscription-limit coupling make them better suited to a single "night shift" task than to a high-frequency job queue.
- Do not treat "green" run status as success anywhere; have the prompt emit an explicit machine-readable verdict.

### Gaps
- No official email or push notification on completion for cloud scheduled tasks was documented; summary delivery depends on connectors or the prompt's own actions.
- Managed Agents scheduled deployments have no documented GitHub-event trigger (cron and manual only).

## KQ4. Capping spend and time per task and per run

### Takeaway
Hard caps exist at three layers: per invocation (`--max-turns`, `--max-budget-usd` / SDK `maxTurns`, `maxBudgetUsd`, subagent depth and concurrency env vars, Managed Agents `budget.max_list_cost` in cents), per organisation on the API (tier monthly spend cap: Start $500, Build $1,000, Scale $200,000; self-set lower limit; workspace limits), and per subscription (5-hour and weekly windows with optional usage credits and a monthly spend limit). Wall-clock caps are weaker: there is no top-level SDK session timeout, so time limits come from your supervisor, the GitHub Actions 6-hour job cap, or Managed Agents idle semantics.

### Cited Findings
- SDK: `max_turns`/`maxTurns` counts tool-use turns, `max_budget_usd`/`maxBudgetUsd` stops when estimated spend reaches the cap; both default to no limit; "Setting a budget is a good default for production agents"; result subtypes `error_max_turns` and `error_max_budget_usd`; budget covers subagents and stops background subagents; spend "can therefore pass the cap by up to the cost of that one response, plus anything that subagents still running at that moment spend before they stop. Leave headroom" — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- `maxBudgetUsd` counts only the call's own spend; totals restored from a resumed session don't count; `/clear` starts the budget over — [Cost tracking](https://code.claude.com/docs/en/agent-sdk/cost-tracking)
- Cost figures are client-side estimates: "`total_cost_usd` and `costUSD` fields are client-side estimates, not authoritative billing data... ### Inferences
- The only true wall-clock caps are external: `timeout` in your supervisor (send SIGINT then SIGTERM), GitHub Actions `timeout-minutes` (max 360), or Managed Agents' pause-on-budget. Budget caps are the reliable in-band stop because they bound tokens regardless of elapsed time.
- Because `--max-budget-usd` is a client-side estimate at list price, set it 10-20% below your true ceiling and additionally set an API workspace spend limit as the backstop.

## KQ5. Keeping a worker from touching files outside its task

### Takeaway
Layer four controls: git worktrees for file-level separation with built-in enforcement against the main checkout; the Bash sandbox (bubblewrap on Linux, Seatbelt on macOS) for filesystem and network confinement of shell commands; permission deny rules and `PreToolUse` hooks with `onFailure: "block"` for path and command policy; and an OS-level container or VM boundary with a credential-injecting egress proxy for anything untrusted. Anthropic's own guidance: deny rules and hooks, not prompt text, are the hard guarantees.

### Cited Findings
- Worktree isolation checks (file edits, command cwd, git redirects, command shape) apply to the session and every subagent it spawns, including background sessions; `cp` and shell redirects into the main checkout are not caught by these checks — [Worktrees](https://code.claude.com/docs/en/worktrees)
- Sandbox: off by default; `"sandbox": {"enabled": true}`; writes allowed by default only to the working directory, a temp dir and `additionalDirectories`; reads allowed broadly by default (including `~/.ssh`, `~/.aws/credentials`) so use `filesystem.denyRead`, `credentials.files` and `permissions.blockReadsOutsideWorkingDirectories`; protected paths such as `.claude/settings*`, `.mcp.json`, `.bashrc`, `.git/hooks` stay write-denied; network goes through a local proxy with `network.allowedDomains` (empty by default); `autoAllowBashIfSandboxed` (default true) lets sandboxed Bash run without prompts; `allowUnsandboxedCommands: false` plus `failIfUnavailable: true` gives strict mode; scope is shell commands only (Read/Edit/Write, MCP servers, hooks run outside the sandbox) — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Sandbox limitations: proxy decides on client-supplied hostname and does not inspect TLS by default, so domain fronting is possible; allowing `github.com` broadly can permit exfiltration; Unix sockets such as `/var/run/docker.sock` grant host access; `enableWeakerNestedSandbox` for containers weakens isolation — [Sandboxing](https://code.claude.com/docs/en/sandboxing)
- Permission rules: `Edit(path)` rules govern Write and NotebookEdit too; `//path` anchors to the filesystem root, `/path` to the rule's source; `disallowed_tools=["Bash(rm *)"]` denies in every mode including bypass; bare-name deny removes the tool from context; `Agent(fork)` can be denied — [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- Hooks: `PreToolUse` exit code 2 blocks the call (exit 1 does not); JSON `hookSpecificOutput.permissionDecision` `allow`/`deny`/`ask`/`defer`; `onFailure: "block"` (v2.1.295+) makes a crashed or timed-out hook fail closed; `if` filters use permission rule syntax such as `"Edit(src/**)"`; a sample path-restriction script inspects `tool_input.file_path`; managed hooks (`allowManagedHooksOnly`) cannot be disabled by users — [Hooks](https://code.claude.com/docs/en/hooks)
- Hook caveat with worktrees: `${CLAUDE_PROJECT_DIR}` stays at the original project root; read the hook input's `cwd` for the worktree path — [Worktrees](https://code.claude.com/docs/en/worktrees)
- `PreToolUse` hook `allow` cannot approve a recognised critical-path `rm -rf ~`; hooks run before deny rules and "a hook deny applies even in `bypassPermissions` mode" — [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- Multi-tenant SDK isolation: `settingSources: []`, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, per-tenant `CLAUDE_CONFIG_DIR` and `cwd`, per-tenant egress rules — [Hosting the Agent SDK](https://code.claude.com/docs/en/agent-sdk/hosting)
- Secure deployment: isolation table (sandbox-runtime: good, very low overhead; Docker: setup dependent; gVisor: excellent, medium/high overhead, file I/O "10-200x slower" in heavy open/close patterns; Firecracker/QEMU VMs: excellent, high overhead); hardened `docker run` example with `--cap-drop ALL`, `--read-only`, `--network none`, a Unix-socket proxy, `--memory 2g`, `--pids-limit 100`, `--user 1000:1000`; credential proxy pattern via `ANTHROPIC_BASE_URL` or `HTTP_PROXY`; `@anthropic-ai/sandbox-runtime` npm package — [Securely deploying AI agents](https://code.claude.com/docs/en/agent-sdk/secure-deployment)
- Reference devcontainer: `init-firewall.sh` restricts egress (needs `NET_ADMIN`/`NET_RAW`), non-root `remoteUser` lets you run `--dangerously-skip-permissions`, but "dev containers do not prevent a malicious project from exfiltrating anything accessible inside the container, including the Claude Code credentials stored in `~/.claude`"; "Avoid mounting host secrets such as `~/.ssh`" — [Development containers](https://code.claude.com/docs/en/devcontainer)
- Cloud sessions: each runs in an isolated Anthropic-managed VM; git credentials and network secrets stay outside the sandbox and are attached by a proxy; the GitHub proxy "rejects branch deletions and pushes of anything other than a branch" but does not limit which branches (use branch protection) — [Cloud sessions](https://code.claude.com/docs/en/claude-code-on-the-web); [Cloud environments](https://code.claude.com/docs/en/cloud-environments)
- Agent view background sessions never push to `main`/`master`, never force-push or merge — [Agent view](https://code.claude.com/docs/en/agent-view)
- Copilot cloud agent: "A firewall is enabled by default to prevent data exfiltration"; blocked requests are reported in the PR body; firewall not compatible with self-hosted runners; CI workflows do not run on Copilot pushes until approved — [GitHub Docs: About Copilot cloud agent](https://docs.github.com/en/copilot/concepts/agents/coding-agent/about-coding-agent) (via snippet)
- Codex: cloud tasks run in isolated containers with internet off by default during the agent phase (setup phase has access; limited or unrestricted configurable, via HTTP/HTTPS proxy); CLI `--sandbox read-only|workspace-write`, `--ask-for-approval never` for CI, `--dangerously-bypass-approvals-and-sandbox` (`--yolo`) "only inside an isolated runner" — [OpenAI Codex docs: Cloud environments](https://developers.openai.com/codex/cloud/environments), [Non-interactive mode](https://developers.openai.com/codex/noninteractive), [Agent approvals and security](https://developers.openai.com/codex/agent-approvals-security) (via snippets)

### Inferences
- A defensible overnight stack on one Linux box: one worktree per worker + sandbox enabled with `allowedDomains` limited to api.anthropic.com, github.com and package registries + `denyRead` on home credential dirs + a `PreToolUse` hook with `onFailure: "block"` that rejects `Edit`/`Write` outside the worktree and any `git push` not on the worker's branch + GitHub branch protection on `main`. Running that inside a container per worker with `--network none` and a proxy socket is the next step up.
- Because hooks, MCP servers and Read/Edit run outside the Bash sandbox, the sandbox alone does not stop the agent reading secrets via the Read tool; pair it with `blockReadsOutsideWorkingDirectories` and Read deny rules.

### Gaps
- The sandbox docs were truncated at 100,000 characters; the final part of the limitations list was not read.
- No official documentation on Codex CLI's Linux sandbox mechanism was reachable (the repo's docs/sandbox.md only links to developers.openai.com/codex/security).

## KQ6. GitHub integration: what each platform gives you free versus what you build

### Takeaway
Claude Code gives you branch, commit and PR mechanics everywhere (Action, cloud sessions, agent view, scheduled tasks), CI-failure and review-comment reaction through cloud "Auto-fix", and PR review through Code Review (Team/Enterprise, usage-credit billed). Copilot's cloud agent is the most "turnkey": assign an issue and get a draft PR, with review-comment handling built in, but capped at 59 minutes per session and one PR per task. Codex returns a PR per cloud task and has a GitHub code-review integration. In every case, orchestration across many tasks, retries, merge-conflict handling and the morning digest are yours to build.

### Cited Findings
- Claude Code GitHub Action (`anthropics/claude-code-action@v1`): interactive mode responds to `@claude` in comments, reviews, issue bodies; automation mode runs a `prompt` on any event; outputs commits to a branch and "returns a link to the PR creation page. A human must create the PR" by default; inputs include `branch_prefix` (default `claude/`), `base_branch`, `assignee_trigger`, `label_trigger`, `allowed_bots`, `allowed_non_write_users` (flagged "RISKY"), `use_commit_signing`, `track_progress`, `use_sticky_comment`, `settings`, `claude_args`, `plugins`; `max_turns` and `model` inputs are deprecated in favour of `claude_args`; no timeout input (use workflow `timeout-minutes`) — [GitHub Actions](https://code.claude.com/docs/en/github-actions); [claude-code-action docs/usage.md](https://github.com/anthropics/claude-code-action/blob/main/docs/usage.md)

- Review workflow via plugin: `prompt: "/code-review:code-review --comment ..."` with `claude_args: '--allowedTools "mcp__github_inline_comment__create_inline_comment"'` posts inline review comments — [GitHub Actions](https://code.claude.com/docs/en/github-actions)

- Scheduled tasks and agent view: `claude/` branches, draft PRs, never push to main — [Scheduled tasks](https://code.claude.com/docs/en/routines); [Agent view](https://code.claude.com/docs/en/agent-view)
- Managed Agents GitHub: mount `github_repository` resources with `authorization_token` (fine-grained PAT, `repo` scope for private clone and PR creation), optional `checkout` branch or sha; declare the GitHub MCP server `https://api.githubcopilot.com/mcp/` for PR creation; repos cached for faster starts — [Managed Agents: Accessing GitHub](https://platform.claude.com/docs/en/managed-agents/github)
- Copilot cloud agent: assigned via issue assignment, agents panel, Copilot Chat, CLI or API; "It will open a draft pull request and work on the task in the background... once it has finished, it will add you as a reviewer"; works on a `copilot/` branch; "Copilot can only work on one branch at a time and can open one pull request per task"; cannot change multiple repositories in one run; "Each Copilot cloud agent session has a maximum execution time of 59 minutes. ### Inferences
- "Free" with Claude Code: branch/commit/PR plumbing, CI-failure and review reaction (Auto-fix), and review comments (Code Review or the Action's review plugin). "Build yourself": task queue and dispatch, per-task budget accounting, rebase on conflicts, deciding when to retry, and the digest.

## KQ7. Claude Agent SDK and Managed Agents for custom long-running loops

### Takeaway
The Agent SDK (TypeScript `@anthropic-ai/claude-agent-sdk`, Python `claude_agent_sdk`) embeds the full Claude Code loop as a subprocess you host, with `query()`/`ClaudeSDKClient`, permission modes, `canUseTool`, hooks, subagents, sessions with `resume`/`fork` and a `SessionStore` for durable transcripts. Managed Agents (beta, `managed-agents-2026-04-01` header) is the hosted alternative: Anthropic runs the loop, sessions persist server-side, sandboxes are Anthropic-managed or self-hosted (Cloudflare, Daytona, Modal, Vercel, GKE named as providers in press), with hard dollar budgets, cron deployments and webhooks. SDK apps must use API keys, not claude.ai logins.

### Cited Findings
- SDK positioning table: Agent SDK = "A library that runs the Claude Code binary... in a process you operate"; Managed Agents = "A hosted agent harness that runs the agent loop, with sessions in an Anthropic-managed cloud sandbox or a self-hosted sandbox" — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods" — [Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview)
- Subprocess model: "One agent session maps to one subprocess"; state on local disk (transcripts in `~/.claude/projects/` or `CLAUDE_CONFIG_DIR`); four session patterns: ephemeral container per task (`TASK_PROMPT` env, `maxTurns: 20` example), long-running (`streamInput()`, `startup()`, `prewarm()` in TS; `ClaudeSDKClient` in Python), hybrid (ephemeral containers hydrating from `SessionStore`), multi-agent container — [Hosting the Agent SDK](https://code.claude.com/docs/en/agent-sdk/hosting)
- Resources: "1 GiB RAM, 5 GiB disk, and 1 CPU per agent is a reasonable starting point"; `agents per host = (host RAM - overhead) / (per-session RAM ceiling)`; "A minimally provisioned container runs roughly $0.05 per hour, while a single long agent session can spend dollars in tokens" — [Hosting the Agent SDK](https://code.claude.com/docs/en/agent-sdk/hosting)
- `SessionStore` mirrors transcripts only (not CLAUDE.md or working-directory artefacts); mirror writes are best-effort with `mirror_error` system messages — [Hosting the Agent SDK](https://code.claude.com/docs/en/agent-sdk/hosting)
- Runtime deps: Python 3.10+ or Node 18+; SDKs bundle a native Claude Code binary pinned to the SDK version — [Hosting the Agent SDK](https://code.claude.com/docs/en/agent-sdk/hosting)
- Permission evaluation order: hooks, deny rules, ask rules, permission mode, allow rules, `canUseTool`; `permissionPrompts: 'none'` (TS) skips the callback; "`allowed_tools` does not constrain `bypassPermissions`"; TS requires `allowDangerouslySkipPermissions: true` for bypass; bypass refuses to start as root; subagents never inherit a `bypassPermissions` value set on their definition (v2.1.267+) — [SDK permissions](https://code.claude.com/docs/en/agent-sdk/permissions)
- Observability: OTEL via `CLAUDE_CODE_ENABLE_TELEMETRY=1`, `OTEL_*_EXPORTER=otlp`; prompt text excluded by default — [Hosting the Agent SDK](https://code.claude.com/docs/en/agent-sdk/hosting)
- Hosting cookbook with deployable Docker, Modal and Kubernetes code — [claude-cookbooks claude_agent_sdk/hosting](https://github.com/anthropics/claude-cookbooks/tree/main/claude_agent_sdk/hosting)
- Managed Agents: beta; concepts Agent, Environment (cloud or self-hosted sandbox), Session, Events; built-in bash, file ops, web search/fetch, MCP; "Long-running execution: Tasks that run for minutes or hours"; "Scheduled execution... through scheduled deployments"; "not currently eligible for Zero Data Retention or HIPAA"; MCP tunnels and "dreaming" are research preview — [Managed Agents overview](https://platform.claude.com/docs/en/managed-agents/overview)
- Managed Agents session API: create with `agent`, `environment_id`, optional `initial_events` (up to 50, starts in `running`), `budget`, `vault_ids`, `resources`; agent overrides per session (`agent_with_overrides` with `model`, `system`, `tools`, `mcp_servers`, `skills`); statuses `running`, `idle`, `rescheduled`, `terminated`; events via SSE or webhooks; `user.interrupt` to steer — [Managed Agents: Start a session](https://platform.claude.com/docs/en/managed-agents/sessions); [Reference](https://platform.claude.com/docs/en/managed-agents/reference)
- Managed Agents rate limits: 300 create requests/min and 1,200 read requests/min per organisation, plus organisation spend and tier limits — [Rate limits](https://platform.claude.com/docs/en/api/rate-limits)
- Managed Agents pricing: tokens at model list price plus $0.08 per session-hour; worked example of a 1-hour Opus 5.5 coding session with 50,000 input and 15,000 output tokens = $0.58, or $0.428 with 40,000 cached input tokens; Batch discount and partner-cloud pricing do not apply — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Self-hosted sandboxes for Managed Agents: Anthropic keeps the agent loop and queues each tool call for your cluster to pull, run and post back; public beta; partners named in press: Cloudflare, Daytona, Modal, Vercel, and Google Cloud via GKE Agent Sandbox — [The Decoder](https://the-decoder.com/anthropic-adds-self-hosted-sandboxes-and-mcp-tunnels-to-claude-managed-agents/); [Kubernetes Agent Sandbox docs](https://agent-sandbox.sigs.k8s.io/docs/use-cases/anthropic-managed-agents/) (press and community sources, not Anthropic docs)
- Dynamic workflows and multiagent orchestration also exist inside Managed Agents (`workflow_run.*` events, shared session budget across threads) — [Reference](https://platform.claude.com/docs/en/managed-agents/reference); [Session budgets](https://platform.claude.com/docs/en/managed-agents/budgets)

### Inferences
- If you want to avoid running any infrastructure overnight and still have hard per-task dollar caps, Managed Agents scheduled deployments with a per-run `budget` are the closest fit, at the cost of API billing (no subscription) and beta status.
- The SDK is the right layer when you need a custom queue, your own worktree-per-task logic, or to run on a Max subscription via the CLI (the SDK itself expects API keys for third-party products, but an internal tool run under your own `claude` login is a different situation the docs do not address directly).

### Gaps
- No official list of Managed Agents sandbox providers was found in Anthropic docs; only press and a Kubernetes SIG page name Cloudflare, Daytona, Modal, Vercel and GKE.
- Maximum Managed Agents session lifetime and idle-to-termination timing were not found on the sessions, reference or budgets pages.

## KQ8. Anthropic pricing, plan versus API, caching and rate limits relevant to overnight runs

### Takeaway
Current list prices (24 Oct 2026): Opus 5.5 $4 in / $20 out per MTok with cache reads at $0.20 (0.05x) and 5-minute cache writes at $5; Sonnet 5.5 $2 / $10 with cache reads $0.10 and writes $2.50; Haiku 5.5 $0.10 / $0.50 for prompts up to 100k tokens ($0.50 / $2.50 above); Batch API is 50% off but is irrelevant to interactive agent loops. ## KQ12. Synthesis: recommended setup today for 6-10 hours of several parallel Claude Code workers, and the traps

### Takeaway
Recommended (API-billed, local or single VM): a supervisor script or SDK orchestrator launches N workers, each `claude --bare -p` in its own `--worktree`, in `auto` (or `dontAsk` plus allowlist) with `--permission-prompts none`, `--max-turns`, `--max-budget-usd`, sandbox enabled with a domain allowlist, a fail-closed `PreToolUse` hook, Sonnet 5.5 by default (Opus 5.5 for hard tasks), a per-task progress file and git commits as checkpoints, structured JSON results, and a final aggregation step that posts the digest. Recommended (no infra, subscription): cloud scheduled tasks or Projects on Max 20x with usage credits on and a monthly spend limit, accepting shared rate limits. Traps: silent permission denials, context exhaustion and compaction losing instructions, cache misses on idle, subagent fan-out blowing budgets, orphaned worktrees and locks, expired OAuth logins, API 429s and spend-cap 429s with no retry-after, and "green" run status that does not mean success.

### Cited Findings
- Denial not stall: `-p` denies unapproved calls and `--permission-prompts none` prevents waiting; denials listed in `permission_denials` — [Headless docs](https://code.claude.com/docs/en/headless)
- Context: "Compaction replaces older messages with a summary, so specific instructions from early in the conversation may not be preserved. Persistent rules belong in CLAUDE.md"; `PreCompact` hook can archive transcripts; CLAUDE.md can hold compaction instructions — [Agent loop](https://code.claude.com/docs/en/agent-sdk/agent-loop)
- Anthropic's harness lessons: agents "often ran out of context mid-implementation", "a later agent saw existing progress and declared the project done", and marked features passing without end-to-end checks; fixes: feature-list JSON only the `passes` flag may change, progress file, git checkpoints, fresh context per session with a bearings routine — [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- Rate limits: API 429 with `retry-after` for rate limits; spend-cap 429 has no `retry-after` and retries fail until the month resets; acceleration limits penalise sharp traffic increases ("increase your traffic gradually") — [Rate limits](https://platform.claude.com/docs/en/api/rate-limits)
- Subscription limit behaviour: Projects threads wait and auto-continue; scheduled-task threads stop with a limit error; workflow usage-limit pause does not apply in `-p`, SDK or background sessions — [Projects](https://code.claude.com/docs/en/claude-projects); [Dynamic workflows](https://code.claude.com/docs/en/workflows)
- Orphans: `-p` worktrees are not cleaned up and stay locked until a later sweep; agent view stops idle unattached sessions after about an hour and marks sessions failed after shutdown; tmux teams can leave orphaned tmux sessions — [Worktrees](https://code.claude.com/docs/en/worktrees); [Agent view](https://code.claude.com/docs/en/agent-view); [Agent teams](https://code.claude.com/docs/en/agent-teams)
- Fan-out: "Large parallel-subagent fanouts can hit rate limits. Break work into smaller batches"; Opus 5 delegates more readily so set depth, concurrency and spend caps — [Hosting the Agent SDK](https://code.claude.com/docs/en/agent-sdk/hosting); [Subagents in the SDK](https://code.claude.com/docs/en/agent-sdk/subagents)
- Credentials: unattended sessions stop when a claude.ai login expires; `--bare` ignores `CLAUDE_CODE_OAUTH_TOKEN`; agent view background dispatch fails with `Could not resolve authentication method` if the supervisor lacks credentials — [Authentication](https://code.claude.com/docs/en/iam); [Headless docs](https://code.claude.com/docs/en/headless); [Agent view](https://code.claude.com/docs/en/agent-view)
- Model choice: "Sonnet handles most coding tasks well and costs less than Opus. Reserve Opus for complex architectural decisions"; "Use Sonnet for teammates" — [Manage costs](https://code.claude.com/docs/en/costs)
- MCP startup: `-p` waits up to `MCP_TIMEOUT` (30 s default) for servers; invalid `--mcp-config` entries are skipped and reported in `mcp_server_errors` so CI can fail fast — [Headless docs](https://code.claude.com/docs/en/headless)

- Prompt-injection surface: "an unattended headless instance is a meaningful attack surface" (vendor roundup) — [mindstudio Q1 2026 roundup](https://mindstudio.ai/blog/claude-code-q1-2026-update-roundup-2) (third party)

### Inferences
- Split the night into bounded tasks (1-2 hours each) rather than one 8-hour session: it matches Anthropic's harness advice, keeps each run under a `--max-budget-usd`, lets the supervisor restart from a fresh context with a progress file, and avoids compaction erasing constraints.
- Stagger worker start times by a minute or two and keep concurrency modest (4 workers plus their subagents) to avoid API acceleration limits.
- For a subscription-only team, run fewer workers (2-3) on Max 20x, enable usage credits with a monthly cap, and prefer Projects (which wait for resets) over scheduled-task threads (which fail at the limit).

## KQ13. Rough cost estimate: 4 workers for 8 hours on Opus 5.5 versus Sonnet 5.5 with caching

### Takeaway
Using published list prices and a modelled unattended loop (roughly 180 model requests per hour per worker, 100k-token cached context, 2k new input, 1k output per request), one worker-hour costs about $9 on Opus 5.5 and about $4.50 on Sonnet 5.5; 32 worker-hours comes to roughly $290 on Opus and $145 on Sonnet, with a plausible range of $150-600 (Opus) and $75-300 (Sonnet) depending on request rate, context size and subagent fan-out. These are inferences from list prices, not measurements; the only official per-hour datapoint is Managed Agents' worked example of a light 1-hour Opus 5.5 session at $0.58.

### Cited Findings
- List prices used: Opus 5.5 $4 input, $5 5-minute cache write, $0.20 cache read, $20 output per MTok; Sonnet 5.5 $2, $2.50, $0.10, $10; Haiku 5.5 $0.10, $0.125, $0.01, $0.50 (≤100k prompt) — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Managed Agents worked example: 1-hour Opus 5.5 session, 50,000 input and 15,000 output tokens = $0.58; with 40,000 cached input tokens = $0.428 including $0.08 runtime — [Pricing](https://platform.claude.com/docs/en/about-claude/pricing)
- Anthropic enterprise average $13 per developer per active day, 90% under $30 — [Manage costs](https://code.claude.com/docs/en/costs)
- Each request re-sends the full conversation at cache-read rate; compaction is itself a large request; subagents and teammates add their own requests; agent teams about 7x tokens — [Manage costs](https://code.claude.com/docs/en/costs)
- Thinking tokens are billed as output and cannot be disabled on Opus 5.5, Sonnet 5.5, Haiku 5.5; lower `effort` reduces them — [Manage costs](https://code.claude.com/docs/en/costs)
- Anecdotes: "$10 per hour on heavy use" and "$25 for a 3-hour session" (API, 2025 prices) — [HN 46765933](https://news.ycombinator.com/item?id=46765933) (via snippet); interactive estimate 100k-300k tokens per hour on Sonnet 4.6 at $0.90-$2.10 per hour before caching — [morphllm](https://www.morphllm.com/claude-code-api-cost) (third party)
- ralph-wiggum README: a large multi-week autonomous job reportedly cost $297 in API tokens — [ralph-wiggum plugin](https://github.com/anthropics/claude-code/tree/main/plugins/ralph-wiggum)

### Inferences
- Per worker-hour model (assumptions stated): 180 requests; each request reads about 100k cached tokens, writes about 2k new tokens to cache, emits about 1k output tokens (text, tool calls, thinking). Opus 5.5: 18M cache-read tokens × $0.20/M = $3.60; 0.36M cache-write tokens × $5/M = $1.80; 0.18M output × $20/M = $3.60; total about $9.00. Sonnet 5.5: $1.80 + $0.90 + $1.80 = about $4.50. Haiku 5.5 (if context stays under 100k): $0.18 + $0.045 + $0.09 = about $0.32.
- 4 workers × 8 hours = 32 worker-hours: Opus 5.5 about $290; Sonnet 5.5 about $145; Haiku 5.5 about $10. Mixed fleet (1 Opus lead, 3 Sonnet workers): about $180.
- Sensitivity: halving request rate (slower tool calls, more test runs) halves cost; a 200k average context doubles the cache-read term; a subagent fan-out of 5 concurrent helpers can multiply a worker's hourly cost by 3-5x while active; a cold cache every 5 minutes (API key, idle gaps) adds up to one full-context cache write per gap ($0.50 per 100k on Opus 5.5). Realistic band: Opus $150-600, Sonnet $75-300 for the night.
- Fixed-cost comparison: Max 20x at $200/month covers an unknown share of this before usage credits kick in at the same list rates, so for nightly 4-worker runs the API or usage-credit cost dominates the subscription fee within the first week.
- Managed Agents adds only 32 × $0.08 = $2.56 of runtime for the same night, so compute is negligible next to tokens; an SDK container at roughly $0.05 per hour is similar.

### Gaps
- No official or practitioner measurement of tokens per hour for unattended Opus 5.5 or Sonnet 5.5 Claude Code runs was found; the model above is an inference and should be calibrated with a one-hour pilot using `--output-format json` cost fields or the Console usage page.
- Anthropic does not publish Max plan token quotas, so the share of a night covered by a subscription cannot be computed.
